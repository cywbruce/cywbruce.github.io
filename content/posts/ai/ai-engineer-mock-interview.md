## 一面：基础与编码

### 1. Embedding 与相似度（初级）

**主问：** Embedding 是什么？向量检索为什么常用余弦相似度？

**参考答案：** Embedding 把文本映射成一个稠密向量，语义相近的文本，向量在空间里也靠得近。余弦相似度只看两个向量的方向、不受长度影响，适合比较语义。很多向量模型输出的向量已经归一化，这时余弦相似度和点积结果相同，用点积算得更快。注意：查询和文档要用同一个 Embedding 模型，换模型之后必须全量重建索引。

**追问：** 向量库为什么用 HNSW 这类近似检索，而不是暴力计算？（数据量大时暴力检索太慢；近似检索牺牲少量召回率换取数量级的速度提升，可以通过 ef 等参数调节）

---

### 2. 手写 RAG 主流程（中级）

**主问：** 用伪代码写出一个最小可用的 RAG：给定问题，返回带引用的答案。

**参考答案：** 步骤：① `chunks = retrieve(query, k=20)`，同时做向量和 BM25 检索，用 RRF 融合结果；② `top = rerank(query, chunks)[:5]`，相关性低于阈值的丢掉，如果一条都不剩，直接回答「资料里没有找到」；③ 拼装 Prompt：系统指令要求「只根据给定资料回答，并标注引用编号」，每段资料前加上 `[1] 来源` 这样的编号；④ 调用模型生成；⑤ 校验答案里的引用编号是否都真实存在，再把编号映射回原文链接。还要注意：资料长度要控制在 token 预算内；检索前先按用户权限过滤文档。

**追问：** 多轮对话里，用户问「那它的价格呢？」，检索前要做什么？（结合历史对话把问题改写成完整的独立问题）

**定级：** 代码有拒答分支和权限过滤 → 中级。

---

### 3. 手写 Agent 循环（中级）

**主问：** 写一个支持工具调用的 Agent 主循环，要求有安全上限。

**参考答案：** `for step in range(MAX_STEPS)`：调用模型，传入消息历史和工具列表 → 如果没有要调用的工具，返回最终答案 → 如果有，先校验参数是否符合 Schema；危险工具需要用户确认才执行；执行时设超时，异常要捕获后作为工具结果返回，而不是直接让程序崩掉 → 把工具结果追加到消息历史 → 进入下一轮。超过最大步数就停止，并告诉用户进展到了哪一步。每一步都记日志（工具名、参数、耗时、消耗的 token），方便排查和计费。

**追问：** 模型反复调用同一个工具陷入死循环，怎么检测？（对工具名加参数做哈希计数，连续重复就打断，并提示模型换个思路）

## 二面：项目与场景

### 4. 智能客服项目深挖（中高级）

**主问：** 你做的 AI 客服上线后，回答准确率是多少？怎么测出来的？效果不好的时候是怎么迭代的？

**参考答案：** 回答结构：先说清楚准确率的定义（比如人工按「正确 / 部分正确 / 错误」三档标注）和评测集来源（从线上真实问题抽样、按意图分层，至少几百条）。迭代时先分析错误的原因分布：检索没召回到、召回了但模型理解错、知识本身缺失、问题超出业务范围；再针对原因改进，例如优化切块、加入关键词检索、加 rerank、补充知识、加转人工的规则，每次改动都跑一遍回归。最后给出数据，比如准确率从 72% 提升到 89%，转人工率下降了 30%。

**追问：** LLM 当评审的打分和人工标注不一致，以哪个为准？（以人工为准，用人工结果来校准评审 Prompt）

**定级：** 能拿出错误归因和数据 → 中高级。

---

### 5. 结构化抽取（中级）

**主问：** 要从合同 PDF 里抽取金额、日期、甲乙方这些字段，怎么保证准确又稳定？

**参考答案：** 先解析文档：扫描件做 OCR，表格保持原有结构，按条款分块。抽取时用结构化输出或函数调用，强制按 JSON Schema 返回，每个字段都附上原文片段作为证据。后处理：Schema 校验，加业务规则（金额大小写是否一致、日期是否合法），校验失败就带着错误信息重试。每个字段给出置信度，低置信度的交给人工复核。上线前用标注好的样本按字段统计准确率。

**追问：** 长合同超过了上下文窗口怎么办？（先定位相关条款再抽取，或者分块抽取后合并去重）

---

### 6. 多 Agent 与工作流（中高级）

**主问：** 什么时候用多 Agent，什么时候用固定工作流？

**参考答案：** 流程固定、步骤可以预先定义的（比如抽取 → 校验 → 写库），用工作流（DAG 加 LLM 节点）：可控、好测、成本低。只有路径确实无法提前确定、需要模型自主规划时，才用 Agent。多 Agent（规划者、执行者、审查者分工）能提升复杂任务的质量，但代价是 token 成本成倍增加、延迟变长、更难调试。原则：先用最简单的方案，只有评测证明有提升时才增加复杂度。

**追问：** 多 Agent 之间怎么共享上下文，又不会让 token 爆炸？（共享状态只传结构化摘要，不传完整历史）

## 三面：架构与权衡

### 7. 企业 AI 平台（高级）

**主问：** 公司有十几个团队都想接入大模型，你来设计一个统一的 AI 网关或平台。

**参考答案：** 网关层：统一鉴权，按团队或项目设置配额和限流，多模型路由并能自动切换备用模型，统一计费，对 Prompt 和响应做审计日志并对敏感数据脱敏，内容安全过滤，缓存。平台能力：Prompt 版本管理、评测服务、RAG 组件（文档解析、向量库、带权限过滤的检索）、工具和 MCP 注册中心、可观测性（链路、成本、质量看板）。治理：数据分级，规定哪些数据可以发给外部模型；模型准入评估；明确 SLA。

**追问：** 某个模型厂商宕机了，怎么做到业务无感知？（多厂商路由、自动切换备用模型，同时对 Prompt 在不同模型上的效果做兼容评测）

**定级：** 能讲出数据合规和多模型容灾 → 高级。

---

### 8. 自建还是调 API（高级）

**主问：** 业务调用量很大，老板问：要不要自己部署开源模型来替代商用 API？你怎么分析？

**参考答案：** 从四个维度比较：① 质量：在自己的评测集上实测，看开源模型能不能达到要求；② 成本：按真实流量估算总成本，包括 GPU、利用率、运维人力，再和 API 账单对比。流量低或波动大时 API 更划算，流量大且稳定时自建才有优势；③ 合规：数据不能出域是自建的强理由；④ 能力：团队有没有推理优化和 GPU 运维的经验。常见的结论是混合方案：高频、简单、敏感的任务用自建小模型（可以微调），复杂任务调商用大模型。

**追问：** 怎么做到逐步迁移，并能随时回滚？（影子流量对比 → 灰度放量 → 按评测指标设置门禁）

---

### 9. AI 产品风险（中高级）

**主问：** AI 功能出过一次事故：模型给用户推荐了错误的退款政策。复盘时你会提出哪些改进？

**参考答案：** 先找根因：是知识过时（索引没同步）、检索到了错误的文档，还是模型自己编出来的？改进措施：政策类问题强制要求引用资料，资料版本要和发布系统联动更新；涉及资金和承诺的回答加上免责说明并转人工确认；把这个案例加入评测集，做回归门禁；加监控（敏感话题的回答抽检、用户投诉触发告警）；明确责任边界和对外话术。

**追问：** 怎么在不影响用户体验的前提下降低这类风险？（按风险分级，只对高风险意图启用严格模式）

## 复盘建议

- 一面的编码题一定要写出**拒答分支、步数上限、异常处理**，这正是区分能不能上生产的地方
- 二面和三面每题都要说明**怎么评测**：没有评测数据支撑的结论，说服力会大打折扣
- 多讲取舍：「先用最简单的方案，用评测证明有提升再加复杂度」
