## 一、大模型基础

### 1. Transformer 与注意力（初级）

**主问：** 简单讲讲 Transformer 的自注意力机制，为什么它比 RNN 更适合大模型？

**参考答案：** 自注意力：每个 token 生成 Q、K、V 三个向量，用 softmax(QKᵀ/√d)·V 计算出对其他所有 token 的加权和，多头注意力让模型能同时关注不同方面的关系。相比 RNN：所有位置可以并行计算，训练效率高；任意两个位置之间的距离都是 1，长距离依赖更容易学到。代价是注意力的计算量和序列长度成平方关系。现在主流的大模型基本都是只用解码器（Decoder-only）的结构，加上因果掩码，逐个 token 往后预测。

**追问：** 为什么要除以 √d？位置编码有什么用？RoPE 是什么？（不让点积过大导致 softmax 饱和；注意力本身不知道顺序；旋转位置编码，外推长度更友好）

**定级：** 能讲清 QKV 和复杂度 → 初级。

---

### 2. Token 与上下文窗口（初级）

**主问：** 什么是 token？上下文窗口长度对应用开发有什么影响？

**参考答案：** token 是模型处理文本的最小单位，由分词器（如 BPE）切分，中文一个字通常是 1～2 个 token，不同模型的分词器不一样。上下文窗口是一次请求里输入加输出能容纳的总 token 数。影响：① 成本和延迟基本跟 token 数成正比；② 内容太长会被截断，或者中间部分的信息容易被模型忽略（lost in the middle）；③ 所以要做历史压缩、检索召回、只放必要的上下文，而不是把所有东西都塞进去。

**追问：** 怎么在请求前估算 token 数？多轮对话越来越长怎么办？（用对应分词器计算；滑动窗口、摘要压缩、把长期记忆放到外部存储）

---

### 3. 采样参数（初级）

**主问：** temperature、top_p 分别控制什么？不同场景怎么设？

**参考答案：** temperature 调整概率分布的平滑程度：越低输出越确定，越高越发散。top_p 是核采样，只在累计概率达到 p 的候选 token 里抽样。经验做法：信息抽取、分类、写代码、要求固定格式输出时用低温度（0～0.3）；创意写作、头脑风暴可以调高。一般只调其中一个，不要两个同时大幅修改。还要记住：即使温度设为 0，输出也不保证完全一致。

**追问：** 为什么温度为 0 时，同一个问题的回答仍可能不同？（批处理和浮点计算的不确定性、后端负载均衡到不同实例等）

## 二、Prompt 与 RAG

### 4. Prompt 工程（初级～中级）

**主问：** 写一个生产环境可用的 Prompt，你会注意哪些点？

**参考答案：** 结构清晰：角色和任务、背景上下文、明确的约束（什么能做、什么不能做）、输出格式（比如 JSON Schema）、少量示例（few-shot）。把指令和用户输入用分隔符或标签隔开，防止用户内容被当成指令。复杂任务拆成多步，或者让模型先列出推理步骤。工程上：Prompt 要做版本管理，配一套评测集做回归，每次修改都要跑一遍才能上线，不能凭感觉改。

**追问：** 输出格式总是不稳定怎么办？（用结构化输出或函数调用约束格式、做 Schema 校验、失败后带着错误信息重试）

---

### 5. RAG 全链路（中级）

**主问：** 从零搭建一个企业知识库问答（RAG），完整链路是什么？每一步容易出什么问题？

**参考答案：** 离线：文档解析（PDF 表格、扫描件要做 OCR）→ 清洗 → 切块（按语义或标题结构切，块之间适当重叠）→ 向量化 → 写入向量库，同时保留元数据（来源、权限、更新时间）。在线：改写用户问题 → 混合检索（向量 + BM25 关键词）→ 重排序（rerank）→ 拼成 Prompt → 生成答案并标注引用来源。常见问题：切块太碎丢了上下文，太大又引入噪声；专有名词、编号这类内容向量检索搜不准，需要关键词检索补充；没有权限过滤，导致越权看到别人的文档；文档更新后索引没同步；召回内容不相关时模型仍然硬编答案。

**追问：** 怎么评估 RAG 的效果？（分开看检索指标：召回率、MRR；和生成指标：忠实度、答案相关性；建一套标注好的评测集）

**定级：** 能讲清检索和生成分开评估 → 中级。

---

### 6. 减少幻觉（中级）

**主问：** 业务方抱怨模型「一本正经地胡说」，你怎么系统性地降低幻觉？

**参考答案：** ① 让答案有依据：用 RAG 提供资料，要求只根据给定资料回答并标注出处，资料里没有就明确回答「不知道」；② 优化检索质量，相关性低于阈值时直接拒答；③ 低温度，结构化输出；④ 事后校验：检查引用是否真实存在，用规则或另一个模型做事实核查；⑤ 高风险场景（医疗、金融、法律）引入人工复核；⑥ 用评测集持续跟踪幻觉率。

**追问：** 怎么自动检测模型的回答没有依据？（逐句检查是否能在召回的资料里找到支撑，也就是忠实度评估）

## 三、Agent 与工程化

### 7. Function Calling 与 Agent（中级）

**主问：** Function Calling 是怎么工作的？一个 Agent 的基本循环是什么？

**参考答案：** 开发者把工具的名称、描述和参数 Schema 传给模型；模型判断需要调用时，输出要调用的工具名和参数（结构化数据）；由应用代码真正执行工具，再把结果作为新消息回传给模型，模型据此继续回答或继续调用。Agent 的循环就是：思考 → 选择工具并调用 → 观察结果 → 再思考，直到任务完成或达到步数上限。工程要点：工具描述要写清楚用途和边界；校验参数；工具要幂等；设置最大步数和超时；危险操作（删除、付款、发消息）必须先让用户确认。

**追问：** 工具数量很多时，模型总选错怎么办？（先按意图路由缩小工具范围、优化描述、给示例、减少单次暴露的工具数）

---

### 8. MCP（中级）

**主问：** MCP（Model Context Protocol）解决什么问题？和直接写 Function Calling 有什么区别？

**参考答案：** MCP 是一个开放协议，把「工具、资源、提示模板」统一用客户端-服务端的方式暴露出来。同一个 MCP Server（比如数据库、Git、内部系统）可以被不同的 AI 应用复用，不用每个应用都各写一遍对接代码。Function Calling 是模型层面的能力；MCP 是在它之上的集成标准，解决的是工具的发现、接入和复用问题。要注意的风险：第三方 Server 的权限要最小化；工具描述和返回内容可能夹带恶意指令（提示词注入）。

**追问：** 怎么防止通过工具返回内容进行的提示词注入？（把外部内容当数据不当指令、敏感操作人工确认、权限隔离）

---

### 9. LLM 应用评测（中高级）

**主问：** 你怎么评测一个 LLM 应用？上线后怎么持续监控质量？

**参考答案：** 离线：按真实场景建评测集，覆盖常见问题、边界情况和攻击样例；指标包括准确率、格式合规率、忠实度等；评分方式有规则断言、用强模型当评审（LLM-as-judge，要先用人工标注校准）、人工抽检。每次改 Prompt、换模型或改检索都要跑回归。线上：记录完整链路（输入、召回内容、输出、耗时、token 数），收集点赞点踩，抽样复评，监控成本和延迟，把差评样本加回评测集。

**追问：** LLM 当评审有哪些偏差？（偏好更长的回答、受答案顺序影响、偏好自己生成的内容）

---

### 10. 成本与延迟优化（中高级）

**主问：** 一个 AI 功能上线后成本太高、响应太慢，你有哪些优化手段？

**参考答案：** 成本：按任务难度路由，简单任务交给小模型，难的才用大模型；精简 Prompt 和上下文；利用提示词缓存（固定的前缀放在最前面）；对相同问题做结果缓存；离线任务走批处理接口。延迟：流式输出，让用户先看到内容；并行调用相互独立的步骤；限制最大输出长度；减少 Agent 的往返次数；需要时自部署推理（vLLM 等），配合量化。做任何优化都要用评测集确认质量没有下降。

**追问：** 什么情况下值得微调一个小模型来替代大模型？（任务固定、调用量大、有足够的高质量数据、对延迟或成本敏感）

## 四、训练、部署与安全

### 11. 微调 vs RAG（中级）

**主问：** 什么时候用微调，什么时候用 RAG？LoRA 的原理是什么？

**参考答案：** RAG 适合知识经常变化、需要标注出处的场景；微调适合固定输出风格和格式、领域专用的表达方式、把大模型能力迁移到小模型上（蒸馏）。微调不擅长给模型「灌」新知识，而且知识更新成本高。两者可以结合使用。LoRA：冻结原始权重，只训练插入的低秩矩阵 A·B（参数量远小于原模型），训练和存储成本低，同一个基座模型可以挂多个适配器。QLoRA 是把基座模型量化到 4bit 后再做 LoRA，进一步省显存。

**追问：** 微调数据要准备多少？质量和数量哪个更重要？（取决于任务；通常几百到几千条高质量样本就能见效，质量比数量更重要）

---

### 12. 推理部署（高级）

**主问：** 自部署一个开源大模型，要让它扛住高并发，你关注哪些技术点？

**参考答案：** 显存占用：模型权重加上 KV Cache（随并发数和上下文长度增长）。吞吐：连续批处理（continuous batching）、PagedAttention（vLLM）、前缀缓存、量化（INT8/INT4、AWQ/GPTQ）、张量并行。延迟指标：首 token 延迟（TTFT）和每个 token 的生成速度（TPOT）分开看。服务化：按 token 限流、请求排队和超时、多实例负载均衡、按显存利用率和队列长度做弹性扩缩容、监控 GPU 利用率。成本上还要和直接调用云端 API 做对比。

**追问：** 为什么并发一高，首 token 延迟就飙升？（预填充阶段计算密集，与解码阶段争抢资源；可以做预填充和解码分离、分块预填充）

**定级：** 能讲清 KV Cache 和批处理调度 → 高级。

---

### 13. AI 安全与合规（高级）

**主问：** 设计一个面向客户的 AI 助手，你会做哪些安全措施？

**参考答案：** 输入侧：检测提示词注入和越狱、对敏感信息（PII）脱敏、内容审核。输出侧：内容安全过滤、不泄露系统提示词、事实性和合规审查、标明 AI 生成。工具和数据：最小权限原则；按用户身份过滤可访问的数据（RAG 也要做权限控制）；高风险操作要人工确认；把外部内容当作数据处理，不当作指令执行。治理：完整的审计日志、红队测试、遵守数据保护和算法备案等合规要求。

**追问：** 用户上传的文档里藏了一句「忽略之前的指令」，怎么防？
