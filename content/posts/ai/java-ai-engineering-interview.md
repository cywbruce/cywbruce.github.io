## 一、全景串讲（开场必问）

### 1. 把概念串成一条链路（中级）

**主问：** 用一次电商客服请求（「我的订单为什么还没发货」），把 LLM、Embedding、向量库、RAG、Tool、MCP、Skills、Agent 串起来讲一遍。

**参考答案：** 可以按五层来讲：① 模型层：LLM 负责理解和生成，本质是预测下一个 token；② 上下文层：用 Embedding 把文本变成向量，用余弦相似度在向量库里召回资料；③ 能力层：RAG 补充业务知识（比如发货规则），Tool 去查订单系统；④ 编排层：Agent 识别意图，决定先查订单、再查规则，最后组织回答，Skills 提供这类任务的标准流程；⑤ 治理层：流式输出、按租户限流、超时降级、权限和审计。MCP 让存量的 Java 订单服务不用改业务代码就能暴露成工具。核心一句话：不是把所有知识塞给模型，而是由 Agent 决定查什么、调什么、怎么回答。

**追问：** 这五层里，哪几层是 Java 后端的主场？（能力层的工具接入、编排层、治理层）

**定级：** 能按层讲清职责和数据流向 → 中级；能讲出治理层的具体手段 → 中高级。

---

### 2. Java 做 AI 应用的优势（初级～中级）

**主问：** AI 应用为什么要招 Java 工程师，而不是只招算法？Java 相比 Python 强在哪？

**参考答案：** 模型层面 Python 生态更好，但大部分 AI 应用的工作量在工程层：接入现有业务系统、并发、可靠性、权限、可观测性。Java 的优势：企业核心系统（订单、支付、ERP）大多是 Java 写的，可以直接在现有服务上挂 MCP Server；虚拟线程能扛住大量阻塞 I/O 的并发；强类型便于对接结构化输出；微服务、熔断、监控体系成熟。可以把 LLM 当作一个又慢、又贵、偶尔出错的第三方服务来治理：超时、重试、熔断、降级、可观测性一样都不能少。

**追问：** Spring AI 和 LangChain4j 你用过哪个？各自适合什么场景？

## 二、向量与检索

### 3. 余弦相似度与归一化（初级～中级）

**主问：** 向量检索为什么用余弦相似度而不是欧氏距离？向量归一化后会发生什么？

**参考答案：** 文本向量的长度会受文本长短影响，而语义主要看方向，余弦只看方向。高维空间里欧氏距离还容易趋同，区分度变差。三个要能说出的数学关系：① L2 归一化之后，余弦相似度等于内积，检索时可以省掉开方和除法；② 归一化之后，余弦越大，L2 距离越小（‖a−b‖² = 2 − 2cosθ），三种度量的排序结果一致；③ 排序一致不代表阈值通用：如果用分数做绝对阈值过滤（比如低于 0.6 判定为无答案），度量方式和是否归一化必须统一，混用的话阈值会失效。

**追问：** 手写余弦函数要注意什么？（用 double 累加避免 float 精度损失；零向量直接返回 0，防止 NaN 污染排序；先校验维度是否一致）

**定级：** 能说出排序等价但阈值不通用 → 中级。

---

### 4. 向量库选型与 ANN（中级）

**主问：** 百万级向量为什么不能自己 for 循环逐个算？HNSW、IVF、PQ 怎么选？Java 项目怎么选向量库？

**参考答案：** 暴力计算的成本是 O(N×维度)，并发一上来 CPU 扛不住。ANN（近似最近邻）用少量召回率换取数量级的速度提升。HNSW 是分层小世界图，召回和延迟综合最好，是通用首选，代价是占内存。IVF 先聚类分桶，只搜最近的几个桶，适合千万级以上数据。PQ 是量化压缩，内存能降一个数量级，但精度有损失，需要重排补偿。验收标准用 recall@K，一般调到 95%～99%。选型：已有 ES 集群就用 ES 8 的 dense_vector，BM25 和向量检索一套系统搞定；已有 PostgreSQL 就用 pgvector，运维不增加；数据到千万甚至亿级、要求低延迟时用 Milvus 或 Qdrant。

**追问：** HNSW 的 efSearch 调大有什么影响？（召回率上升，延迟也上升）

---

### 5. 相似不等于相关（中级）

**主问：** 向量检索有哪些「看起来对、其实错」的坑？

**参考答案：** ① 相似不等于相关：「苹果公司 CEO」和「Tim Cook」在向量空间里可能离得很远，因为向量衡量的是表述是否相似，不是事实是否关联，需要混合检索、rerank 或知识图谱补充；② 编号、型号、制度号这类内容（比如 HR-2025-013）是向量检索的弱项，要靠 BM25 精确匹配兜底；③ 枢纽点（hubness）：有些向量和谁都很近，任何查询都会把它排在前面，可以用去重或 MMR 增加结果多样性；④ 同一份文档存了多份会刷高排名，入库时按内容指纹去重，召回后按文档 ID 聚合。

**追问：** MMR 是什么？（在相关性和结果多样性之间做权衡的重排方法）

## 三、RAG

### 6. 朴素 RAG 为什么不够（中级）

**主问：** 只做「切块 + 向量检索 + 拼 Prompt」的朴素 RAG，上线后会出哪些问题？生产级 RAG 应该长什么样？

**参考答案：** 常见问题：召回不准；精确的编号查不到；固定长度切块把一段完整的论述切断了；多跳问题（比如「X 公司 CEO 的母校排名」）答不出来；「这批文档的核心主题是什么」这类全局问题向量检索天然做不好；召回太多噪声干扰模型。生产级 RAG 的组成：高质量文档解析（OCR、版面还原）+ 混合检索（BM25 + 向量，用 RRF 融合）+ Cross-Encoder 重排 + 按问题复杂度动态决定检索深度（Agentic RAG）+ 全局类问题用 GraphRAG + 持续评测。关键认知：RAG 的瓶颈在检索不在生成，检索这一步错了，后面怎么优化都白搭。

**追问：** 上下文窗口已经很长了，还需要 RAG 吗？（需要：每次全量塞进去成本高、延迟高，长文本中间的信息容易被忽略，而且知识要按条更新、按权限过滤；RAG 负责精准查找，长上下文负责找到之后的细读推理）

**定级：** 能主动说出「瓶颈在检索」→ 中级。

---

### 7. RRF 与重排（中级）

**主问：** 混合检索为什么用 RRF 融合？已经有向量召回了，为什么还要 rerank？

**参考答案：** RRF 的打分公式是 score = Σ 1/(k + rank)，k 常取 60。它只用排名、不用原始分数，所以不需要把 BM25 和余弦这两种量纲完全不同的分数做归一化，比加权求和更稳定。rerank 的原因：向量召回用的是双塔模型，问题和文档分别独立编码，无法细致比较；Cross-Encoder 把问题和文档拼在一起计算相关性，更准但更慢，所以只对粗召回的 Top-50 做精排，最后取 Top-5～8 交给模型。

**追问：** 在 Java 里怎么让两路召回并行执行？（用虚拟线程配合 CompletableFuture 并行，再做 RRF 合并）

---

### 8. 切块与知识同步（中级）

**主问：** 切块策略怎么定？业务数据更新了，向量库还是旧数据，怎么办？

**参考答案：** 切块：按标题和段落结构切，每块大约 500～1000 token，相邻块重叠 10%～20%；用父子块：小的子块用于向量匹配，命中后把完整的父块送给模型；标题和元数据跟着块一起存，既能用来过滤，也能用于回答时标注出处。同步：用 Canal、Debezium 等 CDC 工具订阅 binlog 做增量同步，记录版本号做对比，定期全量对账，再提供一个强制刷新的接口。另外 Embedding 应该离线批量计算，并且支持幂等重放，不要放在用户请求的同步链路里。

**追问：** 换了 Embedding 模型要做什么？（全量重建索引；查询和入库必须用同一个模型、同样的维度）

---

### 9. 证明 RAG 有效（中高级）

**主问：** 怎么证明你的 RAG 效果变好了，而不是「感觉还行」？

**参考答案：** 建一套黄金评测集（100～500 条问答对），重点看三个指标：recall@K（该召回的资料有没有召回到）、忠实度（回答有没有编造）、答案相关性。每次调整切块、换模型或改阈值，都跑一遍回归，并接入 CI 作为发布门禁。可以使用 RAGAS、TruLens 这类工具。

**追问：** 评测集的数据从哪来？怎么防止它慢慢过时？

## 四、Tool、Skills 与 MCP

### 10. Tool Calling 的真相（初级）

**主问：** 大模型是自己去调用接口的吗？

**参考答案：** 不是。模型只是输出「要调用哪个工具、参数是什么」的结构化数据，真正执行的是我们自己的 Java 程序；执行完把结果交回给模型，模型再组织语言回答。这正是安全边界所在：鉴权、幂等、审计、灰度都在我们的代码里完成。工程技巧：工具描述就是写给模型看的接口文档，要写清楚用途、参数格式和是否只读；参数不合法时，不要直接抛异常，而是返回一段模型能看懂的错误说明，让它自己修正参数后重试。

**追问：** 模型传来的参数格式乱填，怎么形成闭环？（用 JSON Schema 强校验，把错误信息回传给模型，限制重试次数）

---

### 11. 工具集收敛（中级）

**主问：** 为什么不能把几十个 @Tool 一次性全部挂给模型？

**参考答案：** 三个原因：① token 成本暴涨，每次请求都要带上所有工具的描述，二十多个工具能让单次请求的 token 数增加好几倍；② 模型更容易选错，描述相似的工具多了，用户问订单状态，它可能去调退款接口；③ 工具列表本身就是权限边界，把权限交给提示词去控制是拦不住越权的。做法：用 ToolProvider 根据租户、角色和意图，在运行时动态下发 5～8 个相关工具；高危的写操作需要单独授权，默认不开放。

**追问：** 怎么判断用户意图该给哪些工具？（先用规则或小模型做意图路由）

---

### 12. Skills 与渐进式披露（中级）

**主问：** Skills 是什么？为什么不直接把操作手册写进 System Prompt？它和 MCP、Prompt 有什么区别？

**参考答案：** Skills 是把「某一类任务该怎么做」沉淀成文件（SKILL.md、脚本、参考资料），平时只加载一段简短摘要，需要时才加载全文，这叫渐进式披露。写进 System Prompt 的问题是：内容永远常驻，占用上下文预算，流程一多就撑爆，也难以单独维护和做版本管理。落地经验：正文控制在 500 行以内，参考文件只放一层深，长文件开头放目录。区别：Skills 管「知道怎么做」（流程），MCP 管「能碰到什么」（数据和动作），Prompt 管「这一次要做什么」。

**追问：** Skill 和 Agent 是什么关系？（Skill 是被动调用的能力，Agent 主动规划，并调用多个 Skill）

---

### 13. MCP 原理与 Function Calling（中级）

**主问：** MCP 解决了什么问题？三个核心原语是什么？和 Function Calling 是什么关系？

**参考答案：** MCP 是一个开放协议，基于 JSON-RPC 2.0，解决 M 个应用对接 N 个工具时要写 M×N 套适配代码的问题：工具按标准协议实现一次，任何支持 MCP 的客户端都能用。三个原语：Tools（由模型决定是否调用的函数）、Resources（由应用提供给模型的上下文数据）、Prompts（由用户选用的预定义提示模板）。关系：Function Calling 是模型这一侧决定调用哪个函数的能力，MCP 是工程这一侧把函数标准化接入的协议，两者互补。远程部署推荐用 Streamable HTTP 传输，老的 SSE 方式正在被淘汰；协议版本变化较快，以官方最新规范为准。Spring Boot 项目引入 MCP Server starter，把已有的 @Tool 方法注册上去，就能对外暴露。

**追问：** 为什么 Streamable HTTP 比 SSE 更适合生产环境？（可以无状态、方便水平扩展，网关、负载均衡和鉴权中间件都能正常介入）

---

### 14. MCP 生产安全（中高级）

**主问：** MCP Server 上线前要做哪些安全措施？写操作的工具要注意什么？

**参考答案：** HTTP 方式部署的 MCP Server，默认暴露的是没有鉴权的端点，任何能访问到的客户端都能列出并调用所有工具，所以绝不能裸露在网络上，即使是内网。必须前置：OAuth2/OIDC 鉴权、网关限流、工具级别的权限控制、调用审计、链路追踪。写操作工具要守三条纪律：权限校验、二次确认（人在回路）、幂等（idempotencyKey 配合唯一索引，或 outbox 模式）。原则：优先提供只读工具，高危写操作默认不开放。

**追问：** 模型重试导致重复退款，怎么防？（用幂等键，第二次请求直接返回第一次的结果）

**定级：** 能主动说出「默认没有鉴权」→ 中高级。

## 五、Agent 与治理

### 15. 生产级 ReAct 循环（中级）

**主问：** Demo 里的 Agent 用一个 while(true) 循环，上生产前要加哪些防护？

**参考答案：** 四道防护：① 硬性步数上限；② 工具出异常时，不要让它直接抛出去，而是转成文本回传给模型，让它换个办法；③ 时间和 token 双预算，超出就熔断；④ 收不住时给出兜底回复，并返回已经拿到的部分结论。另外还要：同一个工具、同样的参数连续调用时直接拦截，避免反复调用、白白烧钱；工具返回的结果要截断（几万行的 SQL 结果直接塞进上下文会撑爆 token）；历史超过预算时压缩，保留最近几轮原文，更早的做成摘要。框架层面可以用 LangChain4j 的 AiServices，配合最大迭代次数和超时设置。

**追问：** 什么时候该用固定 Workflow，而不是 Agent？（路径能提前确定的流程用 Workflow，更稳定也更便宜）

---

### 16. 高并发下的 AI 接口（中高级）

**主问：** 1000 个用户同时问问题，你的 Spring Boot 后端怎么设计？

**参考答案：** ① 流式输出（WebFlux + SSE），边生成边返回，首字延迟可以从好几秒降到几百毫秒；② 按租户限流（Redis + Lua 令牌桶），防止某个租户把配额用光；③ 设置整体超时，超时后降级为直接返回知识库检索到的原文；④ 用虚拟线程处理阻塞的 I/O；⑤ 语义缓存，相似问题直接命中缓存，跳过整条检索和生成链路；⑥ 模型分层路由，简单任务交给小模型；⑦ 统一 ChatModel 抽象，换模型只改配置。模型挂了用三层兜底：多个 Key、多个地域重试 → 切换备用模型 → 返回知识库原文。核心观点：可用性靠架构，不靠模型。

**追问：** 多租户的数据怎么隔离？（元数据带上租户 ID，在检索阶段就先过滤，或按租户分区；不能只靠检索后再过滤）

---

### 17. 踩坑清单（高级）

**主问：** 做 RAG 或 Agent 落地时，你踩过最大的坑是什么？怎么系统性地避免？

**参考答案：** 回答时可以挑 2～3 个讲透，每个都按「现象 → 原因 → 方案 → 效果」来讲：幻觉（硬性约束 Prompt、强制引用、阈值以下拒答、人工兜底）；召回不准（混合检索 + rerank + 改写问题）；上下文爆炸（滑动窗口、摘要、工具结果截断、Skills 按需加载）；越权（权限过滤下推到检索层，工具白名单）；向量库和业务库不一致（CDC 加对账）；多轮对话里的指代丢失（先结合历史改写问题再检索）；技术栈变化快（把易变的部分关进适配层：统一模型抽象、工具走 MCP、Prompt 做版本管理）。最后落到一句：凡是变更都要过评测集回归。

**追问：** 技术栈每个月都在变，怎么让系统不被拖着频繁重写？

---

## 一句话总结

AI 应用的本质，是把**不确定的模型能力**装进**确定的工程系统**里。超时、重试、熔断、降级、幂等、权限、可观测性，这些 Java 工程师熟悉的东西，就是 AI 落地的主战场。
