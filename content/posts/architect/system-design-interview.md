面向**面试官和候选人**。系统设计题没有标准答案，考的是**思考过程**：澄清需求、估算容量、给出方案、讲清取舍。下面先给出统一的答题框架，再给出 10 道高频题。站内其他文章里已有的系统设计题，统一索引在文末。

## 统一答题框架（七步，约 40 分钟）

| 步骤 | 时间 | 要做什么 | 面试官在看 |
| --- | --- | --- | --- |
| 1. 需求澄清 | 5 分钟 | 功能需求（核心 2–3 个）、非功能需求（QPS、延迟、一致性、可用性） | 会不会主动问，会不会砍范围 |
| 2. 容量估算 | 3 分钟 | DAU → QPS（峰值按平均的 3–10 倍）、存储量、带宽 | 数量级对不对 |
| 3. 接口设计 | 3 分钟 | 2–4 个核心 API | 抽象是否清晰 |
| 4. 数据模型 | 5 分钟 | 表结构和 Key 设计、选什么存储 | 存储选型的理由 |
| 5. 架构图 | 10 分钟 | 接入层 → 服务 → 缓存 / MQ → 存储 | 分层是否合理 |
| 6. 深挖瓶颈 | 10 分钟 | 热点、一致性、并发、故障 | **最能定级** |
| 7. 扩展与演进 | 4 分钟 | 10 倍流量怎么办、监控告警、灰度发布 | 有没有工程落地经验 |

**常用估算：** 一天约 10 万秒；1 亿 DAU、每人每天 10 次请求，平均约 1 万 QPS，峰值约 5 万；单台 Redis 约 10 万 QPS；单个 MySQL 实例约几千 TPS。

**定级：**
- 初级：能画出一个可用的架构图
- 中级：能估算容量、说出瓶颈和对应方案
- 高级：能讲取舍、故障演练、成本和演进路线

## 一、流量与稳定性

### 1. 设计一个分布式限流器（中级～高级）

**主问：** 设计一个限流组件，给开放平台的每个 API Key 做每秒和每天的调用配额，单机和集群都要支持。

**参考答案：**

1. **算法选择：**

| 算法 | 特点 | 适用场景 |
| --- | --- | --- |
| 固定窗口 | 实现简单，窗口边界处可能放过 2 倍流量 | 粗粒度的每日配额 |
| 滑动窗口（日志或分桶） | 平滑，但比固定窗口耗内存 | 按秒精确限流 |
| 令牌桶 | 允许一定的突发流量，平均速率受控 | API 限流（**最常用**） |
| 漏桶 | 输出速率恒定，起整形作用 | 保护下游 |

2. **分布式实现：** 在 Redis 里用 Lua 脚本，保证「读取令牌、计算、扣减」是原子操作。

```lua
-- KEYS[1]=桶 key  ARGV: rate, capacity, now(ms), cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or tonumber(ARGV[2])
local ts = tonumber(b[2]) or tonumber(ARGV[3])
tokens = math.min(tonumber(ARGV[2]), tokens + (tonumber(ARGV[3]) - ts) * tonumber(ARGV[1]) / 1000)
local ok = tokens >= tonumber(ARGV[4])
if ok then tokens = tokens - tonumber(ARGV[4]) end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return ok and 1 or 0
```

3. **分层部署：** 网关层做全局限流（Redis）；服务内部做单机兜底（Guava RateLimiter / Sentinel），防止 Redis 故障时整体失控。
4. **配置：** 配额存在配置中心，可以热更新；被限流时返回 429，带上 `Retry-After` 和剩余配额头。
5. **Redis 故障时：** 降级成单机限流（按集群节点数平分配额），不能直接全部放行，也不能全部拒绝。

**追问：**

1. 每次请求都访问 Redis 太慢了，怎么办？（本地预取一批令牌，用完再取；精度换性能）
2. 多机房怎么限流？（各机房按配额比例分别限流，或者异步汇总；接受一定误差）
3. 限流、熔断、降级分别在什么时候触发？

### 2. 订单 30 分钟未支付自动关单（中级）

**主问：** 每天 1000 万订单，下单后 30 分钟没付款要自动关闭，并释放库存。怎么设计？

**参考答案：**

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 定时任务扫表 | 简单、可靠 | 有延迟；数据量大时扫表压力大（需要建 `status + create_time` 索引并分片扫描） |
| MQ 延迟消息（RocketMQ 5.x 任意延迟 / RabbitMQ 延迟插件） | 准时，和业务解耦 | 依赖 MQ 的可靠性；海量延迟消息有存储压力 |
| Redis ZSet（score 存过期时间） | 轻量 | 要自己处理可靠性和多实例争抢 |
| 时间轮（Netty HashedWheelTimer） | 单机性能高 | 进程内存储，重启会丢，需要持久化 |

**推荐做法：** 主方案用 MQ 延迟消息，**加上定时扫表兜底**（每 5 分钟扫一次已超时但还没关单的订单）。

- **关单要幂等，并防止和支付并发：** `UPDATE orders SET status = 'CLOSED' WHERE id = ? AND status = 'UNPAID'`，影响行数为 1 才去释放库存。
- **支付回调晚到（订单已关闭）：** 走自动退款流程，或者人工处理。

**追问：** 用户在第 29 分 59 秒付款，同时关单消息到达，会怎样？（两边都用条件更新，只有一个能成功；输的一方要么退款，要么忽略）

## 二、交易与营销

### 3. 设计抢红包（高级）

**主问：** 设计微信群抢红包：发一个 100 元、20 个的拼手气红包，群里几百人同时抢。

**参考答案：**

1. **拆包算法：** 二倍均值法，每次随机金额范围是 `[0.01, 剩余金额 / 剩余个数 × 2]`，最后一个人拿剩下的全部，保证总额正确、金额以分为单位。拆包可以**发红包时预先拆好**，存进 Redis List，也可以抢的时候实时计算。
2. **抢红包分两步：**
   - 「抢」：Redis 原子操作。用 Lua 判断这个用户是否已经抢过（Set），没抢过就 `LPOP` 一个金额。这一步只决定有没有抢到，很快。
   - 「拆」：异步落库。发 MQ 消息，在数据库里记一条领取记录（`红包 ID + 用户 ID` 唯一索引保证幂等），然后给用户加余额。
3. **数据库：** 红包表、领取明细表，按红包 ID 分库分表。
4. **过期退款：** 24 小时没被领完，用延迟消息触发退款。
5. **对账：** 每个红包的领取总额加上退款要等于发出金额。

**追问：**

1. Redis 抢成功了，但落库失败怎么办？（MQ 重试加幂等；最终靠对账补偿）
2. 为什么不直接用数据库行锁扣减？（几百人并发抢同一行，锁竞争严重；Redis 做第一道闸）
3. 一个红包会有多大的并发？（单个群人数有限，单红包并发不高；真正的压力在春节这类大量红包同时发、同时抢的总量）

### 4. 设计优惠券系统（中高级）

**主问：** 设计一个优惠券系统，支持领券、用券、发券（营销活动定向发放），大促时要能抗住领券高峰。

**参考答案：**

1. **模型：** 券模板（面额、门槛、有效期、总量、每人限领数）加用户券（状态：未使用、已锁定、已使用、已过期）。
2. **领券（高并发）：**
   - Redis 预减库存，用 Lua 同时校验每人限领数；
   - 通过 MQ 异步写入用户券表，用 `用户 ID + 模板 ID + 序号` 做唯一约束；
   - 热门券的库存可以拆成多个分片 Key，分散热点。
3. **用券（强一致）：** 下单时先锁定券（状态改成 LOCKED，条件更新），支付成功后改为已使用，取消订单时解锁。这个流程要和订单事务保持一致，用 TCC 或者本地消息表。
4. **批量定向发券：** 任务分片，通过 MQ 削峰写入，保证幂等，支持暂停和重跑。
5. **查询「我的券」：** 用户券表按用户 ID 分表；下单页计算「可用券」时做本地计算和缓存。

**追问：** 多张券怎么叠加计算最优价格？（规则引擎；先过滤可叠加的组合，再枚举或贪心求最优，数量多时限制枚举规模）

### 5. 点赞与计数系统（中级）

**主问：** 设计一个点赞系统：能点赞和取消，显示点赞数，判断「我是否点过赞」，热门内容一秒有上万次点赞。

**参考答案：**

1. **存储：**
   - 点赞关系：`(user_id, item_id)` 唯一。数据库做持久化；Redis 用 Set 或 Bitmap 判断「是否点过」。
   - 计数：Redis `INCR`，异步合并后写回数据库。
2. **写入路径：** 先写 Redis 的关系和计数，再发 MQ，由消费者批量落库。合并写入的方式是：一段时间内同一内容的计数变化累加后，一次更新数据库。
3. **热点内容：**
   - 计数拆成多个分片 Key（`count:{item}:{0..N}`），读的时候求和；
   - 也可以在本地内存聚合 1 秒再写入 Redis。
4. **一致性：** 计数允许短暂不准，追求最终一致；定期用数据库里的关系数据校准计数。
5. **冷数据：** 时间久的点赞关系只保留在数据库里，查询时回源，避免 Redis 内存无限增长。

**追问：** 「点赞列表按时间倒序分页」怎么做？（ZSet，score 存时间戳；大 V 内容的列表要按时间分段存储）

## 三、位置、消息与存储

### 6. 附近的人 / 附近的店（中级～高级）

**主问：** 设计「附近 3 公里的商家」，按距离排序，商家有 1000 万家。

**参考答案：**

1. **地理编码：** **GeoHash** 把经纬度编码成字符串，前缀越长精度越高（6 位约 1.2km × 0.6km）。查询时取当前所在格子加周围 8 个格子，消除边界问题，再精确计算距离过滤。
2. **实现选择：**
   - Redis GEO（`GEOADD` / `GEOSEARCH`），底层是 ZSet 加 GeoHash，适合中等规模；
   - Elasticsearch 的 `geo_distance` 查询，能同时按类目、评分等条件过滤；
   - MySQL 8 或 PostGIS 的空间索引。
3. **规模：** 1000 万商家按城市分片，热门城市单独部署。
4. **动态位置（附近的人）：** 用户位置更新很频繁，只存在 Redis 里，设置 TTL，定期上报；还要考虑隐私（模糊化处理、用户可以关闭）。

**追问：** 为什么 GeoHash 要查周围 8 个格子？（目标可能就在旁边的格子里，物理距离很近，但编码前缀不同）

### 7. 消息推送与通知中心（中高级）

**主问：** 设计一个统一的通知中心，业务方调用一个接口，就能通过站内信、App 推送、短信、邮件发出通知。

**参考答案：**

1. **架构：** 接入 API（做鉴权、模板校验、频控）→ MQ（按优先级分 Topic：验证码高、营销低）→ 各渠道的发送服务 → 第三方通道（APNs / 厂商推送 / 短信商）→ 回执服务。
2. **模板与路由：** 按模板配置渠道顺序，比如先发推送，失败或未读再降级为短信；用户可以设置免打扰时段，退订后不再发送。
3. **频控和去重：** 同一用户同一类通知每天限制次数；业务方传入 `bizId` 做幂等，避免重复发送。
4. **可靠性：** 发送失败按退避策略重试；一个短信商挂了，自动切换到备用通道；通过回执统计到达率。
5. **站内信：** 写扩散（给每个用户写一份）还是读扩散（存一份全员公告，用户拉取时合并），按发送对象的规模选择。

**追问：** 一次给 1 亿用户推送营销消息，怎么做？（任务按用户分片，限速发送，错峰；推送通道本身有速率限制）

### 8. 网盘与大文件上传（高级）

**主问：** 设计一个网盘，支持 GB 级大文件上传、断点续传、秒传和分享。

**参考答案：**

1. **上传流程：**
   - 客户端计算文件哈希（大文件可以抽样计算哈希加快速度）；
   - 服务端按哈希查询，**已存在就秒传**，只新增一条用户和文件的引用记录；
   - 不存在则分片上传（比如 5MB 一片），并发上传，服务端记录已收到的分片，**中断后可以续传**；
   - 全部分片到齐后合并，再校验整体哈希。
2. **存储：** 文件内容放对象存储（S3 / OSS / MinIO），客户端用预签名 URL 直接上传，不经过应用服务器；元数据（目录树、文件和哈希的映射、引用计数）放数据库。
3. **去重与删除：** 相同内容只存一份，靠引用计数管理；用户删除文件只减少引用，引用为 0 时延迟物理删除。
4. **下载：** CDN 加速，支持 Range 断点下载。
5. **分享：** 生成带随机 token 的链接，可以设置提取码和过期时间，下载接口限流。

**追问：** 秒传有什么安全问题？（攻击者只要知道哈希就能「秒传」得到别人的文件。解决办法：服务端随机抽取文件的几段内容做挑战校验，证明客户端确实拥有这个文件）

### 9. 设计一个分布式缓存（高级）

**主问：** 如果让你从零设计一个类似 Redis Cluster 的分布式 KV 缓存，核心要解决哪些问题？

**参考答案：**

1. **数据分片：**
   - 一致性哈希加虚拟节点，扩缩容时只迁移少量数据；
   - 或者固定哈希槽（Redis 是 16384 个槽），通过槽来迁移数据。
2. **路由：** 客户端缓存路由表，访问到错误节点时，节点返回重定向（MOVED / ASK），客户端更新路由；也可以用代理层（Codis / Twemproxy 模式）。
3. **复制与高可用：** 主从异步复制；用 Gossip 协议探测故障，多数节点确认后由从节点升级为主节点；异步复制在切换时可能丢失少量写入，要接受。
4. **内存管理：** 淘汰策略（近似 LRU / LFU）；过期删除用惰性删除加定期抽样删除。
5. **热点与大 Key：** 客户端本地缓存热点数据，热点 Key 加副本分散读；发现大 Key 后拆分。
6. **持久化（可选）：** 快照加追加日志。

**追问：** 一致性哈希和哈希槽怎么选？（哈希槽的迁移粒度可控，运维更直观；一致性哈希不需要中心化的元数据）

### 10. 搜索联想（输入提示）（中级～高级）

**主问：** 设计搜索框的输入联想：用户每输入一个字符，就在 100ms 内返回 10 个热门补全词。

**参考答案：**

1. **数据：** 从搜索日志离线统计词频（按天，并对时间做衰减），过滤敏感词，生成候选词库。
2. **结构：**
   - **前缀树（Trie）**，每个节点预先存好 Top-K 热门词，查询复杂度是 O(前缀长度)；
   - 简化方案：Redis ZSet，按前缀分 Key（`sug:{prefix}`），存 Top-K；
   - 或者 Elasticsearch 的 Completion Suggester。
3. **加速：**
   - 前端做防抖，并缓存已经查过的前缀；
   - CDN 和浏览器缓存短前缀的结果，因为短前缀请求量最大、结果最稳定；
   - 服务端把热门前缀放在本地内存。
4. **更新：** 离线全量构建，加上实时热词的增量合并（比如热搜事件）；新版本构建好后替换旧版本，不影响线上服务。
5. **个性化：** 先召回通用热词，再结合用户历史做重排，同时控制延迟。

**追问：** 中文怎么做拼音联想？（候选词库额外存拼音全拼和首字母的映射）

| 前端场景题（搜索、大文件上传、监控等） | 初级～高级 | [前端场景题题库](/posts/react/scenario-interview/) |

## 五、面试官组卷

| 级别 | 推荐题目 |
| --- | --- |
| 中级 | 延迟关单、点赞计数、短链、排行榜、限流器（只讲单机） |
| 中高级 | 优惠券、通知中心、附近的人、配置中心 |
| 高级 | 抢红包、网盘、分布式缓存、秒杀、IM、Feed、支付 |
