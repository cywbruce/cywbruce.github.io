## 一面：Java 与中间件基础

### 1. ConcurrentHashMap（中级）

**主问：** ConcurrentHashMap 在 1.8 是怎么保证线程安全的？size 是怎么计算的？

**参考答案：** put 的流程：桶是空的就用 CAS 写入；桶不空就对桶的头节点加 synchronized 再操作链表或红黑树。正在扩容时（遇到 ForwardingNode），当前线程会先帮忙一起迁移数据。size 借鉴了 LongAdder 的思路：baseCount 加上 CounterCell 数组，竞争激烈时把计数分散到不同的 cell 上，取 size 时再求和，所以拿到的是一个近似实时的值。

**追问：** 为什么不允许 null 作为 key 或 value？（并发时无法区分「key 不存在」和「值本来就是 null」）

---

### 2. volatile 与 JMM（中级）

**主问：** volatile 能保证什么、不能保证什么？DCL 单例为什么要加 volatile？

**参考答案：** volatile 能保证可见性和有序性（通过内存屏障禁止指令重排），但不能保证复合操作的原子性，比如 i++。DCL 单例里 `instance = new X()` 实际分三步：分配内存、初始化对象、把引用赋值给 instance。如果后两步被重排，另一个线程可能拿到一个还没初始化完的对象。加上 volatile 就能禁止这种重排。

**追问：** happens-before 有哪几条规则？

---

### 3. Redis 数据结构底层（中级）

**主问：** ZSet 的底层是什么？为什么用跳表而不用红黑树？

**参考答案：** 元素少的时候用 listpack（以前是 ziplist）存储；元素多了改用 dict 加 skiplist：dict 负责按成员 O(1) 查分数，跳表负责按分数排序和范围查询。选跳表的原因：范围查询只要找到起点后顺序遍历；实现更简单；并发友好；通过调整层数的概率，可以在内存和速度之间取舍。

**追问：** 跳表的层数是怎么决定的？（随机，每升一层概率为 1/4，最高 32 层）

---

### 4. Kafka 高吞吐（中级）

**主问：** Kafka 为什么吞吐量高？怎么保证一个分区内消息有序？

**参考答案：** 吞吐量高的原因：顺序写磁盘、利用 page cache、零拷贝（sendfile）、批量发送加压缩、按分区并行处理。有序性：同一个分区内本来就是有序的，按业务 key 选择分区，就能让同一个 key 的消息进同一个分区；生产端开启幂等（`enable.idempotence`），这样重试也不会打乱顺序；消费端对同一个分区单线程处理。

**追问：** 消费积压了怎么处理？（先扩分区和消费者，或临时把消息转存再并行处理）

## 二面：场景设计

### 5. 库存超卖（中高级）

**主问：** 大促时防止库存超卖，从 Redis 到数据库，完整链路怎么设计？

**参考答案：** ① Redis 里用 Lua 脚本原子地做「检查库存 + 扣减」，同时记一条扣减流水；② 扣减成功后发 MQ 消息，异步创建订单；③ 数据库最终扣减时用 `UPDATE … SET stock = stock - 1 WHERE stock > 0` 兜底；④ 订单超时未支付就释放库存（用延时消息）；⑤ 定时对账 Redis 和数据库的库存，修正差异；⑥ 热点商品把库存拆成多段，分散到不同 key 上。

**追问：** Redis 扣成功了，但 MQ 发送失败，怎么办？（用本地消息表或事务消息）

---

### 6. 排行榜（中级）

**主问：** 设计一个千万用户的实时积分排行榜，要求能查 TopN 和我的名次。

**参考答案：** 用 Redis ZSet：`ZINCRBY` 加积分，`ZREVRANGE` 取 TopN，`ZREVRANK` 查自己的名次。同分时要按先到达的排前面，可以把分数编码成「积分 × 10^10 + (MAX_TS - 时间戳)」。千万级数据：按区服或分桶拆成多个 ZSet，再合并；或者只把活跃用户放进 ZSet，冷数据存在数据库里离线计算。每天或每周的榜单用带日期的不同 key，并设置过期时间。

**追问：** 名次要做到绝对准确，又要扛住高并发，怎么取舍？

---

### 7. 慢 SQL 与锁（中高级）

**主问：** 线上突然出现大量锁等待超时，你怎么定位？

**参考答案：** 先查当前事务和锁：`innodb_trx`、`data_locks`（MySQL 8）、`SHOW ENGINE INNODB STATUS` 里的最近一次死锁信息。常见原因：大事务长时间持有锁；UPDATE 的条件没走索引，导致锁住了大量行（RR 隔离级别下还会加间隙锁）；热点行被集中更新。处理：先 kill 掉长事务，再优化索引、拆分大事务、把热点更新改成合并或排队执行。

**追问：** RR 和 RC 隔离级别下，加锁范围有什么区别？

## 三面：项目与架构

### 8. 服务拆分与治理（高级）

**主问：** 你们的系统是怎么拆分服务的？拆完遇到过哪些问题，怎么解决的？

**参考答案：** 按业务域拆分（可参考 DDD 的限界上下文），每个服务拥有自己的数据。拆完常见的问题：调用链变长、延迟上升（用链路追踪定位、做接口聚合）；分布式事务（用最终一致加对账）；故障级联（超时、熔断、隔离）；数据一致性和跨服务查询（用 CQRS 或宽表）。回答时要能讲出真实遇到的问题和对应的指标。

**追问：** 如果让你重新拆，你会合并哪些服务？为什么？

---

### 9. 稳定性建设（高级）

**主问：** 怎么把一个系统的可用性从 99.9% 提升到 99.99%？

**参考答案：** 先算错误预算：99.99% 意味着每月只能停约 4.3 分钟。所以靠人工处理已经来不及，需要：多可用区部署加自动故障转移；变更治理（灰度、自动回滚，大部分事故都是变更引起的）；依赖做降级和隔离；容量要有冗余，并定期压测；用 SLO 驱动告警，故障演练常态化。还要逐个分析每一类历史故障，找到并消除对应的根因。

**追问：** 可用性提升带来的成本，怎么向管理层论证？
