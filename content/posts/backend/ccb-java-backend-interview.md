## 一面：Java 与框架基础

### 1. 泛型擦除（初级～中级）

**主问：** 简述 Java 泛型的擦除机制，以及泛型在实际项目中会带来哪些常见问题？

**参考答案：** 泛型只在编译期做类型检查。编译后类型参数会被擦除成上界（默认 Object），必要的地方由编译器插入强制类型转换，并生成桥方法来保持多态。常见问题：① 运行时拿不到 `T`，不能 `new T()`、不能 `instanceof List<String>`；② `List<String>` 和 `List<Integer>` 擦除后签名相同，不能作为方法重载；③ JSON 反序列化泛型集合时会丢失类型，要用 `TypeReference` 或 `TypeToken`；④ 和原始类型混用会造成堆污染，可能抛出 `ClassCastException`；⑤ 基本类型不能作为类型参数，装箱有开销。

**追问：** 为什么 `TypeReference` 能拿到泛型类型？（匿名子类的 `getGenericSuperclass` 会保留在 class 元数据里）

**定级：** 能讲出桥方法，以及 TypeReference 的原理 → 中级。

### 2. 线程池参数与 Executors（中级）

**主问：** 说说线程池的核心参数、常用队列和拒绝策略。为什么金融项目不推荐用 Executors 创建线程池？

**参考答案：** 7 个参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。任务提交后的流程：核心线程没满就新建线程 → 核心满了就放进队列 → 队列满了且没到最大线程数就继续新建线程 → 都满了就执行拒绝策略。常用队列：ArrayBlockingQueue（有界）、LinkedBlockingQueue（默认几乎无界）、SynchronousQueue（不存储任务，直接交接）、PriorityBlockingQueue。拒绝策略：Abort（抛异常，默认）、CallerRuns（由调用线程执行，起到反压作用）、Discard、DiscardOldest。不推荐 Executors 的原因：`newFixedThreadPool` / `newSingleThreadExecutor` 用的是无界队列，任务堆积会导致 OOM；`newCachedThreadPool` 的最大线程数是 Integer.MAX_VALUE，线程会无限增长。金融场景要求资源可控、出问题能被发现：应该手动创建有界线程池，给线程起有意义的名字，配监控和告警，拒绝时要记录日志或落库补偿，不能静默丢弃交易任务。

**追问：** 核心交易和对账任务要不要共用一个线程池？（要按业务隔离，即舱壁模式）

**定级：** 只会背参数 → 初级；能讲风险和隔离、监控 → 中级。

### 3. Spring 依赖注入方式（初级）

**主问：** Spring IoC 的依赖注入方式有哪些？三种方式的优劣和适用场景分别是什么？

**参考答案：** ① 构造器注入：依赖不可变（可以用 final），对象创建完就是完整的，方便单元测试，官方推荐；依赖太多时会暴露类的职责过重。它无法解决构造器之间的循环依赖，这一点反而能帮你发现设计问题。② Setter 注入：适合可选依赖、需要重新配置的依赖，但对象可能处于未完全初始化的状态。③ 字段注入（@Autowired 加在字段上）：写起来最简洁，但会隐藏依赖、无法声明 final、脱离容器很难测试，一般不推荐。

**追问：** @Autowired 和 @Resource 有什么区别？（前者按类型注入，后者默认按名称）Spring 是怎么用三级缓存解决循环依赖的？

### 4. MVCC 原理（中级）

**主问：** MySQL InnoDB 中 MVCC 的实现原理是什么？它解决了哪些事务问题？

**参考答案：** 由三部分组成：① 每行数据的隐藏列：`DB_TRX_ID`（最后修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo log）；② undo log 把同一行的历史版本串成版本链；③ Read View 记录生成快照时的活跃事务列表、最小活跃事务 ID 和下一个待分配的事务 ID，通过可见性规则沿着版本链找到当前事务能看到的版本。RC 隔离级别下每条 SELECT 都生成新的 Read View；RR 隔离级别下事务第一次读时生成，之后一直复用。MVCC 解决的问题：快照读下不会有脏读和不可重复读，读写之间也不用互相加锁。幻读：快照读靠 MVCC 避免，当前读（`FOR UPDATE`）要靠间隙锁和临键锁（Next-Key Lock）。

**追问：** RR 隔离级别下，事务里先快照读、再当前读，结果会不一样吗？

**定级：** 能讲清 Read View 的可见性规则 → 中级。

### 5. HashMap 1.7 vs 1.8（初级～中级）

**主问：** 简单说一下 HashMap 的底层结构和扩容机制，以及 JDK1.7 和 JDK1.8 的核心区别。

**参考答案：** JDK 1.8 的结构是数组 + 链表 + 红黑树：链表长度 ≥ 8 且数组长度 ≥ 64 时转成红黑树，节点数 ≤ 6 时退回链表。扩容时机是元素个数超过 容量 × 0.75，扩容为原来的 2 倍。容量是 2 的幂，所以下标可以用 `(n-1) & hash` 计算；扩容时每个节点只会留在原位置，或者移到「原位置 + 旧容量」。1.7 和 1.8 的区别：① 1.7 的链表是头插法，并发扩容时可能形成环形链表导致死循环，1.8 改成了尾插法；② 1.8 引入了红黑树；③ 1.8 的 hash 扰动简化成高 16 位和低 16 位异或；④ 1.8 扩容时不再重新计算 hash。不过 HashMap 在任何版本都不是线程安全的，1.8 并发写仍然可能丢数据，并发场景要用 ConcurrentHashMap。

**追问：** 为什么阈值是 8？（按泊松分布，链表长度达到 8 的概率极低）ConcurrentHashMap 1.8 是怎么加锁的？（CAS + 对桶的头节点 synchronized）

### 6. Spring AOP（中级）

**主问：** Spring AOP 的核心原理是什么？常用的通知类型有哪些？项目中如何用 AOP 实现日志记录和权限拦截？

**参考答案：** 原理：在 Bean 初始化之后，由 BeanPostProcessor 为匹配切点的 Bean 生成代理对象。目标类实现了接口时默认用 JDK 动态代理，否则用 CGLIB（Spring Boot 默认就是 CGLIB）。通知类型：@Before、@After、@AfterReturning、@AfterThrowing、@Around。落地做法：先自定义注解，比如 `@OpLog`、`@RequirePerm`；再写一个 `@Around` 切面，记录入参、耗时、结果和异常，配合 traceId 和敏感字段脱敏，异步写入日志；权限切面在 `@Before` 里从上下文取出用户，校验权限码，不通过就抛异常，由全局异常处理器统一返回。有多个切面时用 `@Order` 控制执行顺序。

**追问：** 同一个类里方法 A 调用方法 B，B 上的切面为什么不生效？怎么解决？（自调用不经过代理对象；可以注入自身代理或拆到别的类）

**定级：** 能讲出自调用失效和执行顺序 → 中级。

### 7. 锁分类与锁升级（中级）

**主问：** 简述 Java 锁的分类。偏向锁、轻量级锁、重量级锁的升级过程是怎样的？

**参考答案：** 锁的分类维度：乐观锁 / 悲观锁、公平 / 非公平、可重入、独占 / 共享（读写锁）、自旋锁，以及 synchronized 和 ReentrantLock（基于 AQS）。synchronized 的锁升级过程（状态记录在对象头 Mark Word 里）：无锁 → 偏向锁（只有一个线程访问时，记下它的线程 ID，以后它再进入不需要 CAS）→ 出现其他线程竞争时撤销偏向，升级为轻量级锁（在线程栈里放 Lock Record，用 CAS 加自旋抢锁）→ 自旋失败或竞争激烈时膨胀为重量级锁（使用 Monitor 和操作系统互斥量，抢不到的线程会阻塞）。锁升级一般不可逆。注意：JDK 15 之后偏向锁默认禁用，JDK 18 起相关代码被移除。

**追问：** synchronized 和 ReentrantLock 怎么选？AQS 的核心思想是什么？

**定级：** 能主动说出 JDK 15 后偏向锁的变化 → 加分。

### 8. 联合索引最左匹配（初级～中级）

**主问：** 说说 MySQL 联合索引的最左匹配原则，以及日常开发中如何合理设计索引、避免索引失效。

**参考答案：** 联合索引 (a,b,c) 在 B+ 树里按 a → b → c 的顺序排序，所以查询条件要从最左边的列开始连续使用。遇到范围查询（`>`、`<`、`between`）时，这一列之后的列无法再用来定位（MySQL 8 可能用索引跳跃扫描）；`like 'x%'` 能用索引。设计原则：区分度高、经常用于等值查询的列放前面；尽量做成覆盖索引，避免回表；控制索引数量；利用索引下推（ICP）。常见失效场景：对索引列使用函数或计算、隐式类型转换（字符串列和数字比较）、`like '%x'`、OR 两边条件没有都走索引、`!=` / `not in` 导致优化器判断全表扫描更快。上线前用 EXPLAIN 看 type、key、rows、Extra。

**追问：** `where b=1 and a=2` 能用到索引吗？（能，优化器会调整条件顺序）

## 二面：金融场景与工程实践

### 9. 转账一致性（中高级）

**主问：** 银行转账这类核心场景中，如何通过数据库事务 + 锁机制保证账务数据一致性？

**参考答案：** ① 同一个本地事务里完成扣款和入账，并记录流水，满足 ACID。② 防止并发超扣：用 `SELECT … FOR UPDATE` 悲观锁，并按账户 ID 排好序再加锁，避免死锁；或者用条件更新 `UPDATE acct SET bal=bal-? WHERE id=? AND bal>=?`，影响行数为 0 就失败；也可以用 version 乐观锁。③ 幂等：用唯一流水号加唯一索引，防止重复入账。④ 跨行或跨库时，拿不到单库事务，改用「冻结 → 确认 / 解冻」的 TCC 模式，或者事务消息，再加上日终对账、差错处理作为兜底。⑤ 金额用 DECIMAL 或「分」作为单位，不能用 double。

**追问：** A 转 B、B 转 A 同时发生，怎么避免死锁？热点账户（比如商户收款户）怎么扛并发？（缓冲记账、子账户拆分、汇总入账）

**定级：** 能讲出加锁顺序、幂等、对账 → 中高级。

### 10. 接口慢排查（中高级）

**主问：** 项目中出现接口慢、数据库查询超时，你的完整排查思路和优化方案是什么？

**参考答案：** 先止血：限流、降级、扩容，或回滚最近的变更。然后定位：① 用链路追踪或 APM 确认慢在哪一段（应用、数据库、下游服务）；② 数据库侧看慢查询日志、EXPLAIN、锁等待（`information_schema.innodb_trx`、`SHOW PROCESSLIST`）、连接池是否被打满；③ 应用侧看 GC、线程池排队、jstack。优化：SQL 和索引优化（覆盖索引、避免深分页，改用游标翻页）、拆分大事务、读写分离、缓存、异步化、批量化，合理设置超时和连接池大小。最后复盘：加上慢 SQL 告警，上线前做 SQL Review。

**追问：** 深分页 `LIMIT 1000000,20` 怎么优化？（基于上一页最后的 ID 做游标翻页，或先子查询出 ID 再关联）

### 11. 缓存三大问题（金融场景）（中级）

**主问：** 简述 Redis 缓存穿透、缓存击穿、缓存雪崩的区别，并结合金融业务说明对应的解决方案。

**参考答案：** 穿透：查询不存在的数据，每次都打到数据库（比如被恶意刷不存在的卡号）→ 用布隆过滤器、缓存空值并设短 TTL、做参数校验和风控。击穿：热点 Key 过期的瞬间大量请求打到数据库（比如理财产品详情页、利率配置）→ 用互斥锁重建缓存、逻辑过期加后台异步刷新、热点数据预热。雪崩：大量 Key 同时失效，或者 Redis 宕机 → TTL 加随机值打散、多级缓存、Redis 高可用、熔断降级。金融场景要特别注意：余额、额度这类强一致数据不要依赖缓存直接返回，最终要以数据库为准；缓存只用来扛查询类流量。

**追问：** 布隆过滤器不支持删除，数据下线了怎么办？（定期重建，或者改用 Counting Bloom Filter）

**定级：** 能结合业务给出数据分级 → 加分。

### 12. 事务传播与嵌套事务（中级）

**主问：** 说说 Spring 事务的传播机制和隔离级别。实际项目中嵌套事务会出现什么问题？如何解决？

**参考答案：** 7 种传播行为：REQUIRED（默认）、REQUIRES_NEW、NESTED、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。隔离级别可选 DEFAULT（跟随数据库）、RC、RR 等。常见问题：① 内层方法抛异常，外层把它 catch 住了，提交时报 `UnexpectedRollbackException`，因为事务已经被标记为 rollback-only；② 同一个类里自调用，导致 @Transactional 不生效；③ 方法不是 public、抛出的是受检异常（默认不回滚，要设置 `rollbackFor = Exception.class`）、异常被吞掉；④ 用 REQUIRES_NEW 写审计日志，需要它独立提交，但会多占一个数据库连接，可能引起连接池死锁；⑤ NESTED 基于 savepoint，内层回滚不影响外层。解决：根据业务选对传播行为，注入自身代理或把方法拆到别的类，明确设置 rollbackFor。

**追问：** 操作日志无论主业务成功与否都要落库，怎么设计？（用 REQUIRES_NEW，或者异步写入）

### 13. 超时重试与幂等（中高级）

**主问：** 微服务场景下，服务调用超时、重试导致了幂等性问题，银行系统如何设计幂等方案？

**参考答案：** 超时不等于失败，结果是「未知」。所以：① 调用方生成全局唯一请求号（比如交易流水号），重试时沿用同一个号；② 服务方用唯一索引或去重表拦截重复请求，配合状态机做条件更新，重复请求直接返回第一次的处理结果；③ 并发进来的相同请求，用 Redis `SET NX` 或数据库行锁拦截；④ 结果未知时，先调用查询接口确认状态，再决定是否重试，不要盲目重试；⑤ 重试要限次数，加退避和抖动，只对可重试的错误码重试；⑥ 最后用日终对账来纠正差错。

**追问：** 下游不支持幂等，怎么办？（在本地记录调用流水，加上查证接口和人工差错处理）

### 14. JVM 内存与 GC/OOM 排查（中高级）

**主问：** 简述 JVM 常见内存区域，以及线上项目频繁 GC、OOM 的排查思路和优化手段。

**参考答案：** 内存区域：堆（新生代 Eden/S0/S1 和老年代）、元空间、虚拟机栈、本地方法栈、程序计数器、直接内存。排查：用 `jstat -gcutil` 看 GC 频率和耗时，看 GC 日志；用 `jmap -histo` 查看对象分布；配置 `-XX:+HeapDumpOnOutOfMemoryError` 在 OOM 时自动 dump，再用 MAT 分析支配树，找出泄漏点（常见的有：静态集合、没有上限的本地缓存、ThreadLocal 没有 remove、大查询一次性加载太多数据）。根据报错类型区分：`Java heap space`、`Metaspace`（类加载过多、动态代理）、`Direct buffer memory`、`unable to create native thread`。优化：先修代码，再调整堆大小和新生代比例，选择合适的收集器（G1/ZGC）并设定停顿目标。

**追问：** Full GC 频繁，但老年代占用并不高，可能是什么原因？（元空间满、显式调用 System.gc、大对象直接进入老年代）

### 15. MQ 不丢不重（中级）

**主问：** 消息队列在银行系统中有哪些应用场景？如何保证消息不丢失、不重复消费？

**参考答案：** 应用场景：交易完成后的异步通知（短信、积分）、削峰、系统解耦、事务消息实现最终一致、对账数据分发。不丢失要三端配合：生产端用同步发送加确认（RocketMQ 事务消息，或本地消息表 + 定时补偿）；Broker 端开启同步刷盘和主从同步复制；消费端业务执行成功后再手动提交 ACK，失败就重试，多次失败进入死信队列并告警。不重复：MQ 本身只保证至少一次投递，所以靠消费端幂等（用业务唯一键做去重表或唯一索引，配合状态机）。

**追问：** 消息需要有序时怎么做？（同一个账户的消息路由到同一个队列，单线程顺序消费）

### 16. 分库分表与关联查询（高级）

**主问：** 在高并发查询场景下，MySQL 分库分表适用于什么情况？分表后带来的关联查询问题如何解决？

**参考答案：** 适用情况：单表数据量达到千万甚至亿级，索引和归档都已经优化过仍然不够；或者写入 QPS 超过单库承受能力。优先考虑读写分离、冷热数据归档。分片键选择查询最频繁的维度，比如客户号或账号，用 ShardingSphere 做路由。关联查询的解决办法：① 字段冗余或宽表，避免 join；② 把关联关系相同的表用同一个分片键，让它们落在同一个分片，再做同库 join；③ 小表做成广播表或全局表；④ 在应用层分别查询，再在内存里组装；⑤ 复杂查询和报表走 ES 或数仓，通过 binlog 同步数据。还要配套解决：分布式 ID、跨库事务、扩容时的数据迁移（双写 + 数据校验）。

**追问：** 按客户号分片后，运营要按交易时间做全局查询，怎么办？（建异构索引表或用 ES）

**定级：** 能讲出替代方案和迁移方案 → 高级。
