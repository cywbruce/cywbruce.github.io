## 〇、怎么问才有效

**差问法：** 「什么是观察者模式？」  
**好问法：** 「订单状态变更要通知库存、积分、消息，怎么设计？以后还要加模块怎么办？」

对照 SOLID（尤其单一职责、开闭）听候选人是否真的用过。

## 一、创建型

### 1. 单例（初级～中级）

**主问：** 写一个线程安全单例；项目里哪些东西适合单例？

**参考答案：**

- 常见写法：静态内部类、枚举（防反序列化/反射更稳）、双重检查 + `volatile`。  
- 适合：无状态工具、全局配置、昂贵且可共享的资源管理器。  
- **不适合：** 带请求状态的对象硬做成单例（成隐蔽共享可变状态）。

**追问：**

1. 双重检查为什么要 `volatile`？  
2. Spring 单例 Bean 和 GoF 单例是一回事吗？（容器管生命周期，非 JVM 唯一）  
3. 单例滥用有什么害处？

**定级：** 能写对一种安全写法 → 初级；能讲 volatile/枚举与 Spring 差异 → 中级。

---

### 2. 工厂 / 抽象工厂 / Builder（初～中）

**主问：** 「一堆 if 根据 type 创建对象」怎么重构？

**参考答案：** 简单工厂或工厂方法把创建集中；新产品用开闭方式扩展（注册表/Map + 策略）。抽象工厂：一族产品。Builder：构造参数多、有必选可选、要不可变对象时。

**追问：** 和 Spring `@Component` + 按类型注入列表有何关系？（容器当工厂）

**场景追问：** 支付渠道（微信/支付宝/银行卡）创建支付客户端——用工厂还是策略？两者如何配合？

## 二、结构型

### 3. 代理（中级，联 Spring）

**主问：** 静态代理、JDK 动态代理、CGLIB 差别？在 Spring 哪见过？

**参考答案：** 代理控制访问、加事务/日志/权限。JDK：基于接口；CGLIB：子类。Spring AOP、`@Transactional` 就是代理。自调用不走代理。

**追问：** 和装饰器有何不同？（代理重控制访问，装饰重增强功能；实现常像）

---

### 4. 装饰器（中级）

**主问：** 不修改原类，动态叠加功能（加密、压缩、缓冲），怎么做？

**参考答案：** 装饰器与被装饰者同一接口，可嵌套包装。对比继承：更灵活，避免类爆炸。Java I/O 流是经典例子。

**追问：** 和代理如何区分选型？

---

### 5. 适配器（初级～中级）

**主问：** 老接口和新系统不匹配怎么办？

**参考答案：** 适配器转换接口。对象适配 vs 类适配。项目中：封装第三方 SDK、统一支付/短信网关门面下的适配层。

---

## 三、行为型

### 6. 策略（初级～中级，高频）

**主问：** 消除业务里大段 `if-else` / `switch` 算价、算运费，怎么做？

**参考答案：** 策略接口 + 多实现 + 上下文选择（可用 Map 注册）。符合开闭：加新策略不改老分支（或只改注册）。

**追问：**

1. 策略和工厂怎么配合？  
2. 策略会不会导致类太多？何时觉得过度设计？  
3. 用枚举+方法能代替吗？边界在哪？

**定级：** 能落到代码结构 → 中级；能谈过度设计 → 冲高。

---

### 7. 模板方法（初级～中级）

**主问：** 流程固定、某几步可变（如导入：校验→解析→落库），怎么抽象？

**参考答案：** 父类定骨架，子类覆写钩子步骤。Spring 里能见到类似「回调模板」（`JdbcTemplate`、`RedisTemplate` 思想相近：固定流程，用户补差异）。

**追问：** 和策略差别？（继承骨架 vs 组合算法）

---

### 8. 观察者 / 发布订阅（中级）

**主问：** 事件发生后通知多方，解耦怎么做？

**参考答案：** 观察者：主题维护列表并通知。消息队列是跨进程发布订阅。Spring `ApplicationEvent`、Guava EventBus、MQ 都是变体。

**追问：** 同步事件里抛异常会怎样？是否该异步？顺序与丢失如何保证？

---

### 9. 责任链（中高级）

**主问：** 审批流、过滤器链、网关鉴权多层校验，怎么设计？

**参考答案：** 请求沿链传递，节点可处理或下放。Servlet Filter、Netty Pipeline、敏感词/风控流水线常见。要设计好：是否可中断、顺序、通用上下文。

**追问：** 和装饰器流水线有何不同？链太长如何排查？

---

## 四、原则与重构（高级）

### 10. SOLID 与「你何时不用模式」（高级）

**主问：** 开闭原则在你项目里的一次落地？有没有「过度设计」复盘？

**参考答案期望：** 能举真实重构（策略/插件化）；承认 YAGNI：两处重复再抽象；模式是手段不是KPI。

**追问：** 组合优于继承，你怎么理解？给一个继承滥用改组合的例子。

## 五、场景速测（直接丢给候选人）

### 11. 场景速测：给场景选模式（初级～中级）

**主问：** 下面这些需求，你分别会用什么模式？为什么？多种导出格式（Excel / PDF / CSV）、日志增强和鉴权、IO 叠加缓冲和加密、订单状态变更通知、多级审批、复杂对象构建、兼容老支付 SDK。

**参考答案：**

| 场景 | 推荐模式 | 理由 |
| --- | --- | --- |
| 多种导出格式 | 策略 + 工厂 | 导出算法可替换，工厂按类型选出策略，新增格式不改老代码 |
| 日志增强、鉴权 | 代理 / AOP | 横切逻辑和业务分离，业务代码零侵入 |
| IO 叠加缓冲和加密 | 装饰器 | 功能可以任意组合叠加，避免子类爆炸（`BufferedInputStream` 就是这样） |
| 订单状态变更通知 | 观察者 / MQ | 一对多解耦；跨服务时换成 MQ |
| 多级审批 | 责任链 | 节点可以动态编排，每个节点决定处理还是往下传 |
| 复杂对象构建 | Builder | 参数多、有可选项、需要校验，比多个构造器重载清晰 |
| 兼容老支付 SDK | 适配器 | 不改老 SDK，转换成系统统一的支付接口 |

**追问：** 导出格式只有两种，而且一年都不会变，你还会上策略模式吗？

**期望要点：** 先确认哪里会变，再决定要不要引入模式。变化点少时，一个 `if` 更简单，过早抽象也是一种坏味道。

**定级信号：** 能说出场景对应的模式是初级；能先问「哪里会变」再选型，并说出不用模式的情况，是中级。

## 六、补充模式

### 12. 状态模式（中级，高频）

**主问：** 订单有待支付、已支付、已发货、已完成、已取消几种状态，每种状态下能执行的操作不同，代码里满是 `if (status == ...)`，怎么重构？

**参考答案：**

- **状态模式：** 每个状态一个类，实现同一个 `OrderState` 接口（`pay()`、`ship()`、`cancel()` 等）。当前状态对象负责判断操作是否合法，以及切换到下一个状态。新增状态只需要加一个类。
- **状态机（更常用）：** 用一张转移表声明「当前状态 + 事件 → 目标状态 + 动作」，比如 Spring StateMachine、COLA StateMachine，或者自己写一个枚举加 Map。转移规则一目了然，方便校验和可视化。

```java
enum OrderStatus { CREATED, PAID, SHIPPED, DONE, CANCELED }
enum OrderEvent { PAY, SHIP, CONFIRM, CANCEL }

Map<OrderStatus, Map<OrderEvent, OrderStatus>> rules = Map.of(
    CREATED, Map.of(PAY, PAID, CANCEL, CANCELED),
    PAID,    Map.of(SHIP, SHIPPED, CANCEL, CANCELED),
    SHIPPED, Map.of(CONFIRM, DONE));

OrderStatus next(OrderStatus cur, OrderEvent e) {
    OrderStatus to = rules.getOrDefault(cur, Map.of()).get(e);
    if (to == null) throw new IllegalStateException(cur + " 不能执行 " + e);
    return to;
}
```

- **落库要防并发：** `UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'CREATED'`，影响行数为 0 就说明状态已经被别人改了，这次转移失败。

**追问：**

1. 状态模式和策略模式在结构上几乎一样，区别是什么？（策略由**调用方**选择，彼此之间没关系；状态由**状态自己**决定下一个状态，有转移关系）
2. 支付回调和用户取消同时到达，怎么保证状态不会乱？（数据库条件更新加乐观锁，或者分布式锁；回调要幂等）
3. 状态变更后要发通知、记日志，放在哪里？（转移动作里发领域事件，监听方处理，最好在事务提交后再发）

**定级信号：** 能写出转移表是中级；能讲并发转移和事件驱动是中高级。

### 13. 组合模式（初级～中级）

**主问：** 菜单、组织架构、文件目录这类树形结构，怎么让调用方用同一种方式处理「单个节点」和「整棵子树」？

**参考答案：** 叶子节点和容器节点实现同一个接口（比如 `Component.getPrice()` / `render()`），容器内部持有子节点列表，递归调用子节点。调用方不用区分是叶子还是容器。常见例子：前端组件树、权限菜单树、商品套餐（一个套餐里包含多个商品，计算总价）。

**追问：** 树很深或者有环时要注意什么？（递归改成迭代避免栈溢出；用 visited 集合检测环；`add/remove` 放在接口里还是只放在容器里，就是透明式和安全式的取舍）

### 14. 外观模式（初级～中级）

**主问：** 下单要调用库存、优惠券、积分、支付、物流五个子系统，Controller 里写满了编排逻辑，怎么简化？

**参考答案：** 用外观模式，提供一个 `OrderFacade.placeOrder()`，对外只暴露一个简单入口，内部负责编排各个子系统，调用方不需要知道细节。在微服务里，BFF 和 API 网关聚合接口也是外观思想。

**追问：** 外观类越写越大怎么办？（外观只负责编排，不写业务规则；按用例拆成多个外观；复杂流程改成编排引擎或 Saga）

### 15. 命令模式（中级）

**主问：** 编辑器要支持撤销和重做；或者后台任务要支持排队、重试、记录日志，怎么设计？

**参考答案：** 把「请求」封装成命令对象，包含 `execute()` 和 `undo()`。调用方只负责发出命令，接收方负责执行。

- **撤销和重做：** 维护两个栈，执行命令时压入撤销栈；撤销时弹出、调用 `undo()`，再压入重做栈。
- **排队和重试：** 命令对象可以序列化后放进队列，失败了就重放。
- 常见例子：`Runnable` 和线程池、MQ 消息、事件溯源里的 Command。

**追问：** 撤销时用「反向操作」还是「保存快照」？（反向操作省内存，但每个命令都要写对应的逆操作；快照（备忘录模式）实现简单，但占内存，大对象可以做增量快照）
