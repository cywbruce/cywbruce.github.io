## Part 0：30 秒标准总答

**Q：谈谈你对 AI Agent 的理解。**（标准答法 30 秒，五个得分点）

> AI Agent 是能**感知环境、自主规划、调用工具、根据观察持续迭代以达成目标**的系统，核心是"**LLM 当大脑 + 工具当手脚 + 循环当神经 + 记忆当经验**"。
> 它的本质是**一个由 LLM 驱动的 while loop（循环）**：接收任务→规划（planning）→选工具→执行（action）→观察（observation）→判断是否继续→满足条件后终止，而非一次性问答。
> **工具调用（Function/Tool Calling）** 是模型输出**结构化的调用意图**（函数名+参数），由**外部代码真正执行**再把结果回填进上下文——模型本身不执行代码。
> **推理范式** 多样：ReAct（边想边做）、Plan-and-Execute（先规划后执行）、Reflection（反思修正）、RAG（检索增强）等，各有取舍。
> 难点不在"调框架写循环"，而在**控制流设计、规划/反思/记忆机制与失效模式**（死循环、成本失控、上下文膨胀、参数幻觉）——这是区分 Demo 与生产系统的关键。

**评分要点：** 大脑+工具+循环+记忆四要素 / 本质是 while loop 控制流 / 工具调用是"意图+外部执行" / 推理范式多样 / 失效模式与可靠性五点。能说出"控制流""失效模式"的，直接往 Part 2 追问。

## Part 1：基础认知题

### Q1. 什么是 AI Agent？和工作流（Workflow）、chatbot、RPA 有何区别？

**标准答案：** AI Agent 是**以 LLM 为决策核心、能自主规划并调用工具多步行动以达成目标**的系统，关键在**自主性（autonomy）**与**多步闭环**。它不等于"能聊天的程序"，也不是"写死的自动化脚本"：

| 维度 | AI Agent | 工作流 Workflow | Chatbot | RPA |
|------|----------|----------------|---------|-----|
| 决策 | LLM 动态决策下一步 | 预定义固定路径 | 按对话回复 | 按规则录制的固定操作 |
| 确定性 | 不确定、每次可能不同 | 确定、可复现 | 半确定 | 完全确定 |
| 未知情况 | 能应对未预见情况 | 只能走编排好的分支 | 限于话术/知识 | 界面一变即失效 |

一句话：**Workflow 是"人设计路径、机器执行"，Agent 是"人给目标、机器自己找路径"**；Agent 更灵活但更贵、更不可预测。

**追问 1：那"Agentic Workflow"是什么？和 Agent 对立吗？**
> **答案：** 不是对立，是**光谱（spectrum）**。业界把"给 LLM 工具与自主权"的系统统称 Agentic 系统，从**固定编排的 workflow**到**完全自主的 agent**连续过渡。实战多是混合：关键节点用 workflow 保证确定性，开放环节用 agent 提供灵活性——**能不用 Agent 就不用，是成熟工程的默认心态**。
**追问 2：一个"会调用工具的聊天机器人"算 Agent 吗？**
> **答案：** 单个工具调用不算。判据是**有没有"观察结果后再决定下一步"的循环**：若只是"用户问→调一次天气 API→回复"，是 tool-augmented chatbot；若模型能据返回结果继续规划、多步推进直到达成目标，才进入 Agent 范畴。**循环 + 自主终止判断**是关键门槛。

---

### Q2. Agent 的基本组成（规划、工具、记忆、执行循环）各是什么角色？

**标准答案：** 四块：**规划（Planning）**=把目标拆成子任务、决定顺序，是"想"；**工具（Tools）**=可调用的外部能力（搜索、数据库、API），每个工具有 **schema（名称、描述、参数）**，是"做"；**记忆（Memory）**=短期（上下文窗口）/长期（向量库、摘要），是"经验"；**执行循环（Agent Loop）**=把"感知→规划→行动→观察"串起来的 while loop，是驱动一切的"神经中枢"。关系：**LLM 是大脑，工具是手脚，记忆是经验，循环是神经系统**。

**追问 1：为什么"循环"最易被忽略却最关键？**
> **答案：** 框架把循环封装了，写 Demo 的人只感到"配好 tools 就能跑"。但**生产系统 90% 的坑都在循环控制上**：何时停、超预算怎么办、卡住如何检测、观察结果如何回填。只会配工具不懂控制流的人，遇到死循环烧钱就束手无策——这正是 Part 3/4 的区分点。
**追问 2：四块在常见框架里怎么对应？**
> **答案：** 以 LangChain/LangGraph、AutoGen、CrewAI 为例：工具=Tool 定义，记忆=Memory/State/Checkpointer，规划=Planner 或模型自身的思维链，循环=Agent Executor / graph 的 while 调度。框架名称会变，**四块职责不变**——考察是否抓本质而非背 API。

---

### Q3. Function/Tool Calling 到底是什么？模型真的在执行代码吗？

**标准答案：** 让 LLM 输出**结构化调用意图**的机制，分三步：① **声明**：把工具 schema（名称、用途、参数 JSON Schema）随 prompt 发给模型；② **生成**：模型不执行，只输出"想调哪个函数+参数"的结构化对象，如 `{"name":"get_weather","args":{"city":"深圳"}}`；③ **执行与回填**：**宿主应用代码**解析意图、真正调用 API、把结果作为消息回填上下文，模型再据此继续。**核心：模型只"提出请求"，执行在后端，结果由宿主回填，模型从不直接碰数据库或发请求。**

```text
用户 → LLM（带 tool schema）→ {tool_call: get_weather(city=深圳)}
     → [宿主执行 get_weather] → 结果"28℃"回填 → LLM → 最终回答
```

**追问 1：为何不让模型直接输出 Python 代码执行？**
> **答案：** 结构化调用**可校验、可限制、可审计**：参数必须符合 schema、函数须在白名单、结果可控；而"直接跑模型写的代码"是任意代码执行（RCE）级风险，且格式不稳难解析。Function Calling 用"意图与执行分离"换来了安全与确定性。
**追问 2：为什么会出现"幻觉式工具调用（hallucinated tool call）"？**
> **答案：** 根因是**模型按语言概率生成 token，而非查表执行**：可能**编造不存在的 id/参数**（训练里见过类似格式就"补"一个）、**调用未声明的工具**、**误判工具能力**。本质是"语言生成的流畅性"与"精确调用的严谨性"之争。工具描述模糊会放大混淆；宿主必须做 schema 校验与白名单过滤（见 Q11、Q15）。

### Q4. ReAct 是什么？为何是 Agent 的经典范式？

**标准答案：** ReAct = **Reasoning + Acting（推理+行动）**，让模型在循环中交替产生：**Thought（思考当前状态、规划下一步）→ Action（调用工具）→ Observation（工具返回结果）**，再带着 Observation 进入下一轮，直到得出答案。它把**推理链（CoT）与工具使用结合**：推理指导行动、行动结果反过来修正推理，形成闭环。

```text
Thought: 查深圳天气 → Action: get_weather(深圳) → Observation: 28℃
Thought: 还要不要带伞？查降雨 → Action: get_rain(深圳) → Observation: 无雨
Thought: 信息足够 → Final Answer: 深圳 28℃，无需带伞
```

**追问 1：ReAct 相比"先想完再一次性做"好在哪？**
> **答案：** **边做边看、及时纠错**：每步基于真实观察调整，避免纯规划在信息不全时一步错步步错；Thought 链还提供可追溯的"思维日志"。代价是步数多、延迟与 token 成本高，且可能被中途噪声带偏。
**追问 2：Thought 真的等于模型的"真实思考"吗？**
> **答案：** 保守表述：Thought 是模型生成的**自然语言推理痕迹**，可作解释与调试线索，但**不保证忠实反映内部计算**（存在"思维不忠实"现象）。别把它当可信审计日志——可靠性需额外机制保证。

## Part 2：底层原理题（Agent Loop 与记忆机制）

> "会配框架跑通 Demo"和"懂 Agent 运行机理"的分水岭，L2→L3 的关键。

### Q5. Agent Loop 的完整控制流是怎样的？请用文字流程图描述。

**标准答案：** 标准 Agent Loop 是带状态机的 while 循环：

```text
1. 接收任务（goal）→ 写入上下文
2. 规划（plan）：LLM 分解目标、形成当前子任务
3. 选工具（select）：依据 tool schema 决定调用哪个/不调用
4. 执行（act）：宿主执行 tool_call，得到结果或异常
5. 观察（observe）：把结果结构化回填进上下文（消息角色 tool）
6. 判断（check）：达成目标？超步数/预算/超时？
    - 否 → 带新上下文回到第 2 步（或第 3 步）
    - 是 → 终止，产出最终答案
```

关键在**第 6 步的循环控制**：它决定 Agent 收敛还是发散。LLM 每轮都是**无状态调用**，连续性完全由"不断累积的上下文"提供。

**追问 1：为何必须设最大步数/预算控制？终点条件怎么定？**
> **答案：** 因为 LLM 可能**反复徘徊甚至死循环**（A→B→A），没有外部强制终止就无限烧 token。终止条件应多元：① **目标达成**（给出 final answer 或校验器判定）；② **硬上限**：max_steps、max_tokens、超时、最大成本；③ **停滞检测**：连续 N 步无新信息。只靠"模型自己说完成"不安全，需外部护栏（guardrail）。
**追问 2：为何"工具选择"本质是 prompt 工程？每轮全量发历史有何隐患？**
> **答案：** 工具选择**不是模型真"理解"工具**，而是把**所有工具 schema 拼进 prompt**，模型靠语义匹配生成恰好构成 tool_call 的 token——所以工具描述写得清不清晰直接决定准确率，是"给模型写说明书"，属 prompt 工程；工具多会"选择过载"，需按需裁剪/分层路由。而每轮全量发历史使上下文**线性膨胀**：成本升、延迟长、早期关键指令被"淹没"（lost in the middle）——对策见 Q8 与 Q16。

---

### Q6. 规划能力包含什么？Plan-and-Execute 与 ReAct 如何取舍？

**标准答案：** 规划=把目标**分解为有序子任务（task decomposition）**并决定策略。两条路线：

| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 节奏 | 边想边做，每步重规划 | 先出完整计划再逐步执行 |
| 适应性 | 强，随时据观察调整 | 弱，计划遇变化需 replan |
| 成本/延迟 | 步数多、每步都调 LLM | 计划一次、执行阶段少调 LLM |
| 适用 | 探索性、路径未知 | 步骤清晰、流程长、求效率 |

取舍本质：**用灵活性换成本，还是用效率换刚性**。生产常见混合式——先 Plan 定框架，执行中用 ReAct 处理局部不确定，必要时 replan。

**追问 1：任务分解做得不好会怎样？**
> **答案：** 子任务过粗→单步太复杂做不动；过细→步数爆炸、成本失控；遗漏依赖→后序步骤缺前置信息。好的分解要**粒度适中、标明依赖、可校验**——这是 L4 候选人能结合真实任务讲清的地方。
**追问 2：Plan-and-Execute 的"计划"该一成不变吗？**
> **答案：** 不该。真实环境会变（工具失败、信息更新），需 **replanning**：当结果偏离预期，把"计划+已执行历史+偏差"回喂 Planner 重新生成剩余计划。把计划当死板脚本是常见反模式。

### Q7. 反思/自我修正（Reflection / Reflexion）机制怎么工作？

**标准答案：** 让 Agent **评估自己的输出、发现错误并迭代改进**，而非一条道走到黑。典型 Reflexion 循环：① **执行**：Actor 产出结果；② **评估**：Evaluator（不同 prompt/独立模型/规则）给反馈；③ **反思**：把"结果+反馈"写成经验（常存入记忆）；④ **重试**：Actor 带教训改进后重做，直到通过或达上限。本质是**给循环加一个评审信号**，把"一次生成"变成"生成—批评—改进的迭代"。写码 Agent 的"跑测试→看报错→改代码"就是典型。

**追问 1：Reflexion 和普通"多轮重试"有何不同？**
> **答案：** 普通重试只是重复同样动作；Reflexion **把失败原因显式化并写入上下文/记忆**，让下一轮是"带着教训的改进"。关键在**反馈质量与可操作性**——只说"错了"没用，要指出"哪一步、为什么、怎么改"。
**追问 2：评估器（Evaluator）用什么做？**
> **答案：** 分层：① **客观校验器**（单测、schema、规则）最可靠；② **LLM-as-a-judge** 灵活但主观、可能误判；③ **人工反馈**。优先客观信号，LLM 评审作补充——这直接影响 Reflection 能否真纠错（见 Q17）。

---

### Q8. 记忆如何分层？与工作/情景/语义记忆怎么类比？

**标准答案：** 按"存多久、存哪里"分层：

| 分层 | 认知类比 | 载体 | 特点 |
|------|---------|------|------|
| 短期记忆 | 工作记忆（working memory） | 上下文窗口内的对话/观察 | 快、容量有限、随会话丢失 |
| 长期记忆 | 情景记忆（过去事件）+ 语义记忆（知识事实） | 向量库/摘要/结构化 KV | 持久、可跨会话、需检索 |

**工作记忆**=当前脑中处理的信息（上下文窗口）；**情景记忆**="上次那次经历"（历史轨迹/摘要）；**语义记忆**="知道的事实"（知识库/文档）。长期记忆通常**向量化存储 + 相似检索**，需要时召回进上下文。

**追问 1：长期记忆是不是"全塞进向量库"就行？**
> **答案：** 不是。要考虑**写入什么（非全量）、何时写、如何检索、何时遗忘**。全量写入=噪声爆炸、检索不准、成本飙升。好的设计有**筛选与沉淀**：只写有复用价值的信息，定期摘要/合并/淘汰——这正是 Q13 的主题。
**追问 2：为何不能把所有历史都留在上下文窗口当记忆？**
> **答案：** 窗口有限、成本高，长上下文有"中间遗忘"与注意力稀释。把长期内容外置、按需检索，等于给模型装了"可按需查阅的外部硬盘"，而非全背在身上——这是 context engineering 的核心思想（见 Part 5）。

## Part 3：核心区分度题（推理范式，定级主战场）

> **全题题眼**——能否把 Agent 当成"一套可设计、可权衡的控制流与认知架构"理解，直接决定 L2 还是 L3/L4。
> 主线：**循环是骨架，规划/反思是策略，记忆是经验，工具是接口，可靠性是工程**。

### Q9. ReAct / Plan-and-Execute / Reflection / RAG 的本质差异与适用场景？

**标准答案：** 四者解决**不同维度**的问题，非同一维度的竞品：

| 范式 | 解决什么 | 本质 | 适用场景 |
|------|---------|------|---------|
| ReAct | 边推理边行动 | 推理与工具调用交替的循环 | 路径未知、需探索 |
| Plan-and-Execute | 长任务组织 | 先规划后执行、可 replan | 步骤清晰、求成本效率 |
| Reflection | 输出质量 | 生成—评估—改进的迭代 | 写代码、需自我纠错 |
| RAG | 知识缺口 | 先检索外部知识再生成 | 最新/私域事实、减幻觉 |

**关键区分度**：ReAct/Plan-and-Execute 是**行动编排范式**（怎么走步骤），Reflection 是**质量改进范式**（怎么改好结果），RAG 是**知识注入范式**（怎么知道事实）。它们常**叠加使用**——"RAG 增强的、带 Reflection 的 ReAct Agent"完全合理。把它们当互斥选项说明理解停留在名词层。

**追问 1：为什么说 RAG 不是"一种 Agent"？**
> **答案：** RAG 只是"检索+生成"管道，不含自主循环与终止判断；它常作为**工具/知识层被 Agent 调用**。只有系统能自主决定"何时检索、检索什么、够不够、是否继续"时，RAG 才进入 Agent 循环。把 RAG 等同于 Agent 是常见混淆。
**追问 2：给一个"自动写 SQL 并验证"场景，怎么组合这些范式？**
> **答案：** 用 **Plan-and-Execute** 拆解（理解需求→查 schema→写 SQL→验证）；查 schema 用 **RAG/工具检索**；执行报错触发 **Reflection**（看报错→改 SQL→重试）；局部不确定处用 **ReAct** 边看边调。能这样组合，说明真懂各范式定位。

### Q10. Agentic Workflow 有哪几种模式？如何评价 Anthropic 的分类？

**标准答案：** （引用 Anthropic《Building effective agents》分类，**保守表述：业界有影响力的经验总结，非唯一标准**）
- **Prompt Chaining（提示链）**：固定顺序步骤，前一步输出作后一步输入——确定性高；
- **Routing（路由）**：先分类再分发到不同分支；
- **Parallelization（并行化）**：多个子任务并行再聚合；
- **Orchestrator-Workers（编排者-工人）**：一个 LLM **动态**拆分并分配 worker——"动态"是它与并行化的区别；
- **Evaluator-Optimizer（评估者-优化者）**：一个生成、一个评估反馈、循环改进——Reflection 的 workflow 化。

**核心洞察**：成功的系统多是**简单、可组合的模式**而非复杂框架；**先用最简单的方式，确实需要才加自主性**；workflow 提供确定性，agent 提供灵活性但代价更高。

**追问 1：Orchestrator-Workers 和 Parallelization 差在哪？**
> **答案：** **谁决定拆分**。Parallelization 的拆分**预定义固定**（把文章分3段并行总结）；Orchestrator-Workers 的拆分由 **LLM 动态决定**（现场决定要几个 worker、各做什么）。前者确定，后者灵活但更贵、不可预测。
**追问 2：这些模式是不是"越复杂越好"？**
> **答案：** 恰恰相反。Anthropic 强调**从简单开始**：chaining 能解决就别上 routing，workflow 能解决就别上自主 agent。每加一层自主性都带来成本、延迟和不可预测性。能答出"简单优先、按需加自主性"是成熟标志。

### Q11. Function Calling 的可靠执行依赖什么？schema、参数校验、错误处理如何设计？

**标准答案：** 可靠执行是**工程活**，三根支柱：
1. **Schema 设计**：清晰的 `name`/`description`（含适用场景与边界）、JSON Schema 参数、必填标注、枚举约束——描述越精确，选择与填参越准；
2. **参数校验（validation）**：宿主拿到 tool_call 后**绝不直接信任**，用 Pydantic/Zod 校验类型与必填、校验 id/范围、拒绝白名单外工具——这是不可信输入的"系统边界"；
3. **错误处理与回填**：执行失败时把**结构化错误信息**（如"订单号不存在，可选范围…"）回填，让模型据此纠正重试，而非静默失败或终止。

此外需**幂等性**（重复调用无副作用）、**权限控制**（最小权限）、**超时与重试**。

```text
tool_call → schema 校验 → 白名单/权限检查 → 执行 → 结果或错误
         → 统一格式回填 → 模型继续（成功前进，失败纠正）
```

**追问 1：为何校验必须在宿主侧，不能指望模型"填对"？**
> **答案：** 模型是概率生成，**没有"保证符合 schema"的硬约束**（structured output/coercion 也只是提高概率）；且参数可能来自被检索的不可信文本，有注入风险。宿主校验是不可妥协的安全边界——与"类型只覆盖编译期，边界另校验"同理。
**追问 2：工具执行"看似成功实则错误"怎么办？**
> **答案：** 加**结果校验器**：对返回值做语义/规则校验（返回空、数值异常、状态不符），当作观察反馈触发 Reflection。只信"调用没报错"是不够的——这是可靠性中易被忽略的一层。

### Q12. 多 Agent 协作有必要吗？开销在哪？什么时候不该用？

**标准答案：** 价值在**角色专业化与并行**：让不同 Agent 用不同 system prompt 与工具集，模拟团队分工，适合复杂、可分解、多视角任务（调研→撰写→审校）。但开销显著：**成本/延迟倍增**（通信与各自循环都烧 token）、**协调复杂**（交接、共识、冲突消解）、**错误传播**（一个 Agent 的幻觉被下游当真）、**调试困难**。结论：**单 Agent 能搞定就别上多 Agent**；很多"多 Agent 演示"只是用复杂度换噱头，不如一个组织良好的单 Agent 带几个工具。

**追问 1：多 Agent 和"单 Agent 内部多角色 prompt"有何区别？**
> **答案：** 后者在**同一上下文切换 system prompt/视角**（Reflection 里生成与评估用不同 prompt），共享记忆、无通信开销；前者是**独立上下文、独立循环**的实例。多数场景"单 Agent 多角色 prompt"性价比更高，真正需隔离（并行、不同工具权限）才用多 Agent。
**追问 2：怎么判断"该不该上多 Agent"？**
> **答案：** 问三点：① 任务是否**真能并行/分解**且子任务独立？② 是否需要**不同权限或工具集**隔离？③ 单 Agent 是否已因上下文污染而力不从心？三者都不是就别上。能用 orchestrator-workers 单 LLM 动态拆分的，往往比固定多 Agent 更灵活。

---

### Q13. 记忆的写入、检索、遗忘策略怎么设计？

**标准答案：** 长期记忆是**信息生命周期管理**：
- **写入（write）**：非全量记录，**筛选有复用价值的信息**（用户偏好、关键结论），先写"原始情节"再**摘要/提炼**成语义记忆，可在每轮结束或任务完成时写；
- **检索（retrieve）**：基于**语义相似度（向量）+ 元数据过滤（时间、类型）**按需召回，控制数量与相关性阈值，必要时 **rerank**，把最相关片段注入上下文；
- **遗忘（forget/consolidate）**：更常见是**整合**——把多条相关记忆合并成摘要；过时/低价值记忆降权、归档或淘汰，避免噪声累积。

核心矛盾：**记得太全→检索噪声大、成本高；记得太少→丢失关键上下文**，按"能否被检索到并真正用上"评估记忆系统。

**追问 1：向量检索的"相关性"一定可靠吗？**
> **答案：** 不一定。语义相似 ≠ 任务相关，可能召回"看着像但无用"的片段；纯向量对精确匹配（id、日期）也弱。生产常用**混合检索（向量+关键词 BM25）+ 元数据过滤 + rerank**，并用评估集验证"该召回的有没有召回"。
**追问 2：多用户/多会话场景要注意什么？**
> **答案：** **隔离与权限**：记忆按 user/session 命名空间隔离，防串味与隐私泄露；写入前做隐私过滤（不存敏感信息）。这是记忆系统从 Demo 到 production 的关键工程要求。

## Part 4：实战与陷阱题（失效模式与可靠性）

### Q14. 讲一个 Agent 跑飞/死循环/烧钱的排查思路，"卡循环"根因有哪些？

**标准答案：** 排查遵循"**先止血、再定位、后加固**"：① **止血**：确认有 max steps/预算/超时护栏，必要时 kill 进程、撤销副作用；② **可观测性**：拉完整 trace——每步 Thought、tool_call 参数、Observation、耗时、token，看从哪步开始不再逼近目标、是否重复同一调用；③ **定位**：按根因分类；④ **加固**：补护栏+停滞检测+改进工具描述与错误回填+缓存去重。

**"卡循环"根因**：目标不可达（工具能力不足/信息缺失）、缺进展检测（A→B→A）、反馈含糊、规划缺陷（依赖成环/replan 生成同样计划）、终止条件单一。对策：硬护栏 + 停滞检测（连续 N 步无新信息则中止/换策略）+ 明确错误回填 + 进展度量 + 升级机制（转人工/降级为工作流）。**信号**：同工具高频重复、token 速率异常、上下文暴涨、步数远超基线。

**追问 1：为何"可观测性（tracing）"是排查前提？**
> **答案：** Agent 非确定，没 trace 就是黑盒，无法复现"它当时为什么那么做"。要记录**每步输入输出、工具参数、决策依据、成本**并支持回放。LangSmith、Langfuse 等就是干这个的——**没有 tracing 的 Agent 上生产等于蒙眼开车**。
**追问 2：如何烧钱前就预警？"让它再多想几步"通常有效吗？**
> **答案：** 预警：设**实时预算与速率监控**（单任务 token/成本上限、异常增长告警、单步耗时阈值），对昂贵工具限频与缓存，把成本当一等公民纳入监控。而"多想几步"大多无效——若目标不可达或策略错，只会多烧钱。应先**诊断卡住类型**：信息不足（补工具/检索）、策略错（replan/换范式）、目标无解（升级人工）。盲目加大 max steps 是典型反模式。

### Q15. 工具参数幻觉（编造 id/参数）如何缓解？

**标准答案：** 多层防御：① **减少编造机会**：参数尽量**来自上游真实数据**（检索结果、用户输入、前序工具返回），把可用 id 列表放进上下文并明确"只能从中选"；② **Schema 约束**：必填、类型、枚举、`additionalProperties: false`，配合 structured output；③ **宿主强校验**：白名单/存在性校验、范围校验，失败回填具体错误让其重试；④ **给工具"反幻觉"能力**：提供"搜索/列举"工具让模型先查到真实 id 再用；⑤ **高危操作二次确认**：删除/支付/写库加人工确认或 dry-run。**本质：不指望模型"不幻觉"，而是靠系统设计让幻觉无法造成危害。**

**追问 1："让模型只从给定列表选 id"能根治吗？**
> **答案：** 不能根治，只降低概率。模型仍可能忽略约束或选错，必须配合**宿主校验**（id 确在列表/库里）+ **失败回填重试**。把"约束"当提示而非保证，是工程上的成熟心态。
**追问 2："查到了错误对象的数据"比"调用失败"更危险，怎么防？**
> **答案：** 这类"静默错误"最棘手。对策：① **结果校验**：返回对象关键字段（用户名/订单状态）与上下文交叉核对；② **高风险只读后再写**：先查详情确认再执行写操作；③ **最小权限**：工具无越权能力；④ **审计日志**：带副作用的调用可追溯、可回滚。

### Q16. 上下文膨胀导致"遗忘早期指令"是怎么回事？怎么解？

**标准答案：** 循环累积使上下文塞满历史观察，出现：① **成本/延迟上升**（每轮重发全部历史）；② **"Lost in the middle"**：模型对长上下文中部注意力下降，早期关键约束（"只查2024年数据""不要写库"）被淹没；③ **目标漂移**：最初任务被细节稀释。对策（属 context engineering）：**压缩/摘要**（保留目标、约束、关键决策，压缩过程细节）、**滑动窗口**（最近 N 轮 + 目标常驻）、**外置记忆**（详细历史写外部存储按需召回，见 Q8/Q13）、**关键约束置顶/复述**、**结构化 state**（关键变量用结构化状态记录而非散落对话里）。

**追问 1：摘要压缩会不会丢信息？**
> **答案：** 会，所以要有策略：**任务目标、约束、关键决策、未解决问题必须保留**，纯过程性细节可压缩，并让模型生成摘要后做"关键信息校验"。摘要是"有损压缩"，要清楚什么不能丢。
**追问 2：换更大上下文窗口的模型能解决吗？**
> **答案：** 只能缓解不能根治。窗口再大也有注意力分布问题，且成本更高。正解仍是**主动管理上下文**——只放相关信息、关键指令放首尾显著位置、外置海量历史。这正是 2026 年"context engineering"被强调为独立工程学科的原因（见 Part 5）。

---

### Q17. 反思机制什么情况下反而放大错误？什么时候不该用 Agent？

**标准答案：** **Reflection 放大错误的情形**：① **评估器本身错了**（LLM-as-a-judge 误判，把对的改错，尤在主观/模糊任务）；② **缺客观真值**（写作、策略类无明确对错，反思可能迎合评审偏好而偏离需求）；③ **错误被固化进记忆**（一次错误反思写成"经验"被反复引用，雪球式污染）；④ **循环自我强化**（生成器与评估器同一模型同一偏见，"回音室"互相确认错误）；⑤ **成本/延迟叠加**（为微小改进付出不成比例代价）。对策：**优先客观校验器**、评估器与生成器**解耦**、反思写入记忆前**先用真值验证**、设次数上限与"无实质改进则停"的早停。

**不该用 Agent 的场景**：任务确定步骤固定（数据管道、格式转换——workflow 更可靠可复现且便宜）、高风险需强一致（金融/医疗——不确定性不可接受）、低价值高频、对延迟极敏感、无法定义成功判据。**判断原则：先看能否用确定性代码/工作流解决，只有"路径未知、需推理适应、出错可承受"才上 Agent。**

**追问 1：为何"用同一模型自我评估"有局限？**
> **答案：** 同一模型往往共享相同知识盲区与偏见，"看不出自己错在哪"（像人难自查作文）。有效的 Reflection 常引入**外部信号**：单元测试、独立模型、不同视角 prompt、工具返回的客观事实。
**追问 2："我们的流程有点复杂"是不是就该上 Agent？**
> **答案：** 不是。复杂 ≠ 需要自主。很多复杂流程是**已知分支多**，用 workflow/状态机更可靠。真正需要 Agent 的是**无法预先枚举路径、需 LLM 现场判断**的情形。可**从 workflow 起步，只在确实需要灵活的环节局部替换为 Agent 节点**（分类用 workflow，异常 case 交 Agent），并度量是否真提升成功率再扩大范围。

### Q18. 如何评估 Agent 真的"更聪明"，而非只是"更复杂/更贵"？

**标准答案：** 必须用**结果导向的可量化评估**，而非 Demo 观感：**任务成功率**（固定测试集上完成目标的比例，最核心）、**对比基线**（与单轮 LLM/workflow/更少工具的单 Agent 做 A/B，看复杂度是否换来提升）、**效率指标**（步数、token/成本、延迟——"聪明"不能以成本翻倍为代价）、**可靠性**（失败率、幻觉率、循环失控率）、**质量**（客观校验/人工评分、是否遵循约束）。还要建**可复现评估集与自动评测（eval harness）**，每次改动回归测试——**没有 eval 就无法区分"进步"与"变异"，评估驱动是 Agent 工程区别于 Demo 的核心**。

**追问 1：为何"Demo 看起来很智能"不能作为依据？**
> **答案：** Demo 常是精心挑选的成功案例（幸存者偏差），且流畅的自然语言掩盖错误率与成本。只有大规模、可复现的测试集 + 量化指标才能反映真实能力。
**追问 2：评估 Agent 和评估普通 LLM 有何不同？**
> **答案：** Agent 还要评估**过程与系统属性**：不只看最终答案，还看**轨迹（trajectory）**——工具选择是否正确、步骤是否合理、有无多余循环、成本是否可控。"蒙对答案但过程乱来"的 Agent 不可靠。所以 Agent 评估 = 结果评估 + 轨迹评估 + 成本/可靠性评估。

## Part 5：2026 新趋势（加分题）

> 考察技术视野。**以下为方向与业界讨论，以官方资料和实际演进为准，保守表述即可；不编造具体版本号/基准分数。**

### Q19. "推理模型作为 Agent 大脑"与"Context Engineering"各指什么？

**标准答案：** **推理模型（reasoning model）作为大脑**：以具备更长"思考链"（extended thinking）的模型作决策核心，在**规划、任务分解、工具选择和自我纠错**上更强，能"想清楚再动手"；代价是思考 token 更多、延迟成本更高，需在"该深思的节点"才启用。**保守表述**：这是重要方向，能力持续演进，具体表现因模型与任务而异。**Context Engineering（上下文工程）**：把"给模型看什么上下文"当作**核心工程管理对象**——系统性设计如何**选取、压缩、组织、注入**信息（指令、历史、工具描述、检索结果），让有限窗口内都是高价值信息。它被视为 Prompt Engineering 的演进：从"写好一句话"上升为"设计整个信息供给系统"，核心思想与 Q16 一脉相承——**上下文是稀缺资源，要主动经营**。

**追问 1：推理模型"想得更久"一定更好吗？**
> **答案：** 不一定。长思考适合复杂规划与调试，但简单任务上纯属浪费。关键在**按任务难度动态分配思考预算**，把深思留给关键决策节点。盲目全程深思考是资源浪费。
**追问 2：Context Engineering 和 Prompt Engineering 是替代关系吗？**
> **答案：** 不是替代，是**范围扩展**。Prompt engineering 关注具体指令文案；context engineering 关注整个上下文生命周期（系统提示、记忆、工具定义、检索内容、历史压缩、多轮状态），强调**系统性、可度量、可迭代**。

### Q20. Agentic RAG、Computer-Use Agent、Long-running Agent、多 Agent 编排近年有哪些演进？

**标准答案：** （保守表述，谈方向不编数字）
- **Agentic RAG**：从"一次性检索→生成"升级为 **Agent 自主决定何时检索、检索什么、多源检索、评估结果是否足够、不够则继续**——把 RAG 变成循环中可调用、可迭代的能力，而非固定前置管道；
- **Computer-Use Agent（CUA）**：让 Agent **操作图形界面（点击、输入、截图理解）**使用软件，无需专门 API，覆盖无 API 的遗留系统，但可靠性、速度、安全（误操作）仍是挑战，处于快速演进中，保守看待其成熟度；
- **Long-running Agent 与 checkpoint/恢复**：面向数小时/数天的长任务，依赖**状态持久化、checkpoint、断点续跑、事件驱动唤醒**，核心是"把长任务拆成可持久化的状态机"，而非单个无限循环；
- **多 Agent 编排框架**：从早期对话式多 Agent 向**编排、状态机、有向图（graph）**演进，强调**可控、可观测、可恢复**，业界也在收敛到"简单可组合模式优先"的务实路线（呼应 Q10）。

**追问 1：为何"长时运行 Agent"不能靠把上下文无限拉长实现？**
> **答案：** 窗口、成本、注意力都有限，且进程可能中断。正解是**架构层解决**：把长任务建模为**持久化状态机 + checkpoint**，每步状态可落盘、可恢复；上下文只加载当前所需片段，其余外置。这是从"一个 while 循环"到"分布式工作流"的思路跃迁。
**追问 2：面对新趋势如何不被炒作带偏？**
> **答案：** 回到第一性原理：这个方向**解决了什么根本问题**（知识时效/无 API 系统/长任务/复杂度管理）？**代价与成熟度如何**？是否适用当前场景？能结合主线（循环/规划/记忆/可靠性）分析新趋势本质而非堆砌名词，是 L5 视野的体现。

## Part 6：能否用 Agent 架构定级？如何定级？

### 结论先行

**可以，Agent 是当前区分度极高的探针**——天然分层：会说是 Agent 什么 → 懂工具调用与 ReAct → 讲清 Agent Loop 控制流与规划/反思取舍 → 有生产落地与可靠性经验 → 能做架构选型与跟进演进。但"会调框架写 Demo"门槛很低，**对初中级强问多 Agent 编排只会考到背诵名词**；结合岗位：初中级问到 Part 1/2 即可，推理范式与可靠性题留给中高级。

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 能说清 Agent 是什么、四要素，会写简单循环/调一次工具；讲不清循环控制流与失效模式 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂 Function Calling 的"意图+外部执行"、ReAct、记忆分层、终止与预算控制 |
| **中高级（L3）** | 5–8 年 | Part 3 | 讲清 Agent Loop 控制流与规划/反思/记忆机制取舍，能辨析各推理范式、设计可靠工具调用 |
| **高级（L4）** | 8 年+ | Part 4 | 有真实 Agent 落地，处理过循环失控/成本/上下文膨胀/参数幻觉，能用 eval 量化效果 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 能做架构选型（Agent vs workflow、单 vs 多 Agent）、设计记忆体系、跟进新趋势并务实判断 |

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"四要素 + while loop + 工具调用意图与执行分离 + 失效模式"→ 至少 L3 候选；只会说"Agent 就是让 LLM 调工具、写个循环"→ 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"：工具调用为何不等于模型执行代码？为何必须有预算控制？ReAct 与 Plan-and-Execute 如何取舍？Reflection 为何会放大错误？为何多 Agent 不一定更好？

**第三步：三类信号防背题。** ① **真实性**：能否结合真实项目讲"踩过什么坑、怎么排查、怎么加固"；② **抽象能力**：能否把零散概念统一为"**循环是骨架，规划/反思是策略，记忆是经验，工具是接口，可靠性是工程**"主线；③ **权衡能力**：能否讲清"何时不该用 Agent"、单 vs 多 Agent 取舍、Reflection 边界。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整追问深度：业务开发问到 Part 3 足够，AI 平台/基础设施团队才需 Part 4 可靠性与 Part 5 视野。

### 面试官避坑提醒

- **不要对所有人问到多 Agent 编排级**——区分"理解 Agent 运行机理"与"背过框架名词"，前者更有价值。
- **把"讲清 Agent Loop 控制流 + 一个真实可靠性案例"作为 L4 分水岭**：能结合 trace 讲清一次循环失控的排查加固，一定是真落地过的人。
- **务必问"不该用"**：只堆工具、讲不出代价与何时该用工作流的，通常停在 L2/L3——识别"炫技型"候选人的关键。
- **结合岗位**：业务开发问到 Part 3 即可；AI Infra / Agent 平台团队需要 Part 4 可靠性与 Part 5 深度。

## 附录：面试官速查表（一页纸）

**递进主线（照着问）：**
1. Agent 是什么？→（LLM 大脑+工具手脚+循环神经+记忆经验；自主规划多步达成目标）
2. 与 workflow/chatbot/RPA 区别？→（workflow 人定路径，Agent 机器找路径；光谱非对立）
3. 四要素？→（规划、工具、记忆、执行循环；循环是神经中枢、最易被忽略）
4. Function Calling？→（输出结构化调用意图，宿主执行并回填；模型不执行代码）
5. 幻觉式工具调用？→（参数/工具/能力幻觉；语言生成与精确调用的鸿沟）
6. ReAct？→（Thought/Action/Observation 交替，边想边做；思维痕迹非忠实审计）
7. Agent Loop 控制流？→（接收→规划→选工具→执行→观察→判断→终止；终点+护栏）
8. 终止/预算/工具选择？→（硬上限+停滞检测；工具选择是 prompt 工程）
9. 规划与 Plan-and-Execute vs ReAct？→（灵活性换成本 vs 效率换刚性；可 replan）
10. Reflection？→（生成—评估—改进；客观校验器优先，评估器需解耦）
11. 记忆分层？→（短期=上下文=工作记忆；长期=向量库=情景/语义；写入/检索/整合）
12. 推理范式差异？→（行动编排 vs 质量改进 vs 知识注入；可叠加非互斥）
13. Agentic Workflow 模式？→（chaining/routing/parallel/orchestrator-workers/evaluator-optimizer；简单优先）
14. 可靠性？→（schema/校验/错误回填；参数幻觉；上下文膨胀；反思放大错误；eval 量化）
15. 新趋势？→（推理模型大脑、context engineering、Agentic RAG、CUA、长时 checkpoint；保守表述）

**定级速判：**
- 答到第 2–6 问 → L2
- 答到第 7–11 问 + 能讲清控制流与范式取舍 → L3
- 答到第 12–14 问 + 有落地案例、能排查可靠性问题 → L4
- 答到第 15 问 + 团队级架构选型与演进视野 → L5

**一票否决信号：** 认为"Agent 就是 while 循环调 LLM、没什么技术含量"、"给足工具就一定比工作流好"、"Function Calling 等于模型真的在执行代码"、"记忆就是全塞进 prompt"、说不清循环控制流与终止条件 → 无论年限，最高 L2。
