## Part 0：30 秒标准总答

**Q：谈谈你对 Agent 评测与可观测性的理解。**（标准答法 30 秒，五个得分点）

> LLM/Agent 的输出是**概率性**的、执行**路径不固定**，传统"输入→断言输出等于期望"的单元测试**失效**——没有唯一正确答案，同一个问题两次调用结果可能不同。
> 因此要建一套**质量闭环**：离线有**评测集（eval set）+ 指标（含 LLM-as-judge）**打分，运行有 **Trace 可观测**记录每一步，迭代有**回归测试**防退化，线上有**监控**看真实分布。
> 评测对象是**多元**的：不只看最终答案，还要看**中间轨迹、工具调用、以及成本与延迟**。
> 全程要权衡**质量—成本—延迟三角**：不能为刷质量分数堆资源，也不能只看分数不顾线上体验。
> 最终要能区分"靠感觉说效果不错"和"有**可复现的评测体系 + 线上定位能力**"——后者才是工程化。

**评分要点：** 非确定/无唯一答案/路径不固定 / 质量闭环（评测集+指标+Trace+回归+监控） / 多维对象（答案+轨迹+工具+成本延迟） / 质量成本延迟权衡 / 可复现与线上定位五点。能说出"LLM-as-judge"和"trace 定位"的，直接往 Part 2/3 追问。

## Part 1：基础认知题

### Q1. 为什么传统单元测试不适用于 Agent？评测的基本单位是什么？

**标准答案：** 传统单测假设**给定输入有确定输出**，可写 `assert(output === expected)`。Agent 三点不满足：① **输出非确定**——同一 prompt 两次调用结果不同（采样温度、模型版本）；② **没有唯一正确答案**——开放任务"写一段总结"无法精确断言；③ **多步路径**——Agent 自主规划、循环调用工具，每次走的轨迹不同。所以断言要从"精确相等"变成**评分器打分 + 阈值 / 不变量校验**（如"必须调用了检索工具""答案需忠实于检索内容""成本不超预算"）。评测的**基本单位**：**数据集（dataset）**=一批测试用例；**测试用例（case）**=输入 + 期望/评分标准；**评分器（scorer/metric）**=把输出映射成分数的函数。

**追问 1：那 Agent 就完全没法自动化测了吗？**
> **答案：** 能，但断言形式变了：对**有唯一答案**的部分（格式、工具名、参数、数据库写入）仍用**精确匹配/规则**；对**开放语义**部分用 **LLM-as-judge** 打分或**相对比较**；再加**不变量**（步数上限、无循环、无违规工具调用）。自动化程度不低，只是"断言"升级成"评分器"。

**追问 2：可观测性（observability）和评测（evaluation）是什么关系？**
> **答案：** 评测回答"**好不好**"（打分），可观测回答"**哪一步、为什么**"（记录全链路）。评测消费 trace 提供的数据——没有 trace 只能看最终文本打分；trace 也是线上定位与监控的数据源。二者共享同一套埋点，是可复现评测的前提。

---

### Q2. 评估一个 Agent 到底该看哪些对象？只看最终答案够吗？

**标准答案：** 看四层：① **最终答案**（是否正确、有用、切题）；② **中间轨迹（trajectory）**（步骤顺序是否合理、有无绕路/冗余）；③ **工具调用（tool call）**（工具选对没、参数对不对、调用次数是否合理）；④ **系统指标**（成本 token/$、延迟、成功率）。只看最终答案会漏掉两类问题：**"蒙对"**（过程错但结果碰巧对，下次不复现）和**"结果对但代价高"**（靠反复试错/堆 token 换来的答案，不可上线）。

**追问 1：什么叫"轨迹正确性"（trajectory correctness）？**
> **答案：** 指 Agent 的步骤序列与工具选择**符合预期逻辑**。可用参考轨迹比对（step-level match），或让 judge 评估"每一步是否必要、顺序是否合理"。它比只看结果更能解释"为什么对/为什么错"。

**追问 2：为什么成本、延迟也要当成评测对象？**
> **答案：** Agent 容易出现**循环调用**和**上下文膨胀**，让 token 成本、延迟指数级上升——效果达标但成本/延迟不可接受就上不了线。所以评测报告必须同时给出质量分与成本/延迟，做联合判断。

---

### Q3. Trace 和日志（log）有什么区别？为什么说 trace 是评测的"数据底座"？

**标准答案：** **log** 是离散、无结构的事件流水；**trace** 是一次请求的**全链路 span 树**：有 `trace_id` 贯穿、有父子因果与时序关系，每个 span 记录一步（LLM 调用、工具调用、检索）的输入、输出、耗时、token、错误。评测要复现和归因，必须知道"输入 → 中间发生了什么 → 输出"，这些都在 trace 里——**没有 trace，分数低时无法定位哪一步错，也无法改进**。线上监控本质是对大量 trace 的聚合。

**追问 1：没有 trace 的评测有什么局限？**
> **答案：** 只能**黑盒打分**：知道"这次不好"，但不知道是检索没召回、规划跑偏、工具报错还是生成幻觉，于是改 prompt 只能靠猜；线上出问题也无法复现当时的上下文。

**追问 2：一个 span 应该记录哪些字段？**
> **答案：** 至少：`span_id`/`parent_id`/`trace_id`、名称与类型（llm/tool/retrieve）、`input`/`output`、开始时间与 `duration`、`tokens`/`cost`、状态/错误、模型或工具名。字段越完整，评测与归因越有力（详见 Q7 的结构示意）。

## Part 2：原理题（评测集、指标与 Tracing）

> "知道要看效果"和"能搭出评测体系"的分水岭，L2→L3 的关键。

### Q4. 评测集（eval set）怎么构建？有哪些来源和原则？

**标准答案：** 来源四类：① **真实样本**——线上日志采样，最贴近真实分布；② **人工标注**——给出 golden answer / label 作为金标准；③ **边界与对抗用例**——corner case、歧义、越狱、超长输入；④ **持续积累**——线上 bad case 回流。原则：**代表性**（贴近真实分布）、**覆盖度**、**可复现**（固定评测集版本）、**去污染**（不能让被测模型见过测试题）。一个 case 通常含：输入、上下文、评分标准/期望、元数据（场景标签、难度）。

**追问 1：为什么反复强调"真实分布"？**
> **答案：** 评测集若由工程师凭空想出来，和线上 query 分布偏差大，就会出现"评测高分、线上效果差"（Part 4 Q12）。所以真实样本优先，并定期从线上回流刷新。

**追问 2：评测集会"污染"或"过时"怎么办？**
> **答案：** 用 **holdout 隐藏集**（不公开、不用于迭代）做最终验收；测试题绝不写进 prompt/示例；随版本推进定期刷新、淘汰过时样本，并保留历史版本以做纵向对比。

**追问 3：标注质量怎么保证？**
> **答案：** 关键 case 采用**多人独立标注**，计算标注者间一致率（如 Cohen's kappa），分歧样本讨论后合并成标注规范；golden 质量直接决定评测上限，标注本身也要抽检质检，否则 judge 校准也失去基准。

### Q5. 评分方法有哪些？精确匹配、LLM-as-judge、人工评估各自适用与偏差？

**标准答案：**

| 方法 | 适用 | 优点 | 偏差 / 成本 |
|------|------|------|-------------|
| 精确匹配 / 规则校验 | 有唯一答案、格式、工具参数、数据库写入 | 快、客观、可复现 | 只覆盖可形式化的部分，语义无能为力 |
| **LLM-as-judge** | 开放任务、无标准答案、语义质量 | 可扩展、覆盖语义 | 位置/长度/自我偏好，需校准 |
| 人工评估 | 金标准、校准 judge | 最可信 | 贵、慢、难规模化 |

原则是**能用规则就别用 judge**：客观部分规则更准更便宜，开放语义才用 judge，人工用于抽样校准 judge。评分器伪代码：

```python
def evaluate(case, out, trace):
    s = {}
    if case.has_golden:
        s["exact_match"] = exact_match(out.final, case.golden)   # 规则
    s["tool_accuracy"] = rule_check(trace.tool_calls, case.expected_tools)
    s["faithfulness"]  = llm_judge(RUBRIC_FAITHFUL, case.context, out.final)  # judge
    s["cost"]          = sum(sp.tokens_cost for sp in trace.spans)
    s["latency_ms"]    = trace.root.duration_ms
    return s   # 多指标一起看，绝不只看单一分数
```

**追问 1：什么时候绝不该用 LLM-as-judge？**
> **答案：** 有明确客观答案时（规则更准、更便宜、更稳定）；以及 judge 本身不可信、未与人工校准过时——此时 judge 的分数没有意义。

**追问 2：三种方法怎么组合？**
> **答案：** 规则兜底（客观项）+ judge 规模化打分（语义项）+ 人工抽样校准（验证 judge 与人的一致率）。三者互补，形成可伸缩又有可信度的评分体系。

**追问 3：多个维度的分数怎么聚合成最终结论？**
> **答案：** 可按权重合成总分，但更推荐**分维度报告 + 关键项门控**：如忠实度低于阈值直接判失败，避免"总分达标但致命项不及格"被平均掉；同时报告分数分布而非只报均值，便于发现长尾失败。

### Q6. RAG 和 Agent 场景分别有哪些具体指标？

**标准答案：** 分层看：检索层看"相关文档有没有被召回、排得好不好"，生成层看"是否忠于检索内容、是否切题"，Agent 层看"任务成没成、轨迹对不对、工具用得准不准"，系统层看成本延迟。RAGAS 这类框架把忠实度与相关性拆成独立指标。

| 层次 | 指标 | 含义 |
|------|------|------|
| 检索（RAG） | recall@k / precision@k / MRR / NDCG | 相关文档是否召回、排序质量 |
| 生成（RAG） | **faithfulness** / answer relevancy | 是否忠于检索内容 / 是否切题（RAGAS） |
| Agent 任务 | task success rate | 任务是否完成（终态判定） |
| Agent 轨迹 | trajectory correctness | 步骤顺序、工具选择是否合理 |
| Agent 工具 | tool call accuracy | 工具选择、参数、次数的正确率 |
| 系统 | latency / cost / steps | 延迟、token/费用、步数 |

**追问 1：忠实度（faithfulness）和相关性（relevancy）为什么要分开？**
> **答案：** 两者可独立失效：答案**相关但幻觉**（说得像那么回事却不基于检索内容，忠实度低）；或**忠实但答非所问**（照抄检索片段却不回答用户问题，相关性低）。只报一个"答案质量分"会掩盖问题。

**追问 2：recall@k 的 k 怎么定？**
> **答案：** 权衡：k 太小易漏召回，k 太大把噪声塞进上下文、增成本且干扰生成。应结合下游任务与上下文窗口，用评测集实测不同 k 的效果/成本曲线来定。

**追问 3：为什么还要看 NDCG / MRR 这类排序指标，而不只是 recall？**
> **答案：** recall 只看"相关文档有没有被召回"，不管顺序；但 Agent 通常只把 Top-k 塞进上下文，**排在前面的相关文档才真正被用上**。NDCG/MRR 衡量排序质量——相关文档是否排在靠前位置，直接决定生成质量。

### Q7. Tracing 的原理是什么？trace/span 树怎么组织？离线评测与在线评测有何区别？

**标准答案：** 一次用户请求生成一棵 **trace 树**：每个 **span** 代表一步（一次 LLM、工具、检索调用），记录输入/输出/耗时/token/错误，通过 `parent_id` 形成父子关系，`trace_id` 贯穿全链路。结构示意：

```
trace_id: t-8f3a  (一次用户请求)
└─ span: agent.run              [1200ms, 4200 tok, $0.06]
   ├─ span: llm.plan            [ 320ms] in="用户问题" out="先检索再回答"
   ├─ span: tool.retrieve       [ 180ms] in={query} out=[doc1,doc2,doc3]
   │   └─ 检索评测: recall@3 = 0.67
   ├─ span: llm.answer          [ 650ms] in=docs+query out="最终答案"
   │   └─ judge: faithfulness = 4/5
   └─ span: tool.format         [  50ms]
```

**离线评测**：上线前在固定评测集上跑，可控、可复现，用于回归把关；但分布可能滞后。**在线评测**：用生产真实流量，看真实分布，靠 A/B、灰度、线上监控；但反馈有延迟、缺标注。二者互补：离线防回归、在线验真实效果并把 bad case 回流评测集。

**追问 1：trace 树如何帮助定位"是哪一步错了"？**
> **答案：** 逐 span 检查：每个 span 的输入是上一步输出，找到**第一个"输入对但输出错"的 span**，就定位到根因环节（检索错/规划错/工具错/生成错，见 Q11）。只看最终答案无法归因。

**追问 2：在线没有人工标注怎么做评测？**
> **答案：** 靠**隐式信号**（重试率、点踩、任务完成率、会话放弃）+ **抽样人工复核** + **线上轻量 judge**，并把高频 bad case 回流成新的评测用例，形成闭环。

**追问 3：高流量下全量采集 trace 太贵怎么办？**
> **答案：** 采用**采样**——按比例采样、对错误/慢请求优先保留、关键链路全量；设置 retention 期限与聚合统计。要在"出问题时能定位"与"存储成本"间权衡，而非要么全留要么全丢。

## Part 3：核心区分度题（定级主战场）

> **全题题眼**——能否把"概率性系统的质量工程"当成一套可复现体系来做，直接决定 L2 还是 L3/L4。
> 主线：**评分可信度 → 无标准答案的处理 → 多目标权衡 → 归因定位 → 评测驱动流程**。

### Q8. LLM-as-judge 可靠吗？有哪些偏差，怎么缓解？

**标准答案：** judge 不是绝对客观的"裁判"，有系统偏差：① **位置偏差**——成对比较中偏向某个展示位置；② **长度偏好**——倾向给更长、更详细的答案高分；③ **自我偏好**——偏好自己（同系列）模型生成的内容，跨模型比较失真。缓解：**成对比较 + 交换位置/随机化**消除位置偏差；在 rubric 中明确"不要因长度加分"；**多评委投票**或用更强模型；**用人工标注校准**——计算 judge 与人的一致率/相关性，定期回归验证；对客观项退回规则。

**追问 1：怎么判断一个 judge 本身可信不可信？**
> **答案：** 拿一批已人工标注的样本，算 judge 与人工的**一致率、相关系数（如 Cohen's kappa）**；按场景分组看是否对某类样本系统性偏高/偏低。达不到阈值就调 rubric 或换 judge——**judge 自己也要被评测**。

**追问 2：为什么"自我偏好"特别危险？**
> **答案：** 用某模型评它自己或同系模型的输出会系统性打高分，导致 A/B 对比时"自家模型永远赢"，评测结论失真。要用跨模型评委或人工校准来破除。

**追问 3：多个评委打分不一致怎么办？**
> **答案：** 先看分歧是否集中在某些维度/样本，用多数投票或取中位数聚合；分歧大的样本交人工裁决并反哺 rubric；必要时换更权威的 judge。关键是**别假装分歧不存在**，把分歧率本身当作 judge 质量的信号。

---

### Q9. 如何评测"没有标准答案"的任务？

**标准答案：** 开放任务（创意写作、开放问答、总结）没有唯一正确答案，思路是：① 用 **rubric（评分量规）**定义多个**可观察的质量维度**（相关性、完整性、事实性、语气、格式），每个维度分级并给锚点样例；② 用 **LLM-as-judge 按 rubric 打分**；③ 更稳的是**成对比较（pairwise）**——问"A 和 B 哪个更好"，相对判断比绝对打分更稳定、更少漂移；④ 有参考回答时做参照对比；⑤ 用人工校准。核心是**把模糊的"好不好"拆成可判定的维度**，而不是找"标准答案"。

**追问 1：绝对打分（absolute scoring）和成对比较（pairwise）哪个好？**
> **答案：** pairwise 通常**更稳定**（人/模型更擅长比较而非给绝对分），适合 A/B 选优；但只能得相对结论、难设绝对质量阈值。absolute 能给阈值但分数易漂移。常结合用：pairwise 选版本，absolute + 校准判达标。

**追问 2：rubric 怎么设计才不流于形式？**
> **答案：** 维度要**清晰、可观察、互斥**，每级配**具体锚点样例**（什么叫 3 分、什么叫 5 分），避免"质量高/低"这种主观词；再用人工标注验证 judge 按 rubric 打分的一致性，不一致就改 rubric。

**追问 3：用参考回答做对比有什么风险？**
> **答案：** 参考回答只是**一个样例**，可能**限制多样性**（把有创意但不同的正确答案判低），也可能本身就带错。应把它当"锚点之一"而非唯一标准，配合 rubric 的多个维度综合判断。

### Q10. 什么是评测集过拟合（针对测试优化）？质量—成本—延迟三角怎么权衡？

**标准答案：** **评测集过拟合**：团队反复针对固定评测集调 prompt，甚至把题写进示例，导致分数虚高而真实效果没提升——典型**古德哈特定律（Goodhart's law）**"指标一旦成为目标就不再是好指标"。缓解：**holdout 隐藏集**验收、定期刷新评测集、用线上分布校验、看多指标而非单一分数。**三角权衡**：更强模型/更多步数往往提质量但增成本与延迟；评测必须**同时报告质量、成本、延迟**，看帕累托前沿而非单看质量——靠堆资源刷出来的高分不可上线。

**追问 1：怎么发现团队在"刷分"？**
> **答案：** 看**背离信号**：评测分持续涨但线上任务成功率/满意度不涨；holdout 集表现远低于公开集；换一批真实样本分数骤降。这些都是过拟合的强信号，要立刻用真实分布重建评测集。

**追问 2：怎么在三角里做优化而不牺牲质量？**
> **答案：** **模型分级路由**（简单任务用便宜小模型、难题才升级）、**缓存**重复调用、**压缩上下文**去冗余、设置**步数/预算上限与早停**。本质是把预算花在真正影响质量的步骤上。

**追问 3：预算意识怎么落到评测报告里？**
> **答案：** 每次评测都**并列报告质量分、平均 token/费用、p95 延迟、平均步数**，并画出"质量随成本变化"的曲线，让"提分是否靠堆资源"一眼可见，为上线与模型选型提供决策依据。

### Q11. 如何用 trace 定位"是哪一步错了"？A/B 与灰度怎么做？evals-first 是什么？

**标准答案：** **定位**：沿 span 树逐层检查——检索 span（召回内容相关吗）、规划/LLM span（下一步决策合理吗）、工具 span（参数与返回符合预期吗）、生成 span（是否忠实、有无幻觉），找到第一个"输入对、输出错"的 span 即根因环节，可对**中间步骤也打 eval 分（step-level eval）**。**A/B / 灰度**：线上流量分桶对比新旧版本、小流量逐步放量，看任务成功率、满意度、成本、延迟，并设 **guardrail 阈值**触发回滚。**evals-first**：**先建评测集再改 prompt**，用评测分数驱动迭代，而不是先改完再"感觉更好"。

**追问 1：为什么说要找"第一个出错的 span"？**
> **答案：** 错误会**级联**——检索错了后面全错。若只看最终答案，看到的是"生成幻觉"，但根因可能是"检索没召回"。定位到最早出错的环节，才能对症下药，避免改错地方。

**追问 2：Agent 的 A/B 和普通 Web A/B 有什么不同？**
> **答案：** Agent 结果**有延迟、缺明确转化指标、输出质量需 judge 评估**，且成本/延迟会随流量线性放大。所以要结合隐式信号 + 抽样 judge + 成本延迟 guardrail，不能只看点击率类指标。

**追问 3：step-level eval 具体怎么做？**
> **答案：** 对每个中间 span 也定义评分器（如检索相关性、工具参数正确性、规划合理性），把分数随 trace 一起存；失败可按步骤聚合统计，快速看出"哪类步骤最常出错"，把改进精力投向高频失败环节。

## Part 4：实战与陷阱题（真实 case 排查）

### Q12. 案例：上线后效果差，但评测分数很高，怎么排查？

**标准答案：** 头号原因是**评测集不代表真实分布**：① 采样偏差——评测集是工程师想出来的、偏简单；② 过拟合——针对评测集优化甚至泄漏；③ 陈旧——没跟上线上新 query 类型。排查步骤：对比线上 query 分布与评测集分布；查 holdout 集表现；抽样人工看线上 bad case 并归因；检查是否刷分/泄漏；用 trace 定位真实失败案例错在哪一步。解决：**用线上真实样本重建/刷新评测集**，把 bad case 回流，并在线持续监控。

**追问 1：为什么"评测高、线上差"最常见？**
> **答案：** 因为离线评测集是**静态、相对干净的快照**，而线上是**动态、有噪声的真实分布**（新题型、歧义输入、对抗输入），两者天然有分布漂移；叠加过拟合，分数就失真了。

**追问 2：怎么避免再次发生？**
> **答案：** 建立**闭环**：线上持续采样回流评测集、保留隐藏集做最终验收、上线后灰度 + 监控 guardrail 指标，一旦线上指标与评测分背离就报警并重建评测集。

**追问 3：怎么验证"刷新后的评测集更好"？**
> **答案：** 用新评测集跑历史版本，看它能否**区分已知的"好版本"和"坏版本"**（如回归 case 能被抓出来）。若新旧版本在新集上分数都差不多，说明新集仍无鉴别力，需继续补 bad case——**评测集的价值在于能否区分好坏**。

### Q13. judge 模型自身的偏差导致误判怎么办？成本/延迟突增如何定位？

**标准答案：** **judge 误判**：用人工标注校准、多评委投票、换更强/跨模型 judge、细化 rubric，并对 judge 本身持续评测；对有客观答案的项退回规则，减少对单一 judge 的依赖。**成本/延迟突增**：靠 trace 按 span 聚合 `tokens/cost/duration`，找异常 span——常见三类根因：① **循环**（trace 中出现重复的相同 span 序列，Agent 反复重试）；② **上下文膨胀**（每步输入 token 持续增长，历史全塞进去）；③ **模型选型**（换用了更贵/更慢的模型）。

**追问 1：怎么快速定位成本热点？**
> **答案：** 在 trace 上按 span 类型/名称聚合 token 与费用，排序找 Top 热点 span；再看该 span 的输入是否异常膨胀、是否重复出现。热点通常就是循环或上下文膨胀点。

**追问 2：循环调用是怎么产生的，怎么防？**
> **答案：** Agent 因规划缺陷反复调用同一工具/LLM（如工具返回不符合预期就一直重试）。防法：设**最大步数**、检测重复状态/重复工具调用即早停或换策略、给工具调用加幂等与超时。

**追问 3：上下文膨胀怎么缓解？**
> **答案：** 只保留必要历史（摘要或裁剪旧消息）、工具返回截断 Top-k、设置 token 预算上限、大文档改为检索按需取。核心是别每轮把完整历史无脑拼接进 prompt。

### Q14. 幻觉/事实错误如何量化？评测集维护成本与陈旧怎么办？如何说服团队"这次改动真的更好"？

**标准答案：** **幻觉量化**：用 **faithfulness**（对照检索/来源文本）、事实一致性、引用准确率，借 RAGAS、NLI 类方法判断生成是否有依据；难点在开放域**没有金标**，judge 也可能识别不出隐蔽幻觉。**评测集维护**：版本化管理、定期刷新、从 bad case 回流、控制规模与标注成本，保留隐藏集防污染。**说服团队**：拿**可复现的评测报告**说话——固定评测集分数 + 多次运行的方差/置信区间 + 成本延迟 + 灰度 A/B 的线上数据，而不是"我觉得这次回答更好"。

**追问 1：幻觉为什么特别难量化？**
> **答案：** 开放域无标准事实源、错误可能很隐蔽（看似合理的细节错误），judge 也会"看不出来"；且生成忠实于错误检索内容时 faithfulness 反而高。所以要**多指标交叉 + 人工抽查**，不能单一依赖某个分数。

**追问 2：怎么让评测结论更可信？**
> **答案：** 固定集、多次运行报告**均值与方差**、holdout 验收、跨模型/人工校准 judge，并用线上灰度数据佐证。结论要能被别人**复现**，才有人信。

## Part 5：2026 新趋势（加分题）

> 考察技术视野。涉及标准、平台与版本细节以官方文档为准，不确定的保守表述即可，不编造具体数字。

### Q15. 2026 年 Agent 评测与可观测性有哪些值得关注的趋势？

**标准答案：** （考察视野，重在方向判断，不要求记住具体版本号或数字）
- **LLM-as-judge 成为主流，但重心转向"校准"**：从"用 judge 打分"转向"如何证明 judge 可信"——人工校准、多评委、位置/长度偏差缓解成为标配。
- **可观测性走向标准化**：如 **OpenTelemetry 的 GenAI 语义约定**在推进 LLM/Agent span 的统一字段；**Langfuse / LangSmith / Braintrust** 类平台提供 trace、评测、prompt 管理一体化（具体能力以各平台当前文档为准）。
- **evals-first 开发与质量门禁进 CI**：先写评测再改 prompt，PR 触发评测，分数下降阻断合并。
- **合成数据生成评测集**：用强模型批量造测试用例扩充覆盖，但需人工校验质量与去偏，不能全依赖。
- **持续评测 / 在线监控**：从"上线前一次性评测"走向线上线下一体化、bad case 自动回流。
- **"评测 Agent 的 Agent"**：用 Agent 自动做 judge、生成 rubric、分析失败 case；同时评测这类 meta-Agent 本身成为新课题。

**追问 1：什么是"质量门禁进 CI"？**
> **答案：** 把评测接入持续集成：每次 prompt/代码改动自动跑固定评测集，质量分或成本延迟越过阈值就**阻断合并或发布**。它把"评测"从事后检查变成事前防线，是 evals-first 的落地形态。

**追问 2：合成数据生成评测集靠谱吗？**
> **答案：** 能快速扩充覆盖、降低成本，尤其适合补边界和对抗场景；但合成样本可能有**分布偏差、标签错误、模式单一**，必须人工抽检、去重去偏、与真实样本混合使用——它是补充而非替代真实数据。

**追问 3：采用第三方评测/可观测平台要注意什么？**
> **答案：** 注意**数据隐私与合规**（prompt/输出是否外发）、与自有 trace 体系的**数据接入与可迁移性**、避免被单一平台锁定（选型以当前官方文档与自身需求为准）；核心资产——评测集、rubric、golden 数据——应掌握在自己手里。

## Part 6：能否用 Agent 评测定级？如何定级？

### 结论先行

**可以，Agent 评测与可观测性是全栈/AI 工程面试里区分度很高的探针**——天然分层：知道要看效果 → 懂评测集/judge/trace 概念 → 讲得清指标体系与 judge 偏差、会用 trace 归因 → 有完整体系落地并线上定位过真实问题 → 能设计组织级质量门禁与规范。但它偏"体系工程"，**对初中级强问 judge 偏差与组织规范只会考到背诵**，结合岗位：初中级问到 Part 1/2 即可，资深与架构岗才追 Part 4/5。

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 知道要看效果，但说不清怎么量化、怎么复现 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂评测集、LLM-as-judge、trace 等基本概念 |
| **中高级（L3）** | 5–8 年 | Part 3 | 讲清指标体系、judge 偏差、trace 定位、离在线评测 |
| **高级（L4）** | 8 年+ | Part 4 | 有完整评测体系落地、线上定位过真实问题 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 能设计组织级质量门禁与评测规范、跟进可观测标准演进 |

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"非确定/质量闭环/LLM-as-judge/trace"→ 至少 L2；只会说"我看了下效果、感觉不错"→ 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"：为什么传统单测失效？为什么 judge 需要校准？为什么评测集过拟合会发生？为什么成本延迟也是评测对象？trace 怎么定位根因？

**第三步：三类信号防背题。**
1. **真实性**：能否讲出"我建过什么评测集、 judge 怎么校准、线上定位过什么真实问题"（有具体 case，而非背概念）。
2. **抽象能力**：能否把零散指标统一为"**答案 + 轨迹 + 工具 + 系统（成本/延迟）**"的多维框架，把流程统一为"评测集→评分→trace→回归→监控"闭环。
3. **权衡能力**：能否讲清"何时用规则不用 judge""质量成本延迟怎么取舍""只在最终答案打分有什么问题"。

**第四步：按最深层级定级，不按正确率。** 结合岗位难度调整追问深度：业务开发问到 Part 3 足够，平台/架构岗才需 Part 4/5 的组织级规范视野。

### 面试官避坑提醒

- **不要对所有人问到组织规范级**——很多优秀工程师在团队里扎实落地过评测，但没做过组织级门禁。区分"做过评测体系"与"听过规范名词"，前者更有价值。
- **把"线上真实问题定位"作为 L4 分水岭**：能讲出"评测高分但线上差，我用 trace 定位到是检索没召回"的人，一定是真做过闭环的。
- **务必问"不该怎么做"**：只堆 judge、讲不出偏差校准、成本约束与过拟合风险的，通常停在 L2/L3——识别"纸上谈兵型"候选人的关键。
- **结合岗位**：普通业务开发问到 Part 3 即可；AI 平台、基础架构团队才需要 Part 4/5 的深度与标准视野。
