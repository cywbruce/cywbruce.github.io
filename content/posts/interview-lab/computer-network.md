## Part 0：30 秒标准总答

**Q：谈谈你对计算机网络（TCP/IP 协议栈）的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> 计算机网络本质是解决"两台主机上的进程如何可靠、高效地交换数据"，主流方案是**分层模型**——OSI 七层是理论参考，TCP/IP 四/五层是事实标准，下层向上层提供服务。
>
> **网络层**用 IP 地址 + 路由解决"发给哪台主机"（IP、ARP、ICMP、NAT、子网划分）；**传输层**用 TCP/UDP + 端口解决"交给哪个进程"，TCP 靠**三次握手、序列号/确认号、重传、滑动窗口、拥塞控制**提供可靠有序字节流。
>
> **应用层**的 HTTP 是无状态请求-响应协议，从 1.1 长连接、2.0 多路复用到 3.0 基于 QUIC；**HTTPS = HTTP over TLS**，非对称加密协商密钥、对称加密传数据、CA 证书防中间人。
>
> 一次访问完整经历：**DNS 解析 → TCP（+TLS）握手 → 发 HTTP 请求 → 服务端响应 → 浏览器渲染 → 连接复用或关闭**。

**评分要点：** 分层 / IP+路由 / TCP 可靠 / HTTP+HTTPS / URL 到页面——五点对应入门到高级。能讲清"为何三次握手/TIME_WAIT"的，直接往 Part 2/3 追问。

## Part 1：基础认知题（分层与 UDP）

### Q1. OSI 七层和 TCP/IP 模型分别是什么？各层协议、设备与数据单元？

**标准答案：**
- **OSI 七层**：物理、数据链路、网络、传输、会话、表示、应用；**TCP/IP 四层**：网络接口、网际(IP)、传输、应用；教学常用**五层**（网络接口拆成物理+链路）。
- 核心对应关系：

| 层 | 主要协议 | 设备 | 数据单元 |
|----|---------|------|---------|
| 物理 | 以太网物理规范 | 集线器 | 比特 |
| 链路 | 以太网、ARP | 交换机 | 帧 |
| 网络 | IP、ICMP、路由协议 | 路由器 | 包/数据报 |
| 传输 | TCP、UDP | — | 段/数据报 |
| 应用 | HTTP、DNS、FTP、SMTP | 网关 | 报文 |

- **封装**：发送端自上而下每层加头部（端口→IP→MAC）；**分用**：接收端自下而上读头部决定交给谁——以太网 Type→IP，IP **协议号**（6=TCP/17=UDP）→传输层，TCP/UDP **端口号**→进程。

**追问 1：交换机和路由器的本质区别？**
> **答案：** 交换机在**链路层**基于 **MAC** 转发，隔离冲突域但不隔离广播域；路由器在**网络层**基于 **IP** 选路，隔离广播域、可跨不同网段。三层交换机兼具部分路由能力。

---
### Q2. TCP 和 UDP 的区别？各自适合什么场景？

**标准答案：**

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠、有序、去重、重传 | 尽最大努力，可能丢包乱序 |
| 单位 | 面向字节流（无边界） | 面向报文（有边界） |
| 控制 | 有流量/拥塞控制 | 无 |
| 首部 | 20–60 字节 | 8 字节 |
| 方式 | 仅一对一全双工 | 一对一/一对多/多对多 |
| 应用 | HTTP、FTP、SSH、数据库连接 | DNS、直播、游戏、QUIC |

- **选 TCP**：要求可靠完整（网页、文件、交易）；**选 UDP**：容忍少量丢包但求低延迟，或需组播，也可在 UDP 上自建可靠（QUIC）。

**追问：UDP 真"不可靠就没优点"吗？HTTP/3 为何反用 UDP？**
> **答案：** UDP 无连接、低延迟、无队头阻塞、首部小、可组播。HTTP/3 用 UDP 是为绕开 TCP 内核里的**连接级队头阻塞**和握手延迟，在用户态 QUIC 里重做可靠性与多路复用，做到"丢包只影响单流"和 0/1-RTT 握手——"可靠"和 UDP 并不矛盾。

## Part 2：底层原理题（TCP 连接与可靠传输）

> 这是"会用网络"和"懂协议内核"的分水岭，L2→L3 的关键。

### Q3. 三次握手过程？为什么是三次不是两次？什么是 SYN 攻击？

**标准答案：**

```
客户端                                     服务端
  |--- SYN=1, seq=x ---------------------->|
  |<-- SYN=1, ACK=1, seq=y, ack=x+1 -------|
  |--- ACK=1, seq=x+1, ack=y+1 ----------->|  (双方 ESTABLISHED)
```

1. 客户端发 SYN（seq=随机 ISN）→SYN_SENT；2. 服务端回 SYN+ACK（ack=x+1）→SYN_RCVD；3. 客户端回 ACK（ack=y+1）→双方 ESTABLISHED。

**为何三次**（双方确认对方收发正常、同步 ISN）：两次握手下服务端发出 SYN+ACK 就建连，**无法确认客户端是否收到**；若该 SYN 是**滞留的旧报文**，服务端会白白建无效连接。三次让客户端用第三次 ACK 明确告知"收到你的 SYN 且收发正常"。这是 Lamport 结论：**可能丢失/重复的信道上，三次是建可靠连接的最小次数**。

**SYN 攻击（SYN Flood）**：伪造大量源 IP 发 SYN，服务端回 SYN+ACK 后进入 SYN_RCVD 占用**半连接队列**，攻击者永不回 ACK，队列占满致正常用户无法建连。**防御**：① **SYN Cookie**（不预分配资源，状态编码进初始序号，收到合法 ACK 再建连）；② 调大半连接队列、减少重试；③ 防火墙限流/源校验。

**追问 1：ISN 为什么要随机而非从 1 开始？**
> **答案：** 防止**旧连接延迟报文被新连接误收**；随机化也让序列号不可预测，避免**伪造报文注入（会话劫持）**，提升正确性与安全性。

### Q4. 四次挥手过程？为什么四次？TIME_WAIT 为何 2MSL？大量 TIME_WAIT 怎么办？

**标准答案：**

```
客户端                                     服务端
  |--- FIN=1, seq=u ---------------------->|
  |<-- ACK=1, ack=u+1 ---------------------|
  |        ...服务端继续发剩余数据...        |
  |<-- FIN=1, ACK=1, seq=v, ack=u+1 -------|
  |--- ACK=1, ack=v+1 -------------------->|  (客户端 TIME_WAIT 2MSL)
```

- **为何四次**：TCP 是**全双工**，两个方向分别关闭。服务端收到客户端 FIN 时可能还有数据没发完，于是**先回 ACK**，发完数据再发自己的 FIN，故 ACK 与 FIN 分开发（对比握手 SYN 与 ACK 可合并，所以三次）。

**TIME_WAIT = 2MSL（MSL 为报文最大生存时间）的两个理由**：① **保证最后 ACK 可达**——若丢失，服务端重发 FIN，客户端在 TIME_WAIT 期间还能重发 ACK；② **让残留报文在网络中消散**，避免端口复用后旧报文"污染"新连接。

**大量 TIME_WAIT 处理**（高并发短连接、主动关闭方产生）：根本手段是改**长连接/连接池**、让**客户端主动关闭**；内核调优开启 `tcp_tw_reuse`、调小 `tcp_fin_timeout`、必要时调大端口范围。注意 `tcp_tw_recycle` 在 Linux 4.12 后已移除且 NAT 场景有问题，**勿用**；`SO_LINGER` 强制 RST 会跳过挥手、可能丢数据，**一般不推荐**。

**追问 1：CLOSE_WAIT 大量堆积说明什么？**
> **答案：** CLOSE_WAIT 表示对端已发 FIN、本端未发 FIN，即**应用没及时 close socket**——是代码层面的连接泄漏，与 TIME_WAIT（正常内核状态）性质不同。

### Q5. TCP 报文头关键字段？TCP 如何保证可靠传输？

**标准答案：** 首部**最小 20、最大 60 字节**，关键字段：

| 字段 | 作用 |
|------|------|
| 源/目的端口 | 标识进程 |
| 序列号 seq | 本段首字节序号，保证有序、去重 |
| 确认号 ack | 期望的下一字节（**累积确认**） |
| 控制位 | URG/ACK/PSH/**RST**/**SYN**/**FIN** |
| 窗口 | 流量控制 rwnd |
| 校验和 | 检错 |
| 选项 | MSS、窗口扩大、时间戳、SACK |

**可靠传输**：① **seq + ack** 保证有序/不丢/不重；② **超时重传**（RTO 略大于 RTT，指数退避）+ **快速重传**（3 个重复 ACK 立即重传）；③ 校验和检错；④ 流量/拥塞控制防止压垮接收方与网络。

**追问：RST 和 FIN 有何区别？**
> **答案：** FIN 是**正常关闭**的礼貌信号（四次挥手）；RST 是**异常复位**——连接出错或端口无监听，收到后立即断开、无需确认。访问无监听端口、连接关闭后仍收数据都会触发 RST，出现它往往意味连接被异常重置。

## Part 3：核心区分度题（窗口、拥塞、粘包——题眼）

> **全题题眼**——能否讲清滑动窗口、拥塞控制、粘包，直接决定 L2 还是 L3/L4，定级主要看这里。

### Q6. 什么是滑动窗口？如何用其做流量控制？

**标准答案：**
- **滑动窗口**实现**流水线发送 + 流量控制**：不必发一个等一个 ACK，窗口内可连续发多个报文，收到确认后窗口前移再发新数据，大幅提升吞吐。
- **流量控制**：接收方在 ACK 的**窗口字段（rwnd）** 告知缓冲区还能收多少；**发送窗口 = min(rwnd, cwnd)**，既压不垮接收方也压不垮网络。窗口按**字节**滑动。
- **零窗口死锁**：rwnd=0 时发送方暂停；若接收方腾出空间的 ACK 丢失会互等。用**持续计时器**定期发**零窗口探测报文**，胁迫对方回应当前窗口。

**追问 1：流量控制 vs 拥塞控制？**
> **答案：** 流量控制是**端到端**，防压垮**接收方**（rwnd）；拥塞控制是**全局**，防压垮**网络**（cwnd）。发送窗口取二者较小值。

---
### Q7. 讲清拥塞控制四算法，以及 cwnd 与 ssthresh 的关系。

**标准答案：**（讲完整基本是 L3+）发送方维护 **cwnd（拥塞窗口）** 与 **ssthresh（慢启动门限）**：

1. **慢开始**：cwnd 从 1 MSS 起，每收一个 ACK +1，即**每 RTT 翻倍（指数）**；cwnd ≥ ssthresh 改用拥塞避免。
2. **拥塞避免**：每 RTT **+1（线性）**，缓慢逼近容量。
3. **快重传**：收到 **3 个重复 ACK** 判定丢包，**立即重传**，不等超时。
4. **快恢复**：3 个重复 ACK 意味**轻度拥塞**，`ssthresh=cwnd/2`、`cwnd=ssthresh(+3)`，直接进拥塞避免**线性增长**，不回慢开始。

**关键区分**：**超时**（严重拥塞）→ `ssthresh=cwnd/2`、`cwnd=1`，**重新慢开始**；**3 个重复 ACK**（轻度）→ **快恢复**，从减半处线性增长。

```text
cwnd   /‾‾ 拥塞避免(线性)
      /  慢开始(指数)       /\ 超时→降1重来
     /                    /  \ 3ACK→快恢复(减半后线性)
----+---------------------------------> 时间
   1  2  4  8 ... ssthresh
```

**追问 1："慢开始"其实增长很快？**
> **答案：** 它是**指数增长**，每 RTT 翻倍（1→2→4→8…），到 ssthresh 很快。"慢"是相对一上来就猛发导致立即拥塞而言。

### Q8. 什么是粘包/拆包？为何发生？如何解决？

**标准答案：**
- **本质**：TCP 是**面向字节流**协议，**没有消息边界**。
- **粘包**：多个小消息被合并成一段发送（**Nagle 算法**攒包），接收方一次读到多条。
- **拆包**：大消息被拆成多段（超过 **MSS** 或缓冲区剩余空间），需多次读全。
- **UDP 不粘包**：面向报文，边界天然保留。

**四种解决**（核心是识别消息边界）：① **定长消息**（简单但浪费）；② **分隔符**（如 `\r\n`，Redis/FTP 控制连接）；③ **长度字段 + 内容**（最常用，如 HTTP `Content-Length`）；④ **应用层框架**（Netty `LengthFieldBasedFrameDecoder` 等）。

**追问 1：HTTP 怎么解决粘包？**
> **答案：** 用 `Content-Length` 声明实体长度，接收方据此切分；或 `Transfer-Encoding: chunked` 按块长度解析——正是"长度字段"方案的典型。

## Part 4：网络层与实战应用题

### Q9. 子网划分、NAT、ARP、ICMP、路由、MTU 与分片各解决什么问题？

**标准答案：**
- **IP + 子网划分**：IPv4 为 32 位；用掩码/CIDR（如 `192.168.1.0/24`）分网络号与主机号、借位划子网，提升利用率、缩小广播域。私有段：`10/8`、`172.16/12`、`192.168/16`。
- **NAT**：私网 IP↔公网 IP，缓解 IPv4 耗尽；**NAPT/PAT** 用"公网 IP+端口"区分内网主机，多对一。
- **ARP**：把下一跳 **IP 解析为 MAC**（广播请求、单播应答），有缓存；隐患是 ARP 欺骗。
- **ICMP**：差错报告（不可达、超时、重定向）+ 询问（**ping** 回显、**traceroute** 用超时逐跳）。
- **路由**：按**路由表 + 最长前缀匹配**转发；静态路由与动态路由（RIP/OSPF/BGP）。
- **MTU/分片**：链路层帧最大数据（以太网 **1500**）。超长 IP 报要**分片**到目的重组，设 **DF** 位则丢弃并回 ICMP；分片丢失要整包重传，故 TCP 用 **MSS = MTU−40（约 1460）** 主动避免分片（PMTUD）。

**追问：有了 IP 为何还要 MAC？**
> **答案：** IP 是**逻辑、端到端**地址（跨网络不变），负责跨网选址；MAC 是**物理、逐跳**地址，负责同链路"下一跳给谁"。每过路由器 IP 不变、MAC 逐跳改变，二者分工协作。

---
### Q10. DNS 解析全过程？CDN 原理？

**标准答案：**
**DNS（域名→IP，分布式层级库）**：
1. 查**浏览器缓存**→**系统缓存**（hosts/本地 DNS 缓存）。
2. 请求**本地 DNS（LDNS）**——此步为**递归查询**（LDNS 查到底）。
3. LDNS **迭代查询**：**根(.)→顶级域(.com)→权威(example.com)**，拿到 IP。
4. LDNS 缓存并返回，浏览器缓存。

记录类型：`A`、`AAAA`、`CNAME`、`MX`、`NS`、`TXT`、`PTR`。

**CDN**：把静态资源缓存到离用户最近的**边缘节点**，降延迟、减源站压力、抗 DDoS。域名 **CNAME** 到 CDN，其**智能 DNS 调度**按用户 IP、节点负载/健康把请求导向最优节点；命中则直接返回，未命中则**回源**拉取并按 TTL 缓存。

**追问：DNS 为何用 UDP？何时用 TCP？**
> **答案：** 查询报文小、求快，UDP 无连接开销低；当响应**超 512 字节**或**区域传输（AXFR）**时用 TCP。另有 **DoH/DoT**（DNS over HTTPS/TLS）走 TCP+TLS 加密，防篡改与隐私泄露。

### Q11. HTTP 1.0/1.1/2/3 核心差异？队头阻塞？方法幂等性？常见状态码？

**标准答案：**

| 版本 | 关键特性 |
|------|---------|
| 1.0 | 短连接，每请求新建 TCP，无 Host |
| 1.1 | **长连接 keep-alive**、管道化、Host、分块传输、缓存控制 |
| 2.0 | **二进制分帧、多路复用、HPACK 头部压缩、服务端推送**，基于 TCP |
| 3.0 | 基于 **QUIC(UDP)**，解决 TCP 队头阻塞、连接迁移、0/1-RTT、**QPACK** |

**队头阻塞（HOL）**：① **HTTP 层**——1.1 管道化中响应必须按序返回，一个慢响应阻塞后续；② **TCP 层**——2.0 多流共用一条 TCP，丢包时要等重传、**所有流被阻塞**，这正是 3.0 改用 QUIC 的根本原因（QUIC 各流独立重传）。HPACK 用静态表+动态表+Huffman；**QPACK** 为适配 QUIC 乱序引入 encoder/decoder stream 同步动态表。

**幂等性**（多次执行效果同一次）：幂等——GET/HEAD/**PUT（整体替换）**/DELETE/OPTIONS；非幂等——**POST、PATCH（部分修改）**。PUT 幂等而 PATCH 不幂等是高频陷阱。

**状态码**：`200/201/204/206(部分内容)`；`301(永久)/302(临时)/304(未修改)/307-308`；`400/401/403/404/405/429(限流)`；`500/502(网关错)/503/504(网关超时)`。

**追问：301 和 302 对 SEO 有何影响？**
> **答案：** 301 **永久**重定向，浏览器/搜索引擎**缓存并更新索引**到新地址；302 **临时**重定向，不更新索引。误用 302 做永久迁移会导致权重不传递、SEO 受损。

### Q12. HTTPS 握手过程？TLS 1.2 vs 1.3？对称/非对称加密、CA 证书、中间人防护？

**标准答案：** HTTPS = **HTTP over TLS**（端口 443）。用**非对称加密安全协商对称密钥**，再用**对称加密高效传数据**。

**TLS 1.2（约 2-RTT）**：① ClientHello（版本、套件、随机数 Cr）；② ServerHello（选套件、随机数 Sr、**下发证书**）；③ 客户端**校验证书**，生成 pre-master 用**服务器公钥加密**发回；④ 服务端私钥解密，双方用 Cr+Sr+pre-master 生成**相同会话密钥**；⑤ 互发 Finished 确认，之后对称加密通信。

**TLS 1.3**：**1-RTT 握手**（合并往返、基于 ECDHE 提前密钥交换）；**0-RTT 会话恢复**（有**重放风险**）；移除 RSA 密钥传输等不安全套件、**强制前向保密**（长期私钥泄露也解不出历史流量）。

**证书与 CA**：证书由 CA 签发（域名、公钥、有效期、签名）。客户端验证**证书链**（服务器证书→中间 CA→根 CA，根 CA 预置信任库）+ 域名/有效期/吊销（CRL/OCSP）。

**中间人防护**：攻击核心是**伪造证书/篡改公钥**——靠① 严格校验证书链与域名；② **HSTS** 强制 HTTPS 防 SSL 剥离/降级；③ 高安全场景用**证书锁定**；④ 不绕过证书警告。

**追问 1：为何不全程用非对称加密传数据？**
> **答案：** 非对称加密计算**慢几个数量级**，不适合海量数据。只用它在握手期**协商密钥**，真正数据用**对称加密**（AES-GCM/ChaCha20），兼顾安全与高效。

### Q13. Cookie/Session/Token/JWT 区别？HTTP 缓存、断点续传、WebSocket？

**标准答案：**
- **Cookie**：服务端 `Set-Cookie` 下发，浏览器存并**自动携带**，约 4KB 限制；属性 `HttpOnly`（防 XSS）、`Secure`（仅 HTTPS）、`SameSite`（缓解 CSRF）。
- **Session**：**服务端**存状态，客户端只持 **SessionID**（多放 Cookie）；有状态，分布式需共享（如 Redis），但**可随时服务端失效**。
- **JWT**：`Header.Payload.Signature` 三段 Base64，**无状态**验签鉴权，易跨域/扩展；缺点**无法主动失效**（靠短过期/黑名单）、Payload **非加密**（不放敏感信息）、体积大。

**HTTP 缓存**：**强缓存**（不发请求，命中 200 from cache）——`Cache-Control: max-age`（优先）、`no-cache`（走协商）、`no-store`、`Expires`；**协商缓存**（问服务器，未变 **304**）——`ETag/If-None-Match`（更精确、优先）、`Last-Modified/If-Modified-Since`。先强缓存，过期再协商。

**断点续传**：客户端发 `Range: bytes=500-`，服务端回 `206 Partial Content` + `Content-Range`，声明 `Accept-Ranges: bytes`；用于大文件/多线程下载。

**WebSocket**：经 HTTP `Upgrade: websocket` 握手（回 **101**）升级为**全双工长连接**，帧头小、支持服务端推送，用于聊天/实时推送；靠 ping/pong **心跳**保活。

**追问：JWT 和 Session 在分布式系统怎么选？**
> **答案：** Session 有状态，多实例要**共享 Redis** 或会话粘滞，但可随时失效；JWT 无状态易扩展但失效难。折中：**短 JWT + 长过期可吊销的 Refresh Token**，兼顾扩展与可控失效。

### Q14. 输入 URL 到页面展示的完整过程？网络故障排查？高并发端口耗尽？

**标准答案：**
**URL 到页面**：① **DNS 解析**（域名→IP）；② **TCP 三次握手**（HTTPS 再加 TLS 握手）；③ 浏览器发 **HTTP 请求**；④ 服务端（负载均衡→应用→缓存/DB）返回 **HTTP 响应**；⑤ 浏览器**渲染**：解析 HTML→DOM、CSS→CSSOM→渲染树→布局→绘制，加载子资源；⑥ keep-alive 复用或四次挥手关闭。

**排查工具箱**：`ping`（ICMP 连通性/RTT）、`traceroute`（逐跳定位）、`ss -tunlp`/`netstat`（连接状态、TIME_WAIT/CLOSE_WAIT）、`tcpdump`/Wireshark（抓包看握手、重传、RST）、`dig`/`nslookup`（DNS）、`curl -v`（请求/响应头）。

**端口耗尽**：TCP 连接由**四元组（源IP、源端口、目的IP、目的端口）** 唯一确定。作为**客户端**连同一服务时目的固定，可用组合受限于**源端口**（Linux 默认约 32768–60999，约 2.8 万个），短连接高并发会耗尽端口致 `EADDRNOTAVAIL`，伴随大量 TIME_WAIT；**fd 上限**（`ulimit -n`）也常先成瓶颈。**解决**：连接池/长连接复用、调大 `ip_local_port_range`、开 `tcp_tw_reuse`、调大 fd 上限、多源 IP 或服务多端口分流。

**追问：服务端监听 80 端口为何能接受几万连接不耗尽？**
> **答案：** 服务端只监听**一个端口**，但四元组中对端 IP/端口各异，故能Accept海量连接（受 fd/内存限）。端口耗尽主要发生在**主动发起大量出站连接的客户端**。

## Part 5：2026 新趋势：HTTP/3、TLS 1.3 与后量子

> 加分题，考察技术视野。版本/部署细节以官方与厂商最新公告为准，保守表述、不编造。

### Q15. 聊聊 HTTP/3、TLS 1.3、后量子密码、IPv6 与拥塞控制新算法的现状。

**标准答案：**
- **HTTP/3（QUIC）**：HTTP/3（RFC 9114，2022 定稿）基于 **QUIC（UDP）**，收益是**解决 TCP 连接级队头阻塞**（各流独立重传）、**连接迁移**（Connection ID，Wi-Fi 切 4G 不断线）、0/1-RTT 握手。截至 2026 年主流浏览器与大量站点/CDN 已支持并持续扩大部署，成为重要流量组成；但受 UDP 被中间网络限速、运维成熟度影响，尚未完全取代 HTTP/2，多作为其**并行升级选项**。
- **TLS 1.3**（RFC 8446，2018）：**1-RTT、0-RTT、强制前向保密、精简不安全套件**，已成主流并广泛部署，逐步取代 1.2。
- **后量子密码（PQC）**：NIST 2024 发布首批标准（**ML-KEM/Kyber** 密钥封装、**ML-DSA/Dilithium**、**SLH-DSA** 签名）。业界推进**混合密钥交换**（经典 X25519 + 后量子 ML-KEM，如 **X25519MLKEM768** 已在 Chrome、Cloudflare 等实现/实验部署）。该领域**标准与部署仍在演进**，以官方/RFC 最新进展为准。
- **IPv6**：全球部署持续增长，部分地区已过半，国内推进规模部署；解决地址耗尽、简化头部，但与 IPv4 **长期共存**（双栈、隧道、NAT64 过渡）。
- **拥塞控制新算法**：**BBR**（Google，基于**带宽+RTT 建模**而非丢包，更适合高带宽时延积链路）及 **BBRv3**（改进公平性/收敛）已在 Linux 内核实现并被部分业务采用；**CUBIC** 仍是许多系统默认。重点是理解"丢包驱动 vs 带宽驱动"的思路差异。

**追问：0-RTT 这么快为何不全面默认开启？**
> **答案：** 0-RTT 早期数据**无重放保护**，可被截获重放。支付、下单等**非幂等**请求不应放 0-RTT，或由应用层去重/挑战。

## Part 6：能否用网络题定级？如何定级？

### 结论先行

**可以，网络题区分度很高**——天然分层、可深可浅：知道分层/状态码 → 懂握手 → 懂窗口/拥塞 → 能处理粘包、排查线上 → 跟进 HTTP/3/TLS 1.3 演进。但知识点广，**对初级易"背八股"**，招初中级问到 Part 1/2 即可，强问拥塞细节只会考背诵。

---
### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 知道分层、TCP/UDP 区别、常见状态码；说不清握手与可靠传输机制 |
| **中级（L2）** | 2–5 年 | Part 2 | 能讲清三次/四次握手、TIME_WAIT、可靠传输基本机制 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能讲清滑动窗口、流量/拥塞控制、粘包拆包；理解四算法协同 |
| **高级（L4）** | 8 年+ | Part 4 | 掌握 DNS/CDN、HTTPS，有线上排查实战与高并发调优经验 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 HTTP/3、TLS 1.3、后量子、BBR 等演进，能把网络选型纳入架构 |

---
### 定级操作方法

**第一步：Part 0 摸底。** 能说出"分层+TCP 可靠+IP 定位+HTTP/HTTPS+URL 到页面"→ 至少 L2；只会背名词 → 从 Part 1 问起。
**第二步：沿追问链下探。** 重点问"为什么"：为何三次不是两次（旧报文/双向确认）？为何 TIME_WAIT 2MSL（ACK 可达+旧报文消散）？为何 3ACK 走快恢复而超时走慢开始（拥塞程度不同）？为何 HTTP/3 基于 UDP 反而更快（绕开 TCP 队头阻塞）？
**第三步：三类信号防背题。** ① **真实性**：能否讲具体线上案例（tcpdump 抓到大量 SYN 重传→半连接队列满；ss 见 CLOSE_WAIT 堆积→应用没 close；TIME_WAIT 打满端口→连接池+tw_reuse）；② **抽象能力**：能否归纳主线"分层→可靠传输→定位转发→应用语义→端到端体验"及"流量 vs 拥塞控制""HTTP 层 vs TCP 层队头阻塞"的对照；③ **权衡能力**：能否说清"什么场景不该用"（Nagle 取舍、JWT 失效、0-RTT 边界）。
**第四步：按最深层级定级，不按正确率。** 结合岗位调深度（业务后端问到 Part 3/4 足够，基础架构/网关团队才需 Part 4 全线+Part 5）。

---
### 面试官避坑提醒

- **别变成八股背诵比赛**——状态码、分层名词很多人背得出，"为什么这样设计"才是真理解，多问"为什么""换你怎么设计"。
- **把"线上排查+高并发调优"作为 L4 分水岭**：能讲真实抓包/调参细节的人一定真用过。
- **新趋势听判断力而非名词**：说得出 HTTP/3 为何基于 UDP、0-RTT 为何有风险，比背 RFC 编号有价值；不确定时以官方为准的保守态度反是加分项。
