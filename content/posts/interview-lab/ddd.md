## Part 0：30 秒标准总答

**Q：谈谈你对 DDD 的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> DDD（Domain-Driven Design，领域驱动设计）是应对**复杂业务软件**的一套方法论，核心主张是**让代码模型忠实反映业务领域**，而不是先把需求翻译成数据库表再写逻辑。
>
> 它分**战略设计**和**战术设计**两层：战略层用**统一语言、限界上下文、上下文映射**来划分问题边界与团队边界；战术层用**实体、值对象、聚合、领域服务、仓储、领域事件**来落地模型。
>
> **统一语言**是地基——领域专家和开发用同一套词汇，代码里的类名/方法名就是业务术语，消除"翻译"造成的失真。
>
> 复杂问题靠**分而治之**：先分问题域/解域，再用限界上下文圈定语义边界，每个上下文内部用**聚合**守住业务不变量和事务一致性。
>
> 它不是银弹：**CRUD 型、逻辑简单的系统不需要 DDD**，强行引入只会过度设计。

**评分要点：** 复杂业务 / 战略+战术 / 统一语言 / 限界上下文+聚合 / 不滥用 这几个点，对应入门到高级。能说出"战略 vs 战术"和"边界划分"的，直接往 Part 2 追问。

## Part 1：基础认知题

### Q1. DDD 到底解决什么问题？什么时候不该用 DDD？

**标准答案：**
- 解决"**软件复杂度**"，尤其是**业务逻辑复杂、规则多变、需要领域专家深度参与**的系统（如金融、保险、电商交易、供应链）——Eric Evans 称之为"**知识丰富的领域**"。
- 核心矛盾：业务方说的语言和代码里的语言不一致，需求在"翻译"中不断失真；DDD 通过**模型驱动设计**让业务与代码同源。
- **不该用**的场景：简单 CRUD、以数据存取为主、几乎没有业务规则的后台系统；此时"分层 + MyBatis + 事务脚本"足矣。判断标尺是看**业务复杂度**而非技术复杂度——高并发但逻辑简单的秒杀未必需要 DDD，低并发但规则繁复的理赔反而需要。

**追问 1：DDD 和"数据建模 / 数据库设计"的根本区别是什么？**
> **答案：** 数据建模以**存储与查询效率**为中心，先定表结构再写逻辑；DDD 以**业务行为与不变量**为中心，先建领域模型再考虑持久化（由仓储隔离）。DDD 里数据库只是"模型的一种持久化实现细节"，不应让表结构反向决定领域模型。

**追问 2：问题域、解域、子域是什么关系？**
> **答案：** **问题域**是业务要解决的现实问题空间（做什么、为什么），**解域**是软件实现空间（怎么做）。子域是对问题域的切分：**核心域**（竞争力所在，必须深挖）、**支撑域**（辅助核心业务，可自研或采购）、**通用域**（如认证、支付，倾向外购）。资源应向核心域倾斜。

**追问 3：战略设计和战术设计分别包含什么？只做战术会怎样？**
> **答案：** **战略**＝统一语言/限界上下文/上下文映射/子域，回答"边界在哪、团队怎么分工"；**战术**＝实体/值对象/聚合/领域服务/仓储/工厂/领域事件，回答"一块内部怎么建模"。**先战略后战术**；只做战术会得到一堆局部正确但边界模糊的聚合，最终演变成"分布式单体"。

### Q2. 什么是统一语言（Ubiquitous Language）？怎么落地？

**标准答案：**
- 定义：**领域专家与开发团队共同约定、贯穿需求/设计/代码/测试的一套词汇**，同一个词在某个上下文里含义唯一。
- 落地：维护术语表 + 代码命名对齐（类名/方法名/参数名用业务术语）+ 文档和沟通都用同一套词；发现术语歧义时回头修正模型。
- 价值：消除"业务说‘订单’，代码里叫 Order/Trade/Deal"的翻译损耗，让**模型即文档**。

**追问 1：统一语言是全局唯一的吗？**
> **答案：** 不是。它**只在某个限界上下文内成立**——"商品"在销售上下文是"可售商品"（有价格、库存），在物流上下文是"待运货物"（有重量、体积）。跨上下文同名词含义不同是正常的，这正是要划限界上下文的原因。

**追问 2：为什么统一语言被视为 DDD 的"地基"？**
> **答案：** 因为后续所有建模产物（聚合、事件、仓储）都依赖术语精确。语言不统一，模型必然歧义，边界也划不清。它是**沟通成本最低、收益最高**的实践，也是判断团队是否真在做 DDD 的试金石。

## Part 2：核心概念深层辨析题

> 这是"背过名词"和"真正理解模型"的分水岭，L2→L3 的关键。

### Q3. 实体 Entity 和值对象 Value Object 怎么区分？如何识别值对象？

**标准答案：**
- **实体**：有**唯一身份（ID）**且**状态随时间连续变化**，相等性按 ID 判断（如订单、用户）。
- **值对象**：**无身份**，只由属性值定义，相等性按**所有属性是否相等**判断，且**不可变**（如金额 Money、地址 Address、日期区间）。
- 识别值对象：问"能否只关心**它是什么**而不关心**它是哪个**"？属性变了是"换了一个"还是"同一个变了"？若是前者 → 值对象。

**追问 1：值对象为什么强调不可变？它能带行为吗？**
> **答案：** 不可变保证**共享安全、无副作用、易推理、哈希稳定**（可作 Map key）。值对象**可以有行为**（如 `Money.add()`、`Range.overlaps()`），这正是它强于"基本类型字段"之处——把领域规则内聚进去。要修改就创建新对象替换，而非 setter。

**追问 2：金额为什么推荐用值对象，而不是直接用 BigDecimal 字段？**
> **答案：** 因为金额有**币种、精度、舍入规则**等语义，单个 BigDecimal 表达不了"100 美元 ≠ 100 人民币"。用 `Money(amount, currency)` 把"同币种才能相加、舍入策略"封装起来，避免散落各处的判断逻辑。

---

### Q4. 聚合 Aggregate / 聚合根是什么？为什么聚合是一致性边界？

**标准答案：**
- 聚合是**一组强关联对象的集合**，作为**数据修改与持久化的最小单元**；**聚合根（Root）**是唯一对外暴露的实体，外部只能通过根访问内部对象。
- 聚合内维护**业务不变量**（如"订单行金额之和 = 订单总额"须一次事务内一致），因此聚合是**事务一致性边界**：一个事务通常只改一个聚合；跨聚合靠领域事件走向最终一致。

**聚合边界决策表（示例）：**

| 候选对象 | 与订单强一致 | 同事务变更 | 结论 |
|---------|:---:|:---:|------|
| 订单行 | 是（金额需守恒） | 是 | **放入订单聚合** |
| 收货地址 | 否（快照即可） | 否 | **值对象快照**存于订单内 |
| 支付记录 | 否（异步结果） | 否 | **独立聚合**，领域事件通信 |
| 库存 | 否（可最终一致） | 否 | **独立上下文 + 事件** |

**追问 1：为什么要"小聚合"？大聚合有什么问题？**
> **答案：** 大聚合把大量对象锁在一起 → **并发冲突严重**（改一个订单行就锁整个订单）、**加载/持久化开销大**、**事务边界过大**。原则：按"**真正需要强一致的不变量**"圈定边界，能用最终一致的就拆出去。

**追问 2：聚合之间能直接持有对方的对象引用吗？**
> **答案：** 只能**通过 ID 引用**，不能持有对象引用。这样降低耦合、避免跨聚合的对象图遍历与级联加载，也契合"一个事务一个聚合"。

---

### Q5. 领域事件是什么？它和事务一致性怎么配合？

**标准答案：**
- 领域事件是**领域内已发生的、有业务意义的事实**（如"订单已支付"），命名通常用**过去时**；作用是**解耦聚合**、**表达跨聚合/跨上下文的最终一致**、天然的**审计线索**。
- 事务配合：领域事件要与聚合状态变更在**同一个本地事务**落库，再可靠投递——常用**事务性发件箱（Transactional Outbox）**：事件先和业务数据一起写进 outbox 表，再异步投递 MQ，保证"状态改了事件一定发得出去"。

**追问 1：为什么不能"先提交事务、再发消息"？**
> **答案：** 中间崩溃会导致**状态改了但消息没发**（丢事件），造成不一致。outbox 把"改状态 + 记事件"放进同一事务，从根源消除这个缝隙；消费端还需保证**幂等**。

**追问 2：领域事件和 MQ 消息是一回事吗？**
> **答案：** 不是。领域事件是**领域概念**（表达业务事实），MQ 消息是**技术载体**。同一领域事件可发布给多个订阅方、用不同消息实现；不要把领域模型直接绑定某种中间件 API。

### Q6. 领域服务 / 应用服务 / 基础设施服务怎么分？仓储与工厂的职责？

**标准答案：**
- **领域服务**：承载**不属于单个实体/值对象**的核心业务逻辑（如"转账"涉及两个账户），属于领域层、无状态。
- **应用服务**：**用例编排**——接收外部请求、调用领域对象/领域服务、管理事务边界、发布事件，**不含业务规则**。
- **基础设施服务**：技术实现细节——数据库、MQ、RPC、邮件（如仓储实现、消息发送器）。
- **仓储 Repository**：封装聚合的**存取**，以**聚合为单位**（通常一个聚合一个仓储）；**工厂 Factory**：封装**复杂对象/聚合的创建**逻辑。
- **架构分层**：经典四层为**用户界面层 / 应用层 / 领域层 / 基础设施层**，依赖方向**指向领域层**（依赖倒置：领域层定义接口、基础设施层实现）。**六边形架构（端口与适配器）**是其推广——领域在中心、外部经由端口/适配器接入；**整洁架构 Clean Architecture** 同理，用同心圆表达"依赖由外向内、领域与框架无关"。三者本质一致：**隔离领域模型与技术细节**。

**追问 1：为什么说"只有聚合才有仓储"，而不是每个实体一个？**
> **答案：** 因为持久化与一致性的单位是聚合。给聚合内每个实体配仓储会**破坏聚合边界**（外部可绕过根修改内部对象），导致不变量失控。仓储保证"取出/保存的是一个完整聚合"。

**追问 2：Repository 和 DAO 有什么区别？**
> **答案：** DAO 面向**数据表**、偏技术（CRUD 语句）；Repository 面向**领域聚合**，语义是"按业务条件取回一个聚合对象"，隐藏存储细节。Repository 接口定义在领域层、实现放在基础设施层（依赖倒置）。

## Part 3：核心区分度题（题眼，定级主战场）

> **这一部分是全题的题眼**——能否讲清"边界为什么这样划"，直接决定 L3 还是 L4/L5。定级主要看这里。

### Q7. 限界上下文 Bounded Context 是什么？为什么需要它？

**标准答案：**
- 定义：**一个明确的语义与职责边界**，在这个边界内统一语言和领域模型才有确定含义；边界外同名概念含义可能不同。
- 价值：① **语义边界**——消除同名异义的混乱（"商品"在不同上下文含义不同）；② **团队边界**——一个上下文可由一个团队自治，降低协作成本；③ **演化隔离**——上下文内部变化不轻易波及外部。
- 它是**战略设计的核心成果**，也是微服务拆分的**重要输入**。

**追问 1：限界上下文和子域是什么关系？**
> **答案：** 子域是**问题域**的切分（客观业务划分），限界上下文是**解域**的切分（我们主动划定的模型边界）。理想情况一一对应，但现实常出现多个子域同处一个上下文、或一个子域跨多个上下文。划界依据是**语言与模型的边界**。

**追问 2：上下文划得太大或太小有什么问题？**
> **答案：** 太大 → 模型被迫兼容多义、团队耦合、改动牵一发动全身；太小 → 上下文间交互爆炸、重复建设。划界应看**语言是否同一、团队是否同一、不变量是否同一**，而非拍脑袋按模块拆。

---

### Q8. 上下文映射图 Context Map 有哪些关系模式？

**标准答案：**
- **合作关系 Partnership**：两个上下文共同演进、紧密协作。
- **共享内核 Shared Kernel**：共享一部分公共模型/代码，改动需双方协商。
- **客户-供应商 Customer-Supplier**：上游供给下游，下游需求可影响上游排期。
- **防腐层 ACL（Anti-Corruption Layer）**：下游在边界处自建**翻译/适配**，隔离上游模型的"污染"——最常用的防御模式。
- **开放主机服务 OHS / 发布语言 PL**：上游提供**稳定公开协议**（如 REST API + DTO）供下游消费。
- **另谋他路 Separate Ways**：各走各的、不集成（成本低但重复）。
- （"大泥球 Big Ball of Mud"是应避免的反模式。）

**追问 1：什么时候必须用 ACL？举个场景。**
> **答案：** 当下游要接入**遗留系统 / 外部供应商 / 模型语义差异极大**的上游时，用 ACL 把上游模型翻译成下游领域概念，避免"脏模型"渗透进核心域，保护核心域的纯粹。

**追问 2：OHS + 发布语言与 ACL 分别站在哪一侧？**
> **答案：** OHS/PL 是**上游主动**提供标准化接口（"我给你稳定契约"）；ACL 是**下游主动**建翻译层（"我不信任你的模型，自己适配"）。两者常配合：上游提供 OHS，下游仍用 ACL 做隔离。

---

### Q9. 康威定律怎么指导微服务拆分？限界上下文和微服务是一一对应的吗？

**标准答案：**
- 康威定律："**系统设计的结构，会复制组织的沟通结构**"——团队怎么分，系统往往就长成什么样。
- DDD 的限界上下文强调按**业务语义与团队边界**划界，与康威定律一致：**一个上下文交给一个团队自治**，据此拆微服务，边界清晰、耦合低。
- **但限界上下文 ≠ 微服务，不是一一对应**：上下文是**逻辑边界**，微服务是**部署/运行边界**。可一个上下文拆成多个服务（出于性能/部署需要），也可多个小上下文合在一个服务里（成本考量）。

**追问 1：为什么不能简单"一个上下文一个服务"？**
> **答案：** 微服务有**运维与分布式成本**（网络、事务、部署）。若上下文很小、团队也小，硬拆成服务得不偿失。应先按上下文理清逻辑边界，再结合**团队规模、性能、可用性、部署节奏**决定物理拆分粒度。

**追问 2：反过来"先拆微服务再补 DDD"常见什么问题？**
> **答案：** 容易按**技术分层或数据表**拆出"分布式单体"——服务间共享数据库、调用链混乱、边界与业务不符。DDD 强调**先有正确的领域边界、再有服务边界**，顺序反了往往要返工。

---

### Q10. 充血模型 vs 贫血模型，为什么 DDD 追求充血？

**标准答案：**
- **贫血模型**：实体只有 getter/setter，业务逻辑散落在 Service 里，对象只是"数据容器"。
- **充血模型**：实体/值对象**自带行为与不变量**（`order.pay()`、`order.addItem()` 内部做校验），Service 只做编排。
- DDD 追求充血，因为**行为与数据在一起**才能内聚地守护不变量，避免逻辑散落、重复、漏校验。

**追问 1：充血模型会不会导致实体臃肿、依赖外部服务？**
> **答案：** 会，所以要有边界：实体只承载**依赖自身状态**的逻辑；需要外部依赖（查库存、调支付）的复杂逻辑放**领域服务**，由它编排实体。切忌把 Repository/MQ 注入实体。

**追问 2：JPA/Hibernate 的实体容易做成贫血，怎么办？**
> **答案：** JPA 实体完全可以做充血——关键是**别只生成 setter**，把业务方法、校验写进实体、限制无脑 setter。ORM 只是持久化机制，不妨碍领域模型充血；把"用了 JPA 注解"等同于"做了 DDD"是典型误区。

## Part 4：实战与陷阱题

### Q11. 让你为一个电商订单系统做领域建模，从哪开始、怎么推导聚合边界？

**标准答案：**
1. **事件风暴**对齐认知：贴出领域事件（"订单已创建/已支付/已发货/已取消"）→ 反推命令（"创建订单/支付"）→ 找出**聚合**（产生事件的实体：订单、支付、库存）→ 标出**角色/参与者**与**策略**（如优惠规则）。
2. **划限界上下文**：订单、支付、库存、商品、物流各自成上下文，明确映射关系（订单→支付用 OHS，订单→库存用 ACL）。
3. **定聚合边界**：用 Q4 的决策表逐项判断（订单行入聚合、地址作值对象、支付与库存独立）。
4. **识别值对象**：金额 Money、地址 Address、时间区间——无身份、不可变、带规则。
5. **跨聚合一致性**：下单后通过领域事件触发支付/扣库存，追求最终一致，用 outbox + 幂等。

**追问 1：订单和库存之间如何保证"不超卖"？**
> **答案：** 要么把强一致库存扣减放在库存聚合内（下单即扣、事务保证），要么用"**预占库存 + 领域事件确认**"的最终一致方案；关键是明确"库存不变量由库存聚合守护"，订单聚合不能直接改库存。

**追问 2：订单状态很多（待支付/已支付/已发货/已完成/已取消），怎么建模？**
> **答案：** 用**状态机**封装流转规则（哪些迁移合法），可用枚举 + 状态模式或 Sealed 类型表达；把"只允许合法迁移"作为不变量放在订单聚合内，而非散落在 Service 的 if-else。

---

### Q12. 跨聚合 / 跨上下文的一致性怎么处理？和分布式事务如何取舍？

**标准答案：**
- 原则：**聚合内强一致（单事务），聚合间最终一致（领域事件）**。
- 手段：领域事件 + 事务性发件箱 + MQ + 消费端幂等；必要时用 **Saga** 编排长事务、以补偿动作回滚。
- 取舍：强一致（本地事务/XA）**简单但耦合、性能低**；最终一致**解耦、可扩展但要处理乱序/重复/失败补偿**。DDD 倾向后者换取消晰边界与伸缩性。

**追问 1：领域事件乱序到达（"已发货"先于"已支付"）怎么办？**
> **答案：** 消费端按**聚合版本号/事件序号**做幂等与顺序校验，乱序则暂存或拒绝重试；设计上让事件携带版本，或对乱序不敏感的业务用状态机兜底。

**追问 2：什么时候仍该用强一致而非最终一致？**
> **答案：** 涉及**资金、库存临界、立即不可违反的合规约束**时，宁可用本地事务或 XA 保强一致。最终一致不是教条，要看业务对"短暂不一致"的容忍度。

---

### Q13. 列几个你见过的"伪 DDD / 过度设计"误区。

**标准答案：**
- **把 DDD 等同于分层架构或 JPA 注解**——加了几层 package、用了 @Entity 就说做了 DDD，模型依旧贫血。
- **为 DDD 而 DDD**：简单 CRUD 也硬套聚合/仓储/事件，徒增复杂度。
- **聚合过大**：一个订单聚合塞进商品、库存、支付、物流，导致并发冲突与加载性能问题。
- **贫血领域模型**：实体只有 setter，逻辑全在 Service，DDD 形同虚设。
- **直接把领域模型当 DTO 暴露**：用 JPA 实体直接序列化返回，领域模型被外部契约绑架。

**追问 1：怎么判断一个项目是"真 DDD"还是"套壳"？**
> **答案：** 看三件事——① 有没有**统一语言**且代码命名与之一致；② 领域模型是否**充血、守护不变量**；③ 边界是否由**限界上下文/聚合**驱动而非数据表驱动。套壳项目通常只有分层和注解，模型依旧贫血。

**追问 2：什么时候该"回退"到简单设计？**
> **答案：** 当业务被证明很简单、DDD 的抽象没带来收益只带来成本时，应及时简化。DDD 是**应对复杂度的工具，不是目标**——能简单就简单，是成熟工程师的判断力。

## Part 5：2026 新趋势：DDD 与微服务 / 事件驱动 / AI 辅助建模

> 加分题，考察候选人的技术视野。注意：以下多属**理念/实践趋势**，请保守作答，不宣称已成熟、不编造具体工具 API。

### Q14. DDD 与微服务、中台的演进关系怎么看？事件驱动架构如何结合 DDD？

**标准答案：**
- DDD 与微服务：**DDD 回答"边界怎么划"，微服务回答"边界怎么部署"**；近年共识是"**先领域边界、后服务拆分**"，避免分布式单体。
- 中台：曾是"能力复用"的热词，近年趋于理性——**强行中台化会因抽象过早而僵化**；更务实的是按限界上下文沉淀可复用能力，而非追求"大而全的中台"。
- **事件驱动架构（EDA）+ DDD**：领域事件是二者的桥梁——DDD 定义"发生了什么业务事实"，EDA 负责"把事实可靠传播给关心方"，共同实现松耦合与最终一致。

**追问：为什么说领域事件是 DDD 落地 EDA 的关键接口？**
> **答案：** 因为它把"领域层的业务事实"与"技术层的消息投递"解耦——领域只管产出事件，EDA 基础设施负责传输。这让事件语义稳定、不被中间件绑定，也便于测试。

---

### Q15. CQRS / 事件溯源在 Kafka 等事件流平台上如何落地？AI 辅助建模现状如何？

**标准答案：**
- **CQRS（读写分离）**：写侧按聚合处理命令、产出领域事件；读侧订阅事件构建**物化视图（投影）**供查询，两侧可独立扩展。Kafka 的**日志压缩主题 / 流处理**常用于构建读模型。
- **事件溯源 Event Sourcing**：**以事件序列作为唯一事实源**，状态由事件重放得出。收益是完整审计、可回溯、易做时序分析；代价是**查询复杂（需投影）、事件 schema 演进难、认知成本高**，务必**只在核心域局部使用**，不要全系统铺开。
- **AI 辅助建模（探索中）**：尝试从需求文档/会议对话中**抽取领域术语、候选聚合与事件**，辅助生成事件风暴便签；但**仍需领域专家校验**，准确性与边界判断尚不能依赖 AI。**领域特定语言（DSL）与结构化建模**用结构化描述约束领域规则、辅助代码生成，也是持续探索方向，实践差异大，面试中保守表述即可。

**追问：事件溯源最大的"坑"是什么？**
> **答案：** 把它当银弹全系统铺开——读查询变复杂、事件版本演进困难、团队认知负担陡增。务实做法是**核心高价值聚合用事件溯源，其余仍用普通状态存储**，并配套 CQRS 读模型。

## Part 6：能否用 DDD 定级？如何定级？

### 结论先行

**可以，DDD 是考察"抽象归纳能力"的最佳探针之一**——它天然分层：会背名词 → 能辨析概念 → 能划边界 → 能实战建模 → 能归纳演进与取舍。但 DDD 偏理念、答案开放，**对缺乏复杂业务经验的候选人容易"问空"**，务必用 Part 4 实战题验证是否真做过。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 听过 DDD，能说"实体/值对象/聚合"名词，讲不清边界依据 |
| **中级（L2）** | 2–5 年 | Part 2 | 能辨析实体/值对象、聚合/根、领域事件，知道统一语言 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能讲清限界上下文/上下文映射/康威，区分充血贫血，理解跨聚合一致性 |
| **高级（L4）** | 8 年+ | Part 4 | 能现场对一个业务做事件风暴、推导聚合边界、处理最终一致与陷阱 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 能把 DDD 与微服务/EDA/CQRS 归纳为体系，做边界取舍与演进判断 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"战略+战术+限界上下文+聚合"→ 至少 L2；只会背名词 → 从 Part 1 问起。

**第二步：沿追问链下探，重点问"为什么这样划边界"：**
- 为什么这个值对象是值对象而不是实体？
- 为什么这两个对象在一个聚合、那两个不在？
- 为什么这个上下文要加 ACL，而不是直接调用？

**第三步：三类信号防背题。**
1. **真实性**：能否讲出**真实项目的建模过程与踩坑**（"一开始把订单和库存放一个聚合导致锁冲突，后来拆开用事件"）。
2. **抽象归纳能力（本套核心）**：能否把多个概念统一为本质——
   - 实体 / 值对象 / 聚合 / 限界上下文 → "**不同粒度的边界与不变量守护**"
   - 统一语言 / BC / ACL → "**语义边界与翻译**"
   - 领域事件 / outbox / Saga / CQRS → "**从强一致到最终一致的光谱**"
3. **权衡能力**：能否说清"何时不该用 DDD、聚合为何不能过大、何时仍用强一致"。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整追问深度（业务开发问到 P3/P4，架构/中台团队才需 P5）。

---

### 面试官避坑提醒

- DDD 答案开放，**别用"标准术语"卡人**——能自洽讲清边界与理由 > 背定义。
- **把"现场建模"作为 L4 分水岭**：能对一个陌生业务做事件风暴并推导聚合边界的，才是真懂。
- 警惕"套壳 DDD"：满口术语但模型贫血、边界按数据表划的，不能因术语熟练就定高级。
