## Part 0：30 秒标准总答

**Q：谈谈你对设计模式的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> 设计模式是**前人针对反复出现的面向对象设计问题总结出的可复用解决方案**，经典是 GoF 的 23 种，按目的分为**创建型、结构型、行为型**三类。
>
> 背后有一组共同的设计原则，核心是 **SOLID**（尤其**开闭原则**：对扩展开放、对修改关闭），再加上**迪米特法则（最少知道）** 和**合成复用原则（组合优于继承）**。
>
> 设计模式的本质是**识别变化点并封装变化**——把"会变的"和"稳定的"隔离，让变化不扩散；主要手段是**面向接口编程**而非面向实现。
>
> 工作中最常见的是**单例、工厂、代理、策略、模板方法、观察者、责任链**，它们几乎都不是孤立使用，而是组合出现。
>
> 主流框架里到处是模式：Spring 的 **BeanFactory（工厂）、单例 Bean、动态代理（AOP）、JdbcTemplate（模板方法）、ApplicationEvent（观察者）、HandlerAdapter（适配器）**。

**评分要点：** 分类 / 设计原则（SOLID+开闭）/ 封装变化+面向接口 / 常用模式举例 / 框架落地 这几个点，对应入门到高级。能说出"封装变化"和"开闭原则"的，直接往 Part 2 追问。

## Part 1：基础认知题

### Q1. GoF 23 种模式怎么分类？六大设计原则是什么？

**标准答案：**
- **创建型（5 种）**：解决"对象怎么创建"——单例、工厂方法、抽象工厂、建造者、原型。
- **结构型（7 种）**：解决"类/对象怎么组合"——代理、适配器、装饰器、外观、享元、组合、桥接。
- **行为型（11 种）**：解决"对象间如何交互与职责分配"——策略、模板方法、责任链、观察者、状态、命令、迭代器、中介者、访问者、备忘录、解释器。
- **六大原则**：**S**RP 单一职责 / **O**CP 开闭（**核心**：对扩展开放、对修改关闭）/ **L**SP 里氏替换 / **I**SP 接口隔离 / **D**IP 依赖倒置 = SOLID；再加**迪米特法则（最少知道）** 与**合成复用原则（组合优于继承）**。

**追问 1：为什么开闭原则是核心？怎么做到"对修改关闭"？**
> **答案：** 因为"需求变化"是软件永恒的主题，开闭原则的目标是**加新功能时尽量不改已有代码**。落地手段是**抽象 + 多态**：把变化点抽成接口，新需求通过新增实现类接入，而不是改原有分支判断。策略、工厂模式都是它的典型载体。

**追问 2：里氏替换和多态是什么关系？违反 LSP 有哪些典型信号？**
> **答案：** LSP 是多态正确性的保证——子类必须能"无缝"当作父类用。违反信号：子类**抛出父类不会抛的异常**、**返回 null 而父类有值**、或**空实现父类方法**（如"正方形继承长方形"导致 setWidth 语义冲突）。违反 LSP 往往意味着继承用错，应改用组合。

### Q2. 单例模式有哪几种写法？各自优缺点？

**标准答案：**

| 实现 | 线程安全 | 懒加载 | 评价 |
|------|---------|--------|------|
| 饿汉式 | 是（类加载即创建） | 否 | 简单；但可能提前占资源 |
| 懒汉式（synchronized） | 是 | 是 | 每次 get 都加锁，性能差 |
| DCL 双重检查 | 是（需 volatile） | 是 | 推荐写法之一，但易写错 |
| 静态内部类 | 是（JVM 类加载保证） | 是 | **推荐**，无锁且懒加载 |
| 枚举 | 是 | 否 | **最安全**，防反射/序列化破坏 |

- 饿汉式：利用**类加载的线程安全性**，实例在类初始化时创建。
- 静态内部类：JVM 加载外部类时**不加载内部类**，调用 getInstance 才触发内部类加载，兼具懒加载与安全。
- 枚举：`INSTANCE`，写法极简，《Effective Java》推荐为单例首选。

**追问 1：饿汉式何时创建对象？为什么"非懒加载"可能有问题？**
> **答案：** 在**类初始化阶段**（`<clinit>`）创建。若构造很重而该类加载后始终没被用到，会白白占用内存/资源并拖慢类加载。所以它适合实例创建成本低、或一定会被用到的场景。

**追问 2：静态内部类为什么天然线程安全？**
> **答案：** JVM 加载类时会为 `<clinit>` 加**初始化锁**，保证同一时刻只有一个线程初始化类；内部类 `SingletonHolder` 只在首次被主动使用时加载且只加载一次。这是 JVM 规范保证的，无需显式加锁。

## Part 2：底层原理题（单例 / 工厂 / 代理的机理）

> 这是"背过写法"和"懂背后机理"的分水岭，L2→L3 的关键。

### Q3. DCL（双重检查锁）为什么必须加 volatile？反射和序列化如何破坏单例？

**标准答案：**
DCL 写法：
```java
public class Singleton {
    private static volatile Singleton instance; // volatile 是关键
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {             // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null)       // 第二次检查：防重复创建
                    instance = new Singleton();
            }
        }
        return instance;
    }
}
```
- `new Singleton()` 非原子，分三步：**① 分配内存 → ② 初始化对象 → ③ 引用指向该地址**。
- 不加 volatile，**指令重排**可能把 ②③ 调换：线程 A 执行到③（instance 已非 null，但对象未初始化完），线程 B 第一次检查发现非 null 就取走一个**"半初始化"对象**，使用时可能出错。
- volatile 通过**禁止特定指令重排（写屏障）** 保证②在③之前完成，杜绝"未初始化对象逸出"。
- **反射/序列化破坏**：`setAccessible(true)` 能调私有构造再 new；防御是构造器加"非空则抛异常"守卫。反序列化绕过构造**重建对象**；防御是实现 `readResolve()` 返回现有实例。

**追问 1：volatile 在这里保证的是可见性还是有序性？**
> **答案：** 两者都有，但**防重排（有序性）是关键**。可见性保证改动能被看见；但若发生重排，"被看见的值"本身就是错的。所以 DCL 的核心痛点是**有序性**——这是它与 volatile+JMM 题库的交叉考点。

**追问 2：为什么枚举单例最安全？它就没有缺点吗？**
> **答案：** 安全在于：① 反射调用枚举构造会被 JVM 拒绝（`cannot reflectively create enum objects`）；② 序列化只写**名字**，反序列化经 `Enum.valueOf` 找唯一实例，**不新建对象**。缺点：**非懒加载**（类加载即创建全部枚举项）、**不能继承类**、语义稍显别扭；若需延迟加载大资源或复杂继承，枚举不方便。工程上常权衡选静态内部类，但要清楚"论安全性枚举最强"。

### Q4. 简单工厂、工厂方法、抽象工厂有什么区别和演进关系？

**标准答案：**
- **简单工厂**（静态工厂，非 GoF）：一个工厂类按参数（switch/if）创建不同产品。优点：调用方不必知道类名；缺点：**加新产品要改工厂判断分支，违反开闭原则**。
- **工厂方法**：把工厂也抽象出来，每个产品对应一个具体工厂，由子类决定创建哪一种。优点：**加新产品只加产品类+工厂类，不改原有代码（符合开闭）**；缺点：类数量膨胀。
- **抽象工厂**：围绕一个"产品族"创建**一系列相关产品**（如 Button + TextField 的 Win/Mac 两套）。优点：保证同族一致性、切换产品族方便；缺点：**加新产品维度很麻烦**，要改所有工厂接口。
- 演进主线：**简单工厂（一厂多品）→ 工厂方法（一品一厂）→ 抽象工厂（一厂一族）**。

**追问 1：工厂方法如何体现"把简单工厂的分支判断外移"？**
> **答案：** 简单工厂的 `switch(type)` 分支，在工厂方法里变成了**多态**——不再由一个工厂 if/else 判断，而由调用方选择注入哪个具体工厂，`create()` 被多态分派到对应实现。**用"选择实现类"替代"判断类型码"**，正是开闭原则的落地。

**追问 2：Spring 的 BeanFactory 属于哪种工厂？**
> **答案：** 更接近**工厂方法 + 简单工厂的结合体**。`BeanFactory` 是顶级接口，`getBean()` 按名称/类型返回对象，底层按 BeanDefinition 反射创建，相当于一个"超级工厂"。它把对象创建从 `new` 中解放出来交给容器，是控制反转（IOC）的载体。

### Q5. JDK 动态代理和 CGLIB 代理的原理与区别？如何被 Spring AOP 使用？

**标准答案：**

| 维度 | JDK 动态代理 | CGLIB 代理 |
|------|-------------|-----------|
| 机制 | 基于**接口**，`Proxy` + `InvocationHandler`，运行时生成实现接口的代理类 | 基于**继承**，用 ASM 生成目标类**子类**，重写方法织入增强 |
| 前提 | 目标类**必须实现接口** | 无需接口；但类/方法**不能是 final** |
| 依赖 | JDK 原生 | 第三方库（Spring Core 已内置） |
| 性能 | 调用略慢（反射），JDK 8+ 已大幅优化 | 创建较慢，**调用较快**（FastClass） |

- **Spring AOP 选择**：目标类**有接口 → 默认 JDK 动态代理**；**无接口 → CGLIB**；可用 `proxyTargetClass=true` 强制 CGLIB。两者本质都是**代理模式**的运行时实现，用于方法前后织入横切逻辑（事务、日志、权限）。

**追问 1：Spring Boot 2.x 之后默认代理方式变了吗？为什么？**
> **答案：** **变了**。Spring Boot 2.0 起 `spring.aop.proxy-target-class` **默认改为 true**，即默认用 **CGLIB**。原因：① 避免"没接口的类无法被代理"的坑；② CGLIB 调用性能更好；③ 减少 JDK 与 CGLIB 语义差异带来的困惑。能提到这个版本变化是明显加分点。

**追问 2：代理模式和装饰器都能"增强功能"，怎么区分？**
> **答案：** 见 Part 3 Q6——这是本题库**核心区分度题**。简答：**代理控制访问**（隐藏真实对象、做权限/延迟/远程），**装饰器增强功能**（透明叠加职责、可嵌套）。差异主要在**意图**而非结构。

## Part 3：核心区分度题（装饰器 / 适配器 / 代理辨析与框架落地）

> **这一部分是全题的题眼**——能否讲清"结构型模式之间的意图差异"以及"模式在框架中的真实落地"，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q6. 装饰器、适配器、代理三者都是"包一层"，如何准确辨析？

**标准答案：** （能讲清"意图不同、结构相似"基本是 L3+）

三者结构上都持有被包装对象的引用，但**目的（意图）完全不同**：

| 模式 | 核心意图 | 接口关系 | 典型例子 |
|------|---------|---------|---------|
| **装饰器 Decorator** | **增强/叠加功能**，透明扩展 | 与被装饰者**实现同一接口** | `BufferedInputStream` 包装流；MyBatis 缓存装饰器 |
| **适配器 Adapter** | **转换接口**，兼容不匹配的类 | **实现目标接口、内部持有被适配者**（接口不同） | `Arrays.asList()`；`InputStreamReader`（字节→字符） |
| **代理 Proxy** | **控制访问**，隔离真实对象 | 与真实对象**同一接口** | JDK 动态代理；Spring AOP；`unmodifiableList` |

- **一句话记忆**：装饰器"**加功能**"、适配器"**转接口**"、代理"**控访问**"。
- 装饰器强调**递归嵌套**（可层层套），代理通常只包一层且**客户端可能不知道真实对象存在**。

**追问 1：装饰器和代理都实现同一接口，如何进一步区分？**
> **答案：** 看**客户端感知与关注点**。装饰器重点是**功能叠加**，客户端主动选择套哪些装饰器（`new BufferedInputStream(new FileInputStream(...))`），层层透明叠加；代理重点是**访问控制或隐藏真实对象**，客户端往往只感知代理、甚至不知道被代理对象（远程代理、懒加载代理）。此外装饰器可**递归组合多个**，代理一般一对一。

**追问 2：外观（Facade）和适配器、装饰器有什么不同？**
> **答案：** **外观**为**复杂子系统提供统一高层入口**，简化调用（如 Slf4j 封装日志实现），对象是"**一群类**"而非单个；适配器兼容**单个接口不匹配**，装饰器增强**单个对象功能**。外观强调"**化繁为简**"。

### Q7. Spring 框架中用到了哪些设计模式？行为型模式又如何区分？

**标准答案：** （考察"模式落地"的广度，能归类者 L3+）

| 模式 | Spring 中的体现 |
|------|----------------|
| **工厂模式** | `BeanFactory` / `ApplicationContext` 创建管理 Bean |
| **单例模式** | Bean 默认 singleton 作用域；容器本身是单例 |
| **代理模式** | AOP（JDK/CGLIB）、`@Transactional` 事务增强 |
| **模板方法** | `JdbcTemplate` / `RestTemplate` / `RabbitTemplate` |
| **观察者模式** | `ApplicationEvent` / `ApplicationListener` 事件机制 |
| **适配器模式** | `HandlerAdapter`、`MessageListenerAdapter` |
| **策略模式** | `InstantiationStrategy`、不同 `Resource` 实现 |
| **装饰者 / 建造者** | `HttpServletRequestWrapper` / `BeanDefinitionBuilder`、`UriComponentsBuilder` |
| **职责链模式** | `HandlerInterceptor` 链、`FilterChain` |

**行为型核心区分**（策略 / 模板方法 / 责任链 / 状态）：
- **策略**：一族可互换算法，运行时**主动选一个**（支付方式）。
- **模板方法**：**父类定骨架、子类重写步骤**，靠继承+钩子。
- **责任链**：请求沿**处理链**传递，每级决定处理或转发（Filter 链、审批流）。
- **状态**：**内部状态改变驱动行为改变**，消除状态 if-else（订单状态机）。

**追问 1：JdbcTemplate 是如何用模板方法 + 回调的？**
> **答案：** 传统模板方法靠**继承重写**，但 Java 单继承受限；`JdbcTemplate` 改用**接口回调**——把"处理结果集"封装进 `RowMapper` 传入，既复用"取连接→建语句→执行→关连接"的骨架，又避免继承。这是**模板方法 + 策略/回调**的组合应用。

**追问 2：策略模式和状态模式都用接口替换 if-else，区别在哪？**
> **答案：** 看**谁决定切换**。策略由**客户端显式选择**，策略间彼此独立无感知；状态由**对象内部状态自动驱动**切换，状态间可能互相转换，且常持有 Context 引用以触发迁移。简言之：**策略是"选一个"，状态是"自己变"**。

## Part 4：实战与陷阱题（重构 if-else 与避免过度设计）

### Q8. 代码里有大量 if-else 分支，如何用设计模式重构？如何避免过度设计？

**标准答案：** （考察模式与真实场景的匹配，L3/L4 分水岭）

以"按订单类型算折扣"的庞大 if-else 为例，重构路径：
1. 分支是**"多选一算法" → 策略 + Map 注册**：定义接口、各类型实现，`Map<Type, Strategy>` 启动时注册，`getStrategy(type).discount()` 一行替代 if-else。
2. 分支是**"创建不同对象" → 工厂模式**：把 `new XXX` 的分支交给工厂。
3. 分支是**"固定流程中步骤不同" → 模板方法**：抽公共骨架，差异用回调/子类。
4. 分支是**"多级流转/审批" → 责任链**；分支是**"状态流转" → 状态模式**。

**避免过度设计**：
- **有真实变化点才抽象**：至少已有 2–3 个明确可替换实现，或需求预告会变，才引入模式（YAGNI 原则）。
- **先简单后重构**：先用直白代码实现，变化真正出现、if-else 开始腐化时再重构（"三次法则"）。
- **能说出"封装了什么变化"**：说不清防的是什么变化，多半是过度设计；模式是工具不是 KPI。

**追问 1：用 Map + 策略替代 if-else 有什么坑？**
> **答案：** ① **空策略兜底**：Map 找不到时要有默认实现或明确报错，避免 NPE；② **策略膨胀**：分支过多时类会很多，需配合自动注册（如 Spring 注入所有实现按 key 建 Map）；③ **别为消除而消除**：只为两个稳定分支引入一堆类是过度设计。

**追问 2：违反 YAGNI、提前抽象的具体代价是什么？**
> **答案：** ① **认知负担**：后来者要理解一堆抽象才能改一行；② **僵化**：错误抽象一旦铺开，比 if-else 更难改（"错误的抽象比重复更昂贵"）；③ **性能/调试成本**：多层代理让调用链和排障复杂。所以"**先让它跑，再让它对，最后让它可扩展**"。

---

### Q9. 建造者模式解决什么问题？和 Lombok @Builder 什么关系？其余行为型模式如何速记？

**标准答案：**
- **建造者模式**：对象**构造参数多、可选参数多**时，用 `XxxBuilder` 分步设置、最后 `build()` 一次性构造，避免"重叠构造器"和长串 null。优点：可读性好、参数顺序无关、可校验、可构造**不可变对象**。
- **Lombok `@Builder`**：编译期**自动生成**上述 Builder 代码（私有全参构造 + `builder()` + 内部 Builder 类），是**建造者模式的代码生成工具**，思想不变、省去样板代码；注意加了 @Builder 会**丢失无参构造**，需配合 `@NoArgsConstructor` / `@AllArgsConstructor`。
- **其余模式速记**：

| 模式 | 一句话意图 |
|------|-----------|
| **观察者** | 一对多依赖，主题变化自动通知（发布-订阅） |
| **命令 / 备忘录** | 请求封装成对象支持撤销重做（命令）；保存内部状态支持回滚（备忘录） |
| **迭代器 / 中介者** | 不暴露内部表示统一遍历（迭代器）；用中介封装多对象交互降耦合（中介者） |
| **访问者** | 不改元素类前提下增加新操作（双分派） |
| **享元** | 共享大量细粒度对象的**内部状态**省内存（`Integer` 缓存池） |
| **组合 / 桥接** | 组成树形结构统一对待个体与整体（组合）；抽象与实现分离各自变化（桥接） |

**追问：访问者模式为什么"加新操作容易、加新元素难"？**
> **答案：** 访问者把操作封装在 Visitor 类里，加新操作只需**新增一个 Visitor 实现**；但每个元素类都要有 `accept(visitor)`，所以**加新元素类型要改所有 Visitor**。适合"元素结构稳定、操作常变"的场景。

## Part 5：2026 新趋势：函数式、Sealed/模式匹配与云原生

> 加分题，考察候选人的技术视野与对现代 Java 演进的跟进。

### Q10. 函数式编程（Lambda + Map）能否替代策略模式？Sealed/Record 又有何影响？

**标准答案：** （考察版本事实准确性）
- **Lambda 简化策略**：简单场景可用 Lambda 把策略压缩成函数式接口，配合 `Map<Key, Function>` 注册，消除大量策略类：
```java
Map<PayType, Function<Order, BigDecimal>> strategies =
    Map.of(ALIPAY, this::payByAli, WECHAT, this::payByWechat);
strategies.get(type).apply(order);
```
  策略**逻辑复杂、有状态、需多态或依赖注入**时，仍用完整策略类更清晰可测。**Lambda 是策略模式的轻量表达而非取代**——"封装可互换算法"的思想不变。
- **版本事实（务必准确）**：**Record** 是 JEP 395，**JDK 16** 正式；**Sealed Classes** 是 JEP 409，**JDK 17** 正式；**switch 模式匹配** 是 JEP 441，**JDK 21** 正式（此前为预览）。
- **Sealed + 模式匹配简化访问者**：Sealed 把可能子类型封闭，编译器知道"子类就这几种"，配合 switch 模式匹配可直接穷举：
```java
sealed interface Shape permits Circle, Rect {}
BigDecimal area(Shape s) = switch (s) {
    case Circle c -> ...; case Rect r -> ...;
};  // 穷尽、无需 default，新增子类编译器提示
```
  这让"对不同子类型做不同操作"很直观，**很多场景不再需要完整的访问者双分派**；但 Sealed 要求**子类受控**，开放扩展场景仍需访问者。
- **Record 对 DTO/Builder 的影响**：一行 `record User(String name, int age) {}` 生成不可变 DTO（自动 equals/hashCode/getter），**替代大量纯数据 DTO 和部分 Builder 场景**；但 Record **不可变、无 setter**，复杂/可选参数多时仍需 Builder，两者可组合（@Builder 可标注 Record 上）。

**追问：Sealed Classes 是"访问者模式的终结者"吗？**
> **答案：** 不是，是**另一种更简单的解法**。Sealed 前提是"**类型集合封闭且可预知**"，此时穷举 switch 最简洁；当类型体系**对外开放**（第三方可扩展）时，访问者仍不可替代。体现"版本事实 + 适用边界"才是 L5 水准。

---

### Q11. 设计模式在云原生与微服务架构中如何演变？

**标准答案：**
- **地位变化**：GoF 模式解决**单进程内对象协作**；云原生/微服务把复杂度转移到**进程间、服务间**，诞生了架构级模式（Sidecar、Circuit Breaker、API Gateway、Saga），但**思想一脉相承**——仍是"封装变化、隔离关注点"。
- **演变举例**：**代理 → 服务网格 Sidecar**（通信/重试/熔断抽到 sidecar）；**责任链 → 网关 Filter 链**（Spring Cloud Gateway、K8s admission webhook）；**状态机 → 工作流引擎**（Temporal 等实现分布式状态模式）；**单例/工厂 → 容器 IOC**（生命周期交给 Spring/K8s，控制反转升到平台级）；**函数式/Serverless** 削弱有状态对象模式，转向事件驱动（观察者→事件总线）+ 外部存储。

**追问：微服务时代 GoF 模式过时了吗？**
> **答案：** 没有过时，只是**层次上移**。单个服务内部依然大量用单例、工厂、策略、模板方法（Spring 本身就是证明）；服务间问题用架构模式解决。优秀工程师要能**在两个层次都识别变化点并恰当封装**——这正是区分 L4 与 L5 的能力。

## Part 6：能否用设计模式定级？如何定级？

### 结论先行

**可以，设计模式是考察"抽象能力与工程品味"最好的探针之一**——它天然分层：背过定义 → 知道分类与原则 → 懂单例/工厂/代理机理 → 能辨析相似模式 → 能在框架中识别 → 能结合场景重构 → 懂体系演进。但设计模式**极易背题**，"会背区别不会用"很常见，一定要用**实战题（Part 4）与辨析题（Part 3）交叉验证**。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 能说单例几种写法、知道 23 种分类；说不清设计原则与背后机理 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂 DCL 为何 volatile、工厂演进、动态代理原理；辨析相似模式吃力 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能辨析装饰器/适配器/代理、说清 Spring 用了哪些模式及其意图 |
| **高级（L4）** | 8 年+ | Part 4 | 能用模式重构 if-else、判断何时不该用模式、有真实落地与取舍经验 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进函数式/Sealed/云原生演进，能做抽象归纳与技术选型 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"分类 + 封装变化 + 开闭原则"→ 至少 L2；只会背"单例有五种写法"→ 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"与"区别"：DCL 为何必须 volatile（JMM 有序性，交叉 volatile 题库）？装饰器/适配器/代理都是"包一层"，意图差在哪（意图而非结构）？为何 Spring Boot 2 默认改用 CGLIB（版本事实 + 权衡）？

**第三步：三类信号防背题。**
1. **真实性**：能否讲出**自己重构 if-else、封装 SDK、排查事务失效（代理没生效）**的真实经历与细节。
2. **抽象能力**：能否把多个模式归纳到统一本质——"**都是封装变化点、面向接口、组合优于继承**"，并说出"防的是什么变化"。
3. **权衡能力**：能否讲清"**什么场景不该用模式**"、过度设计的代价、JDK 代理 vs CGLIB 的取舍——只会背优点、讲不出边界的通常停在 L2。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整：业务开发问到 Part 4 足够；架构/中间件团队深挖 Part 5。

---

### 面试官避坑提醒

- **别把"23 种模式默写"当难题**：那是记忆力测试，不是能力测试。重点问"意图、区别、何时用/不用"。
- **把"模式辨析"和"重构实战"作为 L3/L4 分水岭**：能当场辨析装饰器 vs 代理、把一段 if-else 讲出重构思路的，是真懂。
- **警惕"八股式正确但无实战"**：Spring 用了哪些模式背得滚瓜烂熟，却说不清自己项目里用过哪个模式——要压级。
- **版本事实要较真**：Record(16)/Sealed(17)/switch 模式匹配(21) 的正式版年份是高频陷阱，答错说明"伪学习"。
