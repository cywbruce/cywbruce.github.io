## Part 0：30 秒标准总答

**Q：谈谈你对分布式 ID 的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> 分布式 ID 解决的是**分库分表 / 多节点场景下，数据库自增主键不再全局唯一**的问题——需要一个能跨机器生成、全局唯一标识的方案。
>
> 一个合格的分布式 ID 通常要满足：**全局唯一、趋势递增、高可用、高性能**，很多业务还希望它**包含时间信息**便于排序与排查。
>
> 常见方案有：**UUID、数据库自增主键、数据库多主模式、号段模式（如美团 Leaf-segment）、Redis INCR、雪花算法（Snowflake）** 等。
>
> 目前主流是**雪花算法**：用一个 64 位 long，拆成符号位 + 时间戳 + 机器 ID + 序列号，**本地生成、不依赖 IO、趋势递增**，性能极高。
>
> 雪花算法的两大难点是**时钟回拨**（机器时钟倒退可能导致重复 ID）和 **workerId 分配**（多节点不能冲突）；此外 2024 年发布的 **UUIDv7（RFC 9562）** 提供了时间有序的新选择。

**评分要点：** 为什么需要 / 核心要求 / 常见方案 / 雪花算法结构 / 时钟回拨与 workerId，对应入门到高级。能说出 64 位分段的，直接往 Part 3 追问。

## Part 1：基础认知题

### Q1. 为什么需要分布式 ID？分布式场景下对 ID 有哪些要求？

**标准答案：**
- **单机时代**：数据库自增主键（auto_increment）就够用，简单可靠。
- **分布式时代**：一旦**分库分表**、多主库、多节点部署，各库自增主键会从 1 重新开始，**跨库不再唯一**，合并数据或全局路由时就会主键冲突。因此需要独立的、全局唯一的 ID 生成机制。
- 分布式 ID 的典型要求：**全局唯一**（不可妥协）、**趋势递增**（整体按时间递增，利于索引顺序写）、**单调递增**（绝对全局递增，部分场景才需要）、**高可用/高性能**（本地生成最优）、**信息安全**（不轻易推测业务量）、**含时间信息**（便于排序与排查）。

**追问 1：趋势递增和单调递增有什么区别？**
> **答案：** **单调递增**是严格意义上每一次生成都比上一次大，全局有序（如数据库自增、号段模式）；**趋势递增**是"整体上越来越大"，但**跨节点/跨毫秒不保证严格有序**——如雪花算法，A 节点这一毫秒生成的 ID 可能小于 B 节点上一毫秒的 ID（受时钟与节点号影响）。日常面试里把这个区别讲清楚，是理解雪花算法的前提。

**追问 2：为什么数据库索引"喜欢"递增的 ID？**
> **答案：** InnoDB 使用 **B+ 树聚簇索引**，数据按主键顺序物理存放。递增 ID 的新记录总是**追加到索引最右侧**，页分裂少、顺序写、索引紧凑、缓存命中率高。而随机 ID（如 UUID）会**随机插入到索引中间**，频繁触发页分裂与数据移动，产生大量索引碎片和随机 IO，写入性能显著下降。

---

### Q2. 常见的分布式 ID 方案有哪些？各自优缺点是什么？

**标准答案：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| **UUID** | 本地生成、简单、全球唯一 | 太长（36 字符）、无序、索引分裂、不含时间 |
| **数据库自增** | 简单、单调递增 | 单点、DB 压力大、分库分表失效 |
| **数据库多主** | 解决了单点 | 起始值/步长需规划、扩容困难 |
| **号段模式** | DB 压力小、递增、可批量 | 依赖 DB、需双 buffer 优化毛刺 |
| **Redis INCR** | 性能好、递增 | 依赖 Redis、需考虑持久化与单点 |
| **雪花算法** | 本地生成、高性能、趋势递增 | 依赖机器时钟、时钟回拨、workerId 分配 |

**追问 1：UUID 用做数据库主键有什么具体问题？**
> **答案：** 三个核心问题：① **无序** → 随机写入 B+ 树，导致**索引分裂与碎片**，写性能差；② **太长** → 36 个字符（16 字节二进制），聚簇索引下每个二级索引都存一份主键，空间放大严重；③ **不含时间信息**，无法按生成顺序排序。所以 UUID 适合做"标识符"但不适合做"聚簇主键"。

**追问 2：UUID 有哪些版本？常用的是哪个？**
> **答案：** UUID 有多个版本：v1（基于时间+MAC）、v3（基于 MD5 命名空间）、**v4（纯随机，最常用）**、v5（基于 SHA-1 命名空间）。传统 v4 完全随机、无序。2024 年 RFC 9562 又新增了 v6/v7/v8，其中 **v7 是时间有序的**，详见 Part 5。

## Part 2：底层原理题（数据库 / 号段 / Redis）

> 这一部分是"知道有这些方案"和"理解方案为什么这么设计"的分水岭，L2→L3 的关键。

### Q3. 数据库自增主键在分布式下有什么问题？数据库多主模式怎么解决？

**标准答案：**
- **问题**：① 单点——单点 DB 挂了整个发号不可用；② 性能瓶颈——每次发号都要一次 DB IO；③ **分库分表失效**——每个库都从 1 开始自增，跨库主键重复。
- **多主模式**：部署多台主库，每台设置**不同的起始值（auto_increment_offset）** 和**相同的步长（auto_increment_increment）**。例如 2 台主库：A 从 1 开始、B 从 2 开始，步长都设为 2，则 A 生成 1,3,5…，B 生成 2,4,6…，互不冲突。

**追问 1：具体怎么设置起始值和步长？**
> **答案：** 若有 N 台主库，步长设为 N，第 i 台（i 从 1 开始）的起始值设为 i。这样第 i 台生成的 ID 满足 `ID % N == i % N`，天然错位。MySQL 通过 `auto_increment_increment` 和 `auto_increment_offset` 两个参数控制。

**追问 2：多主模式最大的问题是什么？**
> **答案：** **扩容困难**。起始值和步长在规划时就要定死，后期要扩容到 N+1 台时，必须停服重新规划所有节点的参数并迁移数据，否则会冲突。所以多主模式只适合节点数相对固定的中小规模场景。

---

### Q4. 号段模式（Leaf-segment）的原理是什么？双 buffer 优化解决什么问题？

**标准答案：**
- **原理**：不再每次都访问 DB，而是**批量取一段 ID 缓存在本地**。DB 中有一张 `leaf_alloc` 表，记录 `biz_tag`、`max_id`、`step`。业务节点取号时，用一条 `UPDATE ... SET max_id = max_id + step` 抢占下一个号段 [max_id, max_id+step]，之后本地内存从 0 递增发号，用完再来取。
- 这样**把"每次发号一次 DB IO"变成"每 step 次发号一次 DB IO"**，DB 压力骤降。

**追问 1：原始的号段模式有什么"毛刺"问题？双 buffer 怎么解决？**
> **答案：** 原始方案在**号段耗尽的瞬间**才去 DB 加载新号段，这期间的发号请求会阻塞在 DB IO 上，出现**耗时毛刺**（尤其 DB 抖动时）。**双 buffer 优化**：本地维护两个 buffer（号段缓冲区），当当前 buffer 用到一定比例（如 10%）时，**提前异步加载下一个号段**到备用 buffer，用完直接切换。这样 DB 加载对业务无感，消除了毛刺。

**追问 2：号段模式是单调递增还是趋势递增？DB 挂了还能发号吗？**
> **答案：** 号段模式是**全局单调递增**的（号段由 DB 统一分配，严格递增）。DB 短暂挂掉时，只要本地号段还有余量就**仍能继续发号**，有一定的容错窗口——这是它比"每次查 DB"方案更健壮的地方。

---

### Q5. 用 Redis 生成分布式 ID 的原理？有什么坑？

**标准答案：**
- 利用 Redis 的 **`INCR` / `INCRBY`** 原子自增命令：每次发号对某个 key 执行 `INCR`，返回的值就是全局唯一递增 ID。
- 为避免单点，可用 Redis 集群，并通过**不同 key + 不同初始值**区分业务；为避免长期无限增长，可配合过期策略或用 `INCRBY` 按号段批量取。

**追问 1：INCR 和 INCRBY 在做 ID 生成器时有什么区别？**
> **答案：** `INCR` 每次只加 1、返回单个 ID，每次发号都要一次网络 IO；`INCRBY key step` 一次加一个步长，可借鉴号段思想一次领走一段 ID 在本地发，减少网络 IO。但要注意：INCRBY 拿到的"段"需要业务端自己管理边界。

**追问 2：Redis 方案的隐患是什么？**
> **答案：** ① **依赖 Redis 可用性**，Redis 宕机或网络抖动影响发号；② **持久化问题**——RDB/AOF 配置不当，Redis 重启后 ID 可能回退导致重复；③ 每次发号有**网络 IO 开销**，性能不如本地生成的雪花算法。所以它适合已有 Redis 且对性能要求不那么极致的场景。

## Part 3：核心区分度题（雪花算法，题眼）

> **这一部分是全题的题眼**——能否讲清 64 位结构、时钟回拨、workerId 分配，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q6. 雪花算法（Snowflake）的 64 位结构是怎样的？

**标准答案：** （能完整讲下位分配基本是 L3+）

雪花算法用一个 **64 位 long** 表示 ID，最高位为符号位固定 0（保证 ID 为正数），其余按段划分：

```
 0 | 0000000000 0000000000 0000000000 0000000000 0 | 00000 | 000000000000
 ↑ | ←──────────── 41 bit 时间戳 ──────────────→ | 5bit | 12bit
符号位             (相对自定义 epoch 的毫秒差)     机房号  序列号
 1 bit                                          5bit    
                    ←──── 10 bit 机器 ID（workerId）──→
```

- **1 位符号位**：固定为 0。
- **41 位时间戳**：当前时间减去自定义起始时间（`epoch`）的**毫秒差**。
- **10 位机器 ID**：常见拆成 5 位 datacenterId + 5 位 workerId，共支持 2^10 = 1024 个节点。
- **12 位序列号**：同一毫秒、同一节点内递增，支持每毫秒 2^12 = 4096 个 ID。

最终 ID = `时间戳 << 22 | 机器ID << 12 | 序列号`。

**追问 1：41 位时间戳能用多久？为什么要自定义 epoch？**
> **答案：** 2^41 毫秒 ≈ 69.7 年。所以从自定义起始时间算起能用约 70 年。自定义一个较近的 epoch（如产品上线时间）可以**延长可用年限**，避免时间戳过早耗尽高位。

**追问 2：12 位序列号意味着什么？容量不够怎么办？**
> **答案：** 意味着单个节点**同一毫秒最多生成 4096 个 ID**，远超一般业务需求；序列号每毫秒归零重来。若单节点 QPS 极高（>4096/ms），超速时该节点会等待下一毫秒，或需要调整位分配（牺牲机器 ID 位给序列号）。

**追问 3：雪花算法是"绝对递增"的吗？为什么？**
> **答案：** **不是**。它是**趋势递增**，不是全局单调递增：① 不同节点的机器 ID 不同，同一时刻各节点生成的 ID 大小取决于机器 ID，A 节点可能小于 B 节点；② 它依赖各机器本地时钟，机器间时钟不完全同步。所以只能保证**同一节点内按时间递增**，整体呈递增趋势。这是高频陷阱题。

---

### Q7. 什么是时钟回拨？雪花算法如何应对？

**标准答案：**
- **时钟回拨**：机器本地时钟因为 NTP 校时、闰秒、虚拟机迁移等原因**倒退到过去时间**。雪花算法强依赖时间戳单调递增，一旦回拨，可能生成与过去**相同时间戳 + 相同序列号**的 ID，导致**全局唯一性被破坏**（主键冲突）。
- 这是雪花算法**最致命的缺陷**。

**追问 1：常见的时钟回拨处理策略有哪些？**
> **答案：** 四类：① **直接抛异常**——拒绝发号并告警，简单但牺牲可用性；② **等待/自旋**——回拨幅度小（几毫秒）时阻塞等时钟追上，回拨大会长时间阻塞；③ **借位/序列号进位**——回拨很短时沿用上次时间戳递增序列号，溢出再等待；④ **逻辑时钟**——如百度 UidGenerator，用 AtomicLong 维护"逻辑时间戳"，物理回拨时仍基于上次值递增，解耦物理时钟。

**追问 2：如果时钟回拨幅度很大（比如几秒甚至更久），应该怎么办？**
> **答案：** 大幅回拨时"等待"和"借位"都不可行（会长时间阻塞或序列号溢出）。工程上通常**拒绝发号 + 告警 + 摘除该节点**，让其它节点继续服务；同时结合运维手段（关闭 NTP 回拨、使用不受 NTP 影响的时钟源、监控时钟偏移）从根上避免。核心思路是：**宁可牺牲局部可用性，也不能产出重复 ID**。

---

### Q8. workerId（机器 ID）如何分配？冲突有什么后果？

**标准答案：**
- workerId 必须在**全局唯一**，否则不同节点在同一毫秒可能生成相同 ID。常见分配方式：
  - **数据库分配**：节点启动时向 DB 插入/抢占一个 workerId（重启后绑定）。
  - **ZooKeeper 分配**：利用 ZK **持久顺序节点**，节点启动时创建一个顺序节点，用其序号作为 workerId；节点下线时删除。
  - **配置中心 / 运维静态配置**：如通过 Nacos、或 K8s StatefulSet 的固定序号分配。

**追问 1：workerId 冲突会造成什么后果？**
> **答案：** 两个节点拿到相同 workerId 后，若在同一毫秒生成 ID，且序列号也相同（都从 0 开始），就会产生**完全相同的 ID**，直接导致**数据库主键冲突 / 数据覆盖**。这是比"趋势递增被打破"严重得多的问题——破坏的是全局唯一性这个底线。

**追问 2：美团 Leaf-snowflake 为什么说"弱依赖" ZooKeeper？**
> **答案：** Leaf-snowflake 启动时会去 ZK 注册顺序节点获取 workerId，但它会把分配到的 workerId **缓存在本地文件**并定期向 ZK 续约。这样即使 ZK 短暂不可用，节点也能用本地缓存的 workerId 继续发号，**不会因 ZK 抖动而全体停摆**——这就是"弱依赖"的含义，是对 ZK 强依赖方案的工程改良。

## Part 4：实战与陷阱题

### Q9. 分库分表场景下，如何用分布式 ID 做路由？

**标准答案：**
- 分库分表常用**取模路由**：`库/表序号 = ID % N`（N 为库或表数量）。用雪花 ID 做路由键时，通常取 ID 的**低位**（序列号部分分布最均匀）参与取模，保证数据均匀分散。
- 也可用 `userId % N` 路由，保证同一用户的数据落在同一分片。

**追问 1：取模路由在扩容时有什么问题？**
> **答案：** N 变化（如从 4 扩到 8）后，`ID % N` 的结果大量改变，导致**几乎所有数据都要迁移**。工程上常用**一致性哈希**，或按 **2 的幂倍数扩容**（如 4→8，原来 `ID%4=0` 的数据一半留在原库、一半迁到新库），把迁移量降到约一半。

**追问 2：为什么不建议直接用雪花 ID 的高位（时间戳）做取模？**
> **答案：** 高位在短时间内变化很小（同一秒内的时间戳高位几乎相同），取模会集中在少数分片，**数据倾斜严重**。低位（序列号/机器 ID）变化快、分布均匀，更适合做分片键。

---

### Q10. 订单号既要可读又要安全，怎么设计？

**标准答案：**
- **可读性/可排序**：订单号里嵌入**时间信息**（如 `yyyyMMdd` + 雪花 ID），便于按时间排序、分库分表按时序归档、人工排查。
- **安全性**：不能让外部**轻易推测出日订单量或业务规模**。

**追问 1：为什么纯自增订单号不安全？**
> **答案：** 纯自增 ID 会让竞品/爬虫通过"今天订单号从 X 涨到 Y"直接**推算出日订单量**，泄露经营数据。所以订单号要在递增基础上混入**用户 ID 哈希、随机数或混淆位**，让相邻订单号之间的间隔不那么容易被解读。

**追问 2：雪花 ID 会暴露信息吗？**
> **答案：** 雪花 ID 里的时间戳可被反推出**生成时间**，机器 ID 可被反推节点数量，但序列号/顺序不易直接推算业务量。因此对内网系统够用；对外的订单号通常再做一层混淆（如拼随机串、加密或自定义编码）。

---

### Q11. 雪花 ID 返回给前端为什么会精度丢失？怎么解决？

**标准答案：**
- 雪花 ID 是 64 位 long，十进制通常 **19 位**；而 JavaScript 的 `Number` 基于 IEEE 754 双精度浮点，**最大安全整数是 2^53-1（9007199254740991，16 位）**。超过后 JS 会**丢失精度**，导致前端拿到的 ID 尾数被改写。

**追问 1：怎么解决？**
> **答案：** 最通用的做法是**后端把 ID 序列化成字符串返回**（Long → String），前端用 string 接收和传递。Java 中可用 Jackson 的 `@JsonSerialize(using = ToStringSerializer.class)` 注解在字段上，或通过全局 ObjectMapper 配置把 Long 统一转 String；前端则避免用 Number 存储和运算该 ID。

**追问 2：为什么不能再转回 Number 处理？**
> **答案：** 一旦转成 Number，精度已经丢失且不可逆。前端对这类 ID 应全程当**字符串**处理（比较相等、作为 key、传给后端都可以），只做"展示和透传"，不做数值运算。

---

### Q12. 发号服务的性能与容灾怎么设计？K8s 下 workerId 如何分配？

**标准答案：**
- **性能**：雪花算法**本地生成、无 IO**，单机可达百万级 QPS，是性能最优的方案；号段模式需关注双 buffer 预加载；Redis/DB 方案要关注网络与连接池。
- **容灾**：发号服务要避免单点，多节点部署；节点故障后workerId 不能被新节点复用造成冲突。

**追问 1：K8s 动态扩缩容时，雪花算法 workerId 怎么分配才不冲突？**
> **答案：** 这是云原生下的难点，因为 Pod 动态创建销毁、IP 不固定。常见做法：① 用 **StatefulSet** 给每个 Pod 固定的序号（ordinal）作为 workerId；② 通过 **ConfigMap/配置中心或 Lease 资源**动态分配并回收 workerId；③ 改用**不依赖 workerId 的方案**（如 UUIDv7、号段模式）从根本上规避。核心是：**workerId 必须全局唯一且节点下线后要正确回收**。

**追问 2：雪花算法和号段模式，高并发场景怎么选？**
> **答案：** 追求**极致性能、本地无依赖**选雪花算法，但要处理好时钟回拨与 workerId；追求**严格单调递增、可控可运维**选号段模式（如 Leaf-segment），代价是有 DB 依赖（但双 buffer 已弱化）。若已是 UUID 体系且想要有序，可考虑 UUIDv7。

---

### Q13. 三个高频陷阱辨析题

**标准答案：**

**陷阱一：雪花算法是绝对有序的吗？**
> **答案：** 不是。它是**趋势递增、单节点内递增**，但**跨节点、依赖各机时钟**，做不到全局绝对递增（详见 Q6 追问 3）。

**陷阱二：美团 Leaf 是强依赖 ZooKeeper 吗？**
> **答案：** 不是。Leaf 有两个模式：**Leaf-segment（号段模式）根本不依赖 ZK**；**Leaf-snowflake** 虽用 ZK 分配 workerId，但做了本地缓存兜底，是**弱依赖**（详见 Q8 追问 2）。

**陷阱三：既然有数据库自增，为什么还要分布式 ID？**
> **答案：** 因为**分库分表 / 多主库**后各库自增主键会重复，无法全局唯一；数据库自增还有单点、IO 瓶颈和扩容困难问题。分布式 ID 正是为解决这些而生。

## Part 5：2026 新趋势：UUIDv7 与云原生发号

> 加分题，考察候选人的技术视野。

### Q14. 什么是 UUIDv7？它为什么值得关注？

**标准答案：**
- **UUIDv7** 由 **RFC 9562（2024 年 5 月发布，取代旧的 RFC 4122）** 定义，属于新一代 UUID 版本（该标准同时定义了 v6、v7、v8）。
- 它的核心特点是**时间有序**：把 **Unix 毫秒时间戳放在高位**，后面跟随机位。因此 UUIDv7 既能像 UUID 一样**本地生成、无需协调机器 ID**，又能**按生成时间排序**。
- 意义：它**兼顾了 UUID 的分布式生成便利与递增 ID 的索引友好**，被认为是有望**替代雪花算法**的新选择——尤其适合数据库主键、时序查询场景。

**追问 1：UUIDv7 的结构大概是怎样的？**
> **答案：** 大致是"48 位毫秒级 Unix 时间戳 + 版本位 + 若干随机位（含变体位）"，共 128 位。时间戳在高位保证了按时间递增，随机位保证唯一性和不可预测性。注意具体位布局以 RFC 9562 为准。

**追问 2：UUIDv7 能完全替代雪花算法吗？**
> **答案：** 不能说"完全"。UUIDv7 的优势是**标准、无状态、不依赖 workerId 分配、无时钟回拨问题**；缺点是 128 位比雪花 64 位**更长**，存储与索引成本更高，且实现成熟度/生态支持还在演进中。雪花算法在**紧凑、极致性能、生态成熟**上仍有优势。选型要结合存储成本、是否已有标准 UUID 体系、团队运维能力综合判断。

---

### Q15. 还有哪些新方案值得了解？云原生下发号设计趋势是什么？

**标准答案：**
- **UUIDv6 / UUIDv8**：v6 是 v1 的"字节序重排"版本，让时间戳高位在前、恢复时间有序；v8 保留自定义格式给用户扩展。二者与 v7 同属 RFC 9562。
- **ULID**：一种"可排序的唯一 ID"格式，时间戳高位 + 随机位，通常编码为 26 个 Crockford Base32 字符，同样时间有序、本地生成。
- **数据库原生有序 UUID**：部分现代数据库开始内置生成有序 UUID 的能力（如较新版本的 PostgreSQL 提供 UUIDv7 生成函数），让应用侧零成本获得时间有序主键。具体函数与版本以官方文档为准。

**追问 1：云原生/K8s 环境下发号设计的趋势是什么？**
> **答案：** 趋势是**尽量做"无状态、免协调"的发号**：要么用号段模式（状态集中在 DB，服务本身无状态、可随意扩缩容），要么用 UUIDv7 这类**不依赖 workerId** 的方案，从根上避开"Pod 动态变化导致 workerId 冲突"的问题。若必须用雪花算法，则配合 StatefulSet/Lease 做 workerId 分配与回收。

**追问 2：这些新方案是"银弹"吗？**
> **答案：** 不是。任何方案都有取舍：UUIDv7 时间有序但更长；号段模式可控但有 DB 依赖；雪花算法紧凑但有时钟回拨。**没有最好的方案，只有最适合当前规模、存储与运维能力的方案**——能讲清这层权衡，是 L5 的标志。

## Part 6：能否用分布式 ID 定级？如何定级？

### 结论先行

**可以，分布式 ID 是分布式基础里区分度很高的探针**——因为它天然分层：会调工具类 → 知道有雪花/号段等方案 → 懂 64 位结构 → 懂时钟回拨与 workerId → 能结合分库分表/前端/容灾做实战设计 → 了解 UUIDv7 等演进。但要注意：**初中级候选人往往只会用不会讲原理**，强问源码只会考察背诵，要结合岗位使用。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 用过 UUID / 雪花工具类，知道要全局唯一；说不清方案区别与位结构 |
| **中级（L2）** | 2–5 年 | Part 2 | 知道自增/号段/Redis 方案与优缺点，懂号段双 buffer、多主模式 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能讲清雪花 64 位结构、时钟回拨处理、workerId 分配 |
| **高级（L4）** | 8 年+ | Part 4 | 能结合分库分表路由、订单号、前端精度、容灾做实战设计 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 了解 UUIDv7/RFC 9562 等演进，能在云原生下做方案选型与权衡 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"全局唯一 + 趋势递增 + 雪花算法 64 位"→ 至少 L2；只知道"用雪花算法生成 ID"→ 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"：
- 为什么索引喜欢递增 ID？（B+ 树页分裂）
- 为什么雪花是趋势递增而非绝对递增？（跨节点 + 时钟）
- 为什么时钟回拨危险？怎么处理？（唯一性被破坏；等待/抛异常/借位/逻辑时钟）

**第三步：三类信号防背题。**
1. **真实性**：能否讲出**具体的生产实践**（"我们分库分表用 userId 取模 8"、"双 buffer 阈值设 10%"、"Long 转 String 解决前端精度"）。
2. **抽象能力**：能否把各方案统一为"**唯一性来源 + 有序性 + 是否依赖外部组件 + 容量/运维成本**"的对比框架。
3. **权衡能力**：能否讲清"什么场景不该用雪花算法"（如无法保证时钟稳定、节点频繁扩缩容）。

**第四步：按最深层级定级，不按正确率。** 结合岗位难度调整追问深度——业务开发到 Part 4 足够，基础架构才需深挖 Part 5。

---

### 面试官避坑提醒

- **不要对所有人问到时钟回拨源码级**——很多优秀中级工程师没背过实现但理解思想，区分"理解设计"和"背过源码"，前者更有价值。
- **把"时钟回拨 + workerId"作为 L3 分水岭**：能讲清这两点的，一定是真懂雪花算法。
- **注意 2026 新趋势的准确性**：RFC 9562 是 2024-05 发布、定义了 v6/v7/v8；不确定的数据库函数签名保守表述，别编造 API。
