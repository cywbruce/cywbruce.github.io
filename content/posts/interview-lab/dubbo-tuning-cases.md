## Part 0：30 秒标准总答

**Q：线上 Dubbo 调用超时 / 报错，你从哪几个角度排查？**（标准答法 30 秒，五个得分点）

**标准答案：**
> 第一步 **看现象**：分清属于哪类——调用失败/超时、性能瓶颈、注册发现异常、扩展兼容问题；看报错类型（`TimeoutException` / `No provider`）、P99、QPS、重试次数。
> 第二步 **看手段**：查日志与 `telnet localhost 22222`（qos 的 `ls`/`count`/`invoke`/`trace`/`help`）、Dubbo Admin、AccessLog/慢调用日志、Micrometer + Actuator 指标——用数据说话。
> 第三步 **定位层级**：沿 Invoker 链判断问题在路由（Router）/ 集群（Cluster、负载均衡、重试）/ 协议与长连接 / 业务线程池 / 序列化 / 注册中心元数据哪一层。
> 第四步 **验证根因**：用 `trace` 看真实调用耗时与参数、dump 线程堆栈看排队、灰度复现，区分"真超时（下游慢）"与"假超时（线程池排队、GC STW、长连接阻塞、重试放大）"。
> 第五步 **修复并预防**：扩容/限流/隔离/改幂等/切协议，前后量化 P99 与错误率，补线程池活跃度、慢调用、注册推送告警防复发。

**评分要点：** 看现象 / 看手段 / 定位层级 / 验证根因 / 修复预防五点。能说出"先分层再验证闭环"的直接往 Part 4 追问真实案例；只答"调大 retries、加线程数"的从 Part 1 问起。

## Part 1：基础认知题（调优维度与观测手段）

### Q1. Dubbo 调优有哪些常见维度？为什么必须"先定位再调"？
**标准答案：** 四类：① **调用失败/超时**——Cluster 层 Failover/Failfast、重试次数、超时时间；② **性能瓶颈**——业务线程池、序列化（Hessian2/Protobuf）、长连接/编解码、大字段；③ **注册发现异常**——地址推送、本地缓存、服务自省元数据；④ **扩展与兼容性**——SPI、泛化调用、序列化版本、version/group。必须先定位，因为**症状与根因常常错位**：超时可能是下游慢，也可能是线程池排队、GC STW、长连接队头阻塞或重试放大。盲调的危害：参数相互制约（`retries` 增大反而放大流量）、掩盖真因致复发、引出新问题（盲目加线程反压垮下游）、无法量化收益与回滚。

**追问 1：为什么说"超时先调大 retries"通常是错的？**
> **答案：** 重试只在"偶发、瞬时、幂等"失败时有益；持续超时重试会放大流量（1 次变 N 次）、把偶发变雪崩（案例一/四）。正解是先定位超时发生在哪一层，再决定重试/超时/限流/扩容。

**追问 2：接手一个"很慢"的 Dubbo 服务，第一步做什么、不做什么？**
> **答案：** 先量化现象（哪个接口、P50/P99、QPS、错误率、哪类报错），拉出日志与指标；不做的是一上来改 `threads`/`retries`/`timeout`、重启实例——没有基线的"优化"既无法验证也无法回滚。

### Q2. 调优/排障有哪些关键观测手段？各自能回答什么问题？
**标准答案：**

| 手段 | 命令/入口 | 主要回答 |
|------|-----------|---------|
| 服务治理台 | Dubbo Admin | 服务/实例列表、路由规则、配置、订阅关系、调用统计 |
| QoS 在线排查 | `telnet localhost 22222`：`ls`/`ls -l`、`count <svc>`、`invoke <svc.method(args)>`、`trace <method> [n]`、`help`、`status -l` | 在线服务清单、成功/失败/耗时分布、直连验证、最近调用现场 |
| 访问日志 | `accesslog="true"`（写 `$HOME/dubbo/access.log`） | 每次调用的调用方 IP、方法、参数、耗时、结果 |
| 慢调用日志/压缩 | 配慢调用阈值记录长尾调用；`compression=lz4` | 抓 P99 长尾请求、缩小大报文传输体积 |
| 指标监控 | Micrometer + Actuator `/actuator/metrics`（`dubbo.provider.*`、`dubbo.threadpool.*`） | 请求数、耗时直方图、线程池活跃度、注册表变化 |

慢日志/`trace` 告诉你"哪个慢、慢在哪次"，`count`/指标告诉你"慢多少、多频繁"，线程堆栈告诉你"为什么慢"。

**追问 1：`trace` 和 `count` 分别能回答什么？怎么配合？**
> **答案：** `count <service>` 给服务级成功/失败数与平均/最大耗时（看整体分布）；`trace <method> 10` 抓最近 10 次调用的耗时、参数、调用方 IP（看具体现场）。先用 `count` 发现异常，再用 `trace` 定位到具体请求与 provider。

**追问 2：临时开 AccessLog/慢调用日志会影响线上吗？怎么安全开？**
> **答案：** 会额外写磁盘、增加序列化开销。生产要按需、短暂、分级：先设较高慢调用阈值抓最慢的长尾，定位后及时关；AccessLog 采样或限定接口开启，避免全量长时间开启拖慢调用。

### Q3. 原理复盘：为什么说 Dubbo 是"URL 驱动 + Invoker 链路"，任一环节都能出问题？
**标准答案：** Dubbo 把协议、地址、`timeout`、`retries`、`loadbalance`、`serialization`、`version`/`group` 等全部拼进 **URL** 在各层传递，每个 SPI 扩展点按 URL 参数决定行为。一次调用链路：`Proxy → Cluster(Directory/Router/LoadBalance) → Protocol → Exchange → Transport(Netty) → Serialize → Provider 业务线程池 → 反射调用 → 原路返回`。每层都是可替换扩展点，**任一层配错或过载都表现为超时/报错**：路由配错→打到错版本；重试配错→重复写；序列化不匹配→反序列化异常；线程池满→被拒。因此排查必须"分层对齐"，而非笼统说"Dubbo 慢"。

**追问 1：URL 参数写错（如 `version`/`group`/`serialization`）为什么能导致 No provider 或序列化失败？**
> **答案：** Consumer 与 Provider 的 URL 参数必须匹配才能建 Invoker：`version`/`group` 不一致 → Directory 过滤后无可用 Invoker（案例三）；`serialization` 两端不一致 → 编解码失败。排查第一步就是对比两端实际注册/订阅的 URL。

**追问 2：为什么调参常"按下葫芦浮起瓢"？**
> **答案：** 参数跨层耦合——`retries` 影响 Cluster 流量、`threads` 影响业务线程池、`connections` 影响长连接、`compression` 影响编解码与带宽。改一处会沿链路传导（如加线程数放大下游压力），所以每次调参都要配基线与量化验证。

## Part 2：底层原理题（与调优决策相关的 Dubbo 机制）

> 聚焦"做调优/排障决策时必须懂的 Dubbo 机制"，不重讲分层与 SPI 定义（见《服务治理》题库）。这是 L2→L3 的关键。

### Q4. Cluster 容错六种模式（Failover/Failfast/Failsafe/Failback/Forking/Broadcast）的语义与幂等关系？
**标准答案：**

| 模式 | 行为 | 与幂等关系 / 适用 |
|------|------|------------------|
| **Failover**（默认） | 失败自动切换其他节点，`retries` 默认 2 | 只对读/幂等安全；写操作超时重试会重复写（案例四） |
| **Failfast** | 失败立即报错，只调一次 | 非幂等写首选 |
| **Failsafe** | 失败忽略、记日志 | 审计/埋点等非关键调用 |
| **Failback** | 失败记录、定时重发 | 消息通知类 |
| **Forking** | 并行调多个，第一个成功即返回 | 实时性高、容忍资源浪费 |
| **Broadcast** | 逐个广播所有节点，任一失败即失败 | 通知所有节点刷新缓存 |

核心判据：**只有幂等操作才适合自动重试**；`retries=2` 意味着最多调用 3 次（1 次原始 + 2 次重试），流量放大系数约 ×3。

**追问 1：Failover 为什么对写操作危险？"响应超时"等于"调用失败"吗？**
> **答案：** 不等于。Provider 可能已执行成功，只是回包延迟/丢失；Failover 重试就会重复执行。写接口必须改 Failfast 或保证业务幂等（唯一键/CAS）。

**追问 2：Forking 和 Broadcast 有什么区别？各什么时候用？**
> **答案：** Forking 并行调用多个、取首个成功结果（冗余求快、浪费资源）；Broadcast 顺序调用全部、任一失败即失败（如"通知所有节点清理本地缓存"，要保证每台都收到）。

### Q5. 线程池模型：IO 线程 vs 业务线程、隔离、默认 fixed 200、队列与拒绝策略？
**标准答案：** Netty 的 boss/worker **IO 线程**（`iothreads` 约 CPU+1）只负责收发包与编解码，默认 `dispatch=all` 把请求转给**业务线程池**执行真实调用——两者分离，慢业务不直接卡死网络收发。业务线程池默认 **`fixed` 类型、200 线程、`queues` 默认很小/为 0**（无缓冲，占满即拒）；类型还有 `cached`/`limited`/`eager`（eager 先扩线程再入队，适合短突发任务，长任务会线程暴涨）。默认拒绝策略 **`AbortPolicyWithReport`**：拒绝前先把完整线程堆栈 dump 到 `$HOME/dubbo-jstack-*.log` 再抛 `RejectedExecutionException`——**这份 dump 是排查线程池问题的金矿**。核心/非核心业务应用不同线程池实例隔离，防一条慢链路拖垮全部。

**追问 1：`eager` 线程池适合什么？为什么长耗时任务不宜用？**
> **答案：** eager 在队列未满时先创建线程到 `threads` 上限，对"短、突发"任务响应快；但长耗时任务会让线程数迅速冲到上限、上下文切换与内存开销大，反而更慢，长任务宜用 `fixed` + 有界队列 + 拒绝。

**追问 2：jstack dump 里大量线程卡在同一业务方法/下游调用，说明什么？下一步？**
> **答案：** 说明业务线程被慢调用占满（线程池打满的直接证据）。下一步沿这条调用看下游 P99、trace 各 Span 耗时、下游自身线程/GC，确认是"下游真慢"还是"本端排队"。

### Q6. 序列化成本：Hessian2 / JSON / Protobuf 的性能与兼容性？大字段的开销？
**标准答案：**

| 序列化 | 体积/速度 | 兼容性 | 适用 |
|--------|----------|--------|------|
| **Hessian2**（默认） | 紧凑二进制、较快 | 无 IDL、靠字段名，字段增删需谨慎 | Java 生态默认 |
| **JSON**（Fastjson/Jackson） | 文本、体积大、较慢、可读 | 弱 schema、跨语言友好 | 网关/调试/开放接口 |
| **Protobuf** | 最小最快 | 有 IDL + 字段编号，天然向前/向后兼容 | 强契约、高性能、跨语言 |

序列化成本随对象体积线性增长，**两端各做一次编解码**；大对象/大字段（如 5MB 报文）会显著拉长调用耗时，且在 Dubbo2 单长连接上阻塞后续请求（案例九）。对策：字段裁剪、分页、压缩、拆接口、换高效序列化或 Triple。

**追问 1：为什么大字段会让调用变慢甚至超时？**
> **答案：** 大对象序列化/反序列化耗时长（占用 IO 与业务线程），网络传输时间随体积增长，若超时时间按小包设定就会超时；单连接下还形成队头阻塞拖累其他接口。

**追问 2：Hessian2 加字段/删字段的兼容性如何？如何灰度？**
> **答案：** Hessian2 靠字段名匹配、无 schema：加字段相对安全（老端忽略新字段），删字段/改类型会让老端读到 null 或类型不匹配（案例十）。灰度应"只增不删、保留兼容字段"，配合 `version` 隔离、Consumer 先升级，强契约场景迁 Protobuf。

### Q7. 长连接与粘滞连接：Request ID 关联、连接数过多过少的取舍？
**标准答案：** Dubbo2 默认每个 Provider **单长连接**（`connections=1`），报文头带 8 字节 **Request ID**，在同一连接上连续发多请求、响应回来靠 ID 找到对应 Future 唤醒线程——实现异步关联与高并发，连接少、握手开销低，适合小包高并发。**代价是大包/慢响应造成队头阻塞**（案例九）。`connections=N` 可开多条连接分散，但增加 fd、握手与服务端连接压力；`sticky=true` 粘滞连接复用同一连接，对有状态场景友好但可能负载不均。Triple（HTTP/2 多流）从协议层消除队头阻塞。

**追问 1："偶发超时但下游很快"为什么可能是长连接队头阻塞？**
> **答案：** 同一连接上某请求返回大对象/慢响应，序列化与传输占住连接，后续请求排队等待，表现为"下游快、消费端偶发超时"。看连接数、响应体大小、`connections` 配置与抓包可验证（案例二）。

**追问 2：连接数是不是越多越好？如何评估？**
> **答案：** 不是。过多连接增加握手/内存/fd 与服务端负担、可能触发连接数上限；过少则队头阻塞与单连接带宽瓶颈。按响应体大小、并发量与压测拐点评估，大包场景优先改协议/分页而非单纯加连接。

### Q8. 注册中心缓存：`~/.dubbo` 本地缓存、挂了仍可用、地址推送风暴、服务自省元数据？
**标准答案：** Consumer 会把订阅到的 Provider 列表写到 `$HOME/dubbo/` 下的本地缓存文件（`*registry*.cache`），**注册中心挂了仍能用本地缓存 + 已建连接继续调用**（但感知不到上下线，故**禁止重启**）。注册中心抖动恢复时可能触发**全量地址推送**，Consumer 重建 Invoker 树、重算路由、拉元数据，CPU/GC 飙高（案例七）。应用级服务发现把注册维度从"实例×接口"降为"实例"，接口信息走**服务自省元数据服务**按需拉取，大幅降低推送量；但元数据不一致会导致 No provider / No such method（案例三）。

**追问 1：注册中心抖动后消费端 CPU 飙高，可能是什么？**
> **答案：** 全量地址推送 + Invoker 重建 + 路由重算 + 元数据拉取 + 本地缓存反复重写，形成推送风暴。应看"Received new provider list"日志、`Directory.notify` 堆栈、缓存文件写入频率。

**追问 2：应用级服务发现为何能缓解推送压力？元数据不一致为何导致 No provider？**
> **答案：** 维度从"实例×接口"降为"实例"，数据量骤降；接口→应用映射与方法元数据由服务自省机制单独维护，若元数据未上报/映射缺失，Consumer 解析不到接口对应实例，就报 No provider。

### Q9. 服务降级 Mock 与限流：force/fail、TPS 方法级限流、令牌桶/信号量？
**标准答案：** Mock 降级：`mock=force:return+null`（**直接返回兜底、不发调用**，适合依赖已下线/非核心）与 `mock=fail:return+null`（**调用失败后才兜底**，适合容错），可实现名为 `接口名Mock` 的类返回定制值。限流：Dubbo 提供 TPS 限流（可细化到方法级，基于令牌桶/滑动窗口的 `TpsLimitFilter`），也可配合 Sentinel 做 QPS/并发线程数/信号量隔离——**信号量隔离**限制某资源的并发数而不新增线程，适合保护下游。限流要放在入口与关键资源，配合快速失败，而非靠加线程硬扛。

**追问 1：force 和 fail 两种 mock 各适合什么场景？**
> **答案：** force 用于明确知道依赖不可用、主动短路（如大促降级非核心）；fail 用于"正常调、失败兜底"（如查缓存失败返回默认值）。前者保护调用方线程，后者保证可用性。

**追问 2：令牌桶 vs 信号量限流？为什么线程池打满时限流比加线程更有效？**
> **答案：** 令牌桶控"速率"（允许一定突发），信号量控"并发数"（同时占用的资源上限）。线程池打满的根因是处理能力 < 进入速率，加线程会放大下游压力；限流从入口削峰、快速失败，才是治本（配合扩容）。

## Part 3：核心区分度题（分层定位，题眼）

> 全题**题眼**——能否把"现象 → 指标 → 层级 → 根因"系统性用于超时/No provider/性能问题，直接决定 L2 还是 L3/L4。

### Q10. 如何系统性定位"调用超时"？
**标准答案：** 先量化（哪个接口、P99/QPS、报错类型）。再**按层拆解**：① **网络/连接层**——连接数、是否队头阻塞、网络抖动；② **序列化层**——大对象、耗时是否在编解码；③ **业务线程池层**——活跃度、队列、拒绝日志、jstack dump；④ **下游层**——trace 看各 Span、AccessLog 看 Provider 实际耗时；⑤ **JVM 层**——GC STW（老年代 GC  pause）；⑥ **Cluster 层**——重试是否放大流量。工具组合：`count`/`trace`、AccessLog、jstack 堆栈、GC 日志、Micrometer elapsed 直方图。**区分"真超时"（下游确实慢）与"假超时"（排队/GC/阻塞/重试）——靠 Provider 侧 AccessLog 耗时与 Consumer 侧 trace 对比。**

**追问 1：`trace` 显示 Provider 侧耗时只有 5ms，Consumer 侧却超时 1s，问题在哪一层？**
> **答案：** 不在业务方法本身，而在框架/链路侧：业务线程池排队（5ms 执行但等了 1s 线程）、序列化大对象、网络/长连接队头阻塞、或 Consumer 侧 GC STW/重试。对比 AccessLog 的"方法耗时"与"从发起到返回的总耗时"即可定位差额。

**追问 2：如何区分"下游真慢"和"本端线程池排队"？**
> **答案：** 看 Provider 线程池活跃度是否满载、jstack 是否卡在队列、是否有 `AbortPolicyWithReport` dump；若线程均闲、AccessLog 方法耗时本身就高，则是下游/业务真慢；若方法耗时低但线程排队久，则是本端线程池问题。

### Q11. 如何定位"No provider / No such method"？
**标准答案：** 沿维度逐一核对：① **version/group** 是否匹配（Consumer 订阅与 Provider 注册必须一致）；② **方法签名**（参数类型、个数、重载）是否一致；③ **服务自省元数据**——应用级发现下接口→应用映射是否注册、元数据服务是否可达；④ 用 `qos ls` / Admin 看实际注册的服务与地址；⑤ 用 `qos invoke` 直连验证服务本身是否健康；⑥ 两端接口 jar 版本是否一致。**核心是把"服务有没有注册"与"Consumer 能不能匹配到"分开看**——`ls` 能看到不代表订阅能匹配。

**追问 1：`qos ls` 能看到服务，但调用报 No such method，最可能什么原因？**
> **答案：** 方法签名/重载不匹配或接口 jar 版本不一致——Consumer 按"方法名 + 参数类型签名"找方法，Provider 端改了参数类型或没那个重载就会报此错。`invoke` 用正确签名能调通即可确认。

**追问 2：应用级服务发现下，为什么"服务明明部署了却 No provider"？**
> **答案：** 元数据未上报、接口→应用映射缺失、分组/版本不匹配，都会让 Consumer 解析不到实例。要查元数据服务状态、Admin 里的应用→接口映射与订阅关系一致性。

### Q12. 偶发超时但下游接口很快，怎么排查？
**标准答案：** 锁定四类"假超时"：① **线程池排队**——慢请求占线程，其他请求排队；② **GC STW**——老年代 GC 导致偶发长停顿；③ **长连接复用队头阻塞**——大包/慢响应挡住同连接后续请求；④ **重试放大**——超时→重试→流量倍增→更多超时（正反馈）。手段：多次 `trace` 采样 + jstack + GC 日志 + 连接数/响应体大小指标 + 重试率统计。"偶发"比"持续慢"难在不好复现，需采样、压测或故障注入抓取现场。

**追问 1：为什么"偶发"比"持续慢"更难查？如何复现？**
> **答案：** 偶发问题采样窗口短、现场易逝。靠多次 `trace`/慢调用日志攒样本、压测抬升负载放大概率、或注入延迟/大包复现；关键是先把"偶发"变成"可观测的样本分布"。

**追问 2：重试放大会怎样把"偶发"变成"大面积"？**
> **答案：** 偶发超时触发 Failover 重试 → 请求量 ×N → 本已吃紧的下游更慢 → 更多请求超时 → 更多重试，形成雪崩正反馈。必须克制重试次数、只对幂等操作重试、配熔断与限流切断循环。

### Q13. 路由规则配错导致流量打到错误版本 + qos 在线排查技巧？
**标准答案：** **标签路由/条件路由**按 version、分组、IP、方法参数或 tag 分流，灰度发布常用。配错表现：灰度流量打到稳定版、或流量全打到新版本。排查：Admin 看路由规则与优先级、条件表达式（如 `host=192.168.1.*`）、provider 是否打了 tag，`qos trace`/`count` 看实际命中的 provider IP。**qos 在线技巧**：`ls -l` 列详情、`count <svc>` 看分布、`invoke <svc.method(args)>` 不重启直连验证某 provider、`trace <method> 10` 抓最近调用、`status -l` 看健康、`get`/`set` 看改配置（改完验证即回滚）。

**追问 1：标签路由和条件路由有什么区别？灰度更常用哪个？**
> **答案：** 条件路由用条件表达式对地址/参数过滤，灵活但易写错；标签路由给 provider 打 tag、按 tag 圈定灰度实例池，规则简单、隔离清晰。灰度更常用标签路由（配合流量比例/用户维度分流）。

**追问 2：不重启服务如何在线验证某 provider 的方法是否健康？**
> **答案：** 用 `qos invoke` 直连该 provider 的 IP:port 调用目标方法，看返回与耗时；配合该 provider 的 `trace`/`count` 与 AccessLog，定位是否单实例异常（而非整体问题）。

### Q14. 如何做容量评估？
**标准答案：** 核心公式：**所需 Provider 数 = 峰值 QPS × (1 + 重试放大系数) / 单机安全 TPS**，再加 N+1 冗余。单机安全 TPS 靠压测找拐点：CPU<70%、线程池未满、P99 达标、零拒绝时的最大稳定吞吐，按 70% 水位留余量。必须计入 **Failover 重试放大**（`retries=2` → 约 ×3 流量）、序列化/大字段开销、连接数与下游瓶颈。容量不足的典型演进：排队 → P99 陡升 → 线程池拒绝 → 超时雪崩。

**追问 1：为什么容量评估必须把重试算进去？**
> **答案：** Failover 在失败时重试其他节点，`retries=2` 最多把流量放大到 3 倍。若按 1 倍估算，故障重试时实际流量远超容量，直接压垮集群——案例一的雪崩正源于此。

**追问 2：压测时单机 TPS 到拐点后继续加压会出现什么？**
> **答案：** 线程排队 → P99 非线性陡升 → 队列/线程池打满触发 `AbortPolicyWithReport` 拒绝 → Consumer 超时重试 → 流量进一步放大 → 大面积超时雪崩。压测的目的正是找到这个拐点并留出水位。

## Part 4：实战案例题（本套重点，事故复盘驱动）

> 给出现场现象，让候选人按"现象 → 排查 → 根因 → 修复 → 量化结果 → 预防"完整复述。能否给出命令、参数与**前后量化数字**，是 L4 分水岭。

### Q15. 案例一：大促期间 Provider 线程池打满、调用大面积超时
**标准答案：**
**现象→排查：** 大促峰值 Consumer 大面积 `TimeoutException`，错误率 0.1%→15%、P99 200ms→3s。`qos count` 失败数飙升，`status -l` 线程池活跃 200/200；`$HOME/dubbo-jstack-*.log` 出现 `AbortPolicyWithReport` dump，200 个业务线程大量卡在同一 `OrderService.query` 的下游 HTTP 调用；`trace` 显示 `retries=2`。
**根因→修复：** 下游库存服务变慢 → 请求在 Provider 业务线程堆积 → 线程池打满被拒 → Consumer Failover 重试 ×3 放大流量 → 雪崩。应急扩容 Provider 2→8 台 + 非核心调用限流 + 熔断下游；根治：下游调用加 800ms 超时与熔断、核心/非核心线程池隔离、写接口 `retries=0`、按压测重设 `threads`/`queues`。
**量化→预防：** P99 3s→180ms，错误率 15%→0.01%，线程活跃度稳定 <60%。建立线程池活跃度/拒绝数/重试率告警，大促前全链路压测与容量评估。

**追问 1：为什么"加线程数"不是根治？**
> **答案：** 下游慢的根因没变，加线程只会让更多请求同时压向下游、加速打满，还增加上下文切换开销，只是延缓崩溃。治本是下游超时/熔断 + 入口限流 + 扩容 + 隔离。

**追问 2：dump 里大量线程 WAITING 在下游调用，下一步怎么确认是下游慢？**
> **答案：** 看下游服务 P99 与线程池/GC、trace 各 Span 耗时分布（耗时集中在下游 Span）、下游日志；若下游自身耗时高即可确认，而非本端序列化或排队。

### Q16. 案例二：调用偶发超时但下游接口很快
**标准答案：**
**现象→排查：** 每天几十次随机 1s 超时，Provider AccessLog 显示业务方法仅 3–8ms。多次 `trace` 采样见耗时分散在 Consumer 端、无线程池满；GC 日志见偶发 Full GC 200–400ms STW；超时集中在某几个 provider；抓包发现其中一台有 1MB 响应包，`connections=1`。
**根因→修复：** Dubbo2 **单长连接队头阻塞**——某请求返回大对象（序列化+传输约 900ms）占住连接，后续请求排队；叠加偶发 GC STW，下游本身很快。修复：大字段改分页/按需返回、`compression=lz4`、`connections=1→4` 分散、拆分大接口、GC 调优。
**量化→预防：** 超时 40 次/天→0，P99 1s→120ms，GC pause 400ms→80ms。加响应体大小 P99 监控、连接级慢请求告警、GC 告警。

**追问 1：为什么"下游很快"还可能超时？**
> **答案：** 耗时可能在框架侧——序列化大对象、网络/长连接排队、GC STW、重试等待，而不在业务方法本身。对比 AccessLog 的"方法耗时"与 Consumer 的"端到端耗时"差额即可定位。

**追问 2：connections 加大一定能解决队头阻塞吗？**
> **答案：** 只能缓解（把请求分散到多连接），单连接多请求模型固有的队头阻塞仍在；根治靠分页/压缩减小报文，或迁 Triple（HTTP/2 多流彻底消除队头阻塞）。

### Q17. 案例三：加了 version 后消费者找不到服务（No provider）
**标准答案：**
**现象→排查：** 上线给 Provider 加 `version=2.0.0`，Consumer 未改，启动即 `No provider available`。`qos ls` 看 provider 实际注册 URL 的 version=2.0.0、Consumer 订阅 URL version 为空；Admin 核对分组与元数据；`qos invoke` 直连能调通，说明服务本身健康。
**根因→修复：** `version`/`group` 是服务匹配关键维度，两端不一致则 Directory 过滤后无 Invoker；应用级发现下还叠加服务自省元数据中接口→应用映射的版本/分组差异。修复：Consumer 同步 version，或 Provider 先双版本注册灰度过渡、核对 group、确认元数据上报成功。
**量化→预防：** No provider 错误归零，灰度切流 24h 无异常后下线旧版本。把 version/group 变更纳入发布检查清单，用 Admin 做订阅关系一致性校验，禁止单边改动。

**追问 1：`qos ls` 能看到 provider，为什么还说 No provider？**
> **答案：** `ls` 显示的是"已注册实例"，但 Consumer 还会按 version/group/路由规则过滤；过滤后无匹配 Invoker 就报 No provider。两者是不同环节，必须分开看。

**追问 2：应用级服务发现下，版本匹配还涉及什么？**
> **答案：** 还涉及元数据服务中注册的接口列表与方法签名、接口→应用映射的版本/分组。元数据未同步或映射缺失，即便实例在也会匹配失败。

### Q18. 案例四：Failover 重试导致重复写入
**标准答案：**
**现象→排查：** 订单创建偶发重复（同一业务单生成 2 条），用户投诉。日志见同一 traceId 有两个不同 provider IP 的 `createOrder`；`qos trace` 显示第一次调用其实在 Provider 成功了，但响应超时（网络抖动 1.2s > timeout 1s），`retries=2`、`cluster=failover`。
**根因→修复：** Failover 对"响应超时"重试，而"超时≠失败"——Provider 已成功执行，重试造成重复写。修复：写接口改 `cluster=failfast` + 业务幂等键（requestId/业务唯一键 + 唯一索引）；读接口保留 Failover 但 `retries=1`；设合理 timeout 并加幂等校验。
**量化→预防：** 重复订单 ~5 单/天→0，写入成功率 99.7%→99.95%。按幂等性分类配置容错策略，代码评审强制写接口幂等键，重试率纳入监控。

**追问 1：为什么"响应超时"不等于"调用失败"？**
> **答案：** Provider 可能已执行成功，只是回包延迟/丢失。Consumer 侧只看到"没在超时时间内收到响应"，无法据此断定业务未执行——这正是非幂等写不能盲目重试的根源。

**追问 2：除了改 failfast，还有哪些手段防重复？**
> **答案：** 业务幂等键 + 唯一索引、去重表、状态机 CAS、幂等 Token、事务消息。核心是让"重复请求"在业务层被识别并幂等处理，不依赖 RPC 层不重试。

### Q19. 案例五：泛化调用传参类型错误导致 Hessian 序列化失败
**标准答案：**
**现象→排查：** 开放平台网关用 `GenericService` 泛化调用，`HessianException: cannot serialize object` / `No such method`，部分请求失败。查参：网关把金额传成 `String "19.9"`、`int` 传成 `Long`，而接口签名是 `BigDecimal` / `int`；泛化调用靠"方法名 + 参数类型字符串数组 + Object[] 参数值"三元组，`qos invoke` 用正确类型能调通。
**根因→修复：** 泛化调用**无编译期类型检查**，Map/List 的 value 类型与接口 POJO 字段不符时 Hessian 无法编解码，类型签名字符串写错则报 No such method。修复：按接口签名传参（类型用全限定名如 `java.math.BigDecimal`）、Map→POJO 确保字段类型一致、网关维护接口元数据并做入参校验、复杂对象显式构造 DTO 而非裸 Map。
**量化→预防：** 泛化失败率 2%→0、网关 P99 降约 30%（少了异常重试）。加泛化参数 schema 校验、接口元数据版本管理、契约测试。

**追问 1：泛化调用为什么不像普通调用那样在编译期报错？**
> **答案：** 泛化调用无需接口 jar，靠动态代理 + 方法名 + 类型字符串 + 反射在运行时匹配，编译期没有强类型约束，错误只能到运行期序列化/调用时才暴露。

**追问 2：Map 传参时 Hessian 常见坑有哪些？**
> **答案：** value 类型被推断为 HashMap/LinkedHashMap 而非目标 POJO、数字默认 Integer/Long 与 BigDecimal 不匹配、泛型擦除导致元素类型丢失。对策是显式构造对象并校验字段类型。

### Q20. 案例六：RpcContext 隐式参数在异步回调中丢失
**标准答案：**
**现象→排查：** 全链路 traceId 在 Consumer→Provider 正常，但 Provider 异步处理（CompletableFuture 回调/自定义线程池）后日志里 traceId 变空、链路断裂。查代码：用 `RpcContext.getContext().getAttachment("traceId")` 取参数，而异步回调在新线程执行——`RpcContext` 基于 **ThreadLocal**，不跨线程传播，回调线程取不到父线程的 attachment。
**根因→修复：** ThreadLocal 线程隔离 + 异步切线程 → 隐式参数丢失。修复：提交异步任务前把 traceId 取出作为方法参数**显式传递**（或用 `TransmittableThreadLocal`/`TaskDecorator` 透传），回调中从入参恢复 attachment，或借 SkyWalking/OTel Agent 的跨线程传播。
**量化→预防：** traceId 丢失率 100%→0、异步链路完整率 99.9%。规范"隐式参数不跨线程、跨线程显式传"，用代码模板与静态检查落地。

**追问 1：为什么 RpcContext 用 ThreadLocal 而不是全局？**
> **答案：** 为了请求隔离、避免并发调用串参——每个请求的上下文绑定在处理线程上。代价就是不跨线程，异步/回调场景必须显式传递。

**追问 2：除了显式传参，还有哪些跨线程透传方案？**
> **答案：** `TransmittableThreadLocal`（阿里 TTL）、自定义 `TaskDecorator` 在提交任务时复制上下文、Agent 字节码增强（SkyWalking/OTel）自动传播。本质都是把父线程上下文在切线程时带到子线程。

### Q21. 案例七：注册中心抖动导致地址全量推送、消费端 CPU 飙高
**标准答案：**
**现象→排查：** Nacos 集群短暂抖动恢复后，所有 Consumer CPU 20%→90%、GC 频繁、调用超时增多。Consumer 日志大量 "Received new provider list / notify"，实例数没变却收到全量推送；堆栈见大量线程在做 URL 解析、Invoker 重建、`Directory.notify`；`$HOME/dubbo/*registry*.cache` 被反复重写。
**根因→修复：** 抖动触发订阅变更，接口级模型推送"实例×接口"全量地址，Consumer 重建 Invoker 树 + 重算路由 + 拉元数据 → CPU/GC 飙升；大量实例同时重连成推送风暴。应急：**禁止重启 Consumer**（重启丢本地缓存、加剧全量拉取），限流推送、分批恢复；根治：升级应用级服务发现（只按实例推送）、开启增量推送与变更去重、确认本地缓存兜底生效、注册中心多活隔离。
**量化→预防：** CPU 90%→25%、全量推送次数降约 95%，故障期成功率保持 99.9%。加推送变更/Invoker 重建次数告警，注册中心多活，杜绝"抖动即重启"。

**追问 1：为什么"禁止重启"是这里的关键动作？**
> **答案：** 重启会清空本地缓存、触发全量重新订阅与地址拉取，在注册中心刚恢复、正在推送风暴时重启等于火上浇油，可能把局部抖动放大成全站不可用。

**追问 2：应用级服务发现为什么能降低推送量？**
> **答案：** 注册维度从"实例×接口"降为"实例"，接口列表与方法元数据走独立元数据服务按需拉取，地址推送体积与重建成本大幅下降。

### Q22. 案例八：自定义 Filter 顺序不当导致 traceId 断链/Span 丢失
**标准答案：**
**现象→排查：** 接入 SkyWalking 后部分 Dubbo 调用链断裂——Consumer 有 Span、Provider 没有，或 traceId 不一致。查自定义鉴权/日志 Filter 的 `@Activate(order=...)`：Provider 端 Filter 链里自定义 Filter 排在 TraceFilter 之前且鉴权失败时提前 `return`，导致 TraceFilter 未执行、上下文未建立；或自定义 Filter 起新线程却没透传 TraceContext。
**根因→修复：** Filter 是责任链，**order 决定执行顺序**——"提前终止"或"切线程"逻辑若排在链路追踪 Filter 之前，会跳过 trace 上下文建立/传递，造成 Span 缺失、traceId 断链。修复：用 `@Activate(order=...)` 显式排序，让 TraceFilter 先于业务 Filter 执行；鉴权失败也走完整链或手动补 trace 信息；跨线程用 TTL 透传；`qos invoke` 单调验证链完整。
**量化→预防：** 链路完整率 85%→99.8%、Span 丢失归零。制定 Filter 顺序规范并评审，加链路追踪集成测试，`@Activate order` 集中管理。

**追问 1：`@Activate` 的 order 值与执行顺序是什么关系？**
> **答案：** 一般 order 越小越先执行；Dubbo 内置 Filter 有约定的 order 区间，自定义 Filter 要避开并显式声明，否则默认顺序可能与预期不符，导致追踪/上下文类 Filter 被绕过。

**追问 2：自定义 Filter 里"提前 return"为什么会破坏链路追踪？**
> **答案：** 责任链被短路后其后的 TraceFilter 不再执行，trace 上下文未初始化/未上报，Span 自然缺失。解决是让终止逻辑也经过追踪 Filter，或补偿性地建立并上报 trace 信息。

### Q23. 案例九：Dubbo2 协议大字段传输导致单长连接阻塞
**标准答案：**
**现象→排查：** 某查询接口返回 5MB 大报文，上线后该 provider 其他接口 P99 50ms→2s，但下游都很快。`qos invoke` 单调该接口 1.8s、其余 <50ms；`connections=1`；Hessian2 序列化 5MB 约 400ms + 网络传输；抓包见单连接上大包期间后续请求排队；响应体 P99 巨大。
**根因→修复：** Dubbo2 **单长连接 + Request ID 复用**——大报文在一条连接上串行收发，序列化/传输期间后续请求全部队头阻塞，连接数过少放大问题。应急 `connections=1→8` 分散；接口分页/裁字段、去无用大字段、`compression=lz4`；根治迁 **Triple 协议**（HTTP/2 多流、Zero Copy、无队头阻塞）或拆独立服务/连接。
**量化→预防：** 其他接口 P99 2s→60ms、该接口传输体积降约 80%、整体吞吐约 ×3。加响应体大小阈值告警、大字段接口评审，新项目默认 Triple。

**追问 1：为什么单长连接适合"小包高并发"却怕大包？**
> **答案：** 小包时连接握手开销被摊薄、Request ID 异步关联高效；大包时单连接串行占用，后续请求排队形成队头阻塞，并发优势变瓶颈。

**追问 2：压缩（compression）能根治大包问题吗？**
> **答案：** 不能。压缩只缩小体积、缓解传输耗时，单连接串行收发的结构性瓶颈仍在。根治靠分页/裁剪减小数据，或多连接/Triple 多流从并发模型上解决。

### Q24. 案例十：序列化版本不兼容导致反序列化异常
**标准答案：**
**现象→排查：** Provider 升级 DTO（删了一个字段、`int status` 改 `Integer`），灰度期部分 Consumer 报 `HessianException` / 字段为 null。对比新老 DTO 定义，确认两端 jar 版本不同步、`serialization=hessian2`；异常只在交叉调用的新旧组合出现。
**根因→修复：** Hessian2 靠字段名匹配、**无 schema**——删字段/改类型会让老 Consumer 读到 null 或类型不匹配，灰度期新旧版本共存放大不一致。修复：字段只增不删、类型变更走新字段并保留旧字段（兼容期）、用 `version` 做灰度隔离、Consumer 先升级再下线旧字段；强契约场景迁 Protobuf（IDL + 字段编号的向前/向后兼容）；上线前做序列化兼容测试。
**量化→预防：** 反序列化异常 ~1%→0、灰度切换 0 故障。制定 DTO 变更规范（只增不删/保留兼容字段）、版本灰度、契约测试纳入 CI。

**追问 1：Hessian2 与 Protobuf 在兼容性上的本质区别？**
> **答案：** Hessian2 无 IDL、靠字段名反射匹配，字段增删/改名/改类型易不兼容；Protobuf 有 schema 与字段编号，未识别字段被忽略、新字段有默认值，天然支持向前/向后兼容。

**追问 2：为什么灰度期更容易暴露序列化问题？**
> **答案：** 新旧版本并存，请求在新旧 Provider/Consumer 间交叉，双方字段集/类型不一致，平时单一版本内部不会触发的不兼容组合在灰度期出现。

## Part 5：2026 新趋势（3.3.x / Triple X / AOT / Loom，保守表述）

> 加分题，考察技术视野。**以下为已核实方向，涉及版本/GA 状态以官方文档为准，不编造数字**；答"以官方为准、部分为演进中特性"是加分项。

### Q25. Dubbo 处于 3.3.x 维护线，Triple X 协议带来什么？
**标准答案：** **版本现状**：Dubbo 处于 **3.3.x 维护线**（**3.3.7 于 2026-11 发布，支持 JDK 25**）；**Dubbo2（2.7.x）已 EOL、3.1.x 不再积极维护**——老版本升级是常见技术债。**Triple X 协议**（3.3 引入）：统一**南北向/东西向流量**，**gRPC 兼容 + Protobuf**，支持 **HTTP/1/2/3**、**Spring Web 平滑迁移**，针对**弱网与高并发优化**、支持 **Zero Copy**。价值在于一套协议打通"网关→服务→服务"，从协议层消除 Dubbo2 单连接队头阻塞（案例九）。**核心观点**：工具在进化，但"调用链路分层定位 + 容量与幂等意识"仍是排障能力的根。

**追问 1：Triple X 对"大字段单连接阻塞"（案例九）意味着什么？**
> **答案：** HTTP/2 多流让多个请求在同一连接上并发、互不阻塞，配合 Zero Copy 减少拷贝开销，从协议层缓解乃至消除队头阻塞。但分页/裁字段、容量与幂等意识依然不能省。

**追问 2：老项目还停在 2.7.x，升级要注意什么？**
> **答案：** 注册模型从接口级→应用级（元数据/服务自省）、序列化与协议兼容、version/group 分组策略、灰度分批与回滚预案。要当技术债专项推进，而非升个版本号。

### Q26. Native Image AOT、Project Loom 虚拟线程与 3.3.6+ 新特性？
**标准答案：** **Native Image AOT**：快启动、低内存，适配 Serverless 冷启动场景。**Project Loom 虚拟线程**：用少量平台线程承载海量并发请求，降低线程上下文切换与内存开销，但要重新审视"线程池打满"的排查经验（虚拟线程阻塞廉价，但仍需防 pinning、下游慢仍会堆积）。**3.3.6+ 新特性**：Affinity Router（亲和性路由）、方法级 TPS 限流、Mutiny 响应式、增强环境变量配置。**核心观点**：工具在进化，但"调用链路分层定位 + 容量与幂等意识"仍是排障能力的根；新特性以官方文档为准、保守表述、不编造性能指标。

**追问 1：虚拟线程会让"线程池打满"类故障消失吗？**
> **答案：** 不会。虚拟线程降低了线程成本，但阻塞调用仍占用资源、下游慢仍会堆积请求，还引入了 pinning 等新问题。排障思路（分层定位、看排队/下游/GC）依然适用，只是具体指标与手法要更新。

**追问 2：候选人说"Triple X 已全面替代 Dubbo2，不必关注老协议了"，你怎么看？**
> **答案：** 过度断言。存量 Dubbo2 系统规模庞大、迁移有成本与兼容约束，老协议的单连接/序列化/Hessian2 排障仍是高频刚需；合理态度是"新项目用 Triple X、存量按技术债分批迁移"，并据官方 GA 状态判断。

## Part 6：能否用本套定级？如何定级？

### 结论先行

**可以，Dubbo 调优案例集是后端/中间件面试里区分度极高的探针**——天然可证伪：会不会用 qos/telnet、能不能讲出一次完整排查与前后量化数字，背"调参清单"的人一问案例就露馅。但它**高度依赖真实线上经验**，对没处理过 RPC 故障的初中级问深了只会得到标准答案；招初中级问到 Part 1/2 即可，用 Part 4 案例做鉴别。本套属 **G 实战深水区、⭐经验区分器，案例题权重高于原理题**。

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 知道要看日志/Admin/qos，说不出排查层级与验证方法 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂线程池/容错/序列化/长连接/注册缓存基础，但缺体系 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能按层次定位超时/No provider/性能问题，用 trace+jstack+Admin 分析 |
| **高级（L4）** | 8 年+ | Part 4 | 有多个真实 Dubbo 事故的完整复盘（现象→根因→修复→量化） |
| **资深/架构（L5）** | 10 年+ | Part 5 | 能做内核级定制、容量规划，跟进 Triple X/AOT/虚拟线程演进 |

### 定级操作方法

**第一步：Part 0 摸底。** 能说"现象→手段→层级→根因→修复预防"闭环 → 至少 L2；只会"调大 retries、加线程数" → 从 Part 1 问起。

**第二步：沿追问链下探"为什么/怎么验证"。** 为什么响应超时≠失败（案例四）？为什么下游快还超时（案例二）？为什么注册中心抖动禁重启（案例七）？为什么线程 dump 是金矿（案例一）？为什么 Filter order 会断链（案例八）？

**第三步：三类信号防背题。** ① **真实性**：能否讲出命令与前后数字（`trace`/`count`/jstack dump，"P99 3s→180ms、错误率 15%→0.01%"）；② **抽象能力**：能否沉淀为"现象→手段→层级→根因→修复→预防"方法论与四类问题主线；③ **权衡能力**：能否讲清"何时不该重试/加线程/加连接"及取舍（幂等、容量、协议）。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整：业务开发问到 Part 3 足够；SRE/中间件/架构团队才需 Part 4 全量案例与 Part 5 演进视野。

### 面试官避坑提醒

- **不要对所有人问到 SPI 内核/新协议细节**——很多优秀工程师排障扎实但没跟进 Triple X/AOT，区分"能实战"和"背新词"，前者更有价值。
- **把"能完整复述一个带量化结果的 Dubbo 事故"作为 L4 分水岭**：能给命令、根因与前后数字的人一定真处理过。
- **务必问"一票否决信号"**：超时就调 retries、线程池满就加线程不问根因、认为注册中心挂了服务立刻不可用、重试不管幂等、泛化序列化错就加超时——命中任一说明停在背参数层。
- **结合岗位**：业务开发问到 Part 3 即可；SRE/中间件/平台架构才需 Part 4 全量案例与 Part 5 演进视野。

**排障主线（照着问）：**
1. 看现象 →（超时/报错/性能/注册异常；报错类型、P99、QPS、重试次数）
2. 看手段 →（日志、`telnet 22222` 的 ls/count/invoke/trace、Dubbo Admin、AccessLog/慢调用、Micrometer/Actuator）
