## Part 0：30 秒标准总答

**Q：什么是死锁？如何排查和解决？**

**标准答法（30 秒，涵盖五个得分点）：**

> 死锁是指**两个或多个线程互相持有对方所需要的资源，又不肯释放自己持有的资源，导致所有线程都阻塞等待、无法继续推进**的状态。
>
> 死锁产生必须同时满足**四个必要条件**：互斥、请求和保持（占有且等待）、不可剥夺、循环等待。只要破坏其中任意一个条件就能预防死锁。
>
> 处理方式分四类：**预防**（破坏四条件之一）、**避免**（如银行家算法，分配前先检测安全性）、**检测**（定期检测死锁，如资源分配图）、**恢复**（检测到后剥夺资源或回滚）。
>
> 工程中常用的实践是：**按固定顺序加锁**（破坏循环等待）+ **给锁加超时**（tryLock(timeout)，避免无限等待）+ **缩小锁粒度/避免嵌套锁**。
>
> 生产排查死锁的核心工具是 **jstack / jcmd 打印线程 dump**——找到状态为 BLOCKED 的线程，看它们"waiting to lock"和"locked"的对象，分析是否形成等待环。也可以用 JConsole/VisualVM/Arthas 等可视化工具检测。

**评分要点：** 死锁定义 / 四条件 / 四类处理 / 工程实践（顺序加锁+超时）/ jstack 排查，对应入门到高级。能说出具体排查手法的，直接往 Part 2 追问。

## Part 1：基础认知题（死锁四条件）

### Q1. 什么是死锁？产生死锁的四个必要条件是什么？

**标准答案：**
**死锁**：多个线程因竞争资源而造成的一种**互相等待、都无法推进**的僵局。

**四个必要条件**（Coffman 条件，缺一不可）：
1. **互斥条件**：资源一次只能被一个线程占用（如锁）。
2. **请求和保持条件**（占有且等待）：线程已持有至少一个资源，又请求新资源，但不释放已持有的。
3. **不可剥夺条件**：线程已获得的资源在使用完之前不能被强制剥夺，只能自己释放。
4. **循环等待条件**：存在一个线程-资源的循环等待链，每个线程都在等待下一个线程持有的资源（T1 等 T2 的资源，T2 等 T1 的资源）。

**关键**：这四个条件是**必要条件而非充分条件**——死锁发生一定满足四条件，但满足四条件不一定发生死锁。反过来，**破坏任意一个条件就能预防死锁**。

**追问 1：写一个最简单的死锁代码示例。**
> **答案：**
> ```java
> Object lockA = new Object();
> Object lockB = new Object();
>
> // 线程1
> new Thread(() -> {
>     synchronized (lockA) {
>         sleep(100);                    // 增加交叉概率
>         synchronized (lockB) { }       // 持有A，等B
>     }
> }).start();
>
> // 线程2
> new Thread(() -> {
>     synchronized (lockB) {
>         sleep(100);
>         synchronized (lockA) { }       // 持有B，等A
>     }
> }).start();
> ```
> 线程1 持 lockA 等 lockB，线程2 持 lockB 等 lockA → 循环等待 → 死锁。

**追问 2：单线程会发生死锁吗？**
> **答案：** 不会。死锁至少需要两个及以上线程（或执行单元）互相等待。单线程只有自己，不存在"互相"等待的循环。不过要注意：单线程如果自己锁自己且锁不可重入，会**自己阻塞自己**（自死锁），但这不是典型的多线程死锁。

### Q2. 死锁、活锁、饥饿有什么区别？

**标准答案：**
| 概念 | 描述 | 特点 |
|------|------|------|
| **死锁（Deadlock）** | 多个线程互相等待资源，全部阻塞无法推进 | 所有相关线程都卡死，需要外部干预 |
| **活锁（Livelock）** | 线程没有被阻塞，但一直重复相同的操作（如互相礼让），导致谁都无法推进 | 线程在"动"，但没有进展；可能自动解开 |
| **饥饿（Starvation）** | 某个/某些线程长期得不到所需资源，一直等待 | 其他线程能推进，只是个别线程"饿死"（如低优先级线程） |

- **活锁典型例子**：两人迎面相遇，都往同一侧让路，又撞上，又同时让……反复无进展。线程里表现为"检测到冲突→都退让重试→又冲突"的循环。
- **饥饿典型例子**：非公平锁下，某个线程一直抢不到锁；或线程池中长任务占满线程，短任务一直排队。

**追问：如何避免活锁？**
> **答案：** 在重试机制中引入**随机性/退避（backoff）**——比如冲突后随机等待一段时间再重试（如以太网 CSMA/CD 的二进制指数退避），打破"同步礼让"的死循环。Raft 等共识算法选举时的随机超时也是这个思想。

## Part 2：底层原理题（预防、避免、检测、恢复）

> 这是"背过四条件"和"懂系统性处理"的分水岭，L2→L3 的关键。

### Q3. 处理死锁的四种策略是什么？分别怎么做？

**标准答案：**

1. **预防死锁（Deadlock Prevention）**：**破坏四个必要条件之一**（在系统设计时）。
   - 破坏互斥：用资源副本（如无可共享的资源），但很多场景做不到（锁本身必须互斥）。
   - 破坏请求和保持：**一次性申请所有资源**（要么全拿到，要么一个都不占）——缺点是资源利用率低。
   - 破坏不可剥夺：允许抢占——当线程请求新资源失败时，**释放已持有的资源**，稍后重新申请。
   - 破坏循环等待：**资源按线性顺序编号，线程必须按序申请**（如先锁 A 再锁 B，所有线程遵守同一顺序）——这是工程上最可行的方法。

2. **避免死锁（Deadlock Avoidance）**：在**运行时动态检测**资源分配是否会导致死锁，只有安全才分配。经典算法是**银行家算法**（Banker's Algorithm）——模拟分配后检查是否还存在一个"安全序列"能让所有线程完成。

3. **检测死锁（Deadlock Detection）**：允许死锁发生，但**定期检测**（如资源分配图/等待图找环）。检测到后进入恢复流程。

4. **解除/恢复死锁（Deadlock Recovery）**：检测到死锁后：
   - **资源剥夺法**：挂起某些线程，抢占其资源给其他线程。
   - **撤销进程/线程法**：直接终止一个或多个死锁线程（简单粗暴但有效）。
   - **进程回退法**：让线程回滚到某个安全检查点。

**追问 1：为什么工程中很少用银行家算法？**
> **答案：** ① 需要**预先知道**每个线程所需资源的最大值，实际系统很难准确预测；② 算法开销大，每次分配都要做安全性检查；③ 限制太多会降低并发度和资源利用率。所以银行家算法更多是**理论模型**，工程中更常用"预防（顺序加锁）+ 检测（超时/jstack）+ 恢复（重启/回滚）"的组合。

**追问 2：破坏循环等待的"按序加锁"具体怎么做？有什么要注意的？**
> **答案：** 给所有锁分配一个全局唯一的顺序（如按对象 hash、或业务定义的优先级），**所有线程都严格按这个顺序加锁**。比如规定"永远先锁 A 再锁 B"，就不会出现"T1 持 A 等 B、T2 持 B 等 A"的环。
> 注意点：① 顺序必须是全局一致的，任何一个地方违反就前功尽弃；② 要在代码中固化（如用带序号的锁对象、统一封装加锁工具）；③ 释放锁一般按相反顺序。

### Q4. Java 中如何主动避免死锁？有哪些实用手段？

**标准答案：**
1. **固定加锁顺序**：破坏循环等待（最有效）。
2. **使用 tryLock(timeout)**：ReentrantLock 的 `tryLock(timeout)` 在指定时间内拿不到锁就放弃，**避免无限等待**，并可在失败时回滚释放已持有的锁。
3. **缩小锁的粒度/范围**：减少嵌套锁，缩短持锁时间。
4. **避免锁嵌套**：尽量不同时持有多个锁；必须持有时严格按序。
5. **使用并发工具类**：用 ConcurrentHashMap、Atomic 类等无锁/细粒度工具替代手写的大锁。
6. **设置锁超时**：给数据库锁、分布式锁设置合理的超时时间，防止永久阻塞。

**追问 1：tryLock 为什么能避免死锁？它有什么局限？**
> **答案：** tryLock 带超时后，线程拿不到锁不会无限阻塞，超时后会返回 false，线程可以选择**释放已持有的其他锁并重试/回退**，从而打破"请求和保持"和"循环等待"。局限：① 需要开发者正确处理失败分支（回滚释放已持有的锁），处理不当仍可能出问题；② 超时时间难设置——太短误判，太长影响响应；③ 只是"降低死锁概率"而非杜绝。

**追问 2：什么是"锁粗化"？它会增加死锁风险吗？**
> **答案：** 锁粗化是 JVM 把多次相邻的加锁合并成一次（减少加锁解锁开销，详见 synchronized 题库）。它本身不直接增加死锁风险，但如果导致**持锁时间变长、锁范围变大**，会增大锁竞争和与其他锁交叉的概率，间接提升死锁风险。这是对性能与安全的权衡。

## Part 3：核心区分度题（排查实战）

> **这一部分是全题的题眼**——能否讲清用 jstack 定位死锁的完整过程，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q5. 线上发生死锁，你如何排查？完整说一遍。

**标准答案：** （能完整讲下来基本是 L3+）

**排查流程：**

1. **发现现象**：接口卡死无响应、线程池耗尽、CPU 不高但吞吐量归零、请求堆积——这些"静默卡死"是死锁的典型信号（区别于死循环的高 CPU）。

2. **打印线程 dump**：
   - `jstack <pid>` 或 `jcmd <pid> Thread.print` 打印所有线程状态。
   - 生产常用：`jstack -l <pid> > dump.txt` 保存多份（间隔几秒抓 2-3 份对比，确认线程是否一直卡在同一位置）。

3. **分析 dump**：
   - 找状态为 **BLOCKED**（等待进入 synchronized 块）或 **WAITING**（等待锁）的线程。
   - 看每个线程的 **"waiting to lock <0x...>"**（想拿的锁）和 **"locked <0x...>"**（已持有的锁）。
   - 追踪是否形成**等待环**：T1 持有锁 A 等锁 B，T2 持有锁 B 等锁 A → 死锁。

4. **工具辅助**：
   - JVM 的**死锁检测**：jstack 输出末尾会自动报告 "Found one Java-level deadlock"，直接列出死锁线程和锁。
   - `jcmd <pid> Thread.print` 带死锁检测。
   - JConsole / VisualVM 的"线程"标签有"检测死锁"按钮。
   - Arthas：`thread -b` 命令可直接找出当前阻塞其他线程的线程。

5. **定位代码**：根据 dump 中的**线程名 + 堆栈的方法名和行号**，定位到具体代码（这也是为什么要自定义线程名）。

6. **临时恢复 + 根治**：先重启服务恢复（死锁无法自动解除）；再从代码层面根治——按序加锁、tryLock 超时、减小锁粒度。

**追问 1：jstack 输出里，死锁线程通常是什么状态？**
> **答案：** 等待进入 synchronized 的是 **BLOCKED** 状态（waiting to lock）；等待 ReentrantLock 的通常是 **WAITING/park** 状态（因为 ReentrantLock 用 LockSupport.park）。所以排查 ReentrantLock 死锁时，不能只看 BLOCKED，要关注 WAITING 线程的堆栈和锁持有关系。

**追问 2：为什么建议抓多份 dump 对比？**
> **答案：** 单份 dump 只反映某一瞬间，可能捕获到的是瞬时等待（正常竞争）而非死锁。间隔几秒抓 2-3 份，如果同一批线程**始终卡在同一位置、状态不变**，才能确认是死锁而非普通锁竞争。这是避免误判的重要手段。

**追问 3：CPU 很高一定是死锁吗？**
> **答案：** 不是。死锁的典型特征是**CPU 低、线程全卡住、吞吐归零**（线程都阻塞了，不消耗 CPU）。CPU 高通常是**死循环、频繁 GC、大量线程上下文切换、计算密集任务**。所以排查时先看 CPU 和线程状态的关系：CPU 低+线程 BLOCKED → 怀疑死锁；CPU 高+线程 RUNNABLE → 怀疑死循环/计算热点。

### Q6. 如何使用 jcmd / Arthas 等工具定位死锁？

**标准答案：**
- **jcmd**：`jcmd <pid> Thread.print` 打印线程栈（等价于 jstack，但 jcmd 是更现代的多功能工具）；`jcmd <pid> help` 看所有可用命令。
- **Arthas**（阿里开源在线诊断工具）：
  - `thread` 看线程状态统计。
  - `thread -b`：**一键找出阻塞其他线程的线程**（只能找出阻塞别人的那个，死锁中可能找不全，需结合分析）。
  - `thread <id>` 看指定线程堆栈。
  - `stack <class> <method>` 看方法调用路径。
- **可视化工具**：JConsole、VisualVM 的线程面板有死锁检测。
- **线程 dump 中的锁地址**：通过 `<0x数字>` 这样的锁 ID 关联"谁持有、谁在等"，这是手工分析等待环的关键。

**追问：为什么 Arthas 适合生产环境？**
> **答案：**  Arthas 是**在线诊断**工具，不需要重启应用、不需要改代码、随时 attach 到目标 JVM，对业务侵入极小。而 jstack 虽然也轻量，但 Arthas 提供了更丰富的命令（方法执行耗时统计、参数观察、热修复等），排查复杂问题更高效。不过要注意 attach 时会有短暂 STW（Stop-The-World），生产高峰要慎用。

## Part 4：实战陷阱题（活锁、饥饿、数据库锁）

### Q7. 数据库层面的死锁是怎么回事？如何排查和避免？

**标准答案：**
- **数据库死锁**：两个事务互相持有对方想要的锁（行锁/表锁），都无法继续。数据库（如 MySQL InnoDB）通常有**死锁检测机制**（wait-for graph），检测到后**自动回滚代价较小的事务**来解除死锁。
- **常见场景**：
  - 两个事务以**不同顺序更新同一批行**（T1 更新行1再行2，T2 更新行2再行1）→ 死锁。
  - 间隙锁（Gap Lock）在 RR 隔离级别下的死锁。
- **排查**：
  - MySQL：`SHOW ENGINE INNODB STATUS\G` 查看最近一次死锁日志（LATEST DETECTED DEADLOCK），能看到两个事务各自的 SQL 和持有的锁。
  - 开启 `innodb_print_all_deadlocks` 记录所有死锁到错误日志。
- **避免**：
  - **固定更新顺序**（按主键/id 排序后批量更新）——最关键。
  - 缩短事务、避免长事务。
  - 合理设计索引，避免锁扩大到表锁/间隙锁过多。
  - 降低隔离级别（如 RC 减少间隙锁）。

**追问：MySQL InnoDB 是如何自动处理死锁的？**
> **答案：** InnoDB 使用 **wait-for graph（等待图）** 做死锁检测：事务等待锁时构建图，检测到环就说明有死锁。然后选择**回滚代价最小的事务**（通常按 undo log 量判断）来打破死锁，让其他事务继续。被回滚的事务会收到 `ERROR 1213 (40001): Deadlock found` 错误——所以业务代码要**捕获这个异常并重试**。

---

### Q8. 什么是饥饿？如何避免线程/请求饥饿？

**标准答案：**
- **饥饿**：某个线程/请求长期得不到所需资源而无法执行，虽然系统整体在推进。
- **场景与对策**：
  1. **非公平锁**：低优先级或"倒霉"线程一直抢不到锁 → 用公平锁（new ReentrantLock(true)）按 FIFO 分配。
  2. **线程池**：长任务占满线程，短任务/新任务一直排队 → 任务分类隔离（不同线程池）、设置队列容量、拒绝策略。
  3. **优先级**：低优先级线程长期得不到调度 → 合理设置优先级、避免依赖优先级保证正确性。
  4. **写锁饥饿**：读锁一直被占用，写线程拿不到写锁 → ReentrantReadWriteLock 可设置公平策略避免。

**追问：公平锁一定比非公平锁好吗？**
> **答案：** 不一定。公平锁保证 FIFO、避免饥饿，但**吞吐量低**——因为严格排队导致线程切换频繁、CPU 缓存局部性差。非公平锁吞吐高但可能造成个别线程饥饿。选择要看场景：如果"不能容忍饥饿/要求可预测性"用公平锁；追求吞吐、能接受偶发饥饿用非公平锁（这也是 ReentrantLock 默认非公平的原因）。

---

### Q9. 分布式锁场景下的死锁风险有哪些？如何避免？

**标准答案：** （L4 区分度）
- **风险**：
  1. **锁无法释放**：客户端拿到锁后崩溃/网络断开，没执行释放 → 锁永久占用（类似死锁）。
  2. **过期时间设置不当**：锁过期但业务没执行完，另一个客户端拿到锁 → 并发问题。
- **对策**：
  1. **设置过期时间**（Redis SET key value NX EX）——锁自动过期释放，避免永久占用。
  2. **Redlock / 看门狗续期**（Redisson 的 watchdog）：业务没执行完时自动续期，防止提前过期。
  3. **Lua 脚本原子释放**：释放时校验 value 是自己的才删（防止误删别人的锁），用 Lua 保证校验+删除原子性。
  4. **可重入设计**：记录持有者标识和重入次数。

**追问：Redis 分布式锁设置过期时间后，就完全没有死锁风险了吗？**
> **答案：** 仍有风险：如果过期时间**短于业务执行时间**，锁提前释放，另一个客户端获得锁，导致业务逻辑并发执行（这不算死锁，但是严重的正确性问题）。所以需要看门狗自动续期机制，或者合理评估业务耗时并设置足够长的过期时间。这是分布式锁设计中"死锁风险"和"并发安全"的核心权衡。

## Part 5：2026 新趋势：虚拟线程与死锁

> 加分题，考察技术视野。

### Q10. 虚拟线程会带来新的死锁问题吗？

**标准答案：**
- ** pinning 导致的"伪死锁"**：JDK 21-23 中，虚拟线程在 synchronized 块内做阻塞操作会**钉住（pin）载体线程**。如果所有载体线程都被 pin 住，即使还有大量虚拟线程可运行，也没有载体能执行它们——表现为**类似死锁的"卡死"**（Netflix 曾遇到过这种静默停顿）。JDK 24 的 **JEP 491** 解决了 synchronized 的 pinning 问题。
- **虚拟线程不池化**：传统线程池死锁（两个任务互相等待对方的子任务完成，而线程都被占满）在虚拟线程下**大幅缓解**——因为虚拟线程数量几乎无限，不会因为"线程都用完了"而卡死。
- **但共享资源死锁依然存在**：虚拟线程之间如果竞争同一个锁/资源并形成循环等待，**经典死锁依然会发生**——虚拟线程不改变锁的互斥本质。

**追问：虚拟线程下还需要担心传统死锁吗？**
> **答案：** 需要。虚拟线程只是让线程变廉价、调度更高效，不改变"循环等待 + 互斥"这个死锁的根本成因。所以按序加锁、tryLock 超时这些原则依然适用。变化的是"线程池耗尽型"死锁少了，但"资源竞争型"死锁还在。

---

### Q11. 如何在虚拟线程/新 JDK 中检测死锁和 pinning？

**标准答案：**
- **死锁检测**：jcmd/jstack 的死锁检测依然有效（虚拟线程 dump 需用 `jcmd <pid> Thread.dump_to_file -format=json`，因为 jstack 默认不显示虚拟线程栈——见 synchronized/JVM 题库）。
- **pinning 检测**：JDK 24 起用 **JFR 的 `jdk.VirtualThreadPinned` 事件**（`-Djdk.tracePinnedThreads` 已被移除）。
- **监控**：JFR（Java Flight Recorder）录制 + 分析，观察虚拟线程调度、pinning 事件、锁竞争情况。

**追问：为什么 jstack 看不到虚拟线程？**
> **答案：** 虚拟线程数量可达百万级，全部 dump 会非常大且大部分是空闲的，所以 jstack 默认只显示平台线程。要看虚拟线程需用 `jcmd <pid> Thread.dump_to_file -format=json <file>` 导出 JSON 格式的完整线程信息。

## Part 6：能否用死锁题定级？如何定级？

### 结论先行

**可以，死锁题是并发模块里"最贴近生产事故"的探针**——因为它天然区分"背过四条件"和"真的处理过线上卡死"。一个候选人能不能讲清 jstack 排查过程、有没有处理过数据库死锁、懂不懂 tryLock 的实际使用，基本能判断其真实经验层级。但需注意：死锁理论题容易背，要用 Part 3/4 的实战题交叉验证。

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |

### 定级操作方法

**第一步：Part 0 摸底。** 能主动提到 jstack 排查/按序加锁 → 至少 L2；只背四条件 → 从 Part 2 问起。

**第二步：沿追问链下探，重点问"怎么做"。**
- 线上死锁具体怎么用 jstack 定位？（找 BLOCKED 线程，看 waiting to lock / locked，找等待环）
- 为什么要抓多份 dump？（排除瞬时竞争误判）
- tryLock 为什么能避免死锁？局限？（避免无限等待；需正确回滚、超时难设）

**第三步：三类信号防背题。**
1. **真实性**：能否讲出**具体的线上死锁事故**（"我们通过 jstack 发现两个线程互锁，根因是加锁顺序不一致"）——这类开放题最能识别真伪。
2. **抽象能力**：能否把 Java 锁死锁、数据库死锁、分布式锁死锁统一到"**循环等待 + 资源互斥**"这一本质，并对应到"按序/超时/检测恢复"的通用解法。
3. **权衡能力**：能否说清公平 vs 非公平、预防 vs 检测的取舍。

**第四步：按最深层级定级，用 Part 3/4 验证实战经验。**
