## Part 0：30 秒标准总答

**Q：谈谈你对 JVM 和 GC 的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> JVM 的内存（运行时数据区）分为**线程私有**的程序计数器、虚拟机栈、本地方法栈，和**线程共享**的堆、方法区（JDK 8 起用元空间实现）。对象主要分配在堆上，栈帧随方法调用入栈出栈。
>
> 创建一个对象要经过：类加载检查 → 分配内存（指针碰撞 / 空闲列表，配合 TLAB 无锁分配）→ 初始化零值 → 设置对象头 → 执行 `<init>`。对象内存布局分**对象头（Mark Word + 类型指针）、实例数据、对齐填充**；访问定位有句柄和直接指针两种方式，HotSpot 用直接指针。
>
> GC 判定采用**可达性分析**：从 GC Roots（栈中引用、静态字段、常量、JNI 引用等）出发，不可达的对象可回收；引用分强、软、弱、虚四种，对应不同回收时机与场景。
>
> 基础回收算法有**标记-清除、标记-复制、标记-整理**，配合**分代收集理论**（新生代对象朝生夕死用复制，老年代存活率高用标记整理/清除），演化出 Serial、Parallel、CMS、G1、ZGC、Shenandoah 等收集器：CMS 追求低停顿用标记清除，G1 用 Region + SATB 实现可预测停顿，ZGC 用染色指针 + 读屏障做到并发整理、亚毫秒停顿。
>
> 类加载走加载 → 连接 → 初始化，遵循**双亲委派**（SPI、Tomcat 等场景会被破坏）；GC 出问题表现为频繁 Full GC 或 OOM，需要靠 GC 日志与 `jstat`/`jmap`/MAT 排查，再针对性调 `-Xms`/`-Xmx` 与收集器参数。

**评分要点：** 内存分区（私有/共享）/ 对象创建与布局 / 可达性 + 引用类型 / 算法 + 分代 + 收集器 / 类加载 + 排查调优 这几个点，对应入门到高级。能说出"分配 → 判活 → 回收 → 收集器"主线的，直接往 Part 2 追问。

## Part 1：基础认知题

### Q1. JVM 运行时数据区有哪些？哪些线程私有、哪些共享？

**标准答案：**
- **线程私有**：
  - **程序计数器（PC）**：记录当前线程执行的字节码行号，是唯一**不会发生 OOM** 的区域。
  - **虚拟机栈**：每个方法执行创建一个**栈帧**（局部变量表、操作数栈、动态链接、方法出口）。栈深度超限抛 `StackOverflowError`，动态扩展失败抛 OOM。
  - **本地方法栈**：为 `native` 方法服务。
- **线程共享**：
  - **堆（Heap）**：最大一块，存放对象实例与数组，GC 主战场，可分新生代/老年代。
  - **方法区**：存类元信息、常量、静态变量、JIT 代码缓存。JDK 7 用永久代（PermGen），**JDK 8 起改用元空间（Metaspace）**，使用本地内存，规避了永久代 OOM。
- 补充：**直接内存（堆外）**不属于运行时数据区，NIO 使用它，受 `-XX:MaxDirectMemorySize` 限制。

**追问 1：`-Xss` 和 `-Xmx` 分别控制什么？设太大/太小有什么后果？**
> **答案：** `-Xss` 设每个线程栈大小（默认约 1M）。太小 → 深递归/深层调用触发 `StackOverflowError`；太大 → 同样总内存下可创建的线程数变少（线程数 ≈ (可用内存 − Xmx − 元空间)/Xss），容易 `OOM: unable to create new native thread`。`-Xmx` 设堆最大值、`-Xms` 设初始值；生产通常设为相等，避免堆动态扩容带来的抖动。

**追问 2：为什么 JDK 8 要用元空间替代永久代？**
> **答案：** ① 永久代有 `-XX:MaxPermSize` 上限，动态生成类多的场景（JSP、CGLIB、反射代理）容易 OOM，元空间默认用本地内存，只受物理内存限制；② 永久代是 HotSpot 特有的，Oracle 合并 JRockit 时为统一实现而移除；③ 类元数据移到本地内存后，GC 不必再移动它，简化了 Full GC。

### Q2. 对象是如何创建的？内存布局和访问定位是怎样的？

**标准答案：**
- **创建流程**：① 类加载检查（`new` 的参数能否在常量池定位到类，类是否已加载/解析/初始化）；② 分配内存——堆规整用**指针碰撞（Bump the Pointer）**，不规整用**空闲列表（Free List）**，取决于 GC 是否带整理压缩能力；③ 初始化零值（保证字段不显式赋值也能用）；④ 设置对象头（Mark Word、类型指针、GC 分代年龄、锁状态）；⑤ 执行 `<init>` 按程序员意图初始化。
- **内存布局**：**对象头**（Mark Word + 类型指针 Klass Pointer，数组还含长度）、**实例数据**（本类 + 父类字段）、**对齐填充**（HotSpot 要求对象大小是 8 字节的整数倍，不足则补齐）。
- **并发分配安全**：CAS + 失败重试，或 **TLAB（Thread Local Allocation Buffer）**——每个线程在 Eden 预先分一小块私有内存，线程内分配只需指针碰撞、无锁，用完再 CAS 申请。
- **访问定位**：句柄访问（reference 指向句柄池，句柄存实例数据与类型数据地址，稳定但多一次间接寻址）；直接指针（reference 直接指向对象地址，**HotSpot 采用**，快、少一次寻址）。

**追问 1：Mark Word 里存了什么？它和锁升级有什么关系？**
> **答案：** Mark Word 存哈希码、GC 分代年龄、锁状态标志、持有锁的线程 ID、偏向时间戳等。它是**可变结构**，会随锁状态（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）复用不同比特位——这正是 `synchronized` 锁升级能在对象头上完成的原因。

**追问 2：对象一定分配在 TLAB / 堆上吗？**
> **答案：** 不一定。大对象无法放入 TLAB，会直接在 Eden 甚至老年代分配；随着 JIT **逃逸分析**与**标量替换**成熟，未逃逸的对象可被拆成标量直接分配在栈上，不必进堆。TLAB 只是优化小对象分配的无锁手段。

## Part 2：底层原理题（判活、算法与分代）

> 这是"知道有 GC"和"懂 GC 内核"的分水岭，L2→L3 的关键。

### Q3. GC 如何判定对象存活？GC Roots 有哪些？引用类型怎么分？

**标准答案：**
- **可达性分析（Reachability Analysis）**：从一系列 **GC Roots** 出发沿引用链向下搜索，可达的对象存活，不可达的可回收。相比引用计数法，它能解决**循环引用**问题。
- **GC Roots 主要包括**：虚拟机栈（栈帧局部变量表）中引用的对象、方法区类**静态属性**引用的对象、方法区**常量**引用的对象（如字符串常量池）、本地方法栈 JNI 引用的对象、JVM 内部引用（基本类型 Class 对象、常驻异常对象、系统类加载器）、被 `synchronized` 持有的对象等。
- **四种引用**：
  - **强引用**：普通 `new`，只要引用在就绝不回收。
  - **软引用（SoftReference）**：内存不足时才回收，适合**缓存**。
  - **弱引用（WeakReference）**：GC 时无论内存是否充足都回收，适合 `WeakHashMap`、`ThreadLocalMap` 的 key。
  - **虚引用（PhantomReference）**：最弱，必须通过 `ReferenceQueue` 感知回收，用于堆外内存释放钩子（如 Netty / DirectByteBuffer 的 Cleaner）。

**追问 1：对象"不可达"就一定会被回收吗？**
> **答案：** 不一定。第一次标记后筛选：若对象覆盖了 `finalize()` 且未执行过，会放入 F-Queue 由低优先级线程执行；若在其中重新与 GC Roots 建立关联即可"自救"，从待回收集合移除。但 `finalize` 不保证被调度、只执行一次、代价高，JDK 9 起已废弃——实践中可近似认为"两次标记后仍不可达即回收"。

**追问 2：ThreadLocal 内存泄漏和弱引用有什么关系？**
> **答案：** `ThreadLocalMap` 的 Entry 的 key 是 ThreadLocal 的**弱引用**。当外部 ThreadLocal 变量被置 null 后，key 会被 GC 回收变成 null，但 value 是**强引用**且生命周期跟着线程；线程池中线程长期存活，导致 value 无法回收而泄漏。所以用完务必 `remove()`。

### Q4. 三种基础 GC 算法是什么？分代收集理论讲了什么？

**标准答案：**
- **标记-清除（Mark-Sweep）**：标记存活对象后统一清除未标记对象。简单，但①效率不稳定、②产生**内存碎片**（大对象分配时易提前触发 Full GC）。CMS 基于此。
- **标记-复制（Mark-Copy）**：内存分两块，只用一块，存活对象复制到另一块后整体清空。简单高效、无碎片，但**空间利用率只有一半**。针对新生代"朝生夕死"优化为 **Eden : Survivor : Survivor = 8:1:1**，每次用 Eden + 一个 Survivor，利用率 90%，不足时由老年代**担保分担（Handle Promotion）**。
- **标记-整理（Mark-Compact）**：标记后让存活对象向一端移动，再清理边界外内存。无碎片，但移动对象要更新引用、STW 更长。老年代（Serial Old、Parallel Old）用它。
- **分代收集理论**：建立在两个假说上——① **弱分代假说**：绝大多数对象朝生夕死；② **强分代假说**：熬过越多 GC 的对象越难消亡。因此把堆分**新生代（Minor GC 频繁）**和**老年代（Full GC 较少）**；再由**跨代引用假说**（跨代引用占极少数）引出**记忆集（Remembered Set）/ 卡表**，避免回收新生代时扫描整个老年代。

**追问 1：为什么新生代适合复制、老年代适合标记整理/清除？**
> **答案：** 新生代对象存活率极低，复制少量存活对象成本很小，且 8:1:1 解决了空间浪费；老年代对象存活率高，复制会频繁进行且需大量空间担保，成本过高，所以用不移动的标记-清除或移动但省空间的标记-整理。

**追问 2：Minor GC、Major GC、Full GC 如何区分？**
> **答案：** Minor GC 发生在新生代，频繁且快；Major GC 通常指老年代 GC；Full GC 指**整个堆 + 方法区**的回收，STW 长，应尽量避免。术语在业界并不完全统一，面试时说清"回收范围"比死记名词更重要。

## Part 3：核心区分度题（题眼，定级主战场）

> **这一部分是全题的题眼**——能否讲清 CMS/G1/ZGC 的原理与取舍，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q5. 讲一下 CMS 收集器的流程、三色标记和"并发失败"。

**标准答案：** （能完整讲下来基本是 L3+）
- CMS（Concurrent Mark Sweep）是 JDK 9 前 HotSpot 第一款真正意义的**并发收集器**，目标是**最短回收停顿**，适合重视响应速度的 B/S 系统；它是**老年代**收集器，基于**标记-清除**，常配 ParNew 作新生代。
- **四步骤**：① **初始标记**（STW，仅标记 GC Roots 直接关联对象，极快）；② **并发标记**（与用户线程一起遍历对象图，最耗时但不停顿）；③ **重新标记**（STW，修正并发期间因用户线程修改引用导致的标记变动）；④ **并发清除**（与用户线程一起清理死亡对象）。
- **三色标记**：按访问情况把对象标为**白**（未访问，回收候选）、**灰**（自身已访问但引用未处理完）、**黑**（自身与引用都已处理，安全存活）。并发期间用户线程改引用会造成**漏标**（该存活的被误标为白、被错误回收）——这是最危险的情况。
- CMS 用**增量更新（Incremental Update）**解决漏标：把并发期间**新插入的引用**记录下，重新标记阶段以这些黑色对象为根再扫一遍。

**追问 1：什么是"并发失败（Concurrent Mode Failure）"，如何避免？**
> **答案：** 并发清理期间用户线程仍在分配对象，若老年代预留空间不足（CMS 默认老年代占用达阈值即触发，如 92%），JVM 会 STW 并**临时启用 Serial Old 做 Full GC**，停顿可达数秒。避免：降低 `-XX:CMSInitiatingOccupancyFraction`、增大堆、减少大对象分配。

**追问 2：CMS 为什么用标记-清除而不是标记-整理？碎片怎么处理？**
> **答案：** 清理阶段是与用户线程并发的，若移动整理存活对象必须 STW 更新所有引用，会破坏低停顿目标，所以选不移动的标记-清除。代价是碎片，CMS 提供 `-XX:+UseCMSCompactAtFullCollection`（Full GC 时整理）和 `-XX:CMSFullGCsBeforeCompaction` 缓解。

**追问 3：并发标记中的"多标"和"漏标"分别指什么？**
> **答案：** 多标（浮动垃圾）：并发时原本存活的对象变成垃圾，本次不清、留待下次；漏标：原本可达的对象因黑色对象新引用了白色对象而未标记，会被误回收，必须解决。CMS 用增量更新、G1 用 SATB 分别处理漏标（思路相反，见 Q6）。

### Q6. G1 的核心原理？Region、SATB、RSet 各自解决什么问题？

**标准答案：**
- G1（Garbage First）是 **JDK 9 起的默认收集器**，面向服务端大堆，兼顾吞吐与低停顿，通过 `-XX:MaxGCPauseMillis`（默认 200ms）设定**可预测的软停顿目标**。
- **Region 分区**：把堆切成多个大小相等的 **Region**，每个 Region 可扮演 Eden、Survivor、Old 或 **Humongous**（超过 Region 一半的大对象）。新生代/老年代不再物理连续，而是**逻辑分代**。
- **垃圾优先**：G1 维护每个 Region 的回收收益（垃圾比例 + 经验耗时）并排序，优先回收收益最高的 Region——这正是 "Garbage First" 的由来。
- **运作步骤**：① 初始标记（STW，标记 GC Roots 直接可达，常伴随 Minor GC）；② 并发标记（可达性分析，用 **SATB** 记录并发期间引用变化）；③ 最终标记（STW，处理 SATB 残留记录）；④ 筛选回收（STW，按收益排序选多个 Region，把存活对象**复制**到空 Region 并清理旧区——整体是标记-整理/复制，**无碎片**）。
- **RSet（记忆集）**：每个 Region 维护"哪些其他 Region 引用了我"，回收时只查 RSet 而不扫全堆；跨 Region 写引用由写屏障维护 RSet。

**追问 1：SATB 和 CMS 的增量更新有什么区别？**
> **答案：** 都解决漏标，但方向相反。**增量更新（CMS）关注"新插入的引用"**：黑色对象新指向白色对象时记录该黑色对象，重新标记时以它为根再扫（"写后"断点）。**SATB（Snapshot-At-The-Beginning，G1）关注"被覆盖的旧引用"**：在引用被改写前记录旧引用，保证以"标记开始的快照"为准，灰色对象即使取消了对白色对象的引用，白色对象仍被保留。SATB 配合写前屏障。

**追问 2：G1 相比 CMS 的核心优势？为什么 JDK 9 用 G1 替代 CMS？**
> **答案：** ① **内存布局**：CMS 要求分代连续，G1 用 Region 逻辑分代；② **算法**：CMS 标记-清除有碎片，G1 复制/整理无碎片；③ **停顿可控**：CMS 只追求最短停顿但不可预测，G1 按收益选 Region、有停顿软目标；④ 大对象有 Humongous Region 专门处理。CMS 在 JDK 9 被标记废弃、JDK 14 移除，G1 在大堆下更均衡。

**追问 3：G1 的 RSet 有什么代价？**
> **答案：** RSet 是典型的空间换时间：每个 Region 都维护一张引用表，跨 Region 写引用需写屏障更新，带来额外内存（可达堆的 5%–20%）与写屏障开销。这也是 G1 在小堆上未必优于 CMS 的原因之一。

### Q7. ZGC 为什么能做到亚毫秒停顿？染色指针和读屏障是怎么回事？

**标准答案：**
- ZGC（Z Garbage Collector）在 JDK 11 引入（JEP 333 实验性，JEP 377 于 JDK 15 转正），目标是**停顿时间不随堆大小增长**，亚毫秒级（<1ms），支持 TB 级堆。
- **核心技术：染色指针（Colored Pointer）+ 读屏障（Load Barrier）+ 并发整理**。
- **染色指针**：把 GC 元信息（Marked0/Marked1/Remapped 等标记位）直接编码进 64 位**引用指针的几个比特位**，而非存在对象头里——GC 读指针即可知道对象标记/移动状态。代价是寻址空间受限（低 42 位寻址），且**不支持压缩指针**（引用占 8 字节，同量数据需更大堆）。
- **读屏障**：应用每次从堆中读取引用时，JVM 插入一小段代码检查指针"颜色"。若对象已被并发移动（颜色不匹配），读屏障通过**转发表（Forwarding Table）**找到新地址并**自愈（Self-Healing）**指针，再把正确引用交给应用——因此对象能在用户线程运行时被**并发移动/整理**，几乎无需 STW。
- ZGC 的 STW 仅剩极短的初始标记（扫 GC Roots）和阶段切换握手，耗时与堆大小无关。适合延迟极敏感场景（金融交易、实时交互、大堆服务）；代价是额外 CPU（读屏障 + 并发线程）与内存，吞吐通常略低于 G1。

**追问 1：为什么 ZGC 能并发整理，而 G1 整理时要 STW？**
> **答案：** 关键在"移动对象后如何修正所有指向它的引用"。G1 移动时需 STW 暂停所有用户线程逐一更新引用（否则用户线程读到旧地址出错）；ZGC 用染色指针标记状态 + 读屏障，在用户线程读引用时"懒修正"，用户几乎无感，所以移动可与应用并发。代价是每次读引用多一道检查。

**追问 2：ZGC 和 Shenandoah 有什么异同？**
> **答案：** 相同：都追求与堆大小无关的低停顿，都做并发标记 + 并发整理，都有屏障与 CPU 开销。不同：① 路线——ZGC 用**染色指针 + 读屏障**（修正发生在"读"），Shenandoah 用**转发指针 + 读/写屏障**且**支持压缩指针**；② 厂商——ZGC 由 Oracle/OpenJDK 主导，Shenandoah 由 Red Hat 主导（Oracle 构建不带）；③ 过载处理——ZGC 用 Allocation Stall（线程等待），Shenandoah 用 Pacing（放慢分配）→ Degenerated GC → Full GC 逐级升级。

## Part 4：实战与陷阱题（类加载与 OOM）

### Q8. 讲讲类加载机制与双亲委派模型，它会被破坏吗？

**标准答案：**
- **生命周期**：加载 → 连接（验证、准备、解析）→ 初始化 → 使用 → 卸载。
- **加载**：通过全限定名取二进制字节流 → 转为方法区运行时结构 → 在堆中生成 `java.lang.Class` 对象作为访问入口。
- **连接**：验证（文件格式/元数据/字节码/符号引用安全校验）；**准备**（为**静态变量分配内存并赋零值**，如 `static int a=1` 此时 a=0，`static final` 常量才直接赋初值）；解析（常量池符号引用转直接引用）。
- **初始化**：执行类构造器 `<clinit>()`（编译器按出现顺序收集静态变量赋值与静态块），真正赋初值；JVM 保证父类 `<clinit>` 先执行、多线程下只由一个线程初始化。
- **类加载器**：启动类加载器（Bootstrap，加载核心库）→ 扩展类加载器（Extension）→ 应用类加载器（Application/System，加载 classpath）→ 自定义类加载器。
- **双亲委派**：子类加载器收到请求先委派给父加载器，层层向上，父加载器无法完成时才自己加载。好处：①避免类重复加载；②保证 Java 核心 API 不被篡改（自定义 `java.lang.String` 不会被加载）。

**追问 1：双亲委派被"破坏"的典型场景有哪些？**
> **答案：** 三次典型破坏：① JDK 1.2 引入委派前的历史兼容，催生 `findClass()` 覆写点；② **SPI（如 JDBC）**：核心类 `DriverManager`（启动类加载器加载）需加载厂商 Driver（应用类加载器加载），父加载器无法向下委派，于是用**线程上下文类加载器（TCCL）**逆向委派；③ **OSGi / Tomcat 热部署**：为应用隔离，自定义加载器改为"子优先"。

**追问 2：Tomcat 为什么要打破双亲委派？**
> **答案：** 一个容器部署多个 Web 应用，可能依赖同一库的不同版本（Spring 4 与 5），严格委派会共享父加载器的类导致冲突。Tomcat 为每个应用建 WebappClassLoader，**优先加载自己的 WEB-INF/classes 与 lib**，加载不到才委派父加载器；但 `java.*` 核心类仍交给父加载器以保证安全。

### Q9. 线上出现 OOM / Full GC 频繁，你怎么排查和调优？

**标准答案：**
- **常见类型**：`Java heap space`（堆不足/泄漏）、`GC overhead limit exceeded`（GC 占 98% 时间只回收不到 2%）、`Metaspace`（类太多/重复部署）、`StackOverflowError`（栈帧过深）、`unable to create new native thread`（线程过多或 Xss 太大）、`Direct buffer memory`（堆外内存不足）。
- **排查工具**：GC 日志（JDK8 `-XX:+PrintGCDetails`，JDK9+ `-Xlog:gc*`）、`jps`、`jstat -gcutil`（GC 统计）、`jmap -dump`（导出堆快照）、`jstack`（线程栈/死锁）、`jinfo`；离线用 **MAT / JProfiler** 看支配树与 GC Roots 引用链定位泄漏；线上用 **Arthas**、**JFR** 低开销诊断。
- **常用参数**：`-Xms`/`-Xmx`（生产设相等）、`-Xmn`/`-XX:NewRatio`（新生代）、`-XX:SurvivorRatio`（Eden:Survivor，默认 8）、`-XX:+UseG1GC`/`-XX:+UseZGC`、`-XX:MaxGCPauseMillis`、`-Xss`、`-XX:MaxMetaspaceSize`、`-XX:+HeapDumpOnOutOfMemoryError`。

**追问 1：线上 CPU 飙到 100%，如何排查？**
> **答案：** ① `top` 找到高 CPU 的 Java 进程 PID；② `top -H -p PID` 找到高 CPU 线程 TID 并转 16 进制；③ `jstack PID | grep <tid十六进制>` 看该线程栈（业务死循环、正则回溯、还是 GC 线程繁忙）；④ 若是 GC 线程，用 `jstat -gcutil` 看 GC 频率判断内存问题。Arthas 的 `thread -n` 可直接看最忙线程栈。

**追问 2：TPS 骤降、Full GC 频繁，可能是什么原因？**
> **答案：** ① 对象过早晋升（新生代/Survivor 太小）导致老年代撑满；② CMS 并发失败；③ G1 的 Humongous 分配或 To-space exhausted；④ 代码里显式 `System.gc()`；⑤ 元空间不足；⑥ 内存泄漏（某对象持续增长，需 dump 堆看引用链）。先看 GC 日志判断诱因，再针对性调参或改代码。

**追问 3：调优时堆越大越好吗？**
> **答案：** 不是。堆越大，单次 Full GC 停顿越长、启动越慢、换页压力越大。应据存活对象量与分配速率设定，让老年代容纳存活对象并留余量；低延迟场景更应降低分配速率并选低延迟收集器。**调优前必须用数据（GC 日志/监控）定位瓶颈**，忌盲目调参。

## Part 5：2026 新趋势：JDK 21/25 的 GC 演进

> 加分题，考察候选人的技术视野与事实准确性。

### Q10. JDK 21 到 JDK 25 的 GC 有哪些重要演进？

**标准答案：**
- **分代 ZGC（JEP 439，JDK 21 引入）**：把堆分年轻代/老年代，针对"大部分对象朝生夕死"优化——年轻代频繁回收、老年代较少回收，降低高分配速率下的 CPU 与内存开销。JDK 21 用 `-XX:+UseZGC -XX:+ZGenerational` 开启。
- **演进链**：JEP 439（JDK 21，分代作为**可选模式**）→ JEP 474（JDK 23，分代成为 ZGC **默认模式**，非分代弃用）→ JEP 490（JDK 24，**移除非分代模式**）→ **JDK 25（2025-09-16 发布，LTS）**：ZGC 只剩分代形态，`-XX:-ZGenerational` 仅告警并被忽略。
- **必须辨析的事实**：常说"JDK 25 分代 ZGC 成默认"，准确含义是"**启用 ZGC 后默认/只能用分代模式**"，**并不等于整个 JDK 的默认收集器变成 ZGC**——JDK 25 的整体默认 GC 仍是 **G1**，用 ZGC 仍需显式 `-XX:+UseZGC`。
- **分代 Shenandoah**：JEP 404（JDK 24，实验性）→ **JEP 521（JDK 25，产品特性）**；但 JDK 25 默认仍是单代（satb）模式，需 `-XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational` 开启，且长生命周期对象多的场景单代未必更差。
- **紧凑对象头（JEP 519，JDK 25）**：64 位 JVM 对象头从 96/128 位压到 **64 位**，减少堆占用、提升数据局部性（opt-in：`-XX:+UseCompactObjectHeaders`），对小对象密集应用收益明显。
- **虚拟线程（JEP 444，JDK 21 转正）对内存的影响**：单个虚拟线程仅几百字节~几 KB（不占 1MB 本地栈），百万级可行；但海量并发会显著抬高**对象分配速率**， GC 压力主要来自分配速率而非线程数；且线程不池化后，ThreadLocal 存大对象需谨慎清理，推荐用 **Scoped Values（JEP 506，JDK 25 转正）**。

**追问 1：JDK 25 的默认垃圾收集器到底是什么？**
> **答案：** 是 **G1**。这是最易混淆的考点："分代 ZGC 默认"中的"默认"指 ZGC 内部形态，不是 JDK 层面默认 GC。服务器类机器默认仍是 G1，低延迟需求才显式开 ZGC/Shenandoah。能区分这两个"默认"的层次，是 L5 视野的可靠信号。

**追问 2：分代 ZGC 相比非分代 ZGC 解决了什么问题？**
> **答案：** 非分代 ZGC 每次要扫全堆，高分配速率下产生大量"短命垃圾"，GC 线程忙于重复扫描存活的老对象。分代后按年龄分开、频繁回收收益高的年轻代。据 JEP 439 数据，Cassandra 负载下分代 ZGC 用约 1/4 的堆达到约 4 倍于非分代 ZGC 的吞吐，暂停仍保持在 1ms 内。

**追问 3：虚拟线程会让堆内存变大吗？GC 要怎么调整？**
> **答案：** 虚拟线程本身占堆很小，但百万并发把分配速率推高数倍，压力来自分配速率。应对：① 压测确认 G1 是否跟得上分配，出现 Allocation Stall 时考虑 ZGC；② 对有限资源（连接池）限流，避免线程堆积等待时持有对象；③ 用 JFR 找分配热点、减少临时对象；④ 虚拟线程不池化，ThreadLocal 要及时清理，优先用 Scoped Values。

## Part 6：能否用 JVM/GC 定级？如何定级？

### 结论先行

**可以，JVM/GC 是后端面试区分度最高的探针之一**——它天然分层：会配参数 → 知道内存分区 → 懂判活与算法 → 懂收集器原理（CMS/G1/ZGC）→ 能实战排查调优 → 懂版本演进与选型。但 GC 内部实现偏难，**对初中级候选人强问源码只会考背诵**，要结合岗位使用：招初中级问到 Part 1/2 即可，招性能/中间件岗才需 Part 3 以上。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 会配 `-Xmx`/`-Xms`，知道堆/栈/方法区，说不清 GC 怎么判活 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂可达性分析、GC Roots、四种引用、三种算法、分代理论 |
| **中高级（L3）** | 5–8 年 | Part 3 | 讲清 CMS 四阶段与并发失败、G1 的 Region/SATB/RSet、ZGC 染色指针 |
| **高级（L4）** | 8 年+ | Part 4 | 懂类加载与双亲委派破坏，能独立排查 OOM、有 GC 调优实战 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 掌握 JDK 21/25 GC 演进，能辨析"默认"语义，做收集器选型与容量规划 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"分区 → 判活 → 算法 → 收集器"主线 → 至少 L2；只说"GC 就是回收垃圾" → 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"：
- 为什么可达性分析而不用引用计数？（循环引用）
- 为什么新生代用复制、老年代用标记整理/清除？（存活率差异）
- CMS 为什么需要重新标记？（并发期间引用变动导致漏标）
- ZGC 为什么能并发整理？（染色指针 + 读屏障懒修正）

**第三步：三类信号防背题。**
1. **真实性**：能否结合经历讲清一次真实 GC 问题排查（现象 → 工具 → 定位 → 解决）。
2. **抽象能力**：能否把 CMS/G1/ZGC 放进"标记-清除/整理 + 是否并发 + 停顿是否可控"的统一框架对比——这是理解 GC 演进的关键。
3. **权衡能力**：能否讲清吞吐 vs 延迟的取舍、为何没有"最好"的收集器只有"最合适"的场景。

**第四步：按最深层级定级，不按正确率。** 结合岗位难度调整：业务开发问到 Part 3 足够；基础架构/性能团队才需要 Part 4 实战与 Part 5 演进。

---

### 面试官避坑提醒

- **不要对所有人问到 ZGC 读屏障/源码级**——多数优秀中级工程师理解设计即可。区分"理解设计"和"背过源码"，前者更有价值。
- **把"能否独立排查一次线上 GC 问题"作为 L4 分水岭**：能讲出完整排查链路的人一定是真做过。
- **警惕"默认收集器"的语义混淆**：能辨析 JDK 25 中"分代 ZGC 默认"≠"JDK 默认 GC 是 ZGC"是 L5 的可靠信号。
- **注意术语不统一**（Major GC/Full GC 等）：看重候选人是否说清"回收范围/机制"，而非纠结名词。
