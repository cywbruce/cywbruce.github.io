## Part 0：30 秒标准总答

**Q：谈谈你对 Java 线程池的理解。**

**标准答法（30 秒，涵盖五个得分点）：**

> 线程池是一种**线程复用**机制，用来降低频繁创建/销毁线程的开销，并且能**统一管理线程、控制并发数、提供排队和拒绝策略**。
>
> Java 里核心实现是 `ThreadPoolExecutor`，它的构造方法有 **7 个参数**：核心线程数、最大线程数、非核心线程空闲存活时间、时间单位、任务队列、线程工厂、拒绝策略。
>
> 任务提交后的执行流程是：先创建核心线程执行 → 核心满了进队列 → 队列也满了且线程数小于最大值时创建非核心线程 → 达到最大值后触发**拒绝策略**。
>
> 阿里 Java 开发手册**强制要求不用 Executors 的工厂方法**（`newFixedThreadPool` / `newCachedThreadPool` 等），因为它们使用无界队列或无上限线程，可能导致 OOM，要直接用 ThreadPoolExecutor 构造并显式指定参数。
>
> 使用线程池的收益：降低资源消耗、提高响应速度、便于线程管理（统一监控、限流）。

**评分要点：** 复用降开销 / 7 大参数 / 执行流程 / 拒绝策略 / 不用 Executors 这几个点，对应入门到高级。能讲清参数协作关系的，直接往 Part 2 追问。

## Part 1：基础认知题（7 大参数）

### Q1. 为什么要用线程池？它解决了什么问题？

**标准答案：**
1. **降低资源消耗**：复用已创建的线程，避免频繁创建/销毁线程的系统开销。
2. **提高响应速度**：任务到达时可直接使用现成线程，无需等待创建。
3. **便于线程管理**：统一管理线程的生命周期、并发数量，提供排队、拒绝、定时、监控等能力。
4. **限流与削峰**：通过核心/最大线程数和队列，把突发流量平滑处理，避免压垮系统。

**追问：线程池是不是线程越多越好？**
> **答案：** 不是。线程数过多会带来：① 线程上下文切换开销增大（CPU 大量时间花在切换而非执行）；② 内存消耗增加（每个线程有栈空间）；③ 资源竞争加剧。线程数要结合 CPU 核数和任务类型（CPU 密集 vs IO 密集）合理设置。

---

### Q2. ThreadPoolExecutor 的 7 个参数分别是什么？各自作用？

**标准答案：**

| 参数 | 作用 |
|------|------|
| `corePoolSize` | 核心线程数。即使空闲也不会被销毁（除非 allowCoreThreadTimeOut） |
| `maximumPoolSize` | 最大线程数。队列满后能创建线程的上限 |
| `keepAliveTime` | 非核心线程的空闲存活时间，超时后被回收 |
| `unit` | keepAliveTime 的时间单位 |
| `workQueue` | 任务阻塞队列（有界/无界），存放等待执行的任务 |
| `threadFactory` | 线程工厂，用于自定义线程创建（如设置线程名、优先级、是否守护线程） |
| `handler` | 拒绝策略。当队列满且线程数达最大值时，如何处理新任务 |

**追问 1：corePoolSize 和 maximumPoolSize 有什么区别？**
> **答案：** 核心线程是"常驻部队"，非核心线程是"临时工"——队列满了才会临时创建非核心线程，闲下来超过 keepAliveTime 就被回收。两者之差决定了线程池的"弹性扩展"能力。

**追问 2：threadFactory 有什么用？为什么建议自定义？**
> **答案：** 通过自定义线程工厂可以给线程设置有意义的**名称**（如 `order-pool-1`，便于 jstack 排查问题时定位）、统一设置异常处理器、设置为非守护线程等。默认工厂的线程名是 `pool-N-thread-M`，不利于问题定位。

---

### Q3. 为什么阿里规范不建议用 Executors 创建线程池？

**标准答案：** Executors 的几个工厂方法隐藏了风险：

| 工厂方法 | 问题 |
|---------|------|
| `newFixedThreadPool` / `newSingleThreadExecutor` | 使用**无界队列 LinkedBlockingQueue**（默认容量 Integer.MAX_VALUE），任务堆积可导致 **OOM** |
| `newCachedThreadPool` / `newScheduledThreadPool` | 最大线程数为 **Integer.MAX_VALUE**，可创建海量线程导致 **OOM** |

所以规范建议：**直接用 ThreadPoolExecutor 构造方法**，显式指定有界队列和合理的最大线程数，让资源边界可控。

**追问：newWorkStealingPool 呢？**
> **答案：** 它基于 **ForkJoinPool**，使用工作窃取算法，适合处理**Fork/Join 风格的可分解任务**（如并行计算），线程数是 CPU 核数。它和普通 ThreadPoolExecutor 的适用场景不同，不是简单的替代品。

## Part 2：执行流程与源码题（核心区分度）

> **这一部分是全题的题眼**——能否讲清 execute 流程和底层源码，直接决定 L2 还是 L3/L4。

### Q4. 详细描述一个任务提交给线程池后的执行流程。

**标准答案：** （能完整讲下来基本是 L3）

`execute(Runnable command)` 的核心流程（对应源码 `execute` 方法）：

1. **判断核心线程数**：如果当前工作线程数 `workerCount < corePoolSize`，直接 `addWorker(command, true)` 创建一个**核心线程**来执行这个任务。
2. **核心满了，尝试入队**：否则把任务放入阻塞队列 `workQueue.offer(command)`。
3. **再次检查状态**：入队成功后再次检查线程池状态——如果线程池仍在 RUNNING 且工作线程数为 0，则 `addWorker(command, false)` 创建一个**非核心线程**（因为可能核心线程都销毁了，需要有线程来处理队列里的任务）。
4. **队列满了，创建非核心线程**：如果入队失败（队列满），尝试 `addWorker(command, false)` 创建非核心线程来执行任务。
5. **都失败了，执行拒绝策略**：如果创建非核心线程也失败（达到 maximumPoolSize 或线程池已关闭），调用 `reject(command)` 执行拒绝策略。

**记忆口诀**：核心线程 → 队列 → 最大线程 → 拒绝策略。

**追问 1：为什么入队后还要"二次检查"线程池状态？**
> **答案：** 因为入队和检查之间，线程池状态可能已经被其他线程改变（比如调用了 shutdown()）。如果此时线程池已关闭，队列里的任务没人处理，必须创建一个线程来处理队列中的任务（或回滚入队）。这是并发场景下的严谨性设计——防止任务"进了队列却没人执行"。

**追问 2：addWorker 做了什么？**
> **答案：** 它通过 CAS 增加 workerCount（工作线程数），然后创建一个新的 **Worker** 对象（封装了线程和任务），启动线程。Worker 是 AQS 的子类，实现了 Runnable，内部持有 `firstTask` 和继承 AQS 用于**控制锁的中断状态**。每个 Worker 对应一个实际的工作线程。

---

### Q5. 线程池的状态是怎么管理的？calculate 源码了解吗？

**标准答案：** （源码级，L4 区分度）

线程池用 `AtomicInteger ctl` **一个字段同时保存两部分信息**：
- **高 3 位**：线程池运行状态（runState）。
- **低 29 位**：工作线程数量（workerCount）。

五种状态：
| 状态 | 含义 |
|------|------|
| RUNNING | 接受新任务，处理队列任务 |
| SHUTDOWN | 不接受新任务，但处理队列任务 |
| STOP | 不接受新任务、不处理队列任务，中断进行中的任务 |
| TIDYING | 所有任务结束，workerCount=0，即将转为 TERMINATED |
| TERMINATED | 完全终止 |

状态流转：RUNNING → SHUTDOWN（shutdown()）或 STOP（shutdownNow()）→ TIDYING → TERMINATED（terminated() 钩子）。

**追问 1：为什么用一个 AtomicInteger 存两个信息？**
> **答案：** 因为运行状态和线程数**经常需要作为一个整体原子地判断**（比如判断是否接受任务时要同时看状态和计数）。用一个 int 的高低位打包，配合 CAS，可以**一次原子操作完成判断**，避免用两个变量带来的一致性问题——这是非常经典的"状态压缩 + 原子操作"技巧。

**追问 2：shutdown() 和 shutdownNow() 的区别？**
> **答案：**
> - `shutdown()`：平滑关闭。不接受新任务，但**队列里的任务继续处理完**，正在执行的任务不中断。状态转 SHUTDOWN。
> - `shutdownNow()`：立即关闭。不接受新任务，**队列任务不处理（返回未执行任务列表）**，并尝试**中断**正在执行的任务。状态转 STOP。
> 注意：shutdownNow 的中断是"尽力而为"，如果任务代码不响应中断（没检查 isInterrupted），也不会真的停止。

### Q6. 工作线程是怎么"复用"的？getTask() 的循环了解吗？

**标准答案：** （L4）

- 每个 Worker 线程启动后执行 `runWorker(worker)` 方法，里面是一个 **while 循环**。
- 循环里通过 `getTask()` **从阻塞队列里取任务**：`workQueue.take()`（核心线程，阻塞等待）或 `workQueue.poll(keepAliveTime)`（非核心线程，超时返回 null）。
- 取到任务就执行 `task.run()`，执行完回到循环继续取下一个任务——**这就是线程复用的本质：一个线程在循环里不断从队列取任务执行，而不是每来一个任务就 new 一个线程**。
- 当 getTask() 返回 null（线程被回收条件满足）时，退出循环，线程结束。

**追问：核心线程和非核心线程在 getTask 里怎么区分对待？**
> **答案：** 判断是否要回收线程时，看 `wc > corePoolSize`：如果当前线程数大于核心数，用 `poll(keepAliveTime)` 带超时取任务，超时没任务就返回 null 回收该线程；如果小于等于核心数，用 `take()` 无限阻塞等待（核心线程默认不回收）。若设置了 `allowCoreThreadTimeOut(true)`，核心线程也会超时回收。

## Part 3：队列、拒绝策略与状态机题

### Q7. 常见的任务队列有哪些？分别适合什么场景？

**标准答案：**

| 队列 | 特点 |
|------|------|
| `ArrayBlockingQueue` | 数组实现的**有界**队列，容量固定 |
| `LinkedBlockingQueue` | 链表实现，可有界可无界（默认无界，风险点） |
| `SynchronousQueue` | **不存储元素**，每个插入必须等待另一个线程取走。cachedThreadPool 用它，来任务直接交给线程 |
| `PriorityBlockingQueue` | 优先级队列，按优先级执行任务 |
| `DelayedWorkQueue` | 延迟队列，用于 ScheduledThreadPoolExecutor |

**追问：有界队列和无界队列对线程池行为的影响？**
> **答案：** 有界队列下，队列满了会触发创建非核心线程，再到最大线程数后触发拒绝策略——资源有上限，可控。无界队列下，任务会无限堆积，**maximumPoolSize 参数失效**（因为队列永远不满，不会创建非核心线程），堆积过多导致 OOM。这是 Executors 工厂方法的风险根源。

---

### Q8. 四种拒绝策略是什么？如何自定义？

**标准答案：** （JDK 内置的 4 种 RejectedExecutionHandler）

| 策略 | 行为 |
|------|------|
| `AbortPolicy`（默认） | 抛出 `RejectedExecutionException`，让调用方感知 |
| `CallerRunsPolicy` | **由提交任务的线程自己执行**任务，形成天然背压（提交变慢，减缓流量） |
| `DiscardPolicy` | 直接丢弃任务，不抛异常、不通知（静默丢弃） |
| `DiscardOldestPolicy` | 丢弃队列中最老的一个任务，然后重新尝试提交当前任务 |

**追问 1：生产环境该选哪种拒绝策略？**
> **答案：** 默认 AbortPolicy 让问题显式暴露，通常最安全。但**关键业务不能简单丢弃**——更常见的是**自定义拒绝策略**：记录日志 + 降级处理（如把任务持久化到 MQ/数据库，或返回友好提示），保证任务不丢失。CallerRunsPolicy 适合用作简单的背压机制，但要注意它会阻塞提交线程（如 Web 请求线程）。

**追问 2：CallerRunsPolicy 为什么能起到"背压"作用？**
> **答案：** 因为线程池饱和时，让**提交任务的线程（如 Tomcat 的 worker 线程）自己去执行任务**，提交线程被占用就无法继续快速接收新任务，从而降低了任务提交速率，给线程池喘息时间。这是一种负反馈调节。

---

### Q9. 如何合理设置线程池的核心线程数？

**标准答案：** 按任务类型区分（经典公式）：
- **CPU 密集型**（如加密、计算）：线程数 ≈ **CPU 核数** 或 核数+1。设置过多只会增加上下文切换。
- **IO 密集型**（如数据库查询、RPC 调用、文件 IO）：线程数 ≈ **CPU 核数 × 2**，或更精确的公式 `核数 × (1 + IO耗时/CPU耗时)`。因为 IO 等待时线程阻塞，CPU 空闲，需要更多线程填满 CPU。
- 更稳妥的做法：**压测调优**——从经验值出发，通过监控 CPU 利用率、队列长度、响应时间动态调整。

**追问：什么是"IO 密集型"的经验公式原理？**
> **答案：** 核心思想是让 CPU 在 IO 等待期间也有线程可跑。如果任务中 IO 耗时占比越高，就需要越多线程来"填补"CPU 空档。`核数 × (1 + IO/CPU)` 中，IO/CPU 比值越大，线程数越多。比如 IO 占 90%、CPU 占 10%，比值 9，线程数约为核数×10。

## Part 4：生产调优与线上问题题

### Q10. 线上线程池出过哪些问题？如何排查？

**标准答案：** （考察实战经验，L4 关键）
常见问题与排查思路：
1. **任务堆积/OOM**：无界队列导致任务堆积。排查：看队列长度监控、`jmap` dump 堆内存。
2. **线程死锁**：线程池内任务相互等待。排查：`jstack` 看线程状态（BLOCKED/WAITING）。
3. **线程池耗尽**：任务执行慢或有阻塞，线程被占满。排查：监控 activeCount、队列大小。
4. **异常吞掉**：`execute()` 提交的任务抛异常，线程会终止但异常被吞。排查/解决：用 `submit()` 通过 Future.get() 捕获异常，或自定义 Thread.UncaughtExceptionHandler，或重写 afterExecute。
5. **上下文丢失**：ThreadLocal 在线程池复用下串线（呼应 ThreadLocal 题库）。

**追问 1：execute() 和 submit() 提交任务有什么区别？**
> **答案：**
> - `execute()`：无返回值，任务异常会直接抛出（默认由线程的 UncaughtExceptionHandler 处理，可能导致线程终止）。
> - `submit()`：返回 `Future`，可以 `get()` 获取结果或捕获异常（异常被封装在 Future 里，get() 时以 ExecutionException 抛出），不会导致线程终止。
> 生产推荐用 submit，便于异常处理。

**追问 2：如何给线程池做监控？**
> **答案：** 继承 ThreadPoolExecutor 重写 `beforeExecute` / `afterExecute` / `terminated` 埋点；或用 `getPoolSize()` / `getActiveCount()` / `getQueue().size()` / `getCompletedTaskCount()` 等指标接入 Prometheus + Grafana；关键看**活跃线程数、队列长度、拒绝次数、任务执行耗时**。

---

### Q11. 线程池里的任务抛异常会怎样？如何优雅处理？

**标准答案：**
- `execute()` 提交：任务抛异常会导致该 Worker 线程终止，异常打印到控制台但容易被忽略；线程池会补充新线程。
- 处理方式（三选一或组合）：
  1. 用 `submit()` + `Future.get()` 捕获 ExecutionException。
  2. 在任务代码内部用 try-catch 兜底。
  3. 自定义 ThreadFactory 设置 `UncaughtExceptionHandler`，或重写 `afterExecute` 统一处理。

**追问：为什么包装成 Runnable 时异常容易丢？**
> **答案：** 因为 Runnable 的 run() 方法不声明 throws，异常在子线程里抛出后不会传回提交线程。如果不用 Future 或全局 Handler，调用方完全无感知——这是生产上"任务莫名消失"的常见原因。

## Part 5：2026 新趋势：虚拟线程会取代线程池吗

> 加分题，考察技术视野。

### Q12. 有了虚拟线程，还需要 ThreadPoolExecutor 吗？

**标准答案：**
- **不是简单取代，而是分工**。虚拟线程（JDK 21 正式）适合 **高 IO 密集、高并发短请求**场景（如 Web 服务），可以用 `Executors.newVirtualThreadPerTaskExecutor()` 为每个任务创建一个虚拟线程，不再需要精心调参线程池大小。
- 但 ThreadPoolExecutor **依然適用**于：
  - **CPU 密集型**任务（虚拟线程不提升 CPU 并行能力，仍需控制并发数≈核数）。
  - 需要**队列、拒绝策略、精细限流、任务调度**的场景。
  - 运行在 JDK 21 以下的环境。
- 关键认知：**虚拟线程很便宜但不免费**——百万虚拟线程会打爆数据库连接池、内存、下游 API，仍需用 Semaphore 等手段对**真实稀缺资源**限流。线程数不再是天然的背压信号，这是迁移到虚拟线程后最大的思维转变。

**追问 1：虚拟线程池化的传统经验（如"线程数=核数×2"）还适用吗？**
> **答案：** 不适用了。虚拟线程的设计就是"**不池化**"——每个任务一个虚拟线程，创建成本极低。传统公式是针对平台线程（重量级、需复用）的经验，虚拟线程下应该按"任务的资源瓶颈"而非"线程数"来限流。

**追问 2：Spring Boot 怎么启用虚拟线程？**
> **答案：** Spring Boot 3.2+ 可通过配置 `spring.threads.virtual.enabled=true` 让 Tomcat 等组件使用虚拟线程。但启用后要做压测验证——不是所有负载都受益，尤其 CPU 密集或高锁竞争场景。

<a id="part-6"></a>

## Part 6：能否用线程池定级？如何定级？

### 结论先行

**可以，而且线程池是并发模块里"最贴近生产"的定级探针**——因为它既有原理（流程、源码、状态机），又有极强的实战属性（调优、排障、异常处理）。一个候选人是否真的在生产用过线程池，问 Part 4 立刻见分晓。但同样不能只凭这一题定级，需交叉验证。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 知道线程池好处、7 大参数；但说不清参数协作关系和流程 |
| **中级（L2）** | 2–5 年 | Part 2 | 能讲清 execute 执行流程（核心→队列→最大→拒绝）；知道不用 Executors |
| **中高级（L3）** | 5–8 年 | Part 3 | 懂队列/拒绝策略选择、状态流转、shutdown 区别、线程数设置 |
| **高级（L4）** | 8 年+ | Part 4 | 有线上排障经验（jstack/jmap、异常吞噬）、能设计监控、懂 submit/execute 差异 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 理解虚拟线程时代线程池的定位，能做技术选型与资源限流设计 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能讲清流程和"不用 Executors"→ 至少 L2；只会 newFixedThreadPool → 从 Part 1 问起。

**第二步：沿追问链下探，重点问"为什么"。**
- 为什么队列满了才创建非核心线程，而不是先创建到最大？（理解线程池设计意图：优先复用，控制线程数）
- 为什么 ctl 用一个 int 存两个值？（原子性判断）
- 为什么 execute 的异常容易丢？（Runnable 语义）

**第三步：三类信号防背题。**
1. **真实性**：能否讲出具体的线上事故（"我们因为无界队列堆积 OOM 过"）——线程池是最容易问出真实经历的题目。
2. **抽象能力**：能否把线程池理解为"生产者-消费者 + 资源池化 + 限流"的统一模型。
3. **权衡能力**：能否说清不同队列/拒绝策略/线程数策略的适用场景，而非背默认配置。

**第四步：按最深层级定级。** 用 Part 4 的实战题验证"是否真用过"。

---

### 面试官避坑提醒

- **别停在"7 大参数背诵"**——那是 L1 水平。真正的区分度在 execute 流程、状态机、线上排障。
- **善用"讲一次你调优线程池的经历"**——这类开放题最能识别真伪。
- **结合岗位**：业务开发问到 Part 3 足够；高并发/中间件团队要问 Part 4 源码与调优。

## 附录：面试官速查表（一页纸）

**递进主线（照着问）：**

1. 为什么用线程池？→（复用降开销、管理、限流）
2. 7 大参数？→（核心/最大线程数、keepAlive、队列、工厂、拒绝策略）
3. 为什么不用 Executors？→（无界队列/无限线程 → OOM）
4. execute 执行流程？→（核心线程→队列→最大线程→拒绝）
5. 为什么入队后二次检查？→（防止状态变化导致任务无人执行）
6. ctl 状态机？→（高3位状态+低29位线程数，原子判断）
7. shutdown vs shutdownNow？→（平滑处理队列 vs 立即中断）
8. 线程如何复用？→（getTask 循环从队列取任务）
9. 队列/拒绝策略选择？→（有界为主；关键业务自定义拒绝不丢任务）
10. 线程数怎么设？→（CPU密集≈核数；IO密集≈核数×2 或压测）
11. 任务抛异常/监控？→（submit+Future、UncaughtExceptionHandler、指标埋点）
12. 虚拟线程取代吗？→（不取代；IO密集用虚拟线程，CPU密集仍需池化限流）

**定级速判：**
- 答到第 2–3 问 → L1/L2
- 答到第 4–6 问 → L2/L3
- 答到第 7–9 问 → L3
- 答到第 10–11 问 + 有实战 → L4
- 答到第 12 问 + 体系化设计 → L5

**一票否决信号：** 只会 newFixedThreadPool 且不知其风险、说不清 execute 流程、认为线程池线程越多越好 → 无论年限，最高 L2。
