## Part 0：30 秒标准总答

**Q：谈谈你对操作系统的理解，以及它和 Java 后端开发的关系。**

**标准答法（30 秒，涵盖五个得分点）：**

> 操作系统本质是一个**资源管理器 + 抽象层**：向下管理 CPU、内存、磁盘、网卡等硬件，向上给应用提供**进程、虚拟内存、文件、Socket** 这些干净的抽象。
>
> 在 CPU 维度，它用**进程/线程**做调度单位，通过**上下文切换**在多个任务间分时复用，靠**调度算法**决定谁先跑。
>
> 在内存维度，它用**虚拟内存 + 分页**给每个进程"独立且连续"的地址空间幻觉，通过 **MMU/TLB** 做地址转换，缺页时从磁盘换入。
>
> 当多个进程竞争资源可能**死锁**时，它提供预防/避免（银行家算法）/检测恢复的手段。
>
> 在 I/O 维度，它用**系统调用**连接用户态与内核态，用 **I/O 多路复用（epoll）和零拷贝** 支撑高并发网络——这正是 Netty、Kafka 高性能的底层根基。

**评分要点：** 资源管理与抽象 / 进程调度与上下文切换 / 虚拟内存分页 / 死锁处理 / 系统调用与 I/O 多路复用 五个点，对应入门到高级。能说出"抽象"和"epoll/零拷贝落地到 Java"的，直接往 Part 3 追问。

## Part 1：基础认知题（进程·线程·调度）

### Q1. 进程、线程、协程的区别是什么？PCB 是什么？

**标准答案：**
- **进程**：**资源分配的基本单位**，拥有独立的地址空间、文件描述符、堆等资源。切换代价大（要换页表）。
- **线程**：**CPU 调度的基本单位**，属于某个进程，共享进程的地址空间和大部分资源，但有自己的**栈、寄存器、程序计数器（PC）**。切换只需保存/恢复少量上下文。
- **协程**：**用户态的轻量级线程**，由**用户程序自己调度**（而非内核），切换不涉及内核态/用户态转换，开销极小。Java 的虚拟线程（Loom）本质就是语言/运行时层面对协程的支撑。
- **PCB（进程控制块）**：内核描述一个进程的**唯一数据结构**，存有 PID、进程状态、PC、寄存器现场、内存映射、打开文件表等。PCB 是进程存在的标志，进程切换本质就是切换 PCB。

**追问 1：为什么有了线程还要协程？**
> **答案：** 线程由内核调度，数量一多，上下文切换和内核态陷入的开销就很大，且一个线程阻塞会占住内核线程。协程把调度放到用户态，**创建成本低（KB 级栈）、切换无需陷入内核、可大量创建**，特别适合 IO 密集型高并发。代价是：一旦协程执行**阻塞式系统调用**，会阻塞整个底层线程，需要运行时配合（如 Loom 的的多米诺调度）解决。

---

### Q2. 进程有哪些状态？僵尸进程和孤儿进程有什么区别？上下文切换做了什么？

**标准答案：**
- **五态模型**：创建 → **就绪**（等 CPU）→ **运行**（占用 CPU）→ **阻塞/等待**（等 I/O 等事件）→ 终止。
  - 就绪↔运行：被调度 / 时间片用完或被抢占；运行→阻塞：主动等待事件；阻塞→就绪：等待的事件发生。
  - 引入**挂起态**后为七态（就绪挂起、阻塞挂起），用于内存不足时把进程换出到磁盘。
- **僵尸进程（Zombie）**：子进程已退出，但**父进程没调用 wait/waitpid 回收**，其 PCB 仍残留在进程表中，状态为 `Z`。它不占内存和 CPU，但**占用 PID**，多了会导致无法创建新进程。
- **孤儿进程**：**父进程先于子进程退出**，子进程被 **init（PID 1）进程收养**，由 init 负责回收，一般无害。
- **上下文切换**：CPU 从一个进程/线程切到另一个，需**保存当前任务的寄存器、PC、栈指针等到 PCB/TCB，再恢复下一个任务的现场**。开销包括：寄存器保存恢复、**切换页表导致 TLB 失效**、内核/用户态切换。

**追问：什么场景会触发上下文切换？如何减少它？**
> **答案：** 触发场景：时间片到期、被更高优先级抢占、阻塞式系统调用、I/O 等待、中断处理。减少手段：**减少线程数**（避免过多 Runnable 线程抢 CPU）、用**无锁/ CAS** 减少阻塞、用**协程**把切换留在用户态、避免频繁系统调用（批量处理 + 零拷贝）。

---

### Q3. 常见进程调度算法有哪些？各自优劣？

**标准答案：**

| 算法 | 核心思想 | 优点 | 缺点 |
|------|---------|------|------|
| **FCFS** 先来先服务 | 按到达顺序 | 简单公平 | 长作业在前时短作业等待久（**护航效应**） |
| **SJF** 短作业优先 | 优先执行短的 | 平均等待时间最优 | 长作业**饥饿**；需预知执行时间 |
| **优先级调度** | 按优先级高低 | 灵活，可区分任务 | 低优先级饥饿（用**老化 aging** 提升长期等待者优先级缓解） |
| **时间片轮转 RR** | 每个进程轮流跑一个时间片 | 响应快，适合交互 | 时间片太大退化成 FCFS，太小切换开销大 |
| **多级反馈队列 MFQ** | 多个优先级队列 + 时间片，进程可在队列间迁移 | 兼顾长短作业与交互性，综合最优 | 实现复杂，参数需调 |

**追问 1：为什么现代通用操作系统（Linux）不用纯 SJF，而用类似 MFQ/CFS 的调度？**
> **答案：** 因为 SJF 需要**预知作业运行时间**，这对交互式通用系统不现实；且纯 SJF 会让长作业**饥饿**。MFQ 通过"刚创建的交互任务放高优先级短时间片、CPU 密集任务逐步降级"的自适应方式，无需预知运行时间就能兼顾响应速度与吞吐。Linux 的 CFS 则用**虚拟运行时间（vruntime）**保证各任务公平分享 CPU。

## Part 2：底层原理题（内存·死锁·态与中断）

### Q4. 用户态和内核态怎么区分？系统调用、中断、异常有何不同？

**标准答案：**
- **用户态（Ring 3）** 权限受限，不能直接访问硬件和内核内存；**内核态（Ring 0）** 拥有最高权限。区分的目的是**保护系统**——应用不能直接操作硬件。
- **系统调用**：用户程序**主动**请求内核服务（如 read/fork），通过 **`syscall`/`int 0x80` 软中断指令**陷入内核，是"受控的入口"。
- **中断**：**硬件异步**产生的事件（如网卡收包、时钟中断），与当前指令无关，CPU 在指令间隙响应。
- **异常**：CPU **执行指令时同步**产生的事件（如缺页、除零、非法指令），因当前指令触发。
- 三者都会让 CPU 从用户态陷入内核态，走统一的**中断/异常向量表**处理。

**追问：一次 read() 系统调用，数据从磁盘到用户缓冲区经历了什么？**
> **答案：** 应用调用 read（用户态）→ 触发系统调用陷入内核态 → 内核发起磁盘 I/O（可能阻塞当前进程，进程被挂起让出 CPU）→ DMA 把数据从磁盘搬到**内核缓冲区** → 内核再把数据**从内核缓冲区拷到用户缓冲区** → 系统调用返回，进程回到用户态。这里存在"磁盘→内核缓冲→用户缓冲"的两次拷贝，正是**零拷贝**要优化的对象（见 Q11）。

---

### Q5. 逻辑地址、物理地址如何转换？分页、分段、段页式有何区别？页表和 TLB 的作用？

**标准答案：**
- **逻辑地址**：程序生成地址（进程视角）；**物理地址**：内存条上的真实地址。由 **MMU（内存管理单元）** 负责转换。
- **分页**：把地址空间切成**固定大小的页（通常 4KB）**，内存切成同样大小的页框。优点是**无外部碎片**；缺点是最后一页可能有**内部碎片**。
- **分段**：按**逻辑意义**划分（代码段、数据段、栈段），段长不固定。便于**保护和共享**，但会产生**外部碎片**。
- **段页式**：先分段、段内再分页，兼顾二者的保护性与无外部碎片。
- **页表**：记录"逻辑页号 → 物理页框号"的映射。为省内存用**多级页表**（不存在的映射不分配）。
- **TLB（快表）**：缓存最近使用的页表项，命中则**无需访存查页表**，大幅加速地址转换——这也是上下文切换换页表后 TLB 失效、代价高的原因。

**追问：为什么多级页表能省内存？**
> **答案：** 单级页表要为整个地址空间建立全部映射项，即便大部分地址没用也要占空间。多级页表只在某级目录项被用到时才创建下一级页表，**未使用的地址区间完全不占页表内存**，用"多一次访存（或 TLB 命中避免）"换"大幅节省空间"。

### Q6. 什么是虚拟内存与请求分页？页面置换算法有哪些？缺页中断、抖动、内存碎片怎么回事？

**标准答案：**
- **虚拟内存**：让每个进程以为自己拥有**独立、连续、很大的地址空间**，实际只把当前需要的部分装入物理内存，其余在磁盘（换出/换入）。
- **请求分页**：进程运行时**只调入必要的页**；访问到不在内存的页时触发**缺页中断**，OS 从磁盘调入。
- **页面置换算法**（内存满时决定淘汰谁）：
  - ** FIFO**：淘汰最早调入的页，简单但可能有 **Belady 异常**（分配页框增多反而缺页更多）。
  - **LRU**：淘汰最近最久未使用的页，性能接近最优，但需硬件/软件记录访问历史，开销大。
  - **Clock（时钟）**：用访问位近似 LRU，性价比高，工程常用。
  - **OPT（最佳）**：淘汰未来最长时间不用的页，理论最优但**不可实现**（无法预知未来），用作衡量基准。
- **抖动（Thrashing）**：分配给进程的页框太少，导致**频繁换入换出**，CPU 大部分时间耗在页面置换上而非有效计算。解决：增加物理内存或减少并发进程数（**工作集模型**）。
- **内存碎片**：**内部碎片**——分配给进程的空间比需要的大，多出的部分浪费（分页产生）；**外部碎片**——空闲空间总量够但不连续，无法分配大块（分段产生）。

**追问 1：为什么 FIFO 会有 Belady 异常，LRU 不会？**
> **答案：** FIFO 不考虑页的**访问局部性**，淘汰的可能马上又被访问，因此可能出现"页框越多、命中反而越差"的反直觉现象。LRU 符合**栈式算法**特性（分配页框增多时，进程在任意时刻的页集合是旧集合的超集），因此不会出现 Belady 异常。

### Q7. 死锁的四个必要条件是什么？OS 层面如何预防、避免、检测与恢复？

**标准答案：**
- **四个必要条件**（缺一不可）：**互斥**、**请求和保持（占有且等待）**、**不可剥夺**、**循环等待**。
- **预防**（破坏其一）：如**资源有序分配法**（给资源编号，只能按序申请）破坏循环等待；一次性分配所有资源破坏请求和保持。代价是资源利用率低。
- **避免**——**银行家算法**：分配资源前先**模拟分配并检查系统是否仍处于"安全状态"**（存在一个安全序列能让所有进程最终完成），不安全则拒绝分配。
- **检测**：用**资源分配图**，化简后若不可完全化简则存在死锁；或定期检测。
- **恢复**：**剥夺资源**、**终止/回滚**部分进程，打破死锁。

> 本套只讲 OS 原理；Java 线上如何用 jstack 定位死锁见 `Java-死锁排查-面试题库.md`。

**追问 1：银行家算法的"安全序列"是什么意思？**
> **答案：** 指存在一个进程执行顺序 `<P1,P2,...Pn>`，使得每个进程 Pi 在其可获得的剩余资源需求被满足后能完成，并释放其占有的资源，从而让后续进程也能依次完成。若存在这样的序列，系统处于**安全状态**，从该状态出发一定不会死锁；反之则**可能**死锁（不安全状态不等于已死锁，只是有风险）。

## Part 3：核心区分度题（IPC·缓存·I/O）

> **这一部分是全题的题眼**——能否讲清 IPC 选型、缓存一致性、epoll 与零拷贝，直接区分 L2 与 L3/L4。定级主要看这里。

### Q8. 进程间通信（IPC）有哪些方式？各自适用场景？

**标准答案：**

| 方式 | 原理 | 特点 / 场景 |
|------|------|------------|
| **管道 pipe** | 内核缓冲区，半双工 | 仅限**父子/兄弟**进程，如 `ps \| grep` |
| **命名管道 FIFO** | 有路径名的管道 | 无亲缘关系进程也能用 |
| **消息队列** | 内核中的消息链表 | 按消息类型接收，**异步**，解耦生产消费 |
| **共享内存** | 映射同一块物理内存 | **最快**（无需内核拷贝），但需**信号量等同步**配合 |
| **信号量** | PV 操作计数器 | 用于**同步/互斥**，不传数据 |
| **信号 signal** | 软件中断 | **异步通知**，如 SIGKILL、SIGTERM |
| **Socket** | 基于网络协议 | 可**跨主机**，最通用 |

**追问 1：为什么共享内存最快？它有什么坑？**
> **答案：** 普通 IPC 数据要在"用户缓冲区 ↔ 内核缓冲区"之间来回拷贝；共享内存把**同一块物理内存映射到多个进程地址空间**，进程直接读写，无需拷贝、无需陷入内核，所以最快。坑是**没有同步机制**——多个进程同时写会竞态，必须额外配合信号量/锁。

### Q9. CPU 缓存一致性（MESI）是什么？缓存行与伪共享怎么理解？内存屏障有什么用？

**标准答案：**
- **MESI** 是多核 CPU 保证**缓存一致性**的协议，每个缓存行有四种状态：
  - **M（Modified）**：已被修改、与主存不一致，仅本核持有（脏）。
  - **E（Exclusive）**：独占、与主存一致，仅本核持有（干净）。
  - **S（Shared）**：多个核都持有、与主存一致（干净）。
  - **I（Invalid）**：无效，需从主存/其他核重新读取。
  - 某核写 S 状态的缓存行时，需通过**总线嗅探/RFO**让其他核的副本置为 I，保证一致性。
- **缓存行（Cache Line）**：CPU 缓存的最小单位，通常 **64 字节**。CPU 以行为单位加载，**相邻变量可能落在同一行**。
- **伪共享（False Sharing）**：多个核频繁修改**同一缓存行里的不同变量**，导致该行在各核间反复失效、来回同步，性能骤降（变量本身并无逻辑共享）。
- **内存屏障**：一类特殊指令，**禁止指令重排序 + 保证内存可见性**。Java 中 `volatile` 读写、`Unsafe`/`VarHandle` 的内存序，底层都靠插入内存屏障实现。

**追问 1：Java 怎么避免伪共享？**
> **答案：** 用 **`@sun.misc.Contended`** 注解（需 JVM 参数 `-XX:-RestrictContended`），它会在字段前后**填充空白字节**，让该字段独占一个缓存行。典型如 JDK 的 `LongAdder.Cell`、`Thread` 中的部分字段就用了它。手写也可用"填充无用 long 字段"的方式，但 `@Contended` 更规范。

### Q10. 阻塞/非阻塞、同步/异步有什么区别？select、poll、epoll 有何不同？LT 与 ET 是什么？零拷贝有哪些实现？

**标准答案：**
- **阻塞 vs 非阻塞**：看**调用者等待结果时线程是否挂起**。阻塞会挂起线程让出 CPU；非阻塞立即返回（可能数据未就绪），需轮询。
- **同步 vs 异步**：看**数据就绪后由谁完成"读取"**。同步 I/O 需要**调用者自己读**（即便非阻塞，也要应用反复 read）；异步 I/O 由**内核完成后通知**应用（如信号/回调），应用无需自己读。
  - 注意：**select/poll/epoll 都是同步 I/O**（只是"同步非阻塞"的多路复用），真正的异步 I/O 是 **io_uring / Windows IOCP**。
- **select / poll / epoll**：

| 维度 | select | poll | epoll |
|------|--------|------|-------|
| fd 传递 | 每次把 fd_set **拷贝进内核** | 拷贝 pollfd 数组 | **内核维护**，无需重复传 |
| 就绪获取 | 需**遍历**全部 fd，O(n) | 遍历，O(n) | 内核返回**就绪列表**，O(1) 感知 |
| fd 上限 | 通常 **1024** | 无硬限制 | 无硬限制 |
| 触发方式 | 水平触发 | 水平触发 | 支持 **LT / ET** |

- **LT（水平触发，默认）**：只要 fd 就绪就**持续通知**，不处理会反复通知，较安全。
- **ET（边缘触发）**：仅在状态**变化**时通知一次，必须配合**非阻塞 I/O 一次性读完**数据，否则可能再无通知，性能高但易踩坑。
- **零拷贝**：

| 技术 | 原理 |
|------|------|
| **mmap** | 把文件映射到用户空间，减少一次内核→用户的拷贝 |
| **sendfile** | 数据在内核态直接"文件 fd → socket fd"，不出内核 |
| **DMA** | 磁盘/网卡**直接访问内存**，不经过 CPU 搬运 |

**追问 1：Netty 为什么用 epoll？Java NIO 的 Selector 在 Linux 上底层是什么？**
> **答案：** Netty 在高并发长连接下需要高效管理海量 fd，epoll 的"无需重复传 fd + O(1) 感知就绪 + 无 1024 限制"正合适。Java NIO 的 `Selector` 在 Linux 上底层就是 **epoll**（通过 JNI），Netty 还可直接用 **EpollEventLoopGroup** 走 native epoll 并开启 ET 模式以进一步提性能。

**追问 2：epoll 的 ET 模式为什么必须配非阻塞 I/O，且要读到 EAGAIN？**
> **答案：** ET 只在状态变化时通知一次。若用阻塞 I/O 且没读完，线程会卡在 read 上；若读到一半就返回，剩余数据不会再次触发通知，造成"数据饥饿"。所以必须**循环读到返回 EAGAIN（表示暂时无数据）** 才算本次数据处理完，而这要求 fd 是非阻塞的（否则阻塞 read 会卡住线程）。

## Part 4：实战与陷阱题（Linux 排障·文件系统）

### Q11. 线上 CPU 100% 怎么排查？load average 高意味着什么？常用性能命令有哪些？

**标准答案：**
- **CPU 100% 排查思路（OS 通用）**：
  1. `top` 找到高 CPU 的进程 PID；
  2. `top -H -p <pid>` 或 `ps -L` 找到该进程里高 CPU 的**线程**；
  3. 把线程 ID 转成**十六进制**（`printf %x <tid>`）；
  4. 若是 Java 进程，用 `jstack <pid> | grep -A 20 <十六进制tid>` 定位线程栈（Java 实战细节见死锁/JVM 题库）。本质思路是"**进程→线程→线程栈**"逐层定位。
- **load average**：`top/uptime` 显示的 1/5/15 分钟**平均负载**，指**正在运行 + 不可中断睡眠（D 状态，通常是等 I/O）的进程总数**。它是 **CPU + 磁盘 + 网络等综合压力**，不只看 CPU：
  - 单核 CPU：load≈1.0 表示满载；4 核：load≈4.0 满载。
  - **load 高但 CPU 不高** → 多半是 **I/O 等待**（D 状态进程多）或锁竞争；**load 高且 CPU 高** → CPU 密集型打满。
- **常用命令**：

| 命令 | 用途 |
|------|------|
| `top` / `htop` | 进程级 CPU、内存、负载总览 |
| `vmstat` | 内存、swap、上下文切换、CPU、I/O 概览（看 si/so 判断换页） |
| `iostat` | 磁盘 I/O（看 %util、await 判断磁盘瓶颈） |
| `ss` / `netstat` | 连接、端口、Socket 状态（`ss` 更快，推荐） |
| `strace` | 跟踪进程的**系统调用**，定位卡在哪一步 |
| `pstack` | 打印运行中进程的**线程栈** |

**追问：系统很卡但 top 显示 CPU 不高，往哪个方向查？**
> **答案：** 优先查 **I/O 和内存**：用 `vmstat 1` 看 si/so（换页）、wa（I/O 等待）；用 `iostat -x 1` 看磁盘 `%util` 是否接近 100%；用 `top` 看是否有大量 **D 状态（不可中断睡眠）** 进程——这些都会推高 load 但不一定高 CPU。还可能是**锁竞争/死锁**导致线程阻塞（此时 `pstack`/`jstack` 看栈）。

### Q12. 内存泄漏与 OOM Killer 是什么？inode、软链接和硬链接有什么区别？

**标准答案：**
- **内存泄漏**：程序申请内存后**不再使用却不释放**，可用内存逐渐减少。Java 中表现为对象被无意持有（如静态集合、未关闭的资源、ThreadLocal 未清理）导致 **GC 无法回收**。
- **OOM Killer**：Linux 在**物理内存极度不足**时，内核挑一个进程**杀掉**以保住系统（依据 `oom_score`，倾向杀占用内存大的进程）。Java 进程若堆设置过大、超过容器内存限额，就可能被 OOM Killer 直接杀死（日志见 `dmesg`）。注意区分：Java 自己的 `OutOfMemoryError` 是 **JVM 堆内**抛的；被 OOM Killer 杀是 **OS 层**行为，进程直接消失。
- **inode**：存放文件的**元数据**（权限、大小、时间戳、数据块位置等），**文件名存在目录项（dentry）中**，inode 才是文件的实体标识。
- **硬链接**：多个文件名**指向同一个 inode**（同一文件）。删除其中一个名字，文件仍可通过其他名字访问。特点：**不能跨文件系统、不能链接目录**。
- **软链接（符号链接）**：一个**独立文件**，内容存的是**目标路径**。特点：**可跨文件系统、可链接目录**，但删除目标后软链接**失效**（悬空链接）。

**追问 1： df 显示磁盘还有空间，但创建文件报"No space left on device"，为什么？**
> **答案：** 两种常见原因：① **inode 用尽**——大量小文件耗尽了 inode（`df -i` 查看），即使数据块还有空间也无法新建文件；② 空间被**已删除但仍被进程占用**的文件占着（文件被 rm 但句柄未释放，`lsof | grep deleted` 查看），需重启进程释放。

**追问 2：Java 容器里如何避免被 OOM Killer 杀掉？**
> **答案：** 关键是让 **JVM 堆 + 元空间 + 线程栈 + 直接内存** 的总和**小于容器内存 limit**，预留余量。例如容器 limit=2G，Xmx 设 1.2~1.5G 左右，并注意 `-XX:MaxRAMPercentage`（JDK 10+ 可按容器内存比例设堆）。同时监控容器内存和 `dmesg`，区分是 Java OOM 还是被内核 OOM Killer 杀死。

## Part 5：2026 新趋势（io_uring·eBPF·EEVDF）

> 加分题，考察候选人的技术视野。以下演进以官方发布为准，细节保守表述。

### Q13. 说说你了解的操作系统/I/O 近几年的演进方向。

**标准答案：**
- **io_uring**：Linux 引入的高性能**异步 I/O 框架**（约 5.1 起），通过 **SQ（提交队列）/ CQ（完成队列）两个环形缓冲区** 与内核共享内存，显著减少系统调用次数和拷贝。它既支持网络也支持文件 I/O，被视为 **epoll + 异步 I/O 的统一替代方向**。需注意：它在容器/安全沙箱中的可用性受 seccomp 策略影响，生产落地要结合具体内核与环境评估。
- **eBPF**：可在**内核中安全运行沙箱程序**的技术，无需改内核源码或加载内核模块，广泛用于**可观测性（网络、性能、追踪）、安全和网络**（如 Cilium）。它让"零侵入地采集内核级指标"成为可能，是云原生可观测性的重要基石。
- **cgroup v2**：Linux 资源控制（CPU/内存/I/O 等）的**统一层级**新版本，相比 v1 的多层级、行为不一致，v2 用**单一层级树 + 统一控制器接口**，语义更一致。容器（Docker/K8s）的资源隔离正逐步迁移到 v2。
- **EEVDF 调度器**：Linux 社区引入的新**进程调度器**（约 6.6 起成为默认），基于"最早合格虚拟截止时间优先"，旨在替代 **CFS**，改善**延迟敏感型任务**的响应，同时保持公平性。
- **RISC-V**：**开源、模块化的指令集架构（ISA）**，可按需扩展。生态持续成长，在嵌入式、加速器和部分服务器场景受到关注，是 x86/ARM 之外的重要选项。

**追问 1：io_uring 和 epoll 的本质区别是什么？**
> **答案：** epoll 是**同步** I/O 多路复用——就绪后仍需应用自己调用 read/write 去拷贝数据，且每次 epoll_wait 有系统调用开销。io_uring 是**异步**模型——应用把请求放进 SQ、内核完成后把结果放进 CQ，应用**批量提交/收割**，大幅减少系统调用，且读写由内核异步完成。简单说：epoll 解决"等哪些 fd 就绪"，io_uring 更进一步把"读写本身也异步化并批处理"。

**追问 2：作为 Java 后端，这些演进和你有什么关系？**
> **答案：** ① **epoll → io_uring**：Netty 等网络框架已在探索 io_uring 后端，未来高并发网络 I/O 模型可能变化；② **eBPF**：可用它做零侵入的**线上性能诊断与网络观测**（如排查延迟、丢包），比传统 strace/tcpdump 更强；③ **cgroup v2**：直接影响容器里 JVM 的内存/CPU 限额判定与垃圾回收调优；④ 理解这些有助于在**基础架构/性能优化**方向上建立技术判断力，而非只停留在业务 API 层。

## Part 6：能否用操作系统题定级？如何定级？

### 结论先行

**可以，操作系统是区分度极高的探针**——它天然分层：会背定义 → 懂机制 → 懂内核原理与权衡 → 有生产排障经验 → 跟进演进。但 OS 知识面很广，**对纯业务开发候选人不必面面俱到**：招初中级问到 Part 1/2 即可，强问内核细节只会考察背诵；招高并发/基础架构岗则应深挖 Part 3/4。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 背得出进程/线程区别、五态、常见调度算法名；说不清页表、epoll、上下文切换细节 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂虚拟内存/分页、死锁四条件与银行家算法、用户态内核态；但讲不清 epoll/缓存一致性 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能讲清 IPC 选型、MESI/伪共享、同步异步与 epoll LT/ET、零拷贝，并联系到 Java（Netty/Kafka） |
| **高级（L4）** | 8 年+ | Part 4 | 有真实排障经验：CPU 100%/load 高/OOM Killer/inode 问题能定位，讲得出具体命令与现象 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 io_uring/eBPF/cgroup v2/EEVDF，能把 OS 原语与系统架构、性能体系化结合并做选型 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"资源管理/抽象 + 虚拟内存 + epoll/零拷贝落地"→ 至少 L3；只会背"进程是资源分配基本单位"→ 从 Part 1 逐级问。

**第二步：沿追问链下探。** 重点追问"为什么"和"落地"：
- 为什么上下文切换开销大？（TLB 失效 + 态切换 + 保存恢复）
- 为什么 epoll 比 select 快？ET 为什么必须配非阻塞？（O(1) 感知、读到 EAGAIN）
- 为什么页框多了 FIFO 反而可能更慢？（Belady 异常）

**第三步：三类信号防背题。**
1. **真实性**：能否讲出**真实的线上事故与排查细节**（"load 飙高但 CPU 不高，`vmstat` 看到 wa 很高，定位到慢盘" / "容器内存超限被 OOM Killer 杀，`dmesg` 确认"）。能讲细节 > 教科书答案。
2. **抽象能力**：能否把"进程/虚拟内存/文件/Socket"统一为"**操作系统对硬件资源的抽象**"，把 epoll/零拷贝和 Netty/Kafka 高性能对应起来。
3. **权衡能力**：能否说清"什么场景不该用"——如 ET 虽快但易踩坑、预防死锁利用率低、银行家算法通用系统难落地。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整追问深度，业务岗到 Part 3 足够，基础架构岗需 Part 4/5。

---

### 面试官避坑提醒

- **不要对纯业务开发问到内核源码级**——很多优秀工程师没背内核实现但理解思想，区分"理解机制"和"背过术语"，前者更有价值。
- **把 Part 4 排障作为 L4 分水岭**：能讲出具体命令、现象、定位过程的人，通常是真线上打过仗的。
- **注意与其他套题的边界**：死锁只问 OS 原理（银行家/资源图），jstack 实战留给死锁排查套；epoll/零拷贝联系 Java 时，点到为止，避免与网络/JVM 套重复。
- **结合岗位**：应届/初级重点 Part 1/2；高并发中间件重点 Part 3（epoll/伪共享/零拷贝）；基础架构/SRE 重点 Part 4。
