## Part 0：30 秒标准总答

**Q：谈谈你对 Redis 生产实战 / 进阶治理的理解。**

**标准答法（30 秒，五个得分点）：**

> Redis 进阶实战的核心不是"会用命令"，而是**让它在生产环境稳定、正确、高性能地跑**。第一是**可观测性**：靠 slowlog、LATENCY DOCTOR、INFO 与监控指标持续掌握状态，而非等告警才动手。
> 第二是**稳定性治理**：识别并治理大 Key、热 Key，避免慢命令与阻塞拖垮单线程模型。
> 第三是**正确性**：在缓存一致性、分布式锁上做到工程可用，接受最终一致、控制不一致窗口。
> 第四是**内存与性能诊断**：理解碎片率、缓冲区、淘汰策略，能排查 OOM 与延迟毛刺。
> 第五是**架构演进**：用多级缓存、Pipeline / Lua、客户端缓存与版本新特性（如 Redis 8）持续演进。

**评分要点：** 可观测性 / 大 Key 热 Key / 一致性 / 内存性能诊断 / 架构演进。能说出"先观测再动手、单线程怕阻塞"的，直接往 Part 3 追问。

## Part 1：基础认知题（进阶实战视角）

### Q1. 实战中 Redis 有哪些典型误用？

**标准答案：** （考察是否真在生产用过）

| # | 典型误用 | 后果 |
|---|---------|------|
| 1 | 把 Redis 当**主数据库**（无事务回滚、持久化尽力而为） | 切换丢数据、跨槽多 key 报错 |
| 2 | `KEYS *`、`HGETALL`/`SMEMBERS`/`LRANGE 0 -1` 全量取 | O(N) 阻塞单线程，请求超时连锁 |
| 3 | 单 String 超大 JSON、集合百万元素、`DEL` 同步删 | 大 Key，删除 / 同步卡、主线程阻塞 |
| 4 | 不设 TTL / TTL 集中、业务数据混用却配 `allkeys-lru` | 涨满 / 雪崩、不可丢数据被淘汰 |
| 5 | `SETNX` + `EXPIRE` 两条命令加锁 | 非原子，进程崩溃即死锁 |
| 6 | "先删缓存再更新 DB" | 旧值回写，长期不一致 |

**追问 1：为什么"把 Redis 当 DB 用"很危险？**
> **答案：** 持久化尽力而为（RDB 有快照间隔、AOF everysec 最多丢 1 秒），主从切换可能丢数据；MULTI **无回滚**；Cluster 跨槽多 key 报错；内存成本远高于磁盘。它定位是"高速缓存 / 临时数据层"，不是持久化的 source of truth。

**追问 2：哪些会直接引发线上故障，哪些是"慢性隐患"？**
> **答案：** 直接故障：`KEYS` / 全量操作、`DEL` 大 Key、缓冲区 OOM、无 TTL 涨满。慢性隐患：当 DB 用、TTL 集中、淘汰策略选错。能区分轻重缓急体现优先级判断力。

### Q2. 生产环境 Redis 需要监控哪些核心指标？

**标准答案：** （"没有观测就没有治理"，进阶与入门的分水岭）

| 类别 | 关键指标 | 来源 | 关注点 |
|------|---------|------|--------|
| 性能 | P99/P999 延迟、慢查询数 | LATENCY / SLOWLOG | 突增即排查 |
| 内存 | used_memory、mem_fragmentation_ratio | INFO memory | 碎片率 >1.5 或 <1 |
| 连接/流量 | connected_clients、rejected_connections、ops/sec | INFO clients/stats | 逼近上限 / 突变 |
| 持久化 | rdb/aof 上次 bgsave/bgrewrite 状态 | INFO persistence | 失败要告警 |
| 复制 | master_link_status、slave lag | INFO replication | 断开 / 延迟 |
| 系统 | CPU、SWAP、网卡丢包 | OS 层 | SWAP 即性能断崖 |

**追问 1：为什么"延迟"比"QPS"更能反映 Redis 健康？**
> **答案：** QPS 高可能只是业务高峰；但**延迟毛刺直接意味着单线程被阻塞**——慢命令、大 Key 删除、fork、AOF rewrite、网络抖动都会体现在 P99。单线程下延迟是健康"金丝雀"，应监控分位值而非平均值。

**追问 2：光靠 INFO 够吗？**
> **答案：** 不够。INFO 是即时快照，需时序化（Prometheus + redis_exporter + Grafana）做趋势与告警；配合 SLOWLOG、LATENCY MONITOR、OS 层 SWAP / 磁盘 IO 监控。SWAP 一旦发生，换页使性能断崖下降。

## Part 2：底层原理题（与实战相关的机制）

> 聚焦"能解释生产现象"的原理，L2→L3 关键。数据结构 / 持久化基础见基础篇。

### Q3. lazyfree 机制如何避免删除大 Key 阻塞主线程？

**标准答案：** Redis 4.0 引入 lazyfree，把耗时内存释放交给**后台线程（BIO）**异步执行。**命令层**：`UNLINK`、`FLUSHDB ASYNC` / `FLUSHALL ASYNC`；**配置层**：`lazyfree-lazy-eviction`（淘汰）、`lazyfree-lazy-expire`、`lazyfree-lazy-server-del`、`replica-lazy-flush`、`lazyfree-lazy-user-del yes`（让 DEL 也异步）；**原理**：主线程只做"从字典摘除 key"的 **O(1)** 操作，释放底层结构（百万元素逐项 free）丢进 bio 队列由后台线程**分批**释放。

**追问 1：UNLINK 一定完全不阻塞吗？**
> **答案：** 摘除字典项仍在主线程但为 O(1)；耗时的是释放底层结构，交给后台线程。所以只有极短同步开销，不会"卡几百毫秒"，但并非零成本。

**追问 2：开 `lazyfree-lazy-user-del yes` 就万事大吉？**
> **答案：** 不是。异步释放期内存不立即回落，短时间删大量大 Key 会致内存短暂上涨（需留 maxmemory 余量）。根本手段仍是**避免大 Key + 拆分**，lazyfree 只是兜底。

---

### Q4. 内存碎片率怎么产生？activedefrag 如何工作？

**标准答案：** `mem_fragmentation_ratio = used_memory_rss / used_memory`（rss 是 OS 实际分配物理内存）。**> 1.5** 碎片偏高（频繁改删产生无法合并的空闲块）；**1.0~1.1** 健康；**< 1** 危险——部分内存被 **swap 到磁盘**，换页极慢、延迟飙升。**activedefrag（4.0+）**：后台线程低峰"搬移"数据、聚拢占用、释放连续块，参数 `activedefrag yes`、`active-defrag-threshold-lower/upper`、`active-defrag-ignore-bytes`、`active-defrag-cycle-min/max`（控制 CPU 占用）；也可 `MEMORY PURGE`（jemalloc）。

**追问 1：jemalloc 已按大小分桶，为何还有碎片？**
> **答案：** value 大小分布不均 + 频繁改删，会让页"部分占用"（4KB 页只用 1KB，剩余因属不同 size class 无法复用），长期累积成碎片；maxmemory 下反复淘汰也加剧。

**追问 2：碎片率高一定要开 activedefrag 吗？**
> **答案：** 不绝对。先看是否真影响内存与延迟，整理本身耗 CPU 且有搬移开销，内存充裕而只是略高时可不开。**swap（<1）比碎片高（>1.5）更紧急**——那是性能悬崖。

---

### Q5. RESP3 相比 RESP2 有哪些实战相关的变化？

**标准答案：** RESP2 用简单类型标记（+ 状态、- 错误、: 整数、$ 串、* 数组）。RESP3（6.0）新增：类型更丰富（**map %、set ~、null _、boolean #、double ,、push >**）；**Push 类型**支持服务器**主动推送**（客户端缓存失效、Pub/Sub），是 client-side caching 的协议基础；`HELLO 3` 切换后 `HGETALL` 等返回 map 而非扁平数组，语义更准。需客户端库支持（Jedis / Lettuce 高版本）。

**追问 1：用了 RESP3 就一定要开客户端缓存吗？**
> **答案：** 不。RESP3 是协议能力，客户端缓存是上层应用。可只用类型语义增强而不开 tracking；客户端缓存也要按读写比评估普通 / 广播 / 重定向模式的代价。

**追问 2：RESP3 有什么坑？**
> **答案：** ① 老客户端解析不了 map/push；② 开 `HELLO 3` 后服务器主动 push，客户端读循环若不处理 push 通道会当普通回复，致**协议错乱**；③ 即使没开 tracking 也可能收到 invalidate。升级务必测试。

## Part 3：核心区分度题（定级主战场）

> **全题题眼**——能否系统性排查慢查询、内存、一致性，直接决定 L2 还是 L3/L4。

### Q6. 线上 Redis 突然变慢 / 延迟毛刺，如何系统性排查？

**标准答案：** （能讲出路径基本是 L3+）

| 步骤 | 手段 | 看什么 |
|------|------|--------|
| 1 | `SLOWLOG GET` / `LEN` | O(N) 命令、耗时分布 |
| 2 | `LATENCY DOCTOR` / `LATEST` / `GRAPH` | fork / aof-write / expire-cycle 尖峰 |
| 3 | `--bigkeys` / `MEMORY USAGE` | 是否正在删 / 过期大 Key |
| 4 | `INFO stats` / `TOP` | big request、CPU 是否打满 |
| 5 | `INFO clients` / `INFO persistence` / 网卡 / OS | 连接池、fork(`latest_fork_usec`)、SWAP / 丢包 |

> big request（超大 value / 大批量）受 `proto-max-bulk-len`（默认 512MB）限制，占用输入缓冲与网络，也体现在延迟上。

**追问 1：为什么毛刺常不是命令慢，而是 fork / AOF rewrite？**
> **答案：** `bgsave`/`bgrewriteaof` 要 `fork()`，内核复制页表（与内存量成正比），几十 GB 实例可耗几十~上百毫秒，期间主线程被阻塞（STW），表现为延迟尖刺；COW 期大量写入还放大内存与 CPU——这是"没人执行慢命令却卡"的常见真因。

**追问 2：slowlog 里全是 HGETALL，怎么定位业务并治理？**
> **答案：** ① 用 `SLOWLOG GET` 时间戳与客户端地址关联接入层日志；② `CLIENT LIST` 看来源（建议 `CLIENT SETNAME` 标注服务名）；③ 改 `HSCAN` 分批取或把大 Hash 拆小，代码 Review 禁用全量命令。

### Q7. Redis 内存告警甚至 OOM，如何排查？

**标准答案：** ① `INFO memory` 看 used_memory / rss / maxmemory / 碎片率；② **数据真涨了？** `INFO keyspace` 看 key 量，`--bigkeys`/`--memkeys`（7.x）找大户、无 TTL key 是否堆积；③ **碎片？** >1.5 考虑 activedefrag / MEMORY PURGE；④ **缓冲区？** `INFO clients` 看 `client-output-buffer-limit` 三类（normal / replica / pubsub），经典事故是 **replica 复制缓冲区因从库慢 / 网络差堆积撑爆 master**；⑤ **淘汰策略？** `noeviction` 写满报错、混存业务数据用 `allkeys-lru` 会误删；⑥ **COW？** fork 后大量写入使内存近翻倍，需预留余量。

| 现象 | 常见原因 | 处理 |
|------|---------|------|
| 持续涨 / 突然飙升 | 无 TTL 堆积 / replica 缓冲区 / COW | 补 TTL、查从库、留余量 |
| 写入报 OOM | noeviction | 调策略或扩容 |
| rss < used_memory | 发生 swap | 立刻扩容 / 降负载 |

**追问 1：used_memory 与 rss 差别大说明什么？**
> **答案：** rss 远大于 used_memory（>1.5）是碎片多；rss 远小于 used_memory（<1）是 swap——最危险。正常 rss 略大于 used_memory（1.0~1.3）。

**追问 2：配了 maxmemory 为何还被 OOM Killer 杀？**
> **答案：** maxmemory 只限制**数据占用**，不限进程总内存。还有 fork 的 COW、输出缓冲区、复制缓冲区、Lua 临时内存、jemalloc 碎片，合计超系统可用内存即被杀。故 maxmemory 一般设为系统内存 **70%~80%** 留余量。

### Q8. 缓存一致性进阶——脏数据窗口、延迟双删、binlog 订阅怎么取舍？

**标准答案：** （"先更新 DB 再删缓存"是基础，进阶考删除失败与并发脏读）**并发脏数据窗口**：即使"先 DB 后删缓存"，线程 B 在 A 更新 DB 前读到旧值并回写缓存，造成短暂不一致。**延迟双删**：删缓存 → 更新 DB → sleep（几百 ms）→ 再删缓存，sleep 难精确、损吞吐、第二次删仍可能失败。**binlog 订阅（Canal + MQ）**：业务只更新 DB，Canal 伪装 slave 订阅 binlog 经 MQ 异步删缓存，解耦、可重试、最终一致，代价是链路长、毫秒~秒级延迟、需幂等与顺序。**强一致兜底**：锁串行化读改写，或读写都走 DB，或最终一致 + TTL 兜底。

| 方案 | 一致性 | 复杂度 | 适用 |
|------|--------|--------|------|
| 延迟双删 | 较弱（降概率） | 低 | 简单场景 |
| Canal + MQ | 最终一致 | 高 | 中大型、可补偿 |

**追问 1：延迟双删 sleep 设多少？根本缺陷？**
> **答案：** 经验为"大于主从延迟 + 一次 DB 读 + 一次缓存写"，常见几百 ms。缺陷：① 靠拍脑袋、依赖流量；② 损吞吐；③ 第二次删仍可能失败；④ 主从延迟大于 sleep 仍不一致。只是"降概率"，非强一致保证。

**追问 2：Canal + MQ 如何保证消息不丢、不重复、有序？**
> **答案：** ① Canal 记录 binlog position，失败可重放；② MQ 生产者确认 + 消费者 ACK；③ 删缓存天然幂等；④ 按 key hash 到同分区保证同条数据有序；⑤ 监控延迟与积压告警。MQ 延迟期仍有短暂不一致窗口。

## Part 4：实战与陷阱题（案例驱动，本套重头戏）

### Q9. 大 Key 治理——定义、发现、删除、拆分

**标准答案：** **阈值**（经验）：String > 10KB；Hash/List/Set/ZSet 元素 > 5000 或大小 > 10MB，精确判断用 `MEMORY USAGE key`。**危害**：O(N) 操作阻塞单线程、网络慢、删除卡顿、Cluster 倾斜、COW 放大、同步慢。**删除姿势**：`UNLINK` / `FLUSHDB ASYNC`，开 `lazyfree-lazy-user-del`，**绝不 DEL 超大 Key**（曾致主线程阻塞数百 ms~秒级）。**拆分**：大 Hash 按业务拆多 key 或按 field hash 分片；大 List/Set 分 `key:{i}`、读取聚合；大 String 压缩（gzip/snappy）或分段。根本是**设计阶段避免大 Key**。

| 发现方式 | 特点 | 适用 |
|---------|------|------|
| `--bigkeys` / `SCAN`+`MEMORY USAGE` | 前者采样快但不精，后者精确需遍历 | 找候选 / 确认 |
| RDB 离线分析（rdb-tools） | 全量、不影响线上、非实时 | 定期审计 |
| 代理 / 云厂商 | 实时 | 长期监控 |

**追问 1：为何说 `--bigkeys` "采样不准"，怎么用？**
> **答案：** 它内部 SCAN 采样，按 STRLEN/LLEN/SCARD/ZCARD 衡量长度 / 元素数，**非真实内存**（5000 小元素 Set 内存可能不大）。适合快速定位候选，确认再用 `MEMORY USAGE`；每类型只报最大一个，建议低峰或**从库**执行。

**追问 2：删千万元素的 Set，除 UNLINK 还要注意什么？**
> **答案：** ① 后台分批释放期内存不立即降，留余量避免触发淘汰；② 摘除后并发写同名 key 需业务层防竞争；③ Cluster 大 key 集中某槽，删后倾斜才缓解；④ 从库由 `replica-lazy-flush` 控制异步清空；⑤ 更根本是不该产生千万级 Set，应分片。

---

### Q10. 热 Key 问题——发现、本地缓存、打散、云方案

**标准答案：** **危害**：单 key 请求集中超过单线程 / 单分片能力，打垮节点、拖慢同节点其他 key，是击穿温床。**解决**：① **本地缓存 + 多级缓存**（Caffeine → Redis → DB）拦截绝大多数读；② **读写分离**分散读；③ **分片打散**——key 加随机后缀 `hot:{random:N}` 分散，代价是更新要写所有副本、一致性复杂；④ 云厂商热 Key 方案。关键认知：**"发现热 Key"往往比"解决"更难**，Redis 本身不直接统计热度。

| 发现方式 | 特点 |
|---------|------|
| `MONITOR` | 看全部命令但**极危险**，高频下自身阻塞、输出海量，只短时低频抓 |
| `redis-cli --hotkeys` | 基于 LFU 计数采样，需 LFU 策略或 tracking |
| 代理 / LB 统计、业务埋点 | 按 key 聚合频次；埋点最贴近业务 |

**追问 1：为什么 MONITOR 生产要慎用？**
> **答案：** 它把每条命令推给监控客户端，高并发下① 客户端处理不过来致输出缓冲堆积、连接被断；② 增加 Redis 输出压力、自身加重延迟；③ 输出含敏感数据。只用于短时抓包，绝不常开。替代：`--hotkeys`、代理统计、埋点。

**追问 2：本地缓存解决热 Key 如何避免脏数据？**
> **答案：** ① 本地缓存设很短 TTL（秒级）；② key 变更用 Pub/Sub 或客户端缓存失效通知主动清各节点缓存（防广播风暴）；③ 版本号 / CAS 校验；④ 接受最终一致。热 key 多为读多写少、实时性不高的数据（商品详情、配置），适合缓存。

### Q11. 分布式锁进阶——Redlock 争议、看门狗、可重入、Redisson

**标准答案：** （基础 SET NX EX + Lua 原子释放见基础篇）**Redlock 争议**：向多个独立 master 依次加锁、过半成功且耗时 < 锁有效期；Martin Kleppmann 批评其**依赖时钟同步**，GC 停顿 / 网络延迟可致客户端在锁过期后才操作资源、互斥失效，Antirez 反驳；结论是非拜占庭、时钟可靠时可用，**强一致更推荐 etcd / ZK / DB 锁**。**看门狗**：Redisson 默认租期 30s，后台定时任务（Netty HashedWheelTimer）每 10s（leaseTime/3）若仍持有则 `PEXPIRE` 续到 30s，业务结束 / 宕机停止续期、锁自然过期。**可重入**：用 **Hash**，field 为线程标识（UUID+threadId）、value 为重入次数，Lua 加锁同线程 value+1、解锁 value-1、到 0 才删并 publish。**锁等待 / 死锁**：`lock()` 失败后用 **Pub/Sub 订阅 + Semaphore 阻塞等待**避免忙等，"过期 + 看门狗"兜底。

**追问 1：Redlock 到底该不该用？**
> **答案：** 视场景。普通业务单节点 + 看门狗已够，主从切换的极小概率不一致可接受；Redlock 提升可用性但引入时钟依赖与复杂度、争议大；金融 / 强一致用 etcd（Raft + lease）。想听的是**知道边界与争议**，而非站队。

**追问 2：看门狗续期期间主从切换会怎样？**
> **答案：** 经典痛点：锁写在 master，未同步到 slave 就切换，新 master 无锁，另一客户端加锁成功 → "双主持锁"。看门狗只解决"业务没做完锁过期"，**不解决主从切换丢锁**。缓解：Redlock、接受窗口、或改用 etcd / ZK。强一致别依赖异步复制的 Redis 锁。

**追问 3：可重入锁为何用 Hash，不用 String + 计数？**
> **答案：** Hash 的 field 区分**不同线程**、value 存各自**重入次数**，String 无法在一个 key 里原子地多维建模。Hash + Lua 能原子判断"是不是我的锁、重入几次、要不要 ±1"；value 减到 0 才真删，避免误删其他线程。

### Q12. 实战案例复盘

**标准答案：** （L4 分水岭——能否讲清时间线、根因、补救、预防）

**案例一：缓存击穿打挂 DB**
- T0 热点 key（商品详情）到期 → T0+50ms 大量并发未命中，无防护则全量穿透 DB → T0+数秒 DB 连接池打满、慢查询堆积、雪崩。
- 补救：限流降级、缓存预热、DB 兜底；预防：互斥锁（只放一线程重建）或逻辑过期（先返旧值异步更新）、热点 key 逻辑永不过期。

**案例二：Pipeline / Lua 的坑**
- Pipeline 批量上万条一次性发送，内存 / 网络压力大且无原子性 → 分批（每批数百）。
- Lua 写大循环 / 大范围遍历阻塞全局，用 time/random 致主从不一致 → 脚本短小、确定性、禁 `KEYS`；超时后**只读可 `SCRIPT KILL`，写脚本已执行不可杀**（最大陷阱）。

**案例三：数据恢复与误删**
- 误删 key：从 AOF 剔除对应 DEL 后重写恢复，或回滚 RDB 备份。
- 误执行 FLUSHALL：停写 → 恢复快照 → 补增量；AOF 完整可截断到误操作前。
- 教训：`rename-command FLUSHALL ""`、权限隔离、定期做**可回滚演练**。

**追问 1：缓存击穿"互斥锁"和"逻辑过期"怎么选？**
> **答案：** 互斥锁一致性强但其余线程阻塞等待（吞吐降、死锁风险），适合敏感、不能接受旧值；逻辑过期（value 内嵌过期时间，后台异步更新，其余先返旧值）可用性高、不阻塞，适合热点、可容忍短暂不一致。商品详情这类读多写少用逻辑过期更稳。

**追问 2：Lua 脚本执行到一半超时能直接杀吗？**
> **答案：** 分情况：只读脚本可 `SCRIPT KILL` 安全终止；**已执行写命令的脚本会被 Redis 拒绝 KILL**（破坏原子性、致主从不一致），只能 `SHUTDOWN NOSAVE` 或等它跑完。根本是避免写耗时 Lua。

### Q13. Redis 8.0 与客户端缓存、IO 多线程、AI 场景

**标准答案：**
- **Redis 8.0（2025-05 GA）**：**许可变化**——延续 7.4 起多许可（RSALv2 / SSPLv1 / **AGPLv3**），AGPLv3 相对友好，Redis Open Source（原社区版）内置原 Stack 模块（JSON、TimeSeries、概率结构 Bloom / Top-K 等），细节以官方为准；**Vector Set（向量集）**——新增结构，基于 **HNSW** 做高维向量相似度检索，面向 RAG / 语义搜索 / 推荐，仍处 **Beta**、API 可能调整，大规模检索需与专业向量库（Milvus 等）权衡；新增 Hash 字段级过期命令（HGETEX / HSETEX / HGETDEL 等），官方称多项命令延迟显著下降。
- **客户端缓存（CLIENT TRACKING，6.0+）**：基于 RESP3 push 推失效，服务器记录客户端读过的 key，变更时主动推失效；模式有普通（按 key）、广播（按前缀，客户端多时省服务端内存）、重定向（专门连接收失效）；收益是热点本地命中，坑是断连需清缓存、失效风暴、一致性窗口。
- **IO 多线程实战**：`io-threads N`（默认只在**写 / 发送**方向多线程，`io-threads-do-reads yes` 才让读也多线程），经验设 CPU 核数 3/4、一般不超 8，只并行网络收发、命令执行仍单线程。
- **AI 场景**：作为实时数据层支撑 RAG（向量检索 + embedding 缓存）、会话记忆、LLM 调用限流，定位低延迟检索 / 缓存，不替代专业向量库的大规模离线检索。

**追问 1：客户端缓存几种模式怎么选？**
> **答案：** 普通模式按 key 精确追踪、服务端内存随 key 与客户端增长；广播模式按前缀注册失效、服务端内存与客户端数无关，适合客户端多且 key 集集中（如都访问 `user:*`）；重定向用专门连接收失效，适合连接数受限。本质是"服务端内存 vs 客户端内存 vs 失效精度"的权衡。

**追问 2：IO 多线程开了就更快吗？**
> **答案：** 不一定。它只并行网络收发与协议解析，命令执行仍单线程；只有确认瓶颈在网络 I/O 时才有收益。线程数超经验值（~8）收益递减甚至因上下文切换下降，默认还不开启读方向多线程。必须结合 INFO 与压测实测，**别迷信"多线程=快"**。

## Part 6：能否用它定级？如何定级？

### 结论先行

**可以，且是区分"背八股"与"真做过"的强力探针**——天然分层：知道要观测 → 会治理大 Key / 热 Key → 能排查慢查询 / 内存 → 能落地一致性与锁的工程细节 → 有事故复盘 → 跟进版本演进。但若基础题库（五种结构 / 单线程 / 缓存三兄弟）没过，直接用本篇会"问不动"，应先用基础篇摸底。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 会基本命令、知道要看慢日志 / 大 Key，说不清排查路径 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂 lazyfree / 碎片率 / RESP3 原理，能说大 Key 危害 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能系统排查慢查询 / 内存，讲清一致性方案与取舍 |
| **高级（L4）** | 8 年+ | Part 4 | 有真实事故复盘，能落地大 Key / 热 Key 治理与 Redisson 要点 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 8.0 / 客户端缓存 / 向量，能做缓存架构、选型与多活 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"先观测、单线程怕阻塞、大 Key 热 Key、一致性"→ 至少 L2；只会"Redis 快、做缓存"→ 回基础篇补。

**第二步：沿追问链下探"为什么 / 怎么做"。** 为什么 UNLINK 不阻塞？（主线程只 O(1) 摘除）为什么碎片率 <1 比 >1.5 危险？（swap 性能悬崖）为什么延迟双删 sleep 是拍脑袋？（依赖流量、只是降概率）为什么 Lua 写脚本超时不能 KILL？（破坏原子性、致主从不一致）

**第三步：三类信号防背题。** ① **真实性**：能否讲出具体事故细节（"一次 DEL 大 Key 卡 800ms 致超时"）；② **抽象能力**：能否把大 Key / 热 Key / 慢查询统一为"单线程下 O(N) 与热点集中"；③ **权衡能力**：能否讲清"什么场景不该用"（强一致别只用缓存、Redlock 边界、IO 多线程别盲开）。

**第四步：按最深层级定级，不按正确率。** 业务开发问到 Part 3 / 4 足够；中间件 / 架构深挖 Part 5。

---

### 面试官避坑提醒

- **把"真实事故复盘"作为 L4 分水岭**：能讲清时间线、根因、补救、预防的，是实战型选手。
- **警惕"知道名词不会排查"**：能把 slowlog / latency doctor / bigkeys / mem_fragmentation_ratio 串成排查链路的，才往 L4 / L5 定。
- **结合岗位**：普通业务开发不必强求 Redlock 辩论与向量检索；架构岗才需要版本演进与技术选型。
