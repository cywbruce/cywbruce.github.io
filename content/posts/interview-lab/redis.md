## Part 0：30 秒标准总答

**Q：谈谈你对 Redis 的理解。**

**标准答法（30 秒，五个得分点）：**

> Redis 是**基于内存的高性能键值数据库**，常用于缓存、分布式锁、消息队列和会话。
>
> 提供 **String / Hash / List / Set / ZSet** 五种基本结构，背后各有 SDS、listpack、quicklist、哈希表、跳表等精良编码，这是高性能的基础。
>
> 采用**单线程命令执行**（串行无锁竞争）配合 **I/O 多路复用（epoll）**；6.0 起网络读写用多线程，命令执行仍单线程。
>
> 作为缓存必须处理**穿透、击穿、雪崩**三大问题，并保证一致性；分布式场景靠**主从 + 哨兵 + Cluster 哈希槽**实现高可用与水平扩展，用 **RDB/AOF 持久化**保障数据安全。

**评分要点：** 内存数据库 / 五种结构 / 单线程+IO 多路复用 / 缓存三兄弟 / 主从+哨兵+Cluster / 持久化。能说出"单线程命令执行 + 底层编码"的，直接往 Part 2 追问。

## Part 1：基础认知题

### Q1. Redis 有哪几种基本数据结构？各自适合什么场景？

**标准答案：**

| 类型 | 典型场景 | 关键特性 |
|------|---------|---------|
| **String** | 缓存对象、计数器、分布式锁、限流 | 二进制安全，最大 512MB |
| **Hash** | 对象字段、购物车 | 字段级读写，省内存 |
| **List** | 消息队列、最新列表 | 双向链表，支持阻塞弹出 |
| **Set** | 去重、抽奖、共同关注、标签 | 无序去重，支持交并差 |
| **ZSet** | 排行榜、延迟队列、优先级队列 | 每个元素带 score，有序 |

- 扩展类型：**Bitmap（签到）、HyperLogLog（UV 去重）、Geo（位置）、Stream（消息流）**。

**追问 1：ZSet 和 Set 的核心区别？**
> **答案：** Set 是无序去重集合；ZSet 给每个成员绑定一个 **score（双精度浮点）**，按 score 排序，因此可 range（范围查询）、rank（排名）。排行榜是其典型应用。

**追问 2：用 String 还是 Hash 存对象？**
> **答案：** 整体读写、需 JSON 序列化用 String；需**单独读写字段**、字段频繁变化用 Hash，避免整体反序列化且更省内存（小对象用 listpack）。注意 Hash 字段无法单独设 TTL（Redis 8 才新增字段级过期命令）。

---

### Q2. Redis 为什么快？单线程为什么不慢？

**标准答案：**
- **纯内存操作**：数据都在内存，避免磁盘 I/O（持久化后台异步）。
- **单线程命令执行**：串行化，**无上下文切换与锁竞争**。注意 Redis 不是"整个进程单线程"——6.0 起网络 I/O 多线程，但**命令执行始终单线程**。
- **I/O 多路复用**：基于 epoll/kqueue，一个线程监听大量 socket，就绪才处理。
- **高效数据结构**：SDS、跳表、listpack 专为内存场景优化。
- 瓶颈在**网络与内存**而非 CPU，单线程足够且更可控。

**追问 1：单线程有什么风险？**
> **答案：** **慢命令**（`KEYS *`、大 key 的 `HGETALL`、复杂 Lua、大范围 `ZRANGEBYSCORE`）会阻塞整个服务器。故生产禁用 `KEYS` 改用 `SCAN`，大 key 拆分，Lua 控制耗时。

**追问 2：6.0 多线程后命令执行还是单线程吗？为何不改多线程执行？**
> **答案：** 仍是单线程。多线程只用于**网络收发与协议解析**（`io-threads`）。命令执行改多线程会引入锁竞争和并发复杂度，收益有限——瓶颈在网络 I/O 而非 CPU，并行化网络收发性价比最高。

## Part 2：底层原理题（数据结构与持久化）

> 这是"会用 Redis"和"懂内核"的分水岭，L2→L3 的关键。

### Q3. SDS 是什么？相比 C 字符串有何优势？

**标准答案：** SDS（Simple Dynamic String）是 Redis 自实现的字符串，结构含 `len`（已用长度）、`alloc`（分配空间）、`buf[]`、`flags`。优势：
- **O(1) 获取长度**：C 需 `strlen` 遍历，SDS 直接读 `len`。
- **杜绝缓冲区溢出**：拼接前检查 `alloc`，不够自动扩容。
- **减少内存重分配**：空间预分配 + 惰性释放。
- **二进制安全**：用 `len` 判断结束而非 `\0`，可存图片/序列化对象。

**追问 1：SDS 有哪几种头类型？为何要分？**
> **答案：** sdshdr5/8/16/32/64 五种，按长度选不同大小的 `len`/`alloc` 字段（短字符串用 1 字节即可）。**分类型是为省内存**——典型的"按数据量选结构体"优化。

**追问 2：为什么字符串有 int / embstr / raw 三种编码？**
> **答案：** 整数用 int 直接存；短字符串（≤44 字节）用 embstr，**一次分配**连续内存（创建/释放快、缓存友好）；长字符串用 raw，两次分配。按长度分级同样是为了内存与效率。

---

### Q4. 五种数据结构的底层编码是什么？ziplist 为何被 listpack 替代？

**标准答案：** （同一类型在不同数据量下编码不同，可用 `OBJECT ENCODING` 查看）

| 类型 | 底层编码 | 关键点 |
|------|---------|--------|
| String | int / embstr / raw | 整数/短串/长串分级 |
| List | **quicklist**（双向链表 + listpack 节点） | 兼顾内存与两端操作 |
| Hash | listpack / hashtable | 小用 listpack，大用哈希表 |
| Set | intset / hashtable | 整数少用紧凑数组，否则哈希表 |
| ZSet | listpack / **skiplist + hashtable** | 跳表排序+范围，哈希表 O(1) 查 score |

- **ziplist → listpack**：ziplist 是连续内存，每个 entry 记录 `prevlen`（前节点长度），存在**级联更新**——前节点从 <254 涨到 ≥254 时 `prevlen` 由 1 字节变 5 字节，引发连锁扩容。listpack 让每个 entry 记录**自身长度**（放在尾部），可反向遍历，**彻底解决级联更新**且更省内存。Redis 6 逐步引入，**7.0 全面替代 ziplist**。

**追问 1：quicklist 为何是"链表 + listpack"组合？**
> **答案：** 纯双向链表指针开销大、碎片多；纯 listpack 插入要搬移大量元素。quicklist 把 listpack 切成多段用链表串起，两端插入只操作对应 segment，兼顾内存与效率。

**追问 2：ZSet 为何用跳表不用红黑树？**
> **答案：** ① **范围查询自然**：`ZRANGEBYSCORE` 找到起点后顺序遍历即可，红黑树需中序遍历；② **实现简单**：跳表靠随机层数平衡，插入删除只改指针，红黑树旋转变色复杂易错；③ **rank 高效**：节点记 span 可 O(logN) 算排名。二者同阶复杂度，跳表工程成本更低。ZSet 另配 hashtable 实现 member→score 的 O(1) 查找，是两结构互补的经典设计。

### Q5. Redis 持久化有哪几种？RDB 与 AOF 区别？

**标准答案：**

| 维度 | RDB | AOF |
|------|-----|-----|
| 形式 | 某时刻**二进制快照** | 写命令**文本日志** |
| 触发 | `save`/`bgsave` | `appendfsync`：always/everysec/no |
| 恢复/安全 | 恢复快、体积小；丢快照后数据 | 恢复慢、体积大；everysec 最多丢 1 秒 |

- **混合持久化（4.0+）**：AOF 重写时前半段用 RDB 格式存全量、后半段用 AOF 存增量，**兼顾快速恢复与少丢数据**（`aof-use-rdb-preamble yes`）。

**追问 1：bgsave 的 fork 与 COW 原理？**
> **答案：** `bgsave` 时主进程 `fork()` 子进程**共享内存页**，子进程 dump RDB，主进程继续服务。主进程修改某页时触发**写时复制（COW）**——内核复制该页给主进程改，子进程仍看到 fork 时的快照，保证一致性。代价是 fork 瞬间与大量写入时内存/CPU 开销上升。

**追问 2：宕机时 RDB/AOF 各丢多少数据？AOF 重写为何不阻塞？**
> **答案：** RDB 丢上次快照后的所有写入；AOF 在 everysec 下最多丢约 1 秒，always 理论不丢但性能最低。重写由子进程 `bgrewriteaof` 完成，期间新命令写入**重写缓冲区**，完成后追加并原子替换；Redis 7 改为 **Multi-Part AOF**（base + incr 文件），新增增量文件即可，进一步降低开销。

## Part 3：核心区分度题（缓存三兄弟 / 锁 / 高可用，题眼）

> **全题的题眼**——能否讲清缓存三兄弟、分布式锁和高可用取舍，直接决定 L2 还是 L3/L4。定级主看这里。

### Q6. 什么是缓存穿透、击穿、雪崩？分别怎么解决？

**标准答案：** （缓存面试第一题，必问）
- **穿透**：查**缓存和 DB 都不存在**的数据（如 id=-1），每次穿透到 DB。解法：① **布隆过滤器**拦截不存在的 key；② **缓存空值**并设短 TTL。
- **击穿**：某**热点 key 恰好过期**瞬间，大量并发打到 DB。解法：① **互斥锁**（SETNX，只放一个线程重建）；② **逻辑过期**（不设物理 TTL，value 内嵌过期时间，发现过期异步更新，其余先返旧值）。
- **雪崩**：**大量 key 同时过期**或 **Redis 宕机**，请求洪水涌向 DB。解法：① 过期时间**加随机值**打散；② **多级缓存**（本地 Caffeine + Redis）；③ Redis **高可用** + 限流降级兜底。

**追问 1：布隆过滤器的缺点？**
> **答案：** 有误判率——说"不存在"一定不存在（可拦截），说"存在"可能误判（少量仍穿透）。误判率与位图大小、哈希函数个数相关；标准实现**不支持删除**（需计数布隆过滤器）。

**追问 2：互斥锁 vs 逻辑过期怎么选？**
> **答案：** 互斥锁**一致性强**（等待新值）但性能差、有等待/死锁风险，适合敏感数据；逻辑过期**可用性高**（不阻塞、先返旧值再异步更新）但短暂不一致，适合热点数据、实时性要求不高场景（如商品详情）。

### Q7. 过期删除策略与内存淘汰策略分别是什么？

**标准答案：**
- **过期删除**（针对设了 TTL 的 key）：**惰性删除**（访问时才检查，省 CPU 但残留过期 key）+ **定期删除**（每 100ms 抽部分检查），二者组合使用。
- **内存淘汰**（内存达 `maxmemory` 时，`maxmemory-policy`），共 **8 种**：

| 策略 | 含义 |
|------|------|
| noeviction（默认） | 不淘汰，写入报错 |
| volatile-lru / allkeys-lru | 设 TTL 的 / 所有 key 中淘汰最近最少使用 |
| volatile-lfu / allkeys-lfu | 设 TTL 的 / 所有 key 中淘汰最不经常使用 |
| volatile-random / allkeys-random | 设 TTL 的 / 所有 key 中随机淘汰 |
| volatile-ttl | 设 TTL 的 key 中优先淘汰剩余 TTL 最短的 |

**追问 1：LRU 与 LFU 区别？Redis 是精确实现吗？**
> **答案：** LRU 看**最近访问时间**，LFU 看**访问频次**。Redis 用**近似实现**——随机采样若干 key 淘汰最符合条件的（配置 `maxmemory-samples`），而非全量排序。LFU 带衰减机制，避免早期高频但已冷门的 key 赖着不走。

**追问 2：为何生产常把 noeviction 改成 allkeys-lru？**
> **答案：** 纯缓存场景所有 key 都可淘汰，allkeys-lru 能在内存满时自动淘汰冷数据、持续服务；noeviction 会直接写入报错。但**若混存了不可丢的数据**（分布式锁、限流计数），就不能用 allkeys-*，否则会被误删。

### Q8. 如何用 Redis 实现分布式锁？Redlock 与看门狗了解吗？

**标准答案：** （层层递进）
- **加锁**：`SET lock_key requestId NX EX 30` —— NX 保证互斥，EX 过期时间**防死锁**，requestId（UUID）标识持有者。
- **安全释放**：用 **Lua 脚本**原子地"比对 requestId 再删除"，防止误删他人锁（如自己的锁已过期、别人的锁已加上）：
  ```lua
  if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('del', KEYS[1])
  else
      return 0
  end
  ```
- **Redlock**：向多个**独立** Redis 主节点依次加锁，超半数成功且总耗时小于锁有效期才算成功，应对单点/主从切换失效；但依赖时钟、GC 停顿可能导致锁过期，争议较大。
- **看门狗续期**：业务未完而锁快过期时，后台线程定时（Redisson 默认锁 30s、每 10s）自动续期，避免提前释放。
- **Redisson**：生产推荐，提供**可重入锁**（Hash 存线程 ID + 重入次数）、看门狗、阻塞等待、公平锁，封装完善。

**追问 1：为何不能用 SETNX + EXPIRE 两条命令？**
> **答案：** 非原子——SETNX 成功但进程崩溃、EXPIRE 没执行，key 永不过期造成死锁。`SET key value NX EX 30` 单命令原子完成才可。

**追问 2：主从架构下分布式锁有何隐患？**
> **答案：** 锁写在 master，若未同步给 slave 就宕机，哨兵提升 slave 后锁"丢了"，另一客户端可再次加锁 → 两人同时持锁。Redlock 为缓解此问题而生但非绝对可靠；强一致场景应考虑数据库锁或 etcd/ZooKeeper。Redisson 可重入锁用 Hash 存线程 ID + 重入次数，配合看门狗既防误删又防提前过期。

### Q9. Redis 高可用有哪几种方案？各解决什么问题？

**标准答案：**
- **主从复制**：一主多从，写走 master、读走 slave，实现**读写分离**与冗余。
  - **全量复制**：slave 首次连接或增量不足时，master `bgsave` 生成 RDB 发给 slave，期间写命令存复制缓冲区随后补发。
  - **增量复制**：基于**复制偏移量 offset + repl_backlog_buffer**，断线重连只传丢失的命令，用 `runid + offset` 判断能否增量。
- **哨兵 Sentinel**：解决**自动故障转移**。监控主从；主观下线（SDOWN）→ 多哨兵确认客观下线（ODOWN）→ 选举 leader → 提升某 slave 为新 master → 通知客户端。
- **Cluster**：解决**水平扩展与分片**。有 **16384 个哈希槽**，`CRC16(key) & 16383` 决定槽位，每节点负责部分槽；去中心化、gossip 通信；访问错误节点收到 `MOVED`/`ASK` 重定向。

**追问 1：为何哈希槽是 16384 个？**
> **答案：** 槽位信息要随心跳（gossip）传播，16384 位 bitmap 约 2KB，65536 个要 8KB，心跳开销过大；16384 对约千节点集群也足够均匀。

**追问 2：什么是脑裂？如何防止？**
> **答案：** master 与 slave/哨兵网络分区时，哨兵选出新 master，而**旧 master 仍接受写**；恢复后旧 master 降为 slave 并全量同步新 master，分区期间写入丢失。防止：配置 `min-replicas-to-write`（至少 N 个健康 slave）和 `min-replicas-max-lag`（延迟不超过 M 秒），不满足则**拒绝写入**，限制丢失量。Cluster 跨槽多 key 操作会报错，需用 hashtag `{}` 让相关 key 落同槽。

## Part 4：实战与陷阱题

### Q10. 如何保证缓存与数据库的一致性？

**标准答案：** （最能区分"背八股"与"真做过"）
- **主流：先更新 DB，再删缓存**（Cache Aside Pattern）。
  - **删缓存而非更新缓存**：更新缓存易因并发写产生脏数据；删除是懒加载，更简单可靠。
  - **先 DB 后删缓存**：若先删缓存，DB 更新前的读会把旧值写回缓存，导致长期不一致。
- **延迟双删**：删缓存 → 更新 DB → sleep 片刻 → 再删缓存，清理更新期间被读请求写回的旧值。
- **强一致场景**：订阅 **binlog（Canal）** 经 MQ 异步删除，或用分布式锁串行化读改写。
- **兜底**：设合理过期时间，即使删失败也靠过期达到**最终一致**。
- 现实认知：并发下做不到绝对强一致（除非分布式事务/串行化），工程追求最终一致 + 极小不一致窗口。

**追问 1：先删缓存再更新 DB 有什么问题？**
> **答案：** 线程 A 删缓存后、未更新 DB，线程 B 读未命中，从 DB 读旧值写回缓存，随后 A 更新了 DB——缓存永远留旧值。故推荐先更新 DB 再删缓存。

**追问 2：删除缓存失败怎么办？**
> **答案：** 引入**重试**（MQ 重试删除）或订阅 binlog 异步删除；实在不行依赖过期兜底。关键是要有可观测性与补偿，不能"删失败就算了"。

---

### Q11. 什么是大 key 和热 key？危害、发现与解决？

**标准答案：**
- **大 key**（String > 10KB 或集合元素过多）：危害是操作阻塞单线程、网络慢、删除耗时、集群数据倾斜、COW 内存压力。**发现**：`--bigkeys`、`SCAN` + `MEMORY USAGE`、RDB 离线分析。**解决**：**拆分**（大 Hash 拆多个）、压缩 value、删大 key 用 `UNLINK` 异步删除避免阻塞。
- **热 key**（访问极高频）：危害是单点请求集中超过单线程能力、打垮分片。**发现**：`--hotkeys`、业务埋点、**MONITOR**（谨慎）。**解决**：**本地缓存**（Caffeine）、**多副本**（加随机后缀分散）、读写分离。

**追问 1：为何 `KEYS *` 是禁忌？替代方案？**
> **答案：** `KEYS` 一次性遍历全库，数据量大时长时间阻塞单线程，导致请求超时。用 `SCAN`（游标增量迭代）每次只返一批，不阻塞；但可能返回重复元素需业务去重。

**追问 2：`DEL` 与 `UNLINK` 区别？**
> **答案：** `DEL` 同步删除，大 key 会阻塞主线程；`UNLINK` 交给后台线程**异步删除**，不阻塞主线程，删大 key 应优先用它。

---

### Q12. Pipeline、Multi 事务、Lua 脚本有何区别？缓存预热与降级？

**标准答案：**

| 特性 | Pipeline | Multi 事务 | Lua 脚本 |
|------|----------|-----------|---------|
| 减少 RTT | 是 | 部分 | 是 |
| 原子性 | 否 | 按序不插入、无回滚 | **强原子** |
| 服务端逻辑 | 否 | 否 | 是 |

- **Pipeline**：批量命令一次发送减少 RTT，命令间无原子性。
- **Multi**：`MULTI`/`EXEC`/`DISCARD`，命令按序执行不被插入，但**中间失败不回滚**，配 `WATCH` 可做乐观锁。
- **Lua**：服务端**原子执行**整段脚本，是分布式锁释放、原子限流的基石；Redis 7 的 **Function** 是其进化版（可持久化、可复制、命名管理）。
- **缓存预热**：上线前提前加载热点数据，避免冷启动击穿 DB。
- **缓存降级**：缓存异常时降级到本地缓存/默认值/兜底数据，并对 DB 限流。
- **多级缓存**：本地缓存（Caffeine）→ Redis → DB，层层拦截。

**追问 1：Pipeline 和 Multi 能一起用吗？**
> **答案：** 能。用 Pipeline 一次性发送 `MULTI ... EXEC` 包裹的命令，既减少 RTT 又保证按序不被插入，很多客户端 batch 就是这么做的。

**追问 2：Lua 脚本为何原子？使用禁忌？**
> **答案：** 单线程把整个脚本当**一条命令整体执行**，期间不切换，故天然原子。禁忌：脚本内不做耗时操作（大循环、大范围遍历、`KEYS`），否则阻塞全局；保持短小、确定性以免影响复制一致性。

## Part 5：2026 新趋势：Redis 7.x / 8.x

> 加分题，考察技术视野与跟进演进的能力。

### Q13. Redis 6 / 7 / 8 有哪些重要演进？

**标准答案：**
- **6.0**：**多线程 I/O**（`io-threads`，网络收发多线程，命令执行仍单线程）；**客户端缓存 CLIENT TRACKING**（服务器记录客户端读过的 key，写入时主动推送失效通知，客户端本地缓存减少网络请求，需 RESP3）；ACL。
- **7.0（2022）**：**listpack 全面替代 ziplist**；**Redis Functions**（`FUNCTION LOAD`/`FCALL`，函数库**持久化、可复制、命名管理**，替代重启即失效的临时 Lua 脚本）；**Multi-Part AOF**；Sharded Pub/Sub；Client Eviction。
- **8.0（2025 发布）**：新增 **Vector Set（向量集，Beta）**——由 Redis 原作者设计、借鉴 ZSet、基于 **HNSW** 做高维向量相似度检索，面向 RAG、语义搜索、推荐等 AI 场景；30+ 项性能优化（延迟显著下降）；**Community Edition 更名 Redis Open Source**，内置原 Stack 模块（JSON、时间序列、概率结构）；新增 Hash 字段级过期命令（HGETEX/HSETEX/HGETDEL）、向量 int8 量化、混合搜索。

> **保守提醒**：Vector Set 仍处 **Beta**，官方明确其 API/行为未来可能调整；面试讲清"是什么、解决什么、什么阶段"即可，**不要编造具体命令细节**。

**追问 1：客户端缓存（Client Tracking）解决什么问题？**
> **答案：** 传统模式每次读都访问 Redis，网络开销大。客户端缓存把读过的数据放本地，Redis 通过 tracking 记录依赖、数据变更时主动推失效消息，热点数据本地命中，大幅降低网络与 Redis 负载。注意连接断开时客户端需清空本地缓存保证正确性。

**追问 2：Redis Functions 比普通 EVAL 脚本好在哪？**
> **答案：** EVAL 脚本本身不持久化/复制（重启需重载），是临时的；Functions 是**命名、持久化、可复制的函数库**，一次加载长期可用，组织管理与错误处理更完善，适合把复杂逻辑固化为"服务端 API"。Redis 8 的向量集（Beta）更标志其从"纯缓存"向"AI 时代实时数据层"演进，但生产大规模向量检索仍需评估与专业向量库的取舍。

## Part 6：能否用 Redis 定级？如何定级？

### 结论先行

**可以，Redis 是技术栈面试里区分度极高的探针**——天然分层：会用 API → 懂底层编码与单线程模型 → 懂缓存三兄弟与持久化 → 能落地分布式锁和高可用 → 有生产排障经验 → 跟进版本演进。但 Redis 上手门槛低，**很多人停留在"用过"层面**，必须用追问链下探才能问出深度。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 会 set/get，知道五种结构；说不清编码与单线程模型 |
| **中级（L2）** | 2–5 年 | Part 2 | 知道 SDS/跳表/listpack、单线程+IO 多路复用、RDB/AOF 区别 |
| **中高级（L3）** | 5–8 年 | Part 3 | 讲清缓存三兄弟及解法、8 种淘汰策略、分布式锁、主从/哨兵/Cluster |
| **高级（L4）** | 8 年+ | Part 4 | 有双写一致性、大 key/热 key 实战排障经验，懂 Pipeline/Multi/Lua 取舍 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 7.x/8.x 演进，能结合业务做缓存架构与技术选型、权衡一致性 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"五种结构 + 单线程 + 缓存三兄弟 + 主从哨兵 Cluster"→ 至少 L2；只说"Redis 快、做缓存"→ 从 Part 1 问起。

**第二步：沿追问链下探"为什么"。** 为什么 ZSet 用跳表不用红黑树？（范围查询 + 实现简单 + rank）为什么先更新 DB 再删缓存？（避免旧值回写）为什么锁释放要 Lua 原子校验？（防误删他人锁）

**第三步：三类信号防背题。** ① **真实性**：能否讲出具体生产事故与排查细节（"大 key 导致一次 `DEL` 阻塞几百毫秒"），细节 > 教科书答案；② **抽象能力**：能否把三兄弟统一为"高并发下缓存正确性"、把主从/哨兵/Cluster 统一为"冗余 → 切换 → 分片扩展"的演进脉络；③ **权衡能力**：能否讲清"什么场景不该用"——强一致别只用缓存、混存业务数据别用 allkeys-lru、Redlock 的争议。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整：业务开发问到 Part 3/4 足够；中间件/架构团队深挖 Part 5。

---

### 面试官避坑提醒

- **别因"Redis 简单"就低估区分度**——正因门槛低，更要靠追问（跳表、级联更新、脑裂、双写一致性）区分真懂与背题。
- **把"缓存三兄弟 + 双写一致性"作为 L3/L4 分水岭**：能结合真实事故讲清方案和取舍的，是实战型选手。
- **警惕"知道名词不会落地"**：能把 Redlock、看门狗、逻辑过期讲出边界和代价的，才往 L4/L5 定。
- **结合岗位**：普通业务开发不必强求源码级与向量检索；架构岗才需要版本演进与技术选型视野。

**递进主线（照着问）：**
1. 是什么？五种结构？→（内存 KV；String/Hash/List/Set/ZSet）

10. 双写一致性？→（先 DB 后删缓存 + 延迟双删 + binlog 补偿 + 过期兜底）

- 答到第 2–5 问 → L2
- 答到第 6–9 问 → L3

- 答到第 13 问 + 体系化权衡与技术选型 → L5
