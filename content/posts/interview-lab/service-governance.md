## Part 0：30 秒标准总答

**Q：谈谈你对服务治理（Dubbo / Nacos / 微服务）的理解。**

**标准答法（30 秒，五个得分点）：**

> 服务治理解决的是**微服务拆分之后"服务之间怎么可靠地互相调用"**的问题——服务注册发现、流量治理、容错隔离、可观测。
>
> 根基是 **RPC**：一次调用经过**服务注册/发现 → 动态代理 → 序列化 → 网络传输 → 反序列化/反射调用**，屏蔽网络细节，让调用远程像调用本地一样。
>
> **Dubbo** 是高性能 Java RPC 框架，采用**分层架构 + SPI 可扩展**，核心是服务暴露/引用、负载均衡、集群容错，通过注册中心感知上下线。
>
> **Nacos** 同时承担**注册中心**（心跳/健康检查、临时/持久实例）与**配置中心**（长轮询热更新、Namespace/Group/DataId），一致性上**同时支持 AP（Distro）与 CP（Raft）**。
>
> 稳定性靠**三板斧——限流、熔断、降级**防雪崩，再配合**网关、灰度发布、全链路追踪**做流量与可观测治理。

**评分要点：** RPC 调用链 / Dubbo 分层+SPI / 负载均衡+容错 / Nacos 注册+配置双职责 / 熔断降级限流防雪崩。能说出"RPC 完整链路 + Nacos 双职责"的，直接往 Part 2 追问。

## Part 1：基础认知题（RPC / Dubbo / Nacos 认知）

### Q1. 什么是 RPC？一次完整的 RPC 调用流程是怎样的？

**标准答案：**
RPC 让用户**像调用本地方法一样调用远程服务**，屏蔽网络细节。链路：
1. **注册**：Provider 向注册中心注册（服务名、IP、端口、元数据）。
2. **发现**：Consumer 订阅服务列表并本地缓存，变更时推送更新。
3. **动态代理**：调用接口方法时被代理拦截。
4. **封装序列化**：接口名/方法名/参数类型/参数值封装成请求，序列化为二进制（Hessian2/Protobuf/JSON）。
5. **网络传输**：Netty 基于 TCP 长连接发送。
6. **服务端处理**：Provider 反序列化后反射调用真实实现。
7. **返回**：结果序列化回传，Consumer 反序列化得到结果。

**追问 1：为什么需要动态代理？**
> **答案：** 让开发者面向接口编程，屏蔽"组装请求、序列化、发网络请求"的样板代码——远程调用与本地调用写法一致，这是 RPC 的核心价值。

**追问 2：注册中心挂了，已运行的 Consumer 还能调用吗？**
> **答案：** 通常**还能**——Consumer 本地缓存了服务列表、已建连接可继续用；但无法感知 Provider 变更，可能调到已下线节点。这正是 Q10 "注册中心不可用降级"的考点。

---

### Q2. RPC 和 HTTP 有什么区别？gRPC / Thrift / Dubbo 协议如何对比？

**标准答案：**

| 维度 | RPC（Dubbo/Thrift） | HTTP REST |
|------|--------------------|-----------|
| 传输 | 通常 TCP 长连接，报文精简 | 基于 HTTP，JSON 文本、头冗余 |
| 契约 | 接口/IDL 强契约、强类型 | 弱契约、靠文档 |
| 治理 | 内置注册发现、负载均衡、容错 | 需网关/框架补齐 |

- **本质**：RPC 强调"调用远程方法"，REST 强调"操作资源"；现代界限已模糊（gRPC、Dubbo3 Triple 都基于 HTTP/2）。

| 协议 | 序列化 | 传输 | 特点 |
|------|--------|------|------|
| **gRPC** | Protobuf | HTTP/2 | 跨语言、强类型 IDL、多路复用、流式 |
| **Thrift** | Thrift 二进制 | TCP | 高性能、跨语言 |
| **Dubbo 协议** | Hessian2 | TCP 长连接 | Java 生态、治理强、单长连接 |

**追问 1：gRPC 为什么用 HTTP/2？**
> **答案：** HTTP/2 提供**多路复用**（一连接并发多流、无队头阻塞）、头部压缩、双向流——兼顾 HTTP 的通用穿透性与接近原生 TCP RPC 的性能。

**追问 2：Dubbo 协议为何用单一长连接？适用什么场景？**
> **答案：** 减少连接数与握手开销，适合**小数据包、高并发**；但**大数据包会阻塞后续请求**，这类场景应换协议或用短连接。

---

### Q3. Dubbo 的整体分层架构是怎样的？Nacos 扮演什么角色？

**标准答案：**

```
Service/Config      业务服务层 + 配置层（ServiceConfig / ReferenceConfig）
Proxy/Registry      代理层（Invoker）+ 注册中心层（服务注册与发现）
Cluster/Monitor     集群层（路由/负载均衡/容错，治理核心）+ 监控层
Protocol/Exchange   远程调用层（Invoker 为核心）+ 信息交换层（请求-响应/同步转异步）
Transport/Serialize 网络传输层（Netty/Mina，TCP）+ 序列化层（Hessian2/Protobuf）
```

- **Invoker** 是核心抽象，"一切皆 Invoker"——消费者、提供者、集群都被抽象成 Invoker。

**追问 1：为什么 Dubbo 要分这么多层？**
> **答案：** 分层 + SPI 实现**高扩展与解耦**——每层是可替换扩展点：换注册中心、换协议、换负载均衡、换序列化互不影响，这是 Dubbo 设计的灵魂。

**追问 2：Service / Provider / Consumer / Registry 的关系？**
> **答案：** Provider 暴露服务并注册到 Registry；Consumer 从 Registry 订阅地址；Consumer 经 Cluster（负载均衡+容错）选中 Provider 发起 RPC；Monitor 收集统计。注册中心只做"地址簿"，**不参与实际调用流量**。

## Part 2：底层原理题（暴露引用 / 协议 / 注册中心）

> 这是"会配 Dubbo"和"懂内核"的分水岭，L2→L3 的关键。

### Q4. 讲一下 Dubbo 服务暴露（export）/ 引用（refer）流程，以及协议报文头结构。

**标准答案：** （能完整讲下来基本是 L3+）

**暴露（Provider）**：① `ServiceConfig.export()` 触发；② `ProxyFactory` 把实现包装成 **Invoker**；③ `Protocol.export(invoker)` 启动 Netty Server，包装成 **Exporter**；④ 服务 URL 注册到注册中心；⑤ 上报 Monitor。

**引用（Consumer）**：① `ReferenceConfig.init()` → `Protocol.refer()`；② 从注册中心**订阅**提供者 URL，RegistryDirectory 维护 Invoker 列表；③ `Cluster` 包装成 **Directory → Router → LoadBalance**，生成 Cluster Invoker；④ `ProxyFactory.getProxy(invoker)` 生成代理对象。

**报文头**：Dubbo 报文 = **16 字节固定 Header + 变长 Body**——魔数 `0xdabb`(2B，用于协议识别与粘包判断) + 标志位(1B，序列化类型/请求响应/事件) + 状态码(1B) + **Request ID**(8B) + Body 长度(4B)。

**追问 1：Invoker 到底是什么？**
> **答案：** 核心执行体接口 `Result invoke(Invocation inv)`，统一本地/远程调用——不管反射本地实现还是发网络请求，对外都是 Invoker。Cluster 把"多个提供者 Invoker"聚合成"一个可容错 Invoker"，是责任链与组合模式的运用。

**追问 2：URL 和 Request ID 分别起什么作用？**
> **答案：** ① Dubbo 是"**URL 驱动**"的——协议、地址、超时、重试、负载均衡等都拼成 URL 参数在各层传递，扩展点据此决定行为；② 报文头带 Request ID，同一长连接可连续发多个请求，响应回来靠 ID 找到对应 Future/回调唤醒线程，实现**异步关联**，是单连接高并发的基础。

### Q5. Nacos 作为注册中心：注册、心跳、临时/持久实例，以及一致性协议？

**标准答案：**
- **数据模型**：Namespace（环境隔离）> Group > Service > Cluster > Instance。
- **临时实例（默认，ephemeral=true）**：客户端心跳上报健康（1.x 用 HTTP，2.x 用 gRPC 长连接），超时（约 15s 不健康、30s 剔除）**自动摘除**，符合 **AP**。
- **持久实例（ephemeral=false）**：注册信息持久化，服务端主动探测（TCP/HTTP/MySQL），故障**不会自动剔除**，需手动下线，符合 **CP**。
- **一致性协议**：**Distro（AP，自研）**用于临时实例——各节点负责部分写并异步同步，去中心化、高可用；**Raft（CP）**用于持久实例与配置——Leader 选举 + 日志复制 + 多数派提交，强一致。可手动切换集群模式（AP/CP）。

**追问 1：临时实例和持久实例怎么选？**
> **答案：** 常规微服务用**临时实例**，实例弹性启停、异常自动摘除，符合高可用诉求；数据库/外部依赖等需长期存在、手工管控的资源用**持久实例**，避免网络抖动被误摘。

**追问 2：Nacos 2.x 用 gRPC 长连接替代 HTTP 心跳的好处？**
> **答案：** gRPC **双向流**让客户端与服务端实时通信，心跳、服务变更、配置推送都走这条连接，告别 1.x 的"短轮询 + UDP 通知"，**推送更及时、连接更少、延迟更低**。

## Part 3：核心区分度题（SPI / 容错 / 雪崩，题眼）

> **这一部分是全题的题眼**——能否讲清 SPI、集群容错、雪崩防护，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q6. Nacos 作为配置中心：热更新、长轮询机制，及与 Eureka/Consul/ZK 对比？

**标准答案：**
- **定位三要素**：`Namespace` + `Group` + `DataId`（如 `${prefix}-${profile}.${ext}`）唯一定位配置。
- **长轮询**：客户端发请求后服务端**hold 住连接**（约 30s），配置变更或超时才返回——比定时短轮询**请求骤降、近实时**；Nacos 2.x 改走 **gRPC 长连接主动推送**。
- **热更新**：`@RefreshScope` / `@ConfigurationProperties` 配合监听刷新，Bean 不重启即生效。

| 组件 | CAP | 健康检查 | 配置中心 | 一致性协议 |
|------|-----|---------|---------|-----------|
| **Nacos** | AP + CP | 心跳/主动探测 | 支持 | Distro / Raft |
| **Eureka** | AP | 客户端心跳 | 不支持 | 自研 |
| **Consul** | CP | 主动健康检查 | 支持(KV) | Raft |
| **Zookeeper** | CP | 临时节点/会话 | 支持(ZNode) | ZAB |

**追问 1：长轮询相比短轮询和 WebSocket 的取舍？**
> **答案：** 短轮询请求密集浪费资源；长轮询在"实时性 + 实现简单 + 兼容"间平衡，但连接被 hold 占用服务端资源；WebSocket/gRPC 推送最实时但需维护连接状态。Nacos 2.x 正是从长轮询演进到 gRPC 推送。

**追问 2：Zookeeper 做注册中心有什么问题？**
> **答案：** ZK 是 **CP（ZAB）**——Leader 选举期（数十秒）**不可写/不可注册**，牺牲可用性；且无原生配置热推送。服务发现更看重 AP，这是 Dubbo 推荐 Nacos 的原因。

### Q7. Dubbo 的 SPI 机制是什么？和 JDK SPI 有何区别？@Activate / @Adaptive 怎么用？

**标准答案：** （Dubbo 可扩展性基石，L3/L4 分水岭）

| 特性 | JDK SPI | Dubbo SPI |
|------|---------|-----------|
| 配置 | `META-INF/services/接口名`，类名列表 | `META-INF/dubbo/接口名`，**key=value** |
| 加载 | 一次性实例化所有实现 | **按需按名加载** |
| IoC/AOP | 不支持 | 支持**依赖注入 + Wrapper 包装** |
| 缓存 | 每次重新加载 | **ExtensionLoader 缓存** |

- **@Activate**：按条件（group / value / URL 参数）**自动激活**多个扩展，常用于 Filter、Cluster。
- **@Adaptive**：运行时生成代理类，**根据 URL 参数决定真正调用哪个扩展**（如 `LoadBalance` 读 `url.loadbalance` 选策略）——"URL 驱动"的体现。
- 用法：`ExtensionLoader.getExtensionLoader(Xxx.class).getExtension("name")` / `.getAdaptiveExtension()`。

**追问 1：Dubbo SPI 的 IoC / AOP 怎么实现？**
> **答案：** 创建对象后扫描 setter 注入依赖（IoC）；AOP 通过 **Wrapper 类**——Wrapper 构造函数注入真实扩展，在其前后织入逻辑（类似装饰者模式）。

**追问 2：@Adaptive 为何不直接写死一个实现？**
> **答案：** 框架层需**与具体实现解耦**——调用时才知道用哪个扩展（由 URL 参数/配置决定）。自适应扩展生成"按参数动态路由"的代理，把决策推迟到运行时。

### Q8. Dubbo 的负载均衡策略和集群容错机制有哪些？如何选用？

**标准答案：**

**负载均衡**：**Random**（默认，按权重随机）、**RoundRobin**（按权重轮询）、**LeastActive**（选活跃调用数最少者，慢节点自动少分流量）、**ConsistentHash**（相同参数打同一节点，适合有状态/缓存亲和）。

**集群容错**：

| 模式 | 行为 | 适用 |
|------|------|------|
| **Failover**（默认） | 失败自动切换重试其他节点（retries≈2） | 读/幂等操作 |
| **Failfast** | 失败立即报错，只调一次 | 非幂等写 |
| **Failsafe** | 失败忽略、记日志 | 审计日志等非关键调用 |
| **Failback** | 失败记录，定时重发 | 消息通知 |
| **Forking** | 并行调多个，第一个成功即返回 | 实时性高、容忍浪费 |
| **Broadcast** | 广播逐个调所有节点，任一失败即失败 | 通知所有节点更新缓存 |

**追问 1：为什么 Failover 默认只适合读/幂等操作？**
> **答案：** Failover 失败后会**重试其他节点**。若写操作第一次其实已成功（只是响应超时），重试就会重复写入——非幂等写要用 Failfast 或保证接口幂等。

**追问 2：LeastActive 为什么能"慢节点少分流量"？**
> **答案：** 活跃数 = 正在处理未返回的请求数。慢节点处理慢、活跃数堆积，就自然少分新请求——相当于**隐式自适应限流**，对性能差异大的场景有效。

### Q9. 什么是服务雪崩？熔断、降级、限流怎么防？Sentinel/Hystrix/Resilience4j 区别？

**标准答案：**
**雪崩**：下游变慢/宕机 → 上游线程阻塞堆积 → 逐级向上传播 → 整链不可用。

- **限流**：限制入口 QPS/并发，防冲垮系统。算法：固定/滑动窗口、漏桶、令牌桶；Sentinel 基于滑动窗口。
- **熔断**：下游错误率/慢调用比例超阈值 → 熔断器 **Open**，后续调用**直接快速失败**；一段时间后 **Half-Open** 试探恢复。防"反复调已故障下游"。
- **降级**：失败/超时/熔断时返回**兜底结果**（默认值/缓存/空值），牺牲非核心保核心。

| 组件 | 特点 |
|------|------|
| **Sentinel** | 阿里开源，流控/熔断/系统保护，滑动窗口，控制台配规则，轻量 |
| **Hystrix** | Netflix，**已停止维护**；线程池/信号量隔离 |
| **Resilience4j** | 轻量函数式，基于 Vavr，适合 Java 8+ 函数式风格 |

**追问 1：熔断和降级有什么区别？**
> **答案：** **熔断是自动保护机制**——检测到下游故障主动切断调用；**降级是兜底策略**——调用出问题后返回备选结果。二者常配合：熔断触发后走降级。限流则从**入口**控流量，属不同层面。

**追问 2：Dubbo 超时与重试怎么配合？有哪些陷阱？**
> **答案：** 超时时间应匹配下游 P99，重试次数要克制；**重试会放大流量**（1 次变 N 次），需配指数退避+抖动，且只对幂等操作重试。Dubbo 还支持**泛化调用**（GenericService，无需接口 jar，靠方法名+参数类型+参数值调用），常用于网关和开放平台。

## Part 4：实战与陷阱题

### Q10. 线上实战：注册中心不可用、配置推送延迟、调用超时、线程池打满，怎么排查处理？

**标准答案：**

**追问 1：注册中心（Nacos）整体不可用怎么办？**
> **答案：** ① Consumer **本地缓存**了地址，已建连接可继续调用；② 关键是**禁止重启/发布**——重启后无地址可分会导致全站不可用；③ 保持 Provider/Consumer 长连接，等注册中心故障转移恢复；④ 事后排查：集群是否脑裂、Raft/Distro 是否异常、是否误切 CP 导致不可写。原则：**故障期间服务调用尽量"惯性运行"**。

**追问 2：配置变更推送延迟（改了很久才生效）怎么排查？**
> **答案：** ① 看长轮询/gRPC 连接是否正常（是否断开、退化为超时返回）；② 检查 Namespace/Group/DataId 是否匹配——定位错身份最常见；③ 看 `@RefreshScope`/监听器是否生效、Bean 是否被刷新；④ 服务端看配置是否成功发布、是否过 Raft 多数派提交。

**追问 3：Dubbo 调用超时如何系统排查？**
> **答案：** ① 看 Consumer 超时配置与 Provider 实际耗时（P99）是否匹配；② 查 Provider 线程池是否满、有无慢 SQL/下游阻塞；③ 看网络与 GC 停顿；④ 检查重试是否放大流量；⑤ 用链路追踪定位耗时在哪个 Span。区分"**真超时**（下游慢）"与"**假超时**（线程池排队、GC STW）"。

**追问 4：Dubbo Provider 线程池打满怎么处理？**
> **答案：** ① 紧急：扩容实例、临时限流、熔断非核心调用；② 查根因：下游慢致请求堆积、队列过小/策略不当、单请求耗时突增；③ 优化：合理设 `threads`/`queues`、业务线程池隔离、超时+熔断快速失败、异步化；④ 预防：配线程池**活跃度告警**与限流兜底，避免雪崩。

---

### Q11. 微服务治理工程实践：网关、灰度发布、全链路压测与链路追踪怎么做？

**标准答案：**
- **网关（Spring Cloud Gateway / Kong / Nginx）**：统一入口，做**路由转发、鉴权、限流、日志、灰度**，是流量治理的"守门员"。
- **灰度发布/金丝雀**：按比例/Header/用户把**部分流量导到新版本**，观察无异常再全量。Dubbo 可用**标签路由/条件路由**，网关可基于 Header 分流。
- **全链路压测**：构造近线上等量流量压整条链，用**影子表/影子库/影子 topic** 隔离压测数据，评估容量与瓶颈。
- **链路追踪**：用 **TraceId** 贯穿全链，每个调用记为 **Span**，还原拓扑与耗时。SkyWalking（Java Agent 字节码增强，**无侵入**）、Zipkin/Sleuth（需埋点），向 OpenTelemetry 标准收敛。

**追问 1：SkyWalking 和 Zipkin 的核心区别？**
> **答案：** SkyWalking 靠 **Java Agent + 字节码增强**无侵入埋点，对业务零改造且自带 APM 分析；Zipkin 通常需 Brave/Sleuth **在代码/框架层埋点**，更轻量但要改造。二者都在向 OpenTelemetry 收敛。

**追问 2：灰度如何保证同一用户始终命中同一版本？**
> **答案：** 用**用户标识（userId/设备号）哈希取模**分流而非纯随机——保证同一用户每次都路由到同一版本；配合 Cookie/Header 携带灰度标记，让网关到各服务整条链路按同一标记路由。Dubbo 标签路由可让灰度流量只在灰度实例池调用。

## Part 5：2026 新趋势：Dubbo 3 / Nacos 3 / Service Mesh

> 加分题，考察技术视野。以下演进以官方发布为准，细节保守表述。

### Q12. Dubbo 3.x、Nacos 3.x、Service Mesh、Proxyless Mesh、Serverless 对服务治理意味着什么？

**标准答案：**
- **Dubbo 3.x 应用级服务发现**：从 2.x"**接口级**注册"演进为"**应用级**注册"——注册中心只按应用/实例登记，大幅降低数据量与推送压力，对齐 Spring Cloud / K8s 模型；接口与应用的映射交给**元数据（服务自省）机制**。
- **Triple 协议**：Dubbo 3 新一代协议，基于 **HTTP/2**，**兼容 gRPC**（支持 stream 语义、Protobuf），网关/浏览器穿透性好、多语言支持。
- **Nacos 3.x**：向**更云原生**演进——强化 K8s 集成、gRPC 长连接、配置/鉴权安全增强、多集群多活（具体特性以官方为准，不编造版本号或 API）。
- **Service Mesh（Istio + Envoy）**：把注册发现、负载均衡、熔断限流、追踪、mTLS 等治理能力**从 SDK 下沉到 Sidecar（Envoy）**，控制面（Istiod）统一下发——**无侵入、多语言统一治理**，代价是一跳延迟与运维复杂度。
- **Proxyless Mesh**：无需 Sidecar，SDK/Agent（如 gRPC xDS、Dubbo 3）**直连控制面**，兼顾集中治理与性能。
- **Serverless**：实例弹性伸缩、频繁冷启动，对**心跳保活、长连接、配置推送**提出新挑战；治理进一步下沉到基础设施，应用更轻薄。

**追问 1：Service Mesh 会取代 Dubbo 这类 RPC 框架吗？**
> **答案：** 短期**互补而非取代**。Mesh 擅长**跨语言统一治理与无侵入**，RPC 框架在**序列化效率、调用性能、Java 生态集成**上仍有优势。常见做法是共存：Dubbo 负责高效 RPC，Mesh 负责流量治理；Dubbo 3 的 Proxyless 正是融合探索。

**追问 2：应用级服务发现为何能大幅降低注册中心压力？**
> **答案：** 接口级模型下一个应用 N 个接口要注册/推送 N 份，实例数×接口数 急剧膨胀；应用级只按**实例**注册一份，接口列表等元数据走独立元数据服务按需拉取。数据量从"实例×接口"降为"实例"级。

## Part 6：能否用服务治理定级？如何定级？

### 结论先行
**可以，服务治理是技术栈面试里区分度很高的探针**——天然分层：会配注解 → 懂 RPC 链路与注册发现 → 懂暴露引用/SPI/容错 → 懂雪崩防护与 Nacos 一致性 → 有生产排障经验 → 跟进 Mesh/Serverless 演进。但中间件上手门槛低，**很多人停留在"用过"层面**，必须靠追问链下探。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 会配注解，知道 RPC 大概；说不清调用链与注册发现 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂 RPC 链路、Dubbo 分层、Nacos 双职责、临时/持久实例 |
| **中高级（L3）** | 5–8 年 | Part 3 | 讲清暴露引用、SPI、4 种负载均衡+6 种容错、熔断降级限流、Distro/Raft |
| **高级（L4）** | 8 年+ | Part 4 | 有注册中心故障/超时/线程池打满实战排障，懂灰度与链路追踪落地 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 Dubbo3/Nacos3/Mesh/Serverless，能做架构与技术选型权衡 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"RPC 链路 + Dubbo 分层 + Nacos 双职责 + 熔断降级限流"→ 至少 L2；只说"用了 Dubbo/Nacos"→ 从 Part 1 问起。

**第二步：沿追问链下探"为什么"。** 为什么 Dubbo SPI 优于 JDK SPI？（按需加载+IoC/AOP）为什么 Failover 只适合幂等？（重试可能重复写）为什么临时实例符合 AP？（心跳异常自动摘除）

**第三步：三类信号防背题。** ① **真实性**：能否讲出具体事故与排查细节（"Nacos 抖动时靠本地缓存顶住、禁止重启"），细节 > 教科书答案；② **抽象能力**：能否把 Dubbo/Nacos/Mesh 统一为"**注册发现 → 流量治理 → 容错隔离 → 可观测**"主线；③ **权衡能力**：能否讲清"什么场景不该用"——CP 选举期不可用、重试放大流量、Mesh 一跳开销。

**第四步：按最深层级定级，不按正确率。** 结合岗位调整：业务开发问到 Part 3/4 足够；中间件/架构团队深挖 Part 5。

---

### 面试官避坑提醒

- **别因"会配注解"就高估**——正因门槛低，更要靠追问（SPI、容错、雪崩、一致性协议）区分真懂与背题。
- **把"SPI + 雪崩防护 + 注册中心一致性"作为 L3/L4 分水岭**：能结合真实事故讲清方案与取舍的，是实战型选手。
- **警惕"知道名词不会落地"**：能把熔断状态机、灰度路由、注册中心故障降级讲出边界和代价的，才往 L4/L5 定。
- **新增考点保守追问**：Dubbo3/Nacos3/Mesh 版本细节以官方为准，讲清"是什么、解决什么、取舍"即可，别刁难具体 API。
