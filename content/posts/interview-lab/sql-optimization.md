## Part 0：30 秒标准总答

**Q：线上给你一条慢 SQL，你从哪几个角度入手优化？**

**标准答法（30 秒，涵盖五个得分点）：**

> 第一步 **定位**：从慢查询日志 / pt-query-digest 找出真正该优化的 Top SQL——按**总耗时**而非单次耗时排序。
>
> 第二步 **看执行计划**：用 EXPLAIN / EXPLAIN ANALYZE 看 type、key、key_len、rows、Extra，判断有没有全表扫描、索引失效、回表、filesort / temporary。
>
> 第三步 **诊断根因**：是索引没建对、索引失效、扫描行数过多、排序临时表，还是 JOIN 驱动表选错。
>
> 第四步 **改写或加索引**：调联合索引顺序、做覆盖索引、改写 SQL（分页 / 子查询 / OR），必要时调整表结构或加缓存。
>
> 第五步 **验证并沉淀**：对比优化前后 EXPLAIN ANALYZE 与慢日志，灰度上线，建立性能基线（PTA 基线）用数据证明效果。

**评分要点：** 定位 Top SQL / EXPLAIN 三看 / 诊断根因 / 改写与索引 / 验证与基线 五个点，对应入门到高级。能说出"先定位再 EXPLAIN 再验证"闭环的，直接往 Part 4 追问真实案例。

## Part 1：基础认知题（优化方法论）

### Q1. SQL 优化的一般流程是什么？什么时候"不该"优化？

**标准答案：**
- 流程：定位（慢日志 / 监控）→ EXPLAIN 看计划 → 分析根因 → 改写 SQL / 调索引 / 调表结构 → 验证（EXPLAIN ANALYZE + 压测）→ 灰度上线 + 基线对比。
- 优化顺序（由近及远、成本由低到高）：**业务逻辑 → SQL 写法 → 索引 → 表结构 → 缓存 → 分库分表**。先问"这个查询业务上真有必要吗、能不能不查全量"，再动 SQL 与索引，最后才拆表。
- 不该优化的情况：① 执行频率极低、耗时占比小，收益为零；② 瓶颈在下游 / 网络 / 锁等待，不是 SQL 扫描；③ 为炫技过度改写，牺牲可读性与可维护性；④ 数据量还小，优化器走全表本就更快。优化要有基线和收益目标，不追求"理论最优"。

**追问 1：为什么优化顺序是"业务 → SQL → 索引 → 表结构 → 缓存"？**
> **答案：** 因为最有效的优化往往是"少查 / 不查"——分页改按需加载、报表改预聚合、循环调用改批量。业务层砍掉 90% 无用查询，比调任何索引都管用，且不引入索引维护成本。索引是"查得快"，业务是"少查"，后者杠杆更大。

**追问 2：你说的"PTA 基线"是什么？**
> **答案：** 优化前先用统一口径记录该 SQL 的**执行频次、平均 / 最大耗时、扫描行数（Rows examined）、返回行数、慢查询次数**作为性能基线；优化后在相同流量与数据量下用同样口径复测，用数据证明收益，而非凭"感觉快了"。它也是灰度与回滚的判据。

### Q2. 报警说"数据库慢 SQL 暴增"，一定是 SQL 写得差吗？

**标准答案：**
- 不一定，先区分三类：① **真慢 SQL**（扫描大、缺索引、改写差）；② **锁等待 / 长事务伪装**（SQL 本身不慢，但被锁阻塞）；③ **资源层面**（CPU / IO 打满、连接数暴涨、Buffer Pool 命中率骤降、主从延迟导致读超时）。
- 排查顺序：先看 `SHOW PROCESSLIST` 的 State / Time → 看 `SHOW ENGINE INNODB STATUS` / `performance_schema.data_lock_waits` 是否有锁等待 → 看慢日志 Top SQL 是否集中 → 看系统指标。

**追问 1：怎么区分"锁等待"和"真扫描慢"？**
> **答案：** `PROCESSLIST` 里 State 为 `Waiting for lock` / `Locked`、Time 很大但 Rows_examined 不增长，多半是锁等待；真慢查询多为 `Sending data` / `Sorting result`，且慢日志 Rows_examined 巨大。`data_lock_waits` 能直接看到谁阻塞了谁。

**追问 2：如果是锁等待，怎么定位到根因事务？**
> **答案：** 查 `information_schema.INNODB_TRX` / `performance_schema.data_lock_waits`，找到 `blocking_trx_id` 对应的连接与 SQL，通常是某个未提交的大事务或没走索引的 UPDATE。先 kill 阻塞源止血，再从"拆大事务、固定访问顺序、UPDATE / DELETE 带索引"根治。

## Part 2：底层原理题（与优化决策相关的原理）

> 这里聚焦"做优化决策时必须懂的原理"，不重讲 B+树结构 / MVCC / 间隙锁（见原理分册）。这是 L2→L3 的关键。

### Q3. EXPLAIN 重点看哪些字段？type 各级别如何排序？

**标准答案：**

| 字段 | 关注点 |
|------|--------|
| `type` | 访问类型，判断全表扫描还是索引命中 |
| `key` / `key_len` | 实际用到的索引 / 用了几列 |
| `rows` / `Filtered` | 预估扫描行数 / 过滤后剩余比例 |
| `Extra` | filesort / temporary / 覆盖索引等信号 |

- type 优劣：**system > const > eq_ref > ref > range > index > ALL**（越左越好，一般要求至少 range，避免 ALL / index）。
  - system：表仅一行；const：主键 / 唯一索引等值命中一行；eq_ref：JOIN 中被驱动表按主键 / 唯一索引匹配一行；ref：普通索引等值、可能多行；range：范围扫描（BETWEEN / > / IN）；index：全索引扫描（索引比表小但仍扫全树）；ALL：全表扫描。

**追问 1：key_len 怎么算？举例。**
> **答案：** key_len = 各索引列字节之和 + 变长列 2 字节 + 每个可 NULL 列 1 字节（按位向上取整）。定长：INT=4、BIGINT=8、DATETIME=5、TIMESTAMP=4；变长：utf8mb4 下 VARCHAR(n)=n×4+2，CHAR(n)=n×4。例：`INDEX(a INT NOT NULL, b VARCHAR(10) NULL)` 两列都用 → 4 + (10×4+2+1)=47；只用 a → 4。它用来判断联合索引用了几列。

**追问 2：rows 和 Filtered 一定准吗？**
> **答案：** rows 是**基于统计信息的估算值**，不是真实扫描行数，数据倾斜 / 统计过期时会差很多，真实值要用 EXPLAIN ANALYZE。Filtered 是"条件过滤后剩余比例"的估算，rows × Filtered 才是优化器估算的最终行数，是成本计算依据。

**追问 3：Extra 里这些值分别代表什么？**
> **答案：**
> - `Using index`：覆盖索引，无需回表（好事）。
> - `Using where`：存储引擎返回后 Server 层再过滤（索引没完全覆盖条件）。
> - `Using filesort`：额外排序，数据少在内存 sort_buffer 完成，超限才落盘——应争取用索引消除。
> - `Using temporary`：用了临时表（常见于 GROUP BY / DISTINCT / 复杂 UNION）。
> - `Using join buffer (Block Nested Loop)`：JOIN 被驱动表无索引，用 buffer 嵌套循环，约 O(M×N)。
> - `Backward index scan`（8.0）：借助降序索引反向扫描，通常意味着避免了 filesort。

### Q4. EXPLAIN 和 EXPLAIN ANALYZE 有什么区别？慢日志怎么分析？

**标准答案：**
- `EXPLAIN` 只输出**优化器预估**的计划，不真正执行；`EXPLAIN ANALYZE`（8.0.16+）**实际执行** SQL，输出每步 `actual time` 与 `actual rows`、真实循环次数，是验证优化效果的利器。注意它会真正执行，DML 要放事务里回滚。
- 慢查询日志：`long_query_time` 定阈值，配 `log_queries_not_using_indexes` 抓未用索引的查询，`min_examined_row_limit` 过滤扫描少的。海量日志用 **pt-query-digest** 聚合。

**追问 1：pt-query-digest 输出重点看什么？**
> **答案：** 它按**总耗时（Response time）占比**排序而非单次耗时——能抓到"单次不慢但调用极多、累计吃掉 CPU"的 SQL。重点看：执行次数（Calls）、单次 / 总响应时间、Rows examined 与 Rows sent 的差距（差距大说明回表 / 扫描浪费）、SQL 指纹。优先治"总耗时 Top 1"。

**追问 2：为什么"单次不慢但高频"的 SQL 更要盯？**
> **答案：** 它 diluted 在慢日志里单次可能不超标，但 QPS 高时累计 CPU 与 IO 惊人，往往是线上 CPU 100% 的真凶。pt-query-digest 按总量排序正是为了抓这类。

### Q5. 优化器为什么会选错索引？怎么干预？

**标准答案：**
- 优化器基于**成本模型**选计划：用统计信息（cardinality、rows）估算各计划的 IO + CPU 成本，选最低者。选错的根因多是**统计信息过期 / 不准确、数据倾斜、或有更优索引没建**。
- 干预：`ANALYZE TABLE` 更新统计信息；对倾斜列建**直方图**让估算更准；用 `FORCE INDEX` / `IGNORE INDEX` / `USE INDEX` 或 optimizer hint 强制；根治是补更合适的索引或改 SQL 让条件"可索引"。

**追问 1：index_merge 是什么？看到它说明什么？**
> **答案：** 一个查询用到多个索引，优化器分别扫描再取交集 / 并集（Extra 显示 `Using intersect / union`）。它通常是**信号**——说明缺一个能同时覆盖条件的联合索引，建联合索引往往更快更稳。

**追问 2：MRR 和 ICP 分别优化什么？**
> **答案：** **ICP**（索引下推，5.6+）在索引遍历阶段就过滤索引内的列，减少回表，Extra 显示 `Using index condition`；**MRR**（Multi-Range Read，8.0 默认开启）把二级索引查到的主键**先排序再顺序回表**，把随机 IO 转顺序 IO。两者都降低回表代价：ICP 减次数、MRR 减随机性。

## Part 3：核心区分度题（题眼，定级主战场）

> **这一部分是全题的题眼**——能否逐条诊断索引失效、设计合理的索引与改写，直接决定 L2 还是 L3/L4。定级主要看这里。

### Q6. 给几条 SQL，说说为什么索引会失效。

**标准答案：** （能逐条讲清原因与改写，基本是 L3+）

| 失效写法 | 原因 | 改写 / 对策 |
|---------|------|------------|
| `WHERE phone = 13800138000`（phone 是 varchar） | **隐式类型转换**：字符串列与数字比较，MySQL 把列转数字 | 加引号 `phone='138...'` |
| `WHERE DATE(create_time)='2026-01-01'` | 列上用**函数** | 改范围 `>= '2026-01-01' AND < '2026-01-02'`；或 8.0 函数索引 |
| `WHERE name LIKE '%abc'` | **前缀通配**无法利用有序索引 | 改后缀 `LIKE 'abc%'`；或用全文检索 / ES |
| `WHERE a=1 OR b=2`（b 无索引） | OR 有一侧无索引，优化器放弃索引全表扫 | 给 b 建索引，或改 `UNION ALL` |
| `WHERE status != 1` / `NOT IN` | 优化器判断回表多，可能放弃 | 用覆盖索引；改范围 / 枚举 IN |
| `(a,b,c)` 上 `a=1 AND b>2 AND c=3` | **范围后列失效**：b 范围后 c 无序 | 调整列顺序，或靠 ICP 部分过滤 |
| `(a,b,c)` 上 `WHERE b=2` / `a=1 AND c=3` | **破坏最左前缀**（跳列） | 补 `(b,...)` 索引或调整条件 |
| JOIN 两表字段字符集 / 排序规则不同 | 隐式转换使索引失效 | 统一 charset / collation |
| `WHERE id + 1 = 5` | 索引列**参与计算** | `WHERE id = 4` |

**追问 1：为什么"范围后列失效"而等值不失效？**
> **答案：** 联合索引先按 a 排序，a 等值时 b 仍有序，能继续定位；`a>?` 是范围，跨多个 a 值时 b 整体不再有序，无法二分，只能回表逐行判断（ICP 可在索引层先过滤一部分）。

**追问 2：字符集 / 排序规则不一致为什么让索引失效？**
> **答案：** JOIN 或比较的两列若 charset 或 collation 不同，MySQL 需对其中一列做隐式转换才能比较，转换后的表达式用不上原索引，于是全表扫。常见于 `utf8mb4_general_ci` 与 `utf8mb4_0900_ai_ci`、utf8 与 utf8mb4 混用。建表统一字符集是根治。

### Q7. 联合索引列顺序怎么定？覆盖索引、前缀索引怎么设计？

**标准答案：**
- **列顺序原则**：① 等值条件列放左、范围 / 排序列放右（范围后列失效）；② 高频查询字段优先；③ 区分度高的可靠前（但让更多查询命中长前缀优先）；④ 尽量把 SELECT 常查列纳入形成覆盖索引。
- **覆盖索引**：让 WHERE / SELECT / ORDER BY 涉及的列都在索引里，Extra 显示 `Using index`，免回表——"用空间换一次 B+树查找"，高性价比。
- **前缀索引**：长字符串（email、url）只取前 N 字符建 `INDEX(email(10))`，省空间。N 的选择：让前缀区分度（distinct 前缀数 / 总行数）尽量接近完整列。缺点：不能用于 ORDER BY / GROUP BY，也无法覆盖索引。

**追问 1：覆盖索引为什么能提速？**
> **答案：** 二级索引叶子只存索引列 + 主键，所需列都在索引里时，引擎直接从索引返回，省掉"回聚簇索引查整行"的第二次 B+树查找，减少随机 IO——大表、宽表效果显著。

**追问 2：怎么发现并治理冗余 / 重复索引？**
> **答案：** 查 `sys.schema_redundant_indexes` 视图能列出冗余索引（如已有 `(a,b)` 又建 `(a)`）。治理：先设为 invisible 观察，确认慢日志与计划无变化再删。**索引不是越多越好**——占空间、拖慢写（每次写更新所有索引）、增加优化器选错概率。

## Part 4：实战与陷阱题（案例驱动）

> **本套重头戏**：给出场景 / 慢 SQL / 执行计划，让候选人讲诊断 → 讲改写 → 讲验证。能否给出 EXPLAIN 前后对比和效果数字，是 L4 分水岭。

### Q8. `LIMIT 1000000,10` 慢在哪里？怎么改？

**标准答案：**
- 慢因：MySQL 先扫描并丢弃前 100 万行再取 10 行；ORDER BY 列无索引还要 filesort，每行回表，成本极高。
- 方案一 **游标 / 书签续查**：`WHERE id > lastMaxId ORDER BY id LIMIT 10`，用索引直接定位；适合"上一页 / 下一页"，不能随机跳页。
- 方案二 **延迟关联**：
```sql
SELECT t.* FROM t
JOIN (SELECT id FROM t ORDER BY create_time LIMIT 1000000,10) a
  ON t.id = a.id;
```
子查询只在二级索引 `(create_time,id)` 上扫描取 id（不回表、体积小），再回表 10 次。

**追问 1：延迟关联为什么能提速？**
> **答案：** 原查询要对 100 万行逐行回表取完整行；延迟关联让子查询只在覆盖索引上扫描取 id，把回表从 100 万次降到 10 次，随机 IO 大幅下降。

**追问 2：LIMIT 一定能减少扫描行数吗？**
> **答案：** 不一定。`LIMIT 10` 若 ORDER BY 用不上索引，仍需**全表扫描 + 把全部数据排序**后才取 10 行，LIMIT 并未减少扫描；深分页 `LIMIT 1000000,10` 更要扫 100 万行。LIMIT 只限制"返回行数"，不保证"扫描行数"少。

### Q9. ORDER BY 出现 filesort、GROUP BY 出现 temporary，怎么优化？

**标准答案：**
- **filesort**：让 ORDER BY 走索引即可消除——建 `INDEX(a,b)`，`WHERE a=1 ORDER BY b` 时索引内已排好序，Extra 为 `Using index`；8.0 降序索引支持混合升降序。无法用索引时可调大 `sort_buffer_size`、选择合适的全字段 / rowid 排序模式缓解，但根治仍是索引。
- **temporary**：GROUP BY / DISTINCT 的列若是索引最左前缀且有序，可走**松散索引扫描**避免临时表；用 WHERE 代替 HAVING 提前过滤；无法消除时控制分组基数、适当增大 `tmp_table_size`。

**追问 1：为什么 `WHERE a=1 ORDER BY b LIMIT 10` 加 `(a,b)` 索引就不 filesort 了？**
> **答案：** 联合索引 `(a,b)` 先按 a 排序、a 相同按 b 排序。`a=1` 定位后，后续行在索引里天然按 b 有序，引擎按索引顺序扫描即可，无需额外排序，LIMIT 10 也只扫前 10 行。

**追问 2：filesort 一定落盘吗？**
> **答案：** 不一定。数据小于 sort_buffer 时在内存完成，只有超过 `sort_buffer_size` 才借磁盘临时文件。但即便在内存也消耗 CPU，高并发下仍是瓶颈，应尽量用索引消除。

### Q10. 多表 JOIN 怎么优化？IN 和 EXISTS 怎么选？

**标准答案：**
- 核心：**小结果集驱动大表，被驱动表的 JOIN 字段必须有索引**。这样走 Index Nested Loop（NLJ），约 O(M×N log N)；被驱动表无索引则退化为 Block Nested Loop（BNL，Extra 显示 `Using join buffer`），约 O(M×N)，8.0 后等值无索引场景可由 Hash Join 改善。
- 优化器通常自动选驱动表；选错时可用 `STRAIGHT_JOIN` 强制（谨慎，数据变化后可能失效）。能简化成单表或条件下推的优先简化。
- **IN vs EXISTS**：IN 先查内表再匹配外表，适合**内表小**；EXISTS 先查外表再逐行探测内表，适合**外表小且内表 JOIN 列有索引**。现代优化器多数能自动改写，二者常趋同，以 EXPLAIN 实测为准，别死记口诀。

**追问 1：子查询怎么改写更快？**
> **答案：** 相关子查询常改写为 JOIN 或半连接（semi join）；`IN (子查询)` 可改 JOIN 去重；标量子查询可改 LEFT JOIN。目标是让子查询"只算一次"或转成索引可驱动的 JOIN，避免对外表每行重复执行。

**追问 2：OR 连接不同列怎么优化？**
> **答案：** `WHERE a=1 OR b=2` 两列各有索引但优化器放弃时，可改 `SELECT ... WHERE a=1 UNION ALL SELECT ... WHERE b=2`，让两次各走索引。注意语义：UNION 去重、UNION ALL 不去重且更快。

---

### Q11. 大表 COUNT(*) 怎么优化？

**标准答案：**
- InnoDB 不保存总行数（MVCC 下各事务可见行数不同），`COUNT(*)` / `COUNT(1)` 选最小的二级索引扫描，O(n)；`COUNT(列)` 排除该列为 NULL 的行。MyISAM 直接存总数 O(1)——这是**引擎差异**。
- 大表优化：① 建**计数表**或 **Redis** 维护总数；② 用近似值（`information_schema.TABLES.TABLE_ROWS`，但它是估算值）；③ 分条件统计用汇总表 / 预聚合；④ 8.0 并行查询在部分场景可加速。

**追问 1：COUNT(*) 和 COUNT(1) 到底谁快？**
> **答案：** 8.0 后基本无差别，优化器都选最小索引扫描。`COUNT(列)` 因要判断 NULL 可能稍慢，但差别很小。大表优化要靠计数表 / 缓存，而非纠结这三种写法。

**追问 2：为什么 TABLE_ROWS 不能当精确值用？**
> **答案：** 它是 InnoDB 采样估算的近似行数，频繁增删后误差可能很大。适合做量级参考，不能用于对账、分页总数等要求精确的场景。

---

### Q12. 复盘：线上慢 SQL 打满 CPU 100%，你怎么排查？

**标准答案：** （重头戏，考察全流程实战）
1. **止血**：`SHOW PROCESSLIST` 找长时间运行 / 大量重复的 SQL，必要时 kill 阻塞源或限流。
2. **定位**：开慢日志，用 pt-query-digest 找总耗时 Top SQL；8.0 可查 `performance_schema.events_statements_summary_by_digest` 按 digest 聚合。
3. **分析**：对 Top SQL 做 EXPLAIN，发现典型问题——`type=ALL` 全表扫、索引失效（函数 / 隐式转换）、扫描行数暴增、缺覆盖索引、JOIN 无索引 BNL。
4. **解决**：补联合索引 / 改 SQL（分页、子查询、OR）/ 必要时拆大事务、加缓存。
5. **验证灰度**：EXPLAIN ANALYZE 对比前后实际 rows 与耗时，灰度上线观察慢日志与 CPU 确认回落。
6. **复盘防复发**：上线前 SQL 审核、索引变更走 invisible 灰度、数据量增长定期巡检。

**追问 1：CPU 高但慢日志里没有明显 Top SQL 呢？**
> **答案：** 可能是**大量短查询高并发**累积（pt-query-digest 按总量排能发现），或锁等待 / 长事务伪装、连接池打满、IO / Buffer Pool 命中率问题。要结合线程数、QPS、锁等待、系统指标综合判断，不能只盯慢日志。

**追问 2：怎么防止"加索引"引入新问题？**
> **答案：** 索引会拖慢写、占空间、可能让优化器选错。新增索引先走 invisible 灰度观察执行计划与性能，确认收益再 visible；同时检查是否让已有索引冗余，定期用 `sys.schema_redundant_indexes` 清理。

### Q13. 表结构和 DDL 层面有哪些优化手段？

**标准答案：**
- **字段类型**：能用 INT 不用 VARCHAR（IP 用 INT、状态用 TINYINT）；时间用 DATETIME（范围大）或 TIMESTAMP（省空间、带时区），高频排序可用 BIGINT 存毫秒时间戳；字符集统一 **utf8mb4**；字段尽量 `NOT NULL`（省空间、利于索引与统计）。
- **大字段拆表**：把 TEXT / BLOB 放扩展表，避免影响主表查询与页分裂。
- **范式与冗余**：适度冗余（空间换时间）避免多表 JOIN；冷热字段做垂直拆分。
- **分区表**：`PARTITION BY RANGE/HASH` 配合**分区裁剪**只扫相关分区（注意分区键必须包含在唯一键中）。
- **数据量大**：垂直拆列、水平拆行（分库分表），代价是跨片 JOIN / 排序、分布式事务、全局主键。
- **Online DDL**：8.0 的 `INSTANT` 加列只改元数据、秒级完成（有限操作）；改类型 / 建索引仍需 INPLACE / COPY，大表用 gh-ost / pt-osc 在线变更并避开高峰。

**追问 1：DATETIME 和 TIMESTAMP 怎么选？**
> **答案：** DATETIME 8 字节、范围 1000–9999、不随时区变；TIMESTAMP 4 字节、范围 1970–2038、存取按时区转换。国际化业务要注意 TIMESTAMP 的时区语义；超范围或需稳定字面值用 DATETIME；纯排序 / 范围查询用 BIGINT 时间戳也常见。

**追问 2：分区表一定提速吗？**
> **答案：** 不一定。只有查询条件**命中分区键**触发分区裁剪才提速；条件不含分区键会扫所有分区，反而更慢。分区还带来唯一键约束与运维复杂度，别盲目分区。

## Part 5：2026 新趋势：8.x 特性如何服务优化

> 加分题，考察候选人是否跟进版本、能否把新特性用到优化实战中。

### Q14. 8.x 里哪些新特性可以直接服务 SQL 优化？

**标准答案：**
- **降序索引**：8.0 真正支持 `(a DESC, b ASC)`，5.7 忽略 DESC；能让混合排序走索引、消除 filesort（对应 Extra 的 `Backward index scan`）。
- **函数索引**：基于表达式建索引如 `((lower(name)))`，让"列上带函数"的查询也能用索引，破解一类索引失效。
- **不可见索引 Invisible Index**：对优化器隐身但仍维护，用于**灰度验证**删索引是否安全——先 invisible 观察，无碍再 DROP。
- **直方图 Histogram**：对倾斜列统计分布，帮优化器更准估算、选对索引，解决"优化器选错索引"。
- **Instant DDL**：`ALGORITHM=INSTANT` 秒级加列，降低大表 DDL 风险。
- **并行查询**：部分场景（如 COUNT(*)、IN 子查询）可并行扫描加速。
- **窗口函数**：`ROW_NUMBER` / `RANK` / 累计求和等，简化复杂统计 SQL，替代难维护的自连接与相关子查询。

**追问 1：不可见索引在优化流程里怎么用？**
> **答案：** 想删一个可疑索引时，先 `ALTER TABLE t ALTER INDEX idx INVISIBLE`，此时优化器不用它但索引仍维护；观察慢日志与执行计划一段时间，确认无回退再 DROP，期间随时可恢复 VISIBLE。比直接删安全，是 PTA 基线与灰度思想的落地。

**追问 2：函数索引是不是意味着"列上用函数"都能优化？**
> **答案：** 不是万能。函数索引只对**表达式完全一致**的查询生效（建 `lower(name)` 索引后 `WHERE lower(name)=?` 能用，`upper(name)=?` 不能），且增加写维护成本。能用范围改写的（如时间函数改写为范围）通常仍更优，函数索引是补充手段。

## Part 6：能否用本套定级？如何定级？

### 结论先行

**可以，SQL 优化案例集是后端面试里区分度极高的探针**——因为它天然可证伪：会不会 EXPLAIN、能不能讲出一条真实慢 SQL 的"诊断 → 改写 → 验证"过程，背八股的人一问案例就露馅。但它**高度依赖实战经验**，对没接触过大数据量的初中级候选人问深了只会得到标准答案；招初中级问到 Part 1/2 即可，用 Part 4 案例做鉴别。

---

### 定级标准

| 级别 | 典型年限 | 能达到的深度 | 关键判据 |
|------|---------|-------------|---------|
| **初级（L1）** | 0–2 年 | Part 0 + Part 1 | 会写 CRUD，知道 explain 大概看 type / rows，说不出优化流程与索引失效 |
| **中级（L2）** | 2–5 年 | Part 2 | 懂 EXPLAIN 字段、常见索引失效、慢日志定位，但缺体系 |
| **中高级（L3）** | 5–8 年 | Part 3 | 能逐条诊断索引失效、设计联合 / 覆盖索引、理解优化器成本与干预 |
| **高级（L4）** | 8 年+ | Part 4 | 能独立诊断改写深分页 / 排序 / JOIN / COUNT，有 CPU 100% 排查案例，能识别锁等待伪装 |
| **资深/架构（L5）** | 10 年+ | Part 5 | 跟进 8.x 新特性，结合业务做索引 / 表结构 / 分库分表的体系化权衡并建基线 |

---

### 定级操作方法

**第一步：Part 0 摸底。** 能说出"定位 → EXPLAIN → 改写 → 验证"闭环 → 至少 L2；只会说"加索引" → 从 Part 1 问起。

**第二步：沿追问链下探。** 重点追问"为什么"：
- 为什么范围查询后列失效？（范围后列不再有序）
- 为什么延迟关联能提速？（把回表从百万次降到 10 次）
- 为什么单次不慢的高频 SQL 更要盯？（pt-query-digest 按总耗时排）

**第三步：三类信号防背题。**
1. **真实性**：能否说出具体慢 SQL、优化前后 EXPLAIN 对比、耗时数字（"type=ALL → ref，3s → 20ms"）。
2. **抽象能力**：能否把"定位—诊断—改写—验证"沉淀成可复用方法论与基线（PTA）。
3. **权衡能力**：能否讲清何时不该优化、索引不是越多越好、分区不一定加速。

**第四步：按最深层级定级，不按正确率。** 结合岗位难度调整追问深度。

---

### 面试官避坑提醒

- **不要对所有人问到成本模型 / optimizer hint**——很多优秀中级没背这些但能优化慢 SQL，区分"能实战"和"背过参数"，前者更有价值。
- **把"能现场优化一条慢 SQL 并讲清验证"作为 L4 分水岭**：能给 EXPLAIN 前后对比和效果数字的人，一定是真用过。
- **结合岗位**：业务开发问到 Part 3 足够；DBA / 基础架构 / 中间件团队才需要 Part 4 排障与 Part 5 演进。

## 附录：面试官速查表（一页纸）

**递进主线（照着问）：**

1. 拿到慢 SQL 怎么优化？→（定位 Top SQL → EXPLAIN → 诊断 → 改写 / 索引 → 验证基线）
2. 什么时候不该优化？→（收益小 / 瓶颈在锁或下游 / 过度改写；顺序：业务 → SQL → 索引 → 表结构 → 缓存）
3. EXPLAIN 看什么？type 排序？→（type / key / key_len / rows / Extra；system>const>eq_ref>ref>range>index>ALL）
4. key_len 怎么算？rows 准吗？→（列字节 + 变长 2 + NULL 1；rows 是估算，ANALYZE 给真实值）
5. Extra 各值？→（Using index / filesort / temporary / join buffer / Backward index scan）
6. EXPLAIN ANALYZE 与慢日志分析？→（真实执行；pt-query-digest 按总耗时找 Top SQL）
7. 优化器为何选错索引？→（成本模型 / 统计过期 / 倾斜；ANALYZE / 直方图 / FORCE INDEX）
8. 索引失效场景？→（隐式转换 / 函数 / LIKE %前缀 / OR / 范围后列 / 最左前缀 / 字符集 / 计算）
9. 联合索引顺序与覆盖 / 前缀索引？→（等值左范围右、高频优先；覆盖免回表；前缀省空间）
10. 深分页怎么改？→（游标续查 / 延迟关联；LIMIT 未必减少扫描）
11. ORDER BY / GROUP BY 怎么优化？→（索引消除 filesort / temporary；松散索引扫描）
12. JOIN / IN EXISTS / 子查询 / OR？→（小表驱动大表 + 被驱动表索引；按 EXPLAIN 实测选）
13. COUNT(*) 优化？→（计数表 / Redis；引擎差异；TABLE_ROWS 是估算）
14. CPU 100% 排查？锁等待识别？→（pt-query-digest + EXPLAIN；PROCESSLIST State=Waiting for lock）
15. 表结构 / DDL？→（字段类型 / 大字段拆表 / 分区裁剪 / Online DDL INSTANT）
16. 8.x 新特性服务优化？→（降序 / 函数 / 不可见索引、直方图、Instant DDL、并行查询、窗口函数）

**定级速判：**
- 答到第 2–5 问 → L2
- 答到第 6–9 问 → L3
- 答到第 10–14 问 + 有实战案例 → L4
- 答到第 15–16 问 + 体系化权衡 → L5

**一票否决信号：** 认为"LIMIT 一定减少扫描"、"索引越多越好"、"EXPLAIN 的 rows 是真实值"、"count 各引擎一样"、"优化就是加索引"，或讲不出一条真实慢 SQL 的验证过程 → 无论年限，最高 L2。
