## 一、生产级常盯的细分方向

1. **堆与停顿目标**：吞吐优先还是延迟优先；G1 / ZGC 选型  
2. **元空间与类加载泄漏**：动态生成类、热部署失控  
3. **直接内存 / Netty**：堆外打满但堆很「健康」  
4. **线程与栈**：线程爆炸、死锁、池化不当  
5. **JIT 与启动/预热**：冷启动、高峰前预热  
6. **容器与 cgroup**：Limit 与 `-Xmx` / `MaxRAMPercentage` 一致  
7. **观测**：GC 日志、JFR、APM、红线告警  
8. **变更治理**：参数进配置中心/镜像，灰度，禁止人肉乱改线上  

---

## 二、生产环境常见教训

| 教训 | 说明 |
| --- | --- |
| 盲加 `-Xmx` | 堆变大可能拉长单次 GC，或触发宿主机内存竞争；要配观测 |
| 无界队列 + 线程池 | 易 OOM 或假死；池与队列必须有界、有拒绝策略 |
| `ThreadLocal` 不清理 | 线程池复用下典型泄漏 |
| 大对象 / 大缓存进堆 | 老年代打满、频繁 Full / Mixed 压力大 |
| 容器里按「宿主机内存」设堆 | 超过 Limit 被杀（OOMKilled），表现为「莫名重启」 |
| 只看平均 RT | 要看 P99/P999 与 GC 停顿是否重合 |
| 调参无对照实验 | 每次只改一组变量，保留回滚与压测对比 |

## 三、工具链（够用即可）

| 工具 | 用途 |
| --- | --- |
| `jstat -gcutil` | GC 与各区占比趋势 |
| `jstack` / Arthas `thread` | 阻塞、死锁、热点栈 |
| `jmap` / `jcmd GC.heap_dump` | 堆转储，MAT 析泄漏 |
| `jcmd VM.native_memory` | 开启 NMT 后看本地内存 |
| JFR | 低开销事件画像 |
| Arthas | 线上动态 trace / watch（慎用生产变更） |
| GC 日志 + 可视化 | 确认停顿模式 |

流程建议：业务指标异常 → 是否 GC/线程/内存 → 证据（日志/转储）→ 假设 → 小步变更 → 验证。

## 四、场景 A：K8s / 容器中的 JVM

### 关键认知

- 容器有 **memory limit**；进程总占用（堆 + 元空间 + 直接内存 + 线程栈 + 代码缓存等）超过 Limit 会被杀。  
- 现代 JDK 支持容器感知（`UseContainerSupport` 等，版本以你用的 JDK 为准）。  
- 优先用 **百分比** 而非拍脑袋绝对值，例如：

```text
-XX:MaxRAMPercentage=75.0
-XX:InitialRAMPercentage=50.0
```

具体比例要给堆外留余量（直接内存、线程、本地库）。

### 实践要点

1. Limit ≈ 你允许的进程上限；堆只占其中一部分。  
2. 设好 GC 日志与 heap dump on OOM 路径（注意磁盘与权限）。  
3. 就绪/存活探针不要在 Full GC 长停顿时误杀——结合停顿目标与探针超时。  
4. 同工作负载的多副本，堆与 GC 配置尽量一致，避免「随机慢实例」。  
5. 资源 `request/limit` 与 JVM 配置一起进 Git，随镜像发布。

## 五、场景 B：实时数据流（Kafka 消费等）

### 特征

分配速率高、对象短命多、偶发大消息、消费线程与业务线程争用 CPU。

### 原则

1. **减少分配**：复用缓冲区、避免每条消息大额临时对象、注意 JSON 反序列化垃圾。  
2. **控制并行度**：分区数、消费者并发与 CPU 核匹配；不要靠无限加线程。  
3. **GC 选择**：延迟敏感用低停顿收集器（如 ZGC，视 JDK 与运维成熟度）；吞吐型批处理可偏 G1/吞吐收集器。  
4. **背压**：队列有界；处理不过来就降速/丢弃策略明确，避免堆被撑爆。  
5. **观察**：消费滞后、GC 停顿、反序列化 CPU 是否同升。

## 六、场景 C：大规模延迟敏感服务

### 目标

P99/P999 稳定，GC 停顿可控（按业务定预算，例如数毫秒～数十毫秒级，不要空喊「5ms」却无测量）。

### 原则

1. **先定 SLA**：停顿预算、堆大小、机器规格。  
2. **选型**：低延迟优先考虑 ZGC（大堆、多核常见）；G1 调停顿目标也要靠日志验证。  
3. **减少巨型对象与缓存无界增长**；本地缓存设上限。  
4. **线程与锁**：避免停顿之外的锁竞争伪装成「GC 问题」。  
5. **变更**：GC 相关参数走灰度；用压测 + 线上百分位对比。  
6. **协同**：下游超时、重试放大与 GC 叠加会雪崩——限流与舱壁同样重要。

## 七、调优优先级（别颠倒）

```text
业务算法 / SQL / 远程调用
  → 分配与对象生命周期
    → 线程池与连接池
      → 堆大小与 GC 选型/目标
        → 边角 JVM 开关
```

多数「慢」不是缺一个神秘 `-XX`，而是 **N+1、池耗尽、缓存不合理**。可对照 [没有大流量也能练高并发](/posts/java/high-concurrency-practice/)。
