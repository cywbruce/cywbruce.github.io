这题适合有双端经验或从 Vue 转 React 的候选人。目标不是站队，而是看对方是否理解：**Vue 的复杂偏框架规则，React 的复杂偏自由带来的工程决策。**

## 核心差异表

| 维度 | React 更复杂的地方 | Vue 相对省心的地方 |
| --- | --- | --- |
| 写法 | JSX 把结构与逻辑混在 JS 里 | 模板接近 HTML，指令直观 |
| 更新模型 | 不可变更新，显式 `setState` | 响应式自动追踪依赖 |
| 副作用 | `useEffect` 手写依赖，易闭包/重复执行 | `watch` / `computed` 自动收集 |
| 性能 | 默认整树按组件重跑，常需手动 memo | 细粒度更新，多数情况少手动优化 |
| 生态 | 官方只管视图，路由/状态/请求自选 | 官方路径更清晰（Router / Pinia 等） |
| 一致性 | 自由度高，团队要定规范 | SFC 结构更统一 |

## 面试官可展开的五点

1. **Hooks 心智负担**：React 是「组件重新执行，你声明该缓存/该执行什么」；Vue 更接近「数据变了，依赖自动算」。  
2. **不可变与函数式**：对象/数组更新、引用相等、`useReducer`、浅比较。  
3. **工程选型多**：Router、Redux/Zustand、React Query、样式方案、Next vs Vite CSR。  
4. **风格易失控**：同一仓库多种状态流、目录、请求方式并存。  
5. **深入门槛**：并发、SSR/RSC、缓存、复杂 TS 推导。

## 面试怎么问（按级别）

### 初级

**主问：** 你用过 React 和 Vue 的话，感觉哪里不一样？

**期望：** 能提到模板 vs JSX、双向绑定 / `v-model` vs 单向数据流、或「Vue 改数据就能更新、React 要 setState」。

**追问：**

1. React 里直接 `user.name = 'x'` 为什么界面可能不更新？  
2. Vue 的 `ref` / `reactive` 和 React 的 `useState` 直观差别是什么？

**参考答案：**

- **直接改 `user.name` 为什么不更新：** React 靠 `setState` 触发渲染，并用 `Object.is` 比较新旧值。直接修改对象，引用没变，React 不会知道有变化。要创建新对象：`setUser({ ...user, name: 'x' })`。
- **`ref`/`reactive` 和 `useState`：** Vue 用 Proxy 拦截读写，改值就会自动触发更新；React 的 state 是不可变的快照，必须调用 setter，组件函数会整体重新执行。

**定级信号：** 有使用体感即可；说不清更新机制仍可算初级。

### 中级

**主问：** 为什么很多人口中 React「更难」？难在业务页面还是难在工程？

**期望：** 能区分「写页面」与「选架构 / 管副作用 / 做性能」；提到 Effect 依赖、状态提升、生态选型。

**追问：**

1. 同样做一个带搜索+分页的列表，你在 React / Vue 里状态会放哪？  
2. React 里什么时候才上 `useMemo` / `useCallback`？Vue 里对应什么？  
3. 团队从 Vue 迁 React，你最担心哪三类问题？

**参考答案：**

- **难在哪：** 写普通页面两边差不多；React 难在工程层面，包括 effect 依赖、状态放在哪一层、性能优化，以及路由、状态管理、请求库都要自己选型。
- **搜索加分页的列表：** React 里查询条件放进 URL search params 或组件 state，数据交给 React Query，请求参数作为 queryKey，自动缓存并处理竞态；Vue 里条件用 `ref`，`watch` 条件变化后发请求，或者用 VueQuery。
- **`useMemo`/`useCallback` 什么时候用：** 只在计算昂贵或者需要稳定引用时用；Vue 对应的是 `computed`，自动缓存，一般不需要手动优化。
- **从 Vue 迁到 React，最担心的三类问题：**
  - effect 滥用和过期闭包；
  - 状态管理没有统一规范；
  - 直接修改 state 导致界面不更新。
  应对方法是出团队规范、开启 lint、做集中培训。

**定级信号：** 能讲清副作用与状态边界 → 中级。

### 高级

**主问：** 若新项目技术选型，在什么约束下你会选 React，什么约束下选 Vue？如何向业务方解释「复杂度」？

**期望：** 结合团队储备、跨端（RN）、生态（RSC/元框架）、招聘市场、长期可维护性；承认 React 上限高但规范成本也高。

**追问：**

1. React 19 / 并发特性改变了哪些「相对 Vue 更复杂」的点？  
2. 微前端或多团队共建时，哪边的约束模型更好落地？  
3. 如何设计一套 React 规范，把「自由度」收成「可控的一致性」？

**参考答案：**

- **选型：**
  - 选 React：团队有 React 储备，需要 React Native 做跨端，要用 Next.js 或 RSC 做 SSR/SEO，招聘市场更大，长期是大型复杂应用。
  - 选 Vue：团队偏传统前端或后端兼写前端，需要快速交付，后台类页面多，希望官方提供一整套方案。
- **怎么向业务方解释复杂度：** 讲交付速度、招聘成本、长期维护风险，不讲语法细节。
- **React 19 和并发特性：**
  - Actions、`useOptimistic`、`use` 减少了表单和数据加载的样板代码；
  - React Compiler 减少了手写 memo；
  - RSC 引入了服务端和客户端的边界，新增了一层心智负担。
- **微前端和多团队共建：** Vue 的约束更强，风格更统一；React 需要靠统一的脚手架、lint 和设计系统来保证一致性。两者都能落地，关键在治理。
- **把自由度收成可控的一致性：** 定好分层（UI、Hook、服务、store）、请求统一用 React Query、表单方案统一、开启 strict TS 和 lint、提供模板仓库、通过代码评审清单落实。

**定级信号：** 选型有取舍、能谈治理与组织成本 → 高级。
