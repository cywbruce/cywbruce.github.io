### 1. 从 1 个用户扩展到千万用户（中级～高级）

**主问：** 一个 Web 应用从第一个用户开始，一路增长到千万用户，架构要怎样一步步演进？每一步解决什么瓶颈？

**参考答案：** 核心思路是**发现瓶颈，再解决瓶颈**，每一步都要有监控数据来支撑，不要一开始就把架构做满。

| 阶段 | 用户量 | 架构 | 解决的瓶颈 |
| --- | --- | --- | --- |
| 0 | 1 | 单台机器，Web 加数据库 | 先跑起来 |
| 1 | 约 1 千 | **Web 和数据库分开部署**，数据库用托管服务（如 RDS），静态资源放对象存储（S3 / OSS） | 互相抢资源；数据库的运维和备份 |
| 2 | 约 1 万 | **加负载均衡**，部署多台 Web 服务器，**改成无状态**（会话放 Redis）；静态资源加 **CDN**；数据库做主从，主库挂了能切换 | 单台 Web 成为单点；静态资源流量大 |
| 3 | 约 10 万 | **加缓存**（Redis），缓存热点数据和会话；**读写分离**，增加只读从库 | 数据库读压力大 |
| 4 | 约 100 万 | **自动扩缩容**（按 CPU 和 QPS）；**异步化**，耗时任务（缩略图、邮件）放进队列，由工作节点处理；完善监控告警和日志收集 | 流量有波峰波谷；同步调用太慢 |
| 5 | 约 1000 万 | **按功能拆库**，再**分片**；高频访问的 KV 数据放 NoSQL；拆分成**微服务**；**多可用区、多地域**部署，加上 DNS 调度 | 写入扛不住；单个机房的可用性；团队规模变大 |

**每一步都要讲的取舍：**
- 无状态化之后，会话、上传文件都不能再存在本机。
- 读写分离会有复制延迟。刚写完马上读的场景，要强制读主库。
- 分片之后跨分片查询很难，所以分片键要按最主要的查询方式来选。
- 引入微服务后，运维成本会大幅上升，所以要等团队和业务足够复杂再拆。

**追问：**

1. 你怎么知道该进入下一阶段了？（监控指标：数据库 CPU 和慢查询、缓存命中率、P99 延迟、错误率；压测找出系统的拐点）
2. 每个阶段新增的单点在哪里？（负载均衡器、缓存、主库，都需要主备或集群）
3. 成本怎么控制？（预留实例加按量实例、冷热数据分层、只扩容瓶颈部分）

### 2. 设计网页爬虫（中高级）

**主问：** 设计一个搜索引擎用的网页爬虫，要爬取 10 亿个网页，每周更新一次，还要支持按关键词搜索。

**参考答案：**

1. **场景和约束：** 每月抓取约 40 亿次（每周更新一遍，热门页面更频繁）；单个网页平均 500 KB；只抓 HTML，存储量约每月 2 PB；需要去重和遵守抓取规则（robots.txt）。
2. **核心组件：**

```text
种子 URL → [待爬队列：按优先级 + 按域名分桶]
         → 抓取工作节点（DNS 缓存、限速、遵守 robots）
         → 内容解析（提取正文和链接）
         → 去重（URL 和内容）→ 新链接回到待爬队列
         → 存储（原始页面放对象存储，提取的文本建倒排索引）
```

3. **关键设计：**
   - **URL 去重：** 布隆过滤器做第一层过滤，再用 KV 存储做精确判断，记录已经爬过的 URL。
   - **内容去重：** 对网页内容算指纹（**SimHash**），用来识别近似重复的页面，比如镜像站和转载。
   - **礼貌爬取：** 同一个域名控制并发数和请求间隔，所以待爬队列要**按域名分桶**；遵守 robots.txt。
   - **优先级：** 按 PageRank 和更新频率决定抓取顺序；更新频繁的页面重新抓取的间隔更短。
   - **陷阱：** 动态链接会造成无限循环，所以要限制抓取深度和同一域名下的 URL 数量；URL 要做规范化处理。
   - **DNS：** DNS 解析是常见的性能瓶颈，要在本地缓存解析结果。
4. **扩展：** 抓取节点可以水平扩展；待爬队列放在 Kafka 里，按域名分区；倒排索引分片（Elasticsearch / 自研）。

**追问：** 如何判断一个网页需要重新抓取？（看历史上内容变化的频率，并用 HTTP 的 `If-Modified-Since` 和 ETag 做条件请求，没变就不用重新下载）

### 3. 社交网络的数据结构（高级）

**主问：** 社交网络有 1 亿用户，平均每人 50 个好友。设计「查找两个人之间的最短关系链」（类似领英显示的二度、三度人脉）。

**参考答案：**

1. **单机：** 广度优先搜索（BFS）。**双向 BFS**（同时从两个人开始搜索，中间相遇）能把搜索规模从 b^d 降到 2·b^(d/2)，大幅减少需要访问的节点。
2. **数据规模：** 1 亿用户 × 50 个好友 = 50 亿条边，一台机器的内存放不下，所以要**按用户 ID 分片**，存在多台机器上。
3. **分布式 BFS：**
   - 用一个查找服务确定「某个用户的好友列表在哪个分片」；
   - 每一层把待访问的用户按分片分组，**批量**请求各个分片，减少网络往返；
   - 记录已经访问过的用户，避免重复访问。
4. **优化：**
   - 限制搜索深度（通常 3 度以内就足够了，再深没有业务意义）；
   - 提前计算并缓存二度人脉；
   - 把好友多、联系紧密的用户尽量放在同一个分片，减少跨分片访问；
   - 用图数据库（Neo4j / JanusGraph）或者专门的图计算引擎。
5. **数据存储：** 好友关系用邻接表存储（用户 ID → 好友 ID 列表），存在 KV 存储或宽列存储里（HBase）。

**追问：** 超级大 V 有几千万粉丝，BFS 遍历到他会怎样？（一层就会展开出几千万个节点。处理方法：对大 V 特殊处理，比如跳过、抽样，或者单独建索引；也可以区分关注和好友两种关系）

### 4. 统计某个时间窗口内的 Top-K（中高级）

**主问：** 实时统计过去 1 小时搜索次数最多的 100 个词（热搜榜），每秒有 10 万次搜索。

**参考答案：**

1. **精确方案（数据量小时）：** 用哈希表计数，再用一个大小为 K 的小顶堆选出前 K 个，复杂度 O(N log K)。
2. **海量数据：**
   - **流式计算：** 搜索日志写进 Kafka，用 Flink 按**滑动窗口**统计（窗口 1 小时，每分钟滑动一次）。每个分区先算出本地 Top-K，再合并成全局 Top-K。
   - **按词分区：** 同一个词路由到同一个分区，保证每个词的计数在一个地方完成，这样合并局部 Top-K 时结果才准确。
3. **近似算法（节省内存）：**
   - **Count-Min Sketch：** 用多个哈希函数和一个二维数组估算每个词的频次，内存固定；只会高估、不会低估。
   - **Space-Saving / Heavy Hitters：** 只为前若干个候选词维护计数。
4. **展示：** 结果写进 Redis 的 ZSet，每分钟更新；前端读缓存。
5. **离线校准：** 每天用批处理精确计算一次，修正实时结果的误差，同时过滤刷榜和作弊。

**追问：**

1. 滑动窗口和滚动窗口有什么区别？（滚动窗口之间不重叠，滑动窗口互相重叠；滑动窗口也可以拆成多个小桶，滑动时加上新桶、减去旧桶）
2. 有人刷热搜怎么办？（按用户和 IP 去重、风控模型识别、人工审核）

### 5. 设计分布式键值存储（高级）

**主问：** 设计一个高可用的分布式 KV 存储（类似 Dynamo / Cassandra），支持 `get(key)` 和 `put(key, value)`。

**参考答案：**

1. **数据分片：** **一致性哈希加虚拟节点**，节点增减时只需要迁移少量数据，同时数据分布更均匀。
2. **复制：** 每个 Key 存 N 份，存在哈希环上顺时针方向的 N 个节点上，节点最好分布在不同机架或可用区。
3. **可调一致性（Quorum）：** 写入要 W 个副本确认，读取要 R 个副本响应。当 **W + R > N** 时，读写集合必然有交集，能读到最新数据。比如 N=3、W=2、R=2。如果追求低延迟，可以设 W=1 或 R=1。
4. **冲突处理：**
   - 用向量时钟（Vector Clock）检测并发写入产生的冲突，由客户端合并；
   - 或者简单地「最后写入者胜出」（LWW），按时间戳决定，实现简单但可能丢数据。
5. **故障处理：**
   - **临时故障：** 暂时写到其他节点，节点恢复后再交还（Hinted Handoff，暗示移交）；
   - **永久故障：** 用 **Merkle 树**比较副本之间的差异，只同步不一样的部分（反熵修复）；
   - **故障检测：** Gossip 协议在节点之间传播状态。
6. **单机存储引擎：** **LSM-Tree**：先写 WAL 日志和内存表，再刷成磁盘上的 SSTable，后台合并（Compaction）；读的时候用布隆过滤器快速判断 Key 是否存在。

**追问：** Dynamo 选的是 AP，如果业务需要强一致怎么办？（使用基于 Raft 或 Paxos 的 CP 系统，比如 etcd、TiKV；或者对关键操作设置 W=N 来强制同步写入）

### 6. 设计 Pastebin（文本分享）（中级）

**主问：** 设计一个 Pastebin：用户粘贴一段文本，得到一个短链接；可以设置过期时间；统计访问量。

**参考答案：**

1. **约束：** 每月新增 1000 万条，每条平均 1 KB；读写比 10:1；读 QPS 约 40。
2. **写入：** 生成短码（自增 ID 转 62 进制，或者用哈希值截取再检查冲突）；文本内容放对象存储，元数据（短码、对象存储路径、过期时间、创建时间）放数据库。
3. **读取：** 通过短码查到元数据，读取内容；内容基本不会变，适合用 **CDN 和缓存**。
4. **过期：** 读取时检查是否过期，加上定时任务批量清理过期数据。
5. **统计：** 访问日志异步写进 MQ，由批处理或流计算汇总，不在读取请求里同步计数。

**追问：** 和短链系统有什么异同？（短码生成方式相同；Pastebin 要存内容本身，所以存储层要单独设计）
