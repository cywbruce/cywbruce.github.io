## 一、性能与可扩展性

- **性能问题：** 单个用户访问就很慢。
- **可扩展性问题：** 单个用户访问很快，但用户一多就变慢。

**可扩展的定义：** 增加资源后，性能能**按比例**提升。

| 方式 | 说明 | 局限 |
| --- | --- | --- |
| 垂直扩展（Scale Up） | 换更强的机器 | 有上限，单点故障，成本陡增 |
| 水平扩展（Scale Out） | 加更多的机器 | 要求服务**无状态**，引入了分布式复杂度 |

**水平扩展的前提：** 会话、文件、缓存这类状态要从应用服务器上移出去，放到 Redis、对象存储、数据库里。

## 二、延迟与吞吐

- **延迟：** 完成一次操作需要的时间。
- **吞吐：** 单位时间内完成的操作数。
- **目标：** 在可接受的延迟范围内，尽量提高吞吐。

两者经常要互相让步。比如批量处理能提高吞吐，但单条数据的延迟会变高（Kafka 的 `linger.ms` 就是这个取舍）。

## 三、可用性与一致性

### 3.1 CAP 定理

分布式系统最多只能**同时满足以下两项**：
- **C 一致性：** 每次读到的都是最新写入的数据，或者报错
- **A 可用性：** 每个请求都能得到响应，但不保证是最新数据
- **P 分区容错：** 网络分区时系统仍然能运行

**网络分区一定会发生，所以实际上是在 CP 和 AP 之间选：**
- **CP：** 分区期间宁可报错或等待，也不返回旧数据，适合对原子读写有要求的业务（如 ZooKeeper、etcd、HBase）
- **AP：** 分区期间返回可能过期的数据，分区恢复后再收敛，适合可以接受最终一致的业务（如 Cassandra、Eureka、DNS）

**国内面试常见补充：** BASE 理论（基本可用、软状态、最终一致）；PACELC 理论：没有分区时，也要在延迟（L）和一致性（C）之间取舍。

### 3.2 一致性模式

| 模式 | 写入后读取 | 例子 |
| --- | --- | --- |
| 弱一致 | 可能读不到 | 实时音视频、游戏状态、Memcached |
| 最终一致 | 一段时间后能读到（通常是毫秒级），数据异步复制 | DNS、邮件、大多数 NoSQL |
| 强一致 | 立刻能读到，数据同步复制 | 关系数据库事务、文件系统 |

### 3.3 可用性模式

**故障转移：**
- **主备（Active-Passive）：** 主节点和备节点之间发心跳，心跳中断后备节点接管服务 IP。备节点可以是热备（一直在运行）或冷备（需要启动），冷备的切换时间更长。
- **双活（Active-Active）：** 两个节点同时承担流量，靠 DNS 或负载均衡分流。
- **缺点：** 需要更多硬件；切换前如果有数据没复制过去，就会丢失。

**复制：** 主从复制、主主复制，详见第八节。

**可用性的计算：**

| 可用性 | 每年停机时间 | 每月停机时间 |
| --- | --- | --- |
| 99.9%（3 个 9） | 8 小时 45 分 | 43 分 49 秒 |
| 99.99%（4 个 9） | 52 分 36 秒 | 4 分 23 秒 |

- **串联：** 两个组件串联时，总可用性等于两者相乘，比单个组件低。比如 99.9% × 99.9% = 99.8%。
- **并联：** 两个组件互为备份时，总可用性 = 1 − (1 − A)²，比单个组件高。比如两个 99.9% 并联，得到 99.9999%。

## 四、DNS

把域名解析成 IP，结果会在各级缓存（浏览器、操作系统、运营商）里保存一段时间（TTL）。

| 记录类型 | 作用 |
| --- | --- |
| A | 域名 → IPv4 |
| CNAME | 域名 → 另一个域名（CDN 接入常用） |
| MX | 邮件服务器 |
| NS | 指定这个域名由哪台 DNS 服务器解析 |

**流量调度：** 加权轮询、按延迟就近解析、按地理位置解析（智能 DNS，国内常用来区分电信和联通线路）。

**缺点：**
- 解析本身有延迟（可以靠缓存缓解）；
- TTL 导致切换生效慢，故障时不能立刻摘除节点；
- 可能被 DDoS 攻击，或者遭到 DNS 劫持（可以用 HTTPDNS 防劫持）。

## 五、CDN

全球分布的边缘节点缓存静态资源（HTML、CSS、JS、图片、视频），用户从最近的节点获取，**源站压力也会大幅降低**。

| 类型 | 原理 | 适用场景 |
| --- | --- | --- |
| 推送式 CDN | 内容更新时主动推送到 CDN，由你控制过期时间 | 流量小、内容更新少 |
| 拉取式 CDN | 用户第一次请求时，CDN 回源拉取并缓存，到 TTL 过期 | 流量大，**最常用** |

**缺点：** 按流量计费，成本不低；TTL 内的内容可能是旧的（用 URL 带版本号或主动刷新解决）；需要改写静态资源的 URL，指向 CDN 域名。

## 六、负载均衡与反向代理

### 6.1 负载均衡

**作用：** 把请求分发给多台服务器，自动摘除不健康的节点；还可以做 SSL 卸载、会话保持。

**分发算法：** 随机、轮询、加权轮询、最少连接、按会话或 Cookie 保持、四层或七层哈希（一致性哈希）。

| 层次 | 依据 | 特点 | 国内常用 |
| --- | --- | --- | --- |
| 四层（传输层） | IP 和端口 | 只转发数据包，不解析内容，**性能高** | LVS、云厂商的 SLB/NLB、F5 |
| 七层（应用层） | HTTP 头、URL、Cookie | 能按路径路由、改写请求，功能更灵活，性能稍低 | Nginx、HAProxy、Envoy、云 ALB |

**常见组合：** LVS（四层）在前，Nginx（七层）在后，再到应用服务器。

**缺点：** 负载均衡器自己可能成为瓶颈或单点，需要主备或集群部署（比如 Keepalived 加虚拟 IP）。

### 6.2 反向代理

把后端服务集中暴露成一个统一入口：
- **安全：** 隐藏后端的地址，限制连接数；
- **扩展：** 后端可以随意扩缩容；
- **功能：** SSL 终止、压缩、静态文件缓存、直接返回静态资源。

**和负载均衡的区别：** 只有一台后端服务器时，反向代理也有意义；负载均衡要有多台后端才有意义。Nginx 两者都能做。

**缺点：** 增加了一层复杂度，自身也可能成为单点。

## 七、应用层与微服务

- **Web 层和应用层分离：** 两者可以独立扩展，比如读接口和写接口分开部署。
- **微服务：** 一组可以独立部署的小服务，每个服务负责一个业务能力，通过 HTTP 或 RPC 通信。
- **服务发现：** Consul、etcd、ZooKeeper、Nacos、Eureka，配合健康检查使用。
- **缺点：** 部署和运维复杂度大幅增加；分布式事务、链路追踪、接口版本管理都要单独处理。

站内详细内容：[设计与架构手册 · 微服务](/posts/architect/design-architecture-handbook/#sec-3)

## 八、数据库

### 8.1 关系数据库的扩展手段

| 手段 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **主从复制** | 主库负责写，复制到从库，从库负责读 | 读能力可以扩展；主库挂了可以把从库提为主库 | 复制有延迟，可能读到旧数据；写能力扩展不了；从库太多时复制压力大 |
| **主主复制** | 两个主库都能写，互相复制 | 写的高可用 | 需要处理冲突；ID 生成、一致性都更复杂；通常是松散一致 |
| **联合（按功能拆库）** | 用户库、商品库、订单库分开 | 每个库更小，缓存命中率高；可以并行写 | 跨库关联查询要在应用层处理 |
| **分片** | 同一张表按 Key 拆到多个库（按用户 ID 哈希、按范围） | 读写都能扩展；单个分片故障影响范围小 | 跨分片查询难；数据倾斜；扩容要迁移数据；运维复杂 |
| **反范式** | 冗余字段，减少关联查询 | 读得快 | 写入要更新多处；存在不一致的风险 |
| **SQL 调优** | 合适的数据类型、索引、避免全表扫描、分区、慢查询分析 | 成本低 | 需要持续投入 |

**扩展的顺序：** SQL 调优和索引 → 加缓存 → 读写分离 → 按功能拆库 → 分片。每一步都会让复杂度上一个台阶，**不要过早分片**。

站内详细内容：[数据库手册](/posts/mysql/mysql-handbook/) · [MySQL 题](/posts/mysql/mysql-interview/)

### 8.2 NoSQL

NoSQL 大多遵循 **BASE** 而不是 ACID，优先保证可用性。

| 类型 | 模型 | 适合 | 代表 |
| --- | --- | --- | --- |
| 键值 | Key → Value，O(1) 读写 | 缓存、会话、计数器 | Redis、Memcached、DynamoDB |
| 文档 | Key → JSON/BSON 文档，可以按字段查询 | 结构经常变化的业务对象 | MongoDB、Couchbase、Elasticsearch |
| 宽列 | 行键 → 列族 → 列，按时间戳多版本 | 海量写入、时间序列 | HBase、Cassandra、Bigtable |
| 图 | 节点和边 | 社交关系、推荐、风控 | Neo4j、JanusGraph |

### 8.3 SQL 还是 NoSQL

| 选 SQL | 选 NoSQL |
| --- | --- |
| 数据结构化、关系明确 | 半结构化数据、结构经常变化 |
| 需要复杂关联查询和事务 | 不需要关联查询 |
| 一致性要求高 | 能接受最终一致 |
| 生态成熟、人员好招 | 海量写入或超低延迟（TB 到 PB 级、每秒数十万次） |

**适合 NoSQL 的数据：** 埋点和日志、排行榜、临时数据（购物车、会话）、元数据和配置、高频访问的 KV 表。

**实际情况：** 大多数系统是**混合使用**：核心交易数据放 MySQL，缓存放 Redis，搜索放 Elasticsearch，日志放 ClickHouse 或 HBase。

## 九、缓存

### 9.1 缓存层级

客户端（浏览器、App）→ CDN → Web 服务器（反向代理缓存）→ 应用内（本地缓存，如 Caffeine）→ 分布式缓存（Redis）→ 数据库自身的缓存（Buffer Pool）

**缓存的粒度：**
- **缓存查询结果：** 简单，但失效难以精确控制。
- **缓存对象：** 推荐。数据变化时只需要让对应的对象失效，也可以异步预热。

### 9.2 四种更新模式

| 模式 | 读 | 写 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| **旁路缓存（Cache-Aside）** | 先查缓存，没有就查数据库，再回填缓存 | 先写数据库，再**删除**缓存 | 只缓存被访问的数据；缓存挂了还能降级查数据库 | 第一次读一定不命中；短暂不一致 |
| **直写（Write-Through）** | 直接读缓存 | 写缓存，由缓存同步写数据库 | 缓存始终是最新的 | 写入慢；写进去的数据可能从来没人读 |
| **回写（Write-Behind）** | 直接读缓存 | 只写缓存，异步批量写数据库 | 写入非常快 | 缓存宕机会丢数据；实现复杂 |
| **提前刷新（Refresh-Ahead）** | 在数据过期前自动刷新热点数据 | — | 热点数据读取延迟低 | 预测不准会浪费资源 |

**国内面试最常问的是旁路缓存的一致性**，比如延迟双删、订阅 binlog 删除缓存，详见 [Redis 题 · 缓存一致性](/posts/redis/redis-interview/#q6)。

**缓存的通用缺点：** 一致性问题；增加了一个组件；缓存失效策略难设计；还有穿透、击穿、雪崩问题，详见[缓存手册](/posts/redis/redis-handbook/)。

## 十、异步

- **消息队列：** 接收、保存、投递消息，生产者和消费者解耦（Kafka、RocketMQ、RabbitMQ）。
- **任务队列：** 接收任务和数据，执行完返回结果，支持调度和重试（Celery、XXL-Job，以及基于 MQ 实现的任务系统）。
- **用户体验：** 耗时操作先返回「处理中」，完成后再通知用户。

**背压（Back Pressure）：** 队列无限增长会耗尽内存，处理延迟也会越来越高。所以**要限制队列长度**，队列满了就拒绝或者让生产者等待（比如返回 HTTP 503，客户端指数退避重试）。线程池的有界队列加拒绝策略也是同样的思路。

**缺点：** 简单的同步调用加上异步，反而会增加延迟和复杂度。

站内详细内容：[MQ 手册](/posts/mq/mq-handbook/)

## 十一、通信

### 11.1 HTTP 方法

| 方法 | 用途 | 幂等 | 安全（只读） | 可缓存 |
| --- | --- | --- | --- | --- |
| GET | 读取 | ✅ | ✅ | ✅ |
| POST | 创建、执行操作 | ❌ | ❌ | 一般不缓存 |
| PUT | 整体创建或替换 | ✅ | ❌ | ❌ |
| PATCH | 部分更新 | ❌（取决于实现） | ❌ | ❌ |
| DELETE | 删除 | ✅ | ❌ | ❌ |

### 11.2 TCP 与 UDP

| | TCP | UDP |
| --- | --- | --- |
| 连接 | 三次握手建立连接 | 无连接 |
| 可靠性 | 有序、重传、流量控制、拥塞控制 | 不保证 |
| 开销 | 头部大，有连接状态 | 头部小 |
| 适用 | Web、数据库、文件传输 | 音视频、游戏、DNS、QUIC（HTTP/3 在 UDP 之上实现了可靠传输） |

### 11.3 RPC 与 REST

| | RPC（gRPC、Dubbo、Thrift） | REST |
| --- | --- | --- |
| 抽象 | 调用远程方法（动词） | 操作资源（名词 + HTTP 方法） |
| 协议 | 二进制（Protobuf），通常走 HTTP/2 | JSON + HTTP |
| 性能 | 高 | 中 |
| 耦合 | 客户端和服务端强耦合（共享 IDL） | 松耦合，可以被缓存 |
| 适用 | 内部服务之间调用 | 对外开放的 API、浏览器 |

**国内常见做法：** 对外用 REST 或 GraphQL，内部用 gRPC 或 Dubbo。

## 十二、安全

- 传输和存储都要加密（HTTPS / TLS，敏感字段加密存储）
- 所有用户输入都要校验和转义，防止 XSS 和 SQL 注入；SQL 一律参数化
- 最小权限原则
- 详细内容：[前端市场高频题 · XSS/CSRF](/posts/react/market-hot-questions/) · [AI 安全](/posts/ai/ai-engineer-tiered-interview/#q13)

## 速记：系统设计常用取舍

| 取舍 | 说明 |
| --- | --- |
| 性能 vs 可扩展性 | 单机很快，不代表能扩展 |
| 延迟 vs 吞吐 | 批量处理能提高吞吐，但会增加延迟 |
| 一致性 vs 可用性 | 分区时 CAP 只能选一个 |
| 范式 vs 反范式 | 写入方便 vs 读取快 |
| SQL vs NoSQL | 关系和事务 vs 规模和灵活 |
| 同步 vs 异步 | 简单 vs 解耦和削峰 |
| 推 vs 拉 | 实时 vs 可控（CDN、Feed、MQ 都有这个取舍） |
